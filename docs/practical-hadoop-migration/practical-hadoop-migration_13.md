# 第十章：实现并优化过渡

最近，我看到许多组织在关于使用大数据的问题上改变了初衷。这些组织来自不同行业，因此可能无法承受`Hadoop`不适合特定行业这种论断的逻辑。在大多数案例中（显然），性能和易用性不足是决定放弃使用大数据技术的主要问题。诚然，开源软件没有广泛且易于理解的文档或故障排除方法，但如今，有足够多的供应商在销售受支持的`Hadoop`发行版和软件，这些软件提供易于使用的浏览器界面，可执行从数据摄取到最终结果（分析）的各种任务。

那么，为什么对投资`Hadoop`犹豫不决、有所抵触？为什么`Hadoop`没有取代大量的数据仓库？为什么`Hadoop`仍然不是大公司的主流应用平台？这些问题都没有简单的答案。我想重点谈谈感知上的性能提升不足——这是人们想要选择`Hadoop`取代旧技术的一个主要因素。我将讨论如何通过硬件、操作系统、`Hadoop`配置和数据各个阶段的性能调优，从你的`Hadoop`集群中获取最佳性能。

你可能听说过可以使用商用硬件构建`Hadoop`集群，但对于生产环境来说，这并非事实。我将讨论一些适用于生产和开发环境的典型硬件配置。我将介绍为什么需要从操作系统开始进行性能调优。我还将讨论影响性能的主要配置参数，并解释如何以及为何要进行调优。

当操作系统调优完成后，你需要着手处理`Hadoop`配置参数，并对其进行修改，以便为你的特定环境获得最佳性能。众所周知，`Hadoop`将数据存储为文件，因此这些文件的存储格式非常重要。使用特定格式进行存储是有原因的，我将讨论在决定存储格式时需要考虑的因素。同时，考虑到数据量很大，数据压缩是必不可少的。我将讨论压缩编解码器的类型及其优缺点。最后，我将介绍有助于提升性能的特殊索引和缓存技术。

当然，要想从`Hadoop`集群中获得最佳性能，第一步是运行基准压力测试，找出问题领域或性能未达预期的领域。我将从生产/开发环境的`Hadoop`硬件配置开始讲起。

## 硬件配置

你不能假设`Hadoop`集群可以用旧的、废弃的商用硬件构建。你需要使用配备多个 CPU（包含多核）和足够内存的服务器。你的生产集群需要比开发环境拥有更强大的硬件，当然，你的`NameNode`（主节点）需要比`DataNodes`（任一环境的工作节点）更强大。这只是一个简要总结。

## 集群配置

`HDFS`主节点（`NameNode`）需要比工作节点拥有更多内存。此外，主节点的存储应该是`RAID`，并且由于它是`SPOF`（单点故障），因此需要为故障转移场景进行复制。`NameNode`的配置需要基于数据量（以及你计划让集群保存的文件数量）。在配置时，你需要考虑增长预测和数据压缩。

以下是计算生产用途集群规模的方法。我先从单个节点的空间和节点总数说起。由于操作系统和节点上的其他关键应用程序需要一些空间（大约总空间的 25%），并且数据块会根据副本因子（默认为 3）进行复制：

```
每个节点的 HDFS 空间 = (每个节点的原始磁盘空间 – 25% 非 DFS 本地存储) / (副本因子)
```

```
工作节点数 = 总 HDFS 空间 / 每个节点的 HDFS 空间
```

考虑以下用于启动（独立）工作节点配置的建议：
- 最新一代处理器，总计 12 到 16 个核心
- 每个核心 4–8 GB 内存
- 每个核心 1–3 TB SATA 磁盘
- 1GbE 网卡

对于`NameNode`：
- 总计 4–6 个核心
- 内存起始配置如下：(3 GB + 每 100 TB 原始磁盘空间或 100 万个文件对象增加 1 GB)
- 需要复制（用于故障转移）
- `RAID-1`存储
- `NameNode`应在 64 位操作系统上运行，以避免`JVM`堆大小的 3 GB 限制

如果你使用`YARN`，作为经验法则，可以将 2 GB 内存和 1 个 CPU 核心作为`YARN`主节点`Resource Manager`的起始配置。但你可能需要为一个非常繁忙的`Resource Manager`（运行大量调度任务）提升硬件配置。当然，你需要进行工作负载分析，并在高峰时段检查资源使用情况。如果某个资源的使用率达到最大值，请相应地调整资源分配。

你的开发环境规模取决于你的应用程序使用情况。如果你使用的是供应商产品，那么你的开发环境可能仅用于版本升级或定制化（针对供应商产品）。在这种情况下，你大概可以将每个节点的硬件资源减半，并且可能还想将开发环境的工作节点数量也减半。

然而，如果你的应用程序是内部开发的（或在你公司内部开发），那么你可能希望为每个工作节点分配（与生产环境相比）70–80% 的硬件资源，并且工作节点数量也使用（与生产环境相比）70–80% 的计数，因为你可能需要处理大量的应用程序增强功能，并可能需要为它们测试性能。对于一个真正动态的开发环境，你可能需要匹配（生产环境的）开发资源，并且可能需要更大的空间来容纳多个版本的数据（用于测试）。

请注意，这些只是通用集群的指南。对于你特定的配置需求，应咨询你的供应商（获取`Hadoop`发行版）文档或寻求专家建议。

## 操作系统配置

在开始对 Hadoop 集群进行性能调优之前，务必查阅操作系统文档。请记住，`HDFS`只是一个运行在操作系统权限范围内的文件系统（尽管它是分布式的、具有容错性且功能强大），它运行在你各个节点（主节点或工作节点）的操作系统之上。一些操作系统的调整是直观的，而另一些则需要对其有深入的理解。由于`RHEL`（Red Hat Enterprise Linux）或`CentOS`是 Hadoop 集群中常用的 Linux 发行版，我假设你使用的操作系统是其中之一。我将从直观的调整开始：

- **关闭电源节省选项**：你需要在`BIOS`设置中将此选项配置为`PerfOptimized`以优化应用程序的性能（而不是在空闲时关闭）。
- **关闭磁盘控制器上的缓存**：`Hadoop`不使用该缓存。
- **使用`NOATIME`选项挂载磁盘卷**：默认情况下，操作系统会记录文件的最后访问（读取或写入）日期。此选项关闭该行为，从而加速访问（因为`Hadoop`不使用它）。

使用`ext4`文件系统（而不是`ext3`）有很多优点，例如多块分配和延迟分配。因此，你应该考虑使用它。现在，介绍一些不那么直观的设置：

- **禁用透明大页压缩**：启用后，此功能会告诉 Linux 内核尽可能为 Linux 进程分配 2 MB 的页面。但由于压缩部分似乎会导致 Hadoop 作业出现问题并导致高 CPU 使用率，因此需要禁用它。对于`RHEL`，你可以使用以下命令：
    ```
    echo never > /sys/kernel/mm/redhat_transparent_hugepages/defrag
    ```
    为了使更改永久生效，请在`/etc/rc.local`文件中添加以下脚本：
    ```
    if test -f /sys/kernel/mm/redhat_transparent_hugepage/defrag;
    then echo never > /sys/kernel/mm/redhat_transparent_hugepage/
    defrag ;fi
    ```

- **减少文件系统保留块空间**：有 5% 的空间是为特殊操作（例如当文件系统已满时由`root`删除文件）保留的，但`Hadoop`不需要此空间，因此可以移除。使用以下命令：
    ```
    tune2fs -m 0 /dev/sdXY
    ```

## 增加打开文件句柄和文件数

默认情况下，每个用户打开的文件数为 1024，这可能导致类似`java.io.FileNotFoundException: (Too many open files)`的错误。因此，需要设置打开文件数的限制。对于 Linux，存在三个限制：软限制（可由用户设置）、硬限制（仅由`root`或超级用户设置）以及系统级限制（由`root`在服务器配置文件中设置）。选择一个高值（如 4032）作为软限制（用户可以设置到的上限），一个更高的值（例如 32832）作为硬限制（`root`可以设置到的上限），以及一个非常高的值（例如 6544018）作为系统级文件描述符，因为这是整个系统可能的文件描述符总数。使用以下命令：

```
ulimit –S 4096
ulimit –H 32832
sysctl –w fs.file-max=6544018
```

## 内存交换

在 Hadoop 中，交换（将内存中的数据与文件系统交换）会降低作业性能。因此，请将最大数据保留在内存中，并配置你的操作系统仅在发生 `OOM`（内存不足）时才进行内存交换。为此，将内核参数`vm.swappiness`的值设置为 0。使用以下命令：

```
sysctl -w vm.swappiness=0
```

请注意，`sysctl`命令将仅为当前会话设置这些值。要使此值持久化，请将以下行添加到配置文件`/etc/sysctl.conf`中：

```
vm.swappiness=0
```

为了使上述文件描述符值持久化，请将以下行添加到配置文件`/etc/sysctl.conf`中：

```
fs.file-max=6544018
```

## 网络配置

Hadoop 作为一个分布式文件系统，节点间有大量的网络通信。因此，网络性能很重要，网络数据包大小也同样重要。最大传输单元（`MTU`）指示可以使用 `TCP/IP` 协议发送的数据包大小。`MTU` 的默认大小是 1500；你可以将其增加到 9000。大于其默认值的 `MTU` 值被称为巨型帧。你可以通过在配置文件`/etc/sysconfig/network-scripts/ifcfg-eth0`（或你的 `eth` 设备名称）中添加以下行来更改 `MTU` 的值：

```
MTU=9000
```

你必须重启网络服务才能使此更改生效。此外，在修改此值之前，请确保集群中的所有节点（包括交换机）都支持巨型帧。如果不支持，请不要进行此更改。

## Hadoop 配置

Hadoop 配置可以大致分为三类：`HDFS`、`JVM` 和 `YARN`（包括作为容器的 `MapReduce`）。我将讨论所有这些类别以及其中可调优的参数。

### HDFS 配置

`HDFS` 保存你的数据，因此是数据访问的关键考虑因素。你必须确保数据写入和读取以最佳性能执行。

我之前分享了一些关于 `NameNode` 和 `DataNode` 的配置细节，但请注意一些你可以使用的快速驱动器的详细信息。

此外，你应该执行一些通用任务，如时间同步、版本控制和集群平衡。同步所有集群节点上的时间非常重要。否则可能会导致错误，甚至可能难以知道这些错误的真实发生时间。同样重要的是对配置进行版本控制。你不希望出现某些节点处于特定版本而其他节点处于不同版本的情况。`HDFS` 提供了一个工具（`Balancer`）来以统一的方式在你的 `DataNode` 上重新分发数据。这也有助于均匀地分布处理负载，应在集群扩容后使用。

回到配置，你可以考虑关键参数，如块大小或缓冲区大小。以下是完整列表：

-   **驱动器类型**：尽管 `DataNode` 存储不需要 `RAID` 阵列（因为 `HDFS` 会根据指定的复制因子复制数据块），但使用快速的 `SATA` 驱动器来保存数据会有所帮助。`SSD`（固态硬盘）存储是理想之选，但由于价格昂贵，你可以使用 `SSHD`（固态混合硬盘）存储，它提供 7,200 `RPM` 或提供 10,000 `RPM` 的 `SATA III` 驱动器。

-   **`DataNode` 和 `NameNode` 的多个磁盘挂载点**：对于 `DataNode`，用逗号分隔的挂载点（或目录）列表会将数据分布到这些挂载点上，从而提供最佳的访问性能。对于 `NameNode`，多个目录（或挂载点）提供了元数据冗余。`HDFS` 确保你的文件的数据块在 `DataNode` 之间进行复制以实现冗余。相关的属性在`hdfs-site.xml`中：

    ```
    dfs.datanode.data.dir
    dfs.namenode.name.dir
    ```

-   **`DFS` 块大小**：这是一个非常重要的考虑因素。请审查你预期的文件大小及其使用情况。例如，如果你的数据文件很大，但大量用户查询检索的是小数据集（500 MB–5 GB），那么你可能希望从 64 MB 或 128 MB 的块大小开始，因为你是一次写入，多次读取。你可以在写入新文件时覆盖块大小，并根据文件的预期用途为它们设置不同的块大小。相关的属性在`hdfs-site.xml`中：

    ```
    dfs.block.size
    ```

-   **本地文件系统缓冲区**：这是 `HDFS` 为其 `I/O` 操作使用的缓冲区大小（由属性`io.file.buffer.size`控制）。为了提高性能，应将其增加到 64 KB 或 128 KB。此外，根据可用的 `RAM` 量...

# 实现和优化过渡

如果有可用资源，你可以将 `io.sort.factor`（排序文件时合并的映射数）设置为 20 或 25（默认为 10）。请注意，`io.sort.mb`（映射器用于收集映射输出的内存量）的值应为 `10 * io.sort.factor`。因此，若有 10 个映射器任务实例且 `io.sort.mb = 200`，则意味着你的排序总 RAM 分配为 2 GB。相关的属性在 `core-site.xml` 中：`io.file.buffer.size` 以及在 `mapred-site.xml` 中：`io.sort.factor`、`io.sort.mb`。

- **短路读取**：通常，当客户端从 HDFS 请求（文件的）数据块时，客户端会联系相应的 DataNode，并通过 TCP 连接将数据发送给客户端。如果所请求的数据块位于与客户端相同的节点上，那么（对于客户端而言）绕过网络直接从磁盘读取块数据（称为短路读取）会更高效。可以通过将属性 `dfs.client.read.shortcircuit` 设置为 `true` 来启用短路读取。相关的属性在 `hdfs-site.xml` 中：`dfs.client.read.shortcircuit`。你还需要为此目的设置其他属性。详情请参见 [`hadoop.apache.org/docs/r2.4.1/hadoop-project-dist/hadoop-hdfs/ShortCircuitLocalReads.html`](https://hadoop.apache.org/docs/r2.4.1/hadoop-project-dist/hadoop-hdfs/ShortCircuitLocalReads.html)。

- **NameNode/DataNode 并发性**：对于大型集群，必须拥有更多线程以实现最大并发性。参数 `dfs.namenode.handler.count` 控制 NameNode 的服务器线程数，应将其从默认值 10 增加到 50 或 100（取决于集群大小和可用内存）。参数 `dfs.datanode.handler.count` 同样表示处理 DataNode 块请求的线程数。如果你（为每个 DataNode）有多个物理磁盘，可以通过将此数字从默认值 3 增加到 5 或更多来提高吞吐量。相关的属性在 `hdfs-site.xml` 中：`dfs.namenode.handler.count`、`dfs.datanode.handler.count`。

- **DataNode 容错卷数**：此属性默认为 0。如果一个数据卷发生故障，DataNode 将关闭。将其设置为更高的值（2 或 3）将防止在单个数据卷发生故障时 DataNode 关闭。相关的属性在 `hdfs-site.xml` 中：`dfs.datanode.failed.volumes.tolerated`。

## JVM/YARN/MapReduce 配置

所有 Hadoop 守护进程都是 JVM，因此了解如何为 JVM 获得最佳性能非常重要。有一些通用指南，以及促进故障排除的方法，因为你的环境中可能存在某些原因或特定问题，这些原因或问题可能会驱动某些配置参数值，而这些值可能不遵循通用指南。

## 通用 JVM 指南

请注意，以下指南是通用的，你的特定环境可能有特定的要求，可能无法从中受益。

- **为所有守护进程使用启用了压缩 OOPS 的 64 位 JVM**：在 64 位环境中使用 64 位 JVM 非常重要，因为这使你能够使用最大可能的硬件资源（内存）。使用压缩 OOP（普通对象指针）是一种在 64 位环境中减少 Java 对象大小的技术。一个很大的好处是你可以使用相同的内存量容纳更大的 JVM。该技术的一个主要缺点是，在访问由压缩 OOP 引用的内存之前，需要进行地址解压缩。这会影响性能并占用宝贵的 CPU 资源。从 Java 6 更新 18 开始，Oracle（默认情况下）会根据最大 Java 堆大小在 JVM 中启用选项 `UseCompressedOops`。

- **最佳 Java 堆大小**：当 JVM 开始执行时，它会从操作系统获取一些内存，并将此内存用于其所有需求。这部分内存称为 Java *堆内存*。一个好的做法是将最小（或起始）和最大堆大小设置为相同的值（即设置 `Xmx == Xms`）。不要对诸如 `NewSize` 或 `MaxNewSize` 之类的参数使用 Java 默认值。对于大于 4 GB 的 JVM，你可以将 `MaxNewSize` 的比例（新 JVM 与旧 JVM 的大小）设为 1/8 到 1/6。

- **使用低延迟 GC 收集器**：垃圾收集（GC）是对属于已删除对象或已完成进程的堆空间的重用。你应该使用使用选项 `UseConcMarkSweepGC` 的并发算法或收集器。这是因为对于 Hadoop 守护进程的 JVM，它们的内存使用动态性更强，你需要保持 GC 暂停时间更短（即使这会占用更多的 CPU 时间用于 GC）。请注意，并发收集器需要为 JVM 分配更多的 RAM（相对于 GC 的串行或并行收集器）。选项 `ParallelGCThreads=<N>` 设置 GC 工作线程的数量。你应该将 `N` 的值设置为与逻辑处理器数量相同（最多 8 个）。对于更多的逻辑处理器，将 `N` 设置为大约逻辑处理器数量的 5/8（对于较大的 SPARC 系统，`N` 可以约为逻辑处理器数量的 5/16）。为 NameNode 和 JobTracker（YARN 的 ResourceManager）使用较多的 GC 线程，因为你需要 GC 过程无延迟，以实现更有效的内存利用。

- **用于调试的 JVM 配置选项**：

    ```
    -verbose:gc -Xloggc:<file>
    ```
    : 此选项将垃圾收集事件信息记录到文件中。除了 `-verbose:gc` 提供的信息外，每个报告的事件前面都带有自第一次垃圾收集事件以来的时间（以秒为单位）。

    ```
    -XX:+PrintGCDetails
    ```
    : 此选项激活“详细”GC 日志记录模式，该模式取决于所使用的 GC 算法。示例如下：`[GC [PSYoungGen: 246648K->243136K(375296K), 0,0935090 secs]`。此条目指的是一个年轻代 GC 实例，它将占用的堆内存从 246648K 减少到 243136K，耗时 0.0935090 秒。

    ```
    -XX:ErrorFile=<file>
    ```
    : 该文件名用于指定致命错误日志文件的位置（以防 JVM 发生致命错误）。

    ```
    -XX:+HeapDumpOnOutOfMemoryError
    ```
    : 此命令行选项告诉 JVM 在无法为请求分配堆内存时生成堆转储。由于使用此选项没有开销，它可以用于生产系统（在这种情况下，需要很长时间才能知道 JVM 内存不足）。堆转储采用 HPROF 二进制格式。

可以使用任何能导入此格式的工具（例如 `jhat`）进行分析。默认情况下，堆转储会以 `java_pid<JVM pid>.hprof` 的文件名创建在 JVM 的工作目录中。

## 通用 YARN/MapReduce 指南

`MapReduce` 是 Hadoop 起步时用于（作业分布式处理的）框架，但它在后续版本中被 `YARN`（有时称为 *MapReduce 2*）取代。

许多组织出于各种原因仍在使用 `MapReduce`。因此，我将给出一些优化 `MapReduce` 配置的技巧。

### 优化 MapReduce 应用程序

`MapReduce` 是一种编程模型，用于在 Hadoop 集群上通过并行、分布式算法处理大型数据集。一个 `MapReduce` 程序包含一个 `Map` 方法（执行过滤和排序，例如按产品名称对销售额排序）和一个 `Reduce` 方法（执行汇总或聚合，例如按产品统计销售额）。`MapReduce` 框架将处理任务分布在集群的各个节点上，并行运行任务，管理系统各个部分之间的所有通信/数据传输，并提供冗余和容错能力。

## 推测执行
集群中的所有节点运行速度可能不同——可能某个节点较慢。为了应对机器性能差异，Hadoop 会在多个没有其他任务执行的节点上调度同一任务的冗余副本，这个过程称为`推测执行`。当一个任务完成时，它会通知`JobTracker`，最先完成的副本成为最终副本。其他正在推测执行的副本会被放弃，`Reducer`会从最先成功完成的`Mapper`那里接收输入。

默认情况下，推测执行是启用的。如果你的节点配置相同，可以通过禁用此行为来节省宝贵的资源。你可以通过将`mapreduce.map.tasks.speculative.execution`和`mapreduce.reduce.tasks.speculative.execution`选项设置为`false`来禁用`Mapper`和`Reducer`的推测执行。

## Combiner 函数
`Combiner`是一种可用于减少`Reducer`处理数据量的函数。`Combiner`需要匹配`Mapper`的输入/输出键和值类型，并且只能用于单个`Mapper`。通过减少传递给`Reducer`的数据量，`Combiner`还有助于减少 I/O 和网络流量，从而提升性能。

## 数据压缩
你可以使用合适的编解码器来压缩数据，以减少 I/O 和网络流量，从而提升性能。根据数据的格式（本章后续会讨论），你可以使用`LZO`、`Snappy`等多种编解码器进行压缩。

## 分布式缓存
允许你缓存应用程序频繁使用的文件。一旦你为作业缓存了一个文件，Hadoop 就会将其提供给所有执行`Map`/`Reduce`任务的`DataNode`（位于 HDFS 中，而非内存中）。因此，你可以将缓存文件作为本地文件供作业访问。这能节省宝贵的 I/O 并提升性能。更多详情请参见 [`hadoop.apache.org/docs/r2.6.3/api/org/apache/hadoop/filecache/DistributedCache.html`](http://hadoop.apache.org/docs/r2.6.3/api/org/apache/hadoop/filecache/DistributedCache.html)。

如果你使用`Hive`，可以使用 Java 开发一个`UDF`（用户自定义函数）并利用此功能。在`Hive`中，命令`ADD FILE <filename>`会添加一个分布式缓存文件，该文件会被分发到每个节点。

Mapper 的平均运行时间不足一分钟。您可以增大 `mapred.min.split.size`，以便分配更少的 Mapper，从而减少 Mapper 初始化开销。您可以调整以下参数：

- `Mapreduce.map.minsplitsize`
- `Mapreduce.map.maxsplitsize`
- `Number of reducers`（Reducer 数量）
- `mapreduce.task.io.sort.factor`：对于任何正在运行 Map 任务的作业，每当内存缓冲区达到溢出阈值时，都会生成一个新的溢出文件。因此，Map 任务完成写入后，可能会有多个溢出文件，这些文件会合并成一个排序后的输出文件。此配置属性控制一次合并的最大流（文件）数。默认值为 10，但可根据您的数据量以及溢出阈值（默认为 80%）进行调整。
- `mapreduce.task.io.sort.mb`：当 Map 任务执行时，它会写入一个循环内存缓冲区，该缓冲区的大小由 `io.sort.mb` 属性定义。当此循环内存缓冲区被填满（达到溢出阈值）时，输出会被溢出到磁盘（使用单独的线程并行执行）。如果溢出线程写入速度缓慢且缓冲区达到 100% 满，Map 执行将会停止，因此调整此属性以获得最佳 MapReduce 性能非常重要。默认值为 100 MB，应根据您环境的性能和生成的溢出文件进行调整。
- `mapreduce.map.memory.mb` / `mapreduce.reduce.memory.mb`：这是 Hadoop 为每个 Mapper 或 Reducer 任务强制执行的硬性限制，定义了可分配给 Mapper 或 Reducer 容器的最大内存。默认值为 1 GB，但您应根据需要为您环境设置这些值。
- `mapreduce.map.java.opts` / `mapreduce.reduce.java.opts`：这是 Mapper 或 Reducer 任务的 JVM 最大堆大小（`-Xmx`），该值应始终低于属性 `mapreduce.[map|reduce].memory.mb` 的值。通常，此值应为 `mapreduce.map.memory.mb` / `mapreduce.reduce.memory.mb` 属性值的 80%。
- `mapreduce.reduce.shuffle.parallelcopies`：当您的作业执行时，多个 Mapper 在（您集群的）节点上执行，它们的 Map 输出文件位于本地（在执行 Map 任务的节点上）。这些 Map 任务可能在不同时间完成，因此 Reducer 任务会在这些输出完成后立即开始复制。Reducer 任务可用于并行获取 Map 输出的复制线程数由属性 `mapreduce.reduce.shuffle.parallelcopies` 定义。默认值为 5，应根据您的数据量和平均 Mapper 数量进行调整。

# 优化 YARN 执行

YARN（另一种资源协调器）是 Apache Hadoop 最新的资源管理框架。这本质上是 MapReduce 版本 2，具有许多新功能，例如（为 Mapper 和 Reducer）动态内存分配。YARN 的主要组件如下：

- `ResourceManager`：主守护进程，与客户端（请求方）通信，跟踪集群上的资源可用性，并通过向 NodeManager 分配任务来协调工作。
- `NodeManager`：这是一个工作守护进程，负责启动和管理在工作节点上执行的进程。
- `ApplicationMaster`：管理由 `NodeManager` 在 `Container` 内生成的、由 `ResourceManager` 请求的任务（或进程）。
- `Container`：表示在工作节点上预留资源（CPU/RAM）的请求。例如，MapReduce 是在 YARN 内运行的应用程序，`ApplicationMaster` 会生成 Mapper 和 Reducer 在 `Container` 内运行（并根据需要向 `ResourceManager` 请求额外的容器）。

如图 10-1 所示，当客户端进程向 `ResourceManager` 请求资源时，它会定位一个具有可用资源的节点，并向（该节点上的）`NodeManager` 请求这些资源。`NodeManager` 随后会生成一个 `Container`，并随之调用 `ApplicationMaster`。`ApplicationMaster` 管理应用程序（客户端进程）的资源，并（如果需要）向 `ResourceManager` 请求额外的资源。

请注意以下几点：

- Hadoop 集群每个节点的总内存由属性 `yarn.nodemanager.resource.memory-mb` 决定。
- `ResourceManager` 可以分配给 `ApplicationMaster` 容器的最大内存由属性 `yarn.scheduler.maximum-allocation-mb` 决定。默认的最小分配为 1 GB，但可以使用属性 `yarn.scheduler.minimum-allocation-mb` 进行更改。

因此，总结一下，以下是一些您可以调整的 YARN 属性：

- `yarn.scheduler.minimum-allocation-mb`：YARN 允许运行作业的最小容器大小（默认为 1 GB）。
- `yarn.scheduler.maximum-allocation-mb`：YARN 允许运行作业的最大容器大小（默认为 8192m）。
- `yarn.nodemanager.resource.memory-mb`：工作节点上容器的总内存量。该值应为：（总内存）–（操作系统、Hadoop 守护进程和任何其他服务的内存分配）。
- `yarn.nodemanager.vmem-pmem-ratio`：定义虚拟内存与可用物理内存的比率。默认值 2.1 表示虚拟内存将是物理内存大小的两倍。
- `yarn.app.mapreduce.am.resource.mb`：分配给 `ApplicationMaster` 的内存。
- `yarn.app.mapreduce.am.command-opts`：分配给 `ApplicationMaster` 的堆大小（默认为 1 GB）。
- `yarn.nodemanager.resource.cpu-vcores`：节点管理器可以分配给容器的核心数。该值应为：（节点上的总核心数）–（分配给 Hadoop 守护进程和任何其他守护进程的核心数）。

## 选择最佳文件格式

理解您选择用于存储数据的文件格式会直接影响对该数据的查询性能，这一点非常重要。在选择合适的格式时，需要考虑许多参数。您计划执行的查询类型当然是最重要的。下一个是您需要的压缩量。并且您需要确保计划使用的 NoSQL 解决方案支持该存储格式。幸运的是，大多数 NoSQL 解决方案都使得在不同格式之间转换数据变得容易。

文件格式会影响查询性能，因为它决定了系统在响应特定查询时读取数据集的快慢。数据检索速度是查询性能的最大决定因素。目前，数据检索的主要（也是最耗时的）任务是将数据从磁盘移动到内存，反之亦然（除非你使用内存数据库）。例如，如果你的数据集为 1TB，并且你使用接口为 SATA 6 GB/s 的 7200 RPM 硬盘，由于磁盘读取速率接近 160 MB/s，处理 1TB 数据大约需要两小时。对于更大的数据集，类似的性能将无法接受。

如何提高读取性能？有三种方法。首先，你可以通过利用分布式存储和计算技术来并行化读写操作。这将帮助你分割数据并将其分布在多个节点上，同时查询也会相应分布。`HDFS` 提供分布式存储（具备容错性），而像 `MapReduce`、`YARN`（或 `Spark`）这样的处理框架则帮助你实现“将处理移至数据”或在各个工作节点本地处理数据。这构成了在集群的所有节点上优化分布处理，从而以最佳性能完成任务（或作业）。

其次，你可以通过将数据存储在高效使用压缩的文件格式中来减少查询引擎处理的数据总量。文件格式支持不同的压缩算法，并以多种方式将这些算法应用于数据。请注意，压缩算法之间的权衡在于速度与压缩比。更高的压缩比会花费更多时间（同时消耗更多 CPU 资源）来进行压缩或解压缩。当然，你的文件会更小，从而节省磁盘空间。

使用各种文件格式的压缩方案能实现多大的压缩比？这取决于文件格式与压缩方案的组合。例如，对于大约 1GB 的文本（`CSV`）文件，`Snappy` 或 `GZIP` 可以将其压缩至约 500MB（如果存储为 `SequenceFile`）或约 300MB（如果使用 `ORCFile` 或 `Parquet` 格式）。表 10-1 列出了适用于各种行导向和列导向文件格式的压缩方案。

提高读取性能的第三种方法是使用预存储的聚合统计信息。这仅受`Parquet`和`ORC`等格式支持，它们可以获取基于最小值/最大值和空值计数的聚合统计信息作为预计算数据。此外，`Parquet`和`ORCFile`格式以牺牲写入性能为代价来优化读取性能（这遵循了 Hadoop“一次写入，多次读取”的理念）。

最后，数据的组织方式会影响各种类型查询的性能。

例如，当数据以行导向格式存储时，返回大量列（针对行子集）的查询速度更快。根据经验，返回超过 60%列的查询受益于行导向格式。或者，如果数据以列导向格式存储，则那些跨表（或其子集）的所有行对少数列进行汇总或聚合的查询性能更佳。因此，如果你期望大多数查询的形式为`select * from MyTable;`，则应使用行导向格式。

但如果你的查询形式为`select sum(MyColumn) from MyTable`（即，你只对数据集中的少数列执行聚合或生成汇总统计），那么你应该使用列导向格式。接下来，我将讨论一些行格式和列格式及其属性。

## 基于行的格式

# Hadoop 中的行式存储格式

Hadoop 生态系统中最流行的行式存储格式是文本文件、序列文件和 Avro。相信您之前一定使用过文本文件。CSV 文件易于使用，并且受到 Hadoop 生态系统中（以及外部）几乎所有工具的支持。序列文件在 Hadoop 生态系统内部也得到了广泛应用。

`Avro` 文件占用空间非常小，因此（与序列文件和文本文件相比）能提供更好的性能。但与另外两种行式文件格式相比，支持 `Avro` 的应用程序并不多。

## 文本文件

最简单、最常用的文件格式是文本文件。大多数数据库系统或应用程序都支持将数据导出为 CSV 或制表符分隔文件等文本格式。通常，这些文本文件包含 ASCII 或 UTF 字符，各个 `字段`（或列值）由称为 `分隔符` 的特殊字符（如逗号、分号、与号或制表符）分隔，记录之间用换行符分隔。

使用文本文件的优点如下：

-   它们可读性强且非常易于使用。
-   有大量可用于处理它们的工具。
-   大多数应用程序和数据库系统都可以接收（以及输出）文本文件。

尽管文本文件易于使用，但它们无法提供最佳性能。文本文件将所有字段值（包括数字或布尔值）存储为字符串。因此，如果您需要存储一个 `500` 的整数值，文本文件会将该值转换为等价的字符串（三个字符 `"500"`），然后再写入文件。

将所有数据存储为字符串存在几个问题：

-   数字和布尔值如果存储为字符串会占用更多空间（例如，`50,000,000` 作为字符串需要 `8` 个字节，但作为整数只需 `4` 个字节；布尔值 `"False"` 存储为字符串需要 `5` 个字节，但作为布尔值仅需 `1` 个字节）。这种空间占用增加会累积起来，导致文件体积庞大，需要更长时间才能加载（到内存），并对查询性能产生不利影响。
-   将字符串转换为适当的数据类型会为查询增加额外的工作。这对于 Hadoop 尤其重要，因为 Hadoop 生态系统中的大多数工具都遵循 `读时模式` 或读取时解析数据类型的理念。因此，每次执行查询时，都必须执行这种数据类型转换（除非您的所有数据真的是字符串或文本），这会减慢查询速度，并消耗额外的系统资源。

## 序列文件

序列文件是在 Hadoop 生态系统中广泛使用的文件格式（仅次于文本文件）。序列文件使用二进制格式，将数据存储为由键值对组成的记录。下面是序列文件的结构：

```
<文件头><键 1,(Doe,John,387-45-9876,1990-02-14,Chicago,IL)><同步标记>
```

因此，序列文件由一个文件头后跟记录（表示为键值对）组成。文件头包含关于文件和数据的元数据。同步标记用作记录终止符。Hive（以及 Impala）使用序列文件的简化版本，该版本忽略记录的键部分，并将每一行编码为字符串，使用特殊字符 `'\01'` 作为行分隔符。

例如，如果要对使用 Snappy 压缩方案的序列文件的 Hive 表数据进行压缩，请在 Hive 命令提示符下进行如下设置：

```
> set hive.exec.compress.output=true;
> set mapred.output.compression.type=BLOCK;
> set mapred.output.compress.codec=org.apache.hadoop.io.compress.SnappyCodec;
```

使用序列文件的主要优点是 Hadoop 生态系统中的所有组件都支持读写序列文件。不幸的是，Hive 和 Impala 使用序列文件的方式削弱了这种格式的许多优势，导致文件大小与文本文件相似（并因此带有与文本文件相同的问题）。

Hive 和 Impala（默认情况下）将数据以字符串形式存储在序列文件中。这意味着它们占用的空间与文本文件一样多，数字、布尔值和其他数据类型占用的空间超出了它们实际所需。此外，文件中的同步标记也会增加文件大小。

## Avro

`Avro` 是目前可用的最先进的行式格式，与文本或序列文件格式的区别如下：

-   `Avro` 在文件中包含或嵌入了数据（对应于表）的模式。这消除了每次在应用程序之间共享 `Avro` 文件时重新定义模式的需要。
-   `Avro` 根据字段的数据类型对字段进行编码（而不是将所有字段存储为文本）。这减少了（未压缩的）文件大小，并使得能够更有效地压缩文件。因此，网络传输时间和文件处理时间（用于数据类型转换）大大减少，为您的查询提供了更好的性能。
-   `Avro` 简化了模式变更（从而实现模式演化）。使用 `Avro`，可以更轻松地添加列，而无需重写底层数据以匹配新模式。如果您需要向数据中添加新列，可以通过在末尾包含附加字段并为旧记录提供默认值来实现。对于缺少此值的旧记录，Hive 将简单地使用默认值替换缺失值。

下面是 `Avro` 文件的结构：

```
<文件元数据><同步标记><数据块（对象计数，对象大小，数据）><同步标记>
```

该文件由一个文件头（包含序列化为 JSON 字符串的文件模式信息和压缩编解码器信息）后跟一个或多个数据块组成。每个数据块包含若干条记录和元数据（如记录数、记录大小等）以及实际数据，这些数据可以使用任何支持的编解码器进行压缩。以下代码使用 `Avro` 文件格式创建了一个 Hive 表（`Employee_avro`）：

```
> CREATE TABLE Employee_avro
(lastname STRING COMMENT '员工姓氏',
firstname STRING COMMENT '员工名字',
dept_code SMALLINT COMMENT '部门代码',
dob TIMESTAMP COMMENT '出生日期',
zip STRING COMMENT '邮政编码',
employee_since TIMESTAMP COMMENT '首次入职日期')
ROW FORMAT SERDE 'org.apache.hadoop.hive.serde2.avro.AvroSerDe'
STORED AS INPUTFORMAT 'org.apache.hadoop.hive.ql.io.avro.AvroContainerInputFormat'
OUTPUTFORMAT
'org.apache.hadoop.hive.ql.io.avro.AvroContainerOutputFormat'
TBLPROPERTIES ('avro.schema.literal'='{
"name": "employee_summary",
"type": "record",
"fields": [
{"name":"lastname", "type":"string"},
{"name":"firstname", "type":"string"},
{"name":"dept_code", "type":"int"},
{"name":"dob", "type":"string"},
{"name": "zip", "type": "string"},
{"name": "employee_since", "type": "string"}
]}');
```

从 `"name": "employee_summary"` 开始的部分是 JSON 模式定义，被包含在文件头中（作为文件元数据的一部分）。压缩编解码器的指定方式与为序列文件指定的方式完全相同。

`Avro` 也有一些缺点：

-   使用 `Avro` 格式可能比使用任何文本格式更复杂，并可能导致更长的开发时间。
-   （Hadoop 生态系统外部的）很少有应用程序支持或能读取这种格式。
-   对于 `Avro`，您需要在实际写入文件之前预先定义好模式，这在某些情况下是不可能的。

总而言之，`Avro` 对于使用全部或大部分列的查询来说是一个绝佳选择，因此对于数据仓库非常有用；尤其是那些包含数百列宽事实表的数据仓库。

## 列式格式

# 列式存储格式

列式存储格式更适合（且经过优化）用于分析场景，因为你需要聚合或汇总少量列。考虑上一节中的`Employee`表，假设有一个名为`Salary`的额外列用于存储员工薪资。使用列式文件格式时，检索薪资超过平均薪资两倍的员工列表会快得多，因为列式格式按列存储数据，这使得聚合操作变得简单（且快速）。

Hadoop 生态中最流行的列式（或基于列）格式是`RCFile`、`Parquet`和`ORCFile`。每种格式各有优劣，我将在本节中讨论。需要注意的是，列式存储格式不仅用于 Hadoop 生态，也被`Greenplum`或`Vertica`等高性能分析数据库所采用。

总结而言，在以下情况下应使用列式格式：

-   你经常需要在查询中执行聚合操作（例如`count`、`avg`、`min`、`max`）。

-   大多数查询只选择少量列，并使用少量列作为过滤条件（在`where`子句中）。

最后，请确保你的环境满足上述条件（再选择列式格式），因为如果不满足，存储在列式格式中的数据在需要检索整条记录时，将不得不执行*行重建*（即收集属于同一行的所有列并将其重新组合的过程）。这对系统来说涉及大量工作（非连续数据读取），因为每一行并非连续存储，这将对性能产生严重影响。

## RCFile

行列式（`RCFile`）文件格式（于 2011 年引入）是 Hadoop 生态中使用最广泛的列式格式之一。它节省了空间，从而加快了查询速度，因为需要检索的数据量更少。`RCFile`中的数据按如下结构组织：

```
<行组 1(<元数据头><列 1(值)><列 2(值)><列 3(值)><同步标记>)>,<行组 2(...)>,<行组 3(...)>
```

因此，`RCFile`同时将数据进行水平和垂直分区。首先，数据被划分为多个行组，然后在每个行组内，数据按列组织。此外，`RCFile`格式确保某行的所有列都位于同一节点上（它们适合单个 HDFS 块），以降低行重建的成本（如果需要）。最后，每个行组中的数据按列压缩（压缩编解码器的指定方式与 Sequence 或 Avro 文件完全相同）。

作为一个主要优势（因为`RCFile`是第一个列式格式），Hadoop 生态中的几乎所有工具都支持`RCFile`。此外，许多 Hadoop 生态之外的工具也支持它，因此如果你计划使用除`Hive`或`Impala`之外的工具对数据运行分析查询，则需要考虑此格式。

然而，与`Parquet`和`ORCFiles`相比，`RCFile`缺乏许多高级特性。例如，`ORCFiles`和`Parquet`允许存储更复杂的数据类型，提供让`Hive`限制加载到内存中数据量的方法，并且可以将数据加密成更小的文件。

## ORCFile

`ORCFile`格式作为`RCFile`格式的继承者被引入，并为其增加了许多特性。例如，它使用复杂的数据编码方案来进一步减小数据大小。它还存储元数据，以便更容易跳过不符合常见查询标准的行，并存储列的基本统计信息。这带来了显著更快的查询速度和高度压缩的数据。`ORCFiles`中的数据按如下结构组织：

```
<索引数据><行组 1(...)><条带页脚>,<索引数据><行组 2(...)><条带页脚>………<文件页脚><后记>
```

数据行组的结构与`RCFile`相同，但每个行组之前有一个索引数据块，之后跟着一个条带页脚。在数据文件末尾，有一个文件页脚和一个后记标记。这些额外的块为`ORCFile`提供了高级功能。压缩编解码器作为表属性指定。

`ORCFile`是最先进的列式文件格式之一。它使用复杂功能来减少文件空间，使查询更容易识别文件的关键部分并避免文件扫描。一个主要问题是缺乏对该格式的支持。例如，`Impala`目前不支持`ORCFiles`。因此，使用`ORCFile`格式可能会限制你可以用来处理数据的工具集。

## Parquet

`Parquet`格式由 Cloudera 和 Twitter 的工程师设计。它基于 Dremel 论文中描述的*记录拆分与组装算法*（Dremel 是 Google 设计的一种用于分析只读嵌套数据的可扩展、交互式临时查询系统）。

`Parquet`提供了非常高效的压缩和编码方案，并使用三种类型的元数据：文件元数据、列（块）元数据和页面头部元数据。

在最顶层，文件元数据包含关于模式、行数、行组列表和键/值列表的信息。在下一层，行组元数据包含行组的列块列表、总字节大小和行数。列块元数据包含文件路径（对于该块）、文件偏移量和列元数据（对于该块中的列）。列块可能包含多个页面，页面头部元数据包含详细信息（例如（未）压缩页面大小、数据页面头部、索引页面头部等）。数据和索引页面头部包含值和编码的详细信息。一个包含`M`个行组和`N`个列的`Parquet`结构化文件结构如下所示：

```
<文件元数据><行组 1 元数据(<列 1 元数据(页面元数据)>………<列 N 元数据(页面元数据)>)………<行组 2 元数据(...)>……<行组 M 元数据(...)><文件页脚>
```

总结来说，`Parquet`实现了一个复杂的数据物化引擎，结合了先进的编码技术，在压缩和速度之间取得了平衡。同时，`Parquet`会为你的每个数据列决定正确的编码格式。你可以按如下方式为`Parquet`文件选择压缩方案（以`Hive`为例）：

```
> set parquet.compress=SNAPPY
```

幸运的是，`Parquet`（与`ORCFile`相比）得到了更广泛的支持，因此它无疑是一种值得推荐的列式格式。

### 索引性能考量

索引是查询性能的一个非常重要的考量因素，尽管 Hadoop（与 RDBMS 相比）没有提供高级索引级别，但有一些通用指南可以遵循。首先，索引指南例如索引的最佳使用（索引过多会影响插入性能，或者索引应与常见查询模式匹配等）是有效的。此外，对于`Hive`，索引分区应与表分区匹配（在使用的分区列方面）。你可以参考 Hive 索引文档 [`cwiki.apache.org/confluence/display/Hive/IndexDev`](https://cwiki.apache.org/confluence/display/Hive/IndexDev) 获取关于 Hive 索引的全面解释。

在本节中，我将重点介绍 Hadoop 中常用的两种主要索引类型及其最佳用法：紧凑索引和位图索引。

### 紧凑索引

# 紧凑索引

通常，对于包含大量不同或唯一值（例如员工 ID）的列，可以使用`紧凑索引`。对于包含数值类型的列，应当使用紧凑索引。在内部，紧凑索引以排序表的形式存储（例如在 Hive 中），其中包含所有待索引列的值以及这些值所在的存储块。由于索引本身也是一张表，你需要使用与表格式相匹配的最佳格式（`ORC`、`Parquet`、`Avro`）来存储它，并在必要时进行压缩。如果你的表进行了分区，那么索引也会被分区，不过你可以根据需要更改索引的分区结构。通过设置属性 `IDXPROPERTIES 'hive.index.compact.binary.search'='true'`，确保该索引可用于紧凑二分查找。

创建索引后，如果源表中的数据发生变化，你需要按如下方式刷新或更新索引：

```
ALTER INDEX <索引名> ON <表名> REBUILD;
```

你可以让索引自动更新，但考虑到 Hadoop 处理的数据量巨大，更好的做法是手动计划索引更新，安排在系统空闲时进行。

## 位图索引

*位图索引*适用于仅有少量不同值的列（例如性别、逻辑值（是/否）、类别或类型）。对于这些列，不同值的数量与表中行数的比值很小。这个比值被称为*基数*。

使用传统索引对一个大表进行完全索引会占用大量磁盘空间，而位图索引仅使用索引数据大小的一小部分。原因是，传统索引为包含给定键值的行提供了一个指针（指向表中的数据行），因此针对每个键值都包含一个行 ID 列表（对应于具有该值的行）。

然而，对于位图索引，每个键值使用一个位图来代替行 ID 列表。位图中的每一位对应一个行 ID。如果该位被置位，则表示对应的数据行包含该键值。通过一个映射函数将位的位置转换为实际的行 ID。此外，位图索引会对位图本身进行压缩。因此，对于少量不同的键值，位图索引能提供更好的压缩比。由于多个位图索引的位图可以轻松组合，你应该使用单列位图索引。与紧凑索引类似，为了使位图索引有效，你需要对要建立索引的列的数据进行排序——否则，将会读取位图索引中包含值的所有块。因此，你应该将属性 `hive.enforce.sorting` 设置为 `true`，并在 `CREATE TABLE` 语句中指明哪些列应当被排序。

由于（Hive 中的）位图索引本质上也是另一张表，你需要指定有效的存储格式和压缩方式（如果索引很大）。

其他索引类型用于 `ORCFile` 和 `Parquet` 格式，例如*存储索引*（一种最小值/最大值索引，如果某个值不包含在数据块中则可以跳过该块，适用于数值类型以及使用 `<`、`>`、`=` 运算符的查询），以及*聚合索引*（类似于一个预定义了聚合操作的表，例如针对特定列的 `count`、`sum`、`average`，并按该列进行分组）。

总而言之，你需要了解并评估你的数据以实现有效索引，同时还需要制定根据数据（源表）变化定期更新索引的机制。

### 选择 NoSQL 解决方案并优化数据模型

为你的环境（和数据）选择正确的 NoSQL 解决方案的重要性常常被忽视。例如，如果你的数据主要是非结构化的，并且数据量较小（大约 2-5 TB），那么列式数据库就不是一个合适的解决方案。

首先，你需要了解 NoSQL 数据库的主要类型、它们的特性、优缺点，以及它们在你需要的处理类型（基于你的业务需求）下的表现。你的选择将对环境的性能和所支持的功能产生巨大影响。

关于 NoSQL 数据库的类型、特性以及为你的环境（基于你的数据）选择合适 NoSQL 数据库的标准，请参见[第 6 章](http://dx.doi.org/10.1007/978-1-4842-1287-5_6)的“选择合适的 NoSQL 数据库”部分。

关于 NoSQL 需要强调的一点是：它确实已经（并将进一步）转变为 LimitedSQL，因为最初的 NoSQL 键值对、基于 MapReduce 的数据库正被下一代数据库所取代，这些数据库提供了（更简单的）基于 SQL 的接口，对分析很有用。此外，这些具备 LimitedSQL 能力的数据库在性能和功能方面也在不断改进。

回到 NoSQL，在选择了合适的 NoSQL 解决方案之后，下一步就是准备你的数据以迁移到 NoSQL。大多数情况下，`OLTP` 或 `OLAP` 系统会迁移到 NoSQL。随后，你需要转换你的数据，使其能在 NoSQL 数据库中优化运行。例如，存储在关系型 `OLTP` 环境中的数据定义了参照完整性，因此你需要执行连接操作来检索所需数据。关系型数据库通常在连接操作上表现良好，并拥有提升性能的特性，如索引、统计信息定义、数据和查询计划缓存等。如果你将关系型数据迁移到 NoSQL 环境，大部分 `RDBMS` 的特性就不复存在了。而且，NoSQL 数据库在连接操作上表现不佳。

因此，你需要重新设计数据模型并消除连接。你可能需要为此目的对数据进行反规范化，并且可能需要合并某些数据表以形成更大的表。需要采用不同的技术来将你的关系型（`OLTP`）或星型模式（`OLAP`）设计转换为适用于 NoSQL 的形式。更多信息请参见[第 6 章](http://dx.doi.org/10.1007/978-1-4842-1287-5_6)。

### 总结

性能调优本身就是一个庞大的主题，考虑到其涉及的各种子主题，其专业程度足以自成书。本章并非旨在涵盖所有方面。其目的在于吸引你关注可以调优 NoSQL 环境的不同方法。例如，MapReduce 或 HDFS 参数列表并非详尽无遗。请参阅 Apache 文档以获取完整的参数列表，并调优其他与环境更相关的参数。

或者，如果你考虑索引，请仔细审查你的查询需求，并添加你可能未涉及到的适当类型的索引。

同时，也要考虑硬件方面。像 Teradata 这样的大型公司主要专注于设计用于管理 PB 级数据的硬件。几年前，英特尔推出了其基于硬件的解决方案，以在不牺牲性能的情况下促进加密和解密。你可能不想（或没有资源）走得那么远。关于硬件优化的部分旨在提供通用指南，并帮助你优化计划用于实现方案的硬件。

你的环境会有特定的需求，但至少你有了一个良好的起点。当然，不可能考虑到所有类型的优化场景。

不同的组织在性能调优方面采用不同的方法。

# 文档排版

## 性能优化与规划

一些组织从通用指南开始，只有在遇到具体问题时才考虑性能调优。这样，他们可以专注于问题领域并节省宝贵资源（时间和金钱）。这种方法的问题在于，当前问题虽然能快速解决，但能保证该领域或其他领域不会出现额外问题吗？当然不能。这就是为什么需要从良好的规划开始。执行压力测试，考虑数据增长（以及随之而来的使用量增加），同时还要考虑`边界条件`（最小值和最大值）。边界条件可能适用于你的硬件资源、NoSQL解决方案、网络容量，甚至技术支持资源。

充分理解增长以及边界条件，将有助于你有效规划近期可能出现的任何性能问题。如你所知，随着技术的动态变化（尤其是在NoSQL领域），没有哪个系统能保证长久存在，但如果你主动出击并预测问题，而不是等问题出现才应对，至少可以避免近期内的问题。

### 基于Hadoop解决方案的设计与实现案例研究
