## 缓存十分钟

`memcacheclt:set(key, final_array, 10 * 60)`

`return final_array`

当您缓存此产品的销售数据行时，最多十分钟内您将看到相同的数据。这意味着您所做的任何数据更改最多需要十分钟才能生效（除非您通过更改数据来主动使缓存失效）。通常，您可以为 Web 应用程序使用键值数据库，并保存用户配置文件/偏好、会话详细信息和购物车。

## 文档数据库

面向文档的数据库将数据存储为文档并进行管理。一个*文档*可以是一组结构化或半结构化数据。面向文档的数据库可以被视为键值存储的一个子类，因为数据的存储和检索方式相似，但数据的处理方式不同。对于键值存储，数据对数据库来说本质上是不可知的；它只是键对应的值。相比之下，面向文档的系统会读取数据（或文档）的内部结构以提取元数据，并将其用于进一步的处理和优化。

面向文档的数据库从数据本身提取类型信息，并将相关信息分组以便于使用。例如，XML 数据库（一个特定的子类）针对从 XML 文档中提取元数据进行了优化。此外，文档数据库通常也针对复杂的随机文本搜索（例如，`elasticsearch`）进行了优化。

使用面向文档的数据库，您可以灵活地使每个数据实例彼此不同，这为可选值以及更新提供了宝贵的支持。这就是为什么它们在 Web 应用程序中如此受欢迎的原因——这些应用程序经常更改，可能包含半结构化数据，并且还需要快速部署。接下来，让我通过一个示例讨论什么是文档。请看以下文本：

```
蓝色条纹衬衫
IL（美国）
```

尽管您可能清楚此文档包含服装商品的详细信息，但其他各个字段代表什么并不清楚。如果将此信息存储在键值存储中，语义内容（表示 Web 零售商的此库存商品）可能会丢失，并且数据库将无法有效地优化或索引这些数据。也许可以运用额外的逻辑将字符串分隔成字段并将字段分配给表中的列，但这并非易事。

如果没有元数据，解析像这样的自由格式数据可能会很复杂。现在考虑用伪 XML 标记的同一文档：

```
<Item>
  <ItemName>蓝色条纹衬衫</ItemName>
  <ItemType>男士衬衫</ItemType>
  <ItemSize>大号</ItemType>
  <ItemNumber>226453</ItemNumber>
  <Quantity>20</Quantity>
  <WarehouseNum>12345</WarehouseNum>
  <State>IL</State>
  <Country>US</Country>
</Item>
```

所以现在，文档既包含数据也包含元数据，并且元数据解释了每个字段。这样，就可以查询数据，例如“查找位于'IL'州的所有 `<Item>`”，或者为了性能而在`state`字段上设计索引。您可以像任何其他数据库一样组合搜索条件，但主要区别在于将元数据嵌入文档本身，这消除了预定义数据库字段的需要。它还提供了添加或删除某些字段的灵活性，因此数据库中的每个文档都可以有不同的格式。一个`<Item>`可能包含`<Size>`，而另一个可能只有`<Style>`。这并不会使之前查找伊利诺伊州商品的查询失效。

嵌入的元数据还允许更改文档格式而不影响现有文档。假设向新文档添加了一个新的`<ItemPicture>`字段。这不会影响任何现有文档——它们只是没有关联的图片。此外，通常，任何基于不属于某个文档的字段的查询都不会检索到它们。

文档的流行格式包括 XML、YAML、JSON 和 BSON。一些文档不包含明确定义的元数据（例如，PDF），而管理它们的数据库可能提供使用索引映射数据的方法，或者包含基于 XML 的预定义格式，如 MathML、JATS 或 DocBook。在某些情况下，使用模式语言如 DTD、XSD 或 Relax NG 将文档映射为更可用的格式。JSON 是许多面向文档的数据库最流行的格式（主要用于交互式基于 Web 的应用程序）。

文档可以使用唯一的键进行引用存储，并可以使用该键进行检索。键可以是字符串、URI 或路径。在键字段上创建索引有助于加快文档检索。可以创建更多索引以加快频繁搜索。大多数流行的面向文档的数据库都提供工具来提取和索引它们所管理的文档的几乎所有元数据以及数据内容。查询语言的支持进一步支持了查询，使用户更容易使用。

面向文档的数据库可用于包含以下内容的数据：

- 多种数据类型，可能有多种访问模式

- 需要构建 CRUD（创建、读取、更新、删除）应用程序

- 类似于 JSON、HTTP、REST、JavaScript 的数据类型，并与基于 Web 的应用程序一起使用

- 涉及大量小型（且可能易变的）连续读写操作的处理

- 不断变化的数据类型或需要灵活的列数（由于可选数据）

- 大型媒体（BLOB 类型）或半结构化数据

适用于文档数据库的应用程序包括事件日志记录、电子商务应用程序和内容管理应用程序。流行的面向文档的数据库系统有 MongoDB、CouchDB 和 OrientDB。

## 列式数据库

*列式*数据库按列而不是按行组织其数据。这重新定位了数据的焦点，有助于更有效地从硬盘存储读写数据，从而加快对数据集执行的查询速度。一个*数据列*由名称和值（有时还有时间戳）组成。每一行可以有不同数量的列。行键可用于查询，也可以使用（在列值上创建的）二级索引。

对于列式数据库，列值在物理上被分组在一起，而不是行。由于数据是按记录顺序存储的，因此列 1 的第 5 个条目和列 2 的第 5 个条目是同一记录的一部分。这使得作为一组按列访问单个数据元素（例如以下产品详细信息）成为可能，而不是逐行访问。

以下是产品表示例：

```
ID 产品名称        类别    数量  价格
1  绿茶包           茶      100  3.99
2  红茶包           茶      100  2.99
3  姜茶包           茶      100  4.99
```

对于面向行的数据库，数据将存储为：`1,绿茶包,茶,100,3.99;2,红茶包,茶,100,2.99;3,姜茶包,茶,100,4.99;` 对于面向列的数据库，数据将存储为：`1,2,3; 绿茶包,红茶包,姜茶包;茶,茶,茶;100,100,100;3.99, 2.99,4.99;` 但是为什么要按列组织数据呢？一个原因是它提供的存储压缩。因此，列操作（例如 `MIN`、`MAX`、`SUM`、`COUNT` 和 `AVG`）可以非常快速地执行。此外，由于列式数据库是自索引的，与关系数据库管理系统相比，它可以更有效地存储数据（就磁盘空间而言）。而且，列式数据库提供的数据压缩是一个很大的优势。这些特性的好处在大数据量下可见，此时数据访问性能至关重要。否则，对于较小的数据量，提供内存分析功能的数据库可以轻松地使面向行与面向列数据库的相对优势变得有些无关紧要，因为它们速度很快——尽管列式数据库提供的数据压缩仍然有用，因为内存很昂贵，而压缩可以帮助您使用更小的 RAM 容纳数据集。

什么样的应用程序可以使用列式数据库？如前所述，需要大数据量才能看到性能差异。此外，列式数据库非常适合于聚合在少数列中的大量数据。列式数据库不支持 ACID 事务，在可以容忍“最终一致性”的情况下更有用。

关于列式数据库的另一件要记住的事情是，它们在写入更频繁的应用程序中与在查询中一样表现良好。此外，这些数据库在应用程序需要一次只访问少数列（涉及大量行）时表现良好。列式数据库可以通过帮助您专注于必要的列而无需读取数千行来加快分析查询。

最后，列式数据库还可以用于依赖于时间的列（或具有过期时间的数据），因为可以设置在特定日期后自动使列过期。

虽然列存储的概念之前已作为关系数据库的一部分实现，但 RDBMS 不提供跨列族行不同的列的灵活性，而 NoSQL 列式数据库允许这样做（每行可以有不同数量的列）。

众所周知，列式数据库源自 Google 的 Big Table。流行的分布式横向扩展列式数据库包括 HBase 和 Cassandra。

总结一下，如果您的数据满足以下条件，可以使用分布式横向扩展列式数据库：

- 需要高可用性和冗余

- 需要跨越不同地理位置的数据中心，并且您需要一个能够处理长延迟的分布式、分区容忍的选项

- 有不需要任何一致性保证的连续数据流

- 具有不断变化的数据类型和动态字段

- 有可能达到真正的大数据量，例如数百 TB，并且需要对少数列进行聚合

通常，以下类型的应用程序可以从这种大数据处理能力中受益：

- 数据分析（用户行为、网络流量、日志文件）

- 生物信息学（遗传和蛋白质组数据）

- 股票市场分析（交易数据）

- 网络规模应用程序（搜索引擎）

- 社交网络服务

## 图数据库

图数据库起源于瑞士数学家莱昂纳德·保罗·欧拉提出的图论。图数据库的主要组成部分是*节点*和*边*（或*关系*）。节点和关系都可以具有与之关联的属性。此外，节点还可以用零个或多个标签进行标记。节点表示您可能想要监控（或查询）的实体，关系是节点之间存在的关系。属性（或特征）提供关于节点或关系的信息。

例如，如果“Practical Hadoop Security”是一个节点，则可以根据“Practical Hadoop Security”的哪些方面与特定数据库相关，将其与“书籍”、“安全参考资料”或“220 页”等属性关联起来。

对于大数据集上的复杂查询，图数据库通常比关系数据库更快，因为它们不需要昂贵的连接操作。由于它们不依赖于静态模式，因此对于频繁变化的数据以及不断演进的模式，它们表现更好。然而，对于具有大量数据元素的静态模式，它们（比关系数据库）表现不佳。当然，图数据库最适合于类似图的查询（例如计算两个节点之间的最短路径或计算图的直径）。

对于涉及各种节点（或实体）之间复杂相互关系（例如，涉及连接城市的多条高速公路、蛋白质与蛋白质之间的相互作用、员工与员工协作的查询）的场景，图数据库效果最好。这就是为什么图数据库非常适合以下类型的问题领域：

- 网络和 IT 基础设施管理
- 身份和访问管理
- 业务流程管理
- 产品和服务推荐
- 社交网络

关于图数据库需要记住的一件重要事情是，它们不擅长处理大量数据，因此对于涉及大规模图的应用程序（例如社交网络），通常使用列式（或其他合适的）数据库进行存储和检索，而图操作则作为一个增加性能的顶层处理层工作（例如，`Titan` 图数据库）。

我将以 `LinkedIn` 的架构为例。`LinkedIn` 混合使用 `Oracle`、`Voldemort`、`Espresso`、`Pinot` 和 `XML` 进行数据存储。数据库被水平和垂直分区（为了性能）。由于分区，无法实现引用完整性或跨域 `JOIN`。此外，使用了最终一致性模型，因此不能保证数据一致。`Voldemort` 和 `Pinot` 是键值存储。`Espresso` 是 `LinkedIn` 的在线分布式容错 `NoSQL` 数据库，被超过 30 个 `LinkedIn` 应用程序使用，包括会员档案、`InMail`（会员对会员消息系统）、主页部分内容、移动应用程序等。`Oracle` 因其成本而被谨慎使用。

`Voldemort` 是一个简单的键查找系统，用于快速查找小块数据（例如用户资料、*您可能感兴趣的工作*、*您可能认识的人*等数据）。`Pinot` 用于更大规模的键值查找，例如历史数据（*给我一月至三月所有的大数据工作*），并且可扩展以存储大量数据。

`Cloud` 是一个服务器，它将整个 `LinkedIn` 网络图缓存在内存中（`LinkedIn` 为此目的开发了一个专有的图数据库，它几乎位于每个操作的中心）。每个 `Cloud` 实例支持 2200 万个节点和 1.2 亿条边，需要 12 GB `RAM`。到 2008 年，生产环境中已有 40 个 `Cloud` 实例（我不确定现在有多少个）。`Cloud` 实例使用更新后的数据实时更新，并在关闭时持久化到磁盘。将所有内容放在 `RAM` 中是一个限制，但由于对图进行分区很困难，没有其他选择。

尽管 `Cloud` 缓存了整个 `LinkedIn` 网络，但每个用户只需要查看与他相关的信息，并且由于计算这些单个用户视图代价高昂，`LinkedIn` 仅在用户连接时进行计算并保持缓存。此缓存的网络视图在会话期间不会更新，除非用户自己添加/删除链接（此外，如果用户的任何联系人进行了更改，也不会更新）。

对于搜索，使用了 `Lucene` 搜索引擎的定制版本，并且由于搜索的是缓存数据，结果返回非常快。`Kafka` 和 `Databus` 用于数据复制，而 `Zoie`（使用 `Lucene` 的实时搜索和索引引擎）、`Bobo`（用于 `Lucene` 的分面搜索库，*分面*是用户的属性，如行业、前公司、专利等）和 `SenseiDB`（实时、分面、键值和全文搜索引擎）用于在线搜索。

图数据建模是一个用户通过节点和关系的连接图来表示特定领域的过程。然后使用这个图来回答以 `Cypher`（`Neo4j` 查询语言）查询形式提出的问题。让我先描述一下我的示例领域。

# 使用 Neo4j 的示例

## 领域描述

考虑以下关于两个人 `James` 和 `Scott` 之间联系的描述。他们为同一家公司工作。`James` 和 `Scott` 都在 `Amazon.com` 购买了一套烛台。

我们可以使用此语句来识别组件节点、标签和关系，并构建我们的模型。

## 节点

节点是主要组件，可以具有属性、关系（与其他节点）和标签。通常，节点是具有唯一概念身份标识的实体。

在这种情况下，需要定义以下节点：

- `James`
- `Scott`
- 一套烛台

## 标签

接下来，让我们决定是否需要为您的节点分配任何标签。*标签*用于将节点分组到集合中，并且是可选的。如果定义了标签，数据库查询可以使用标签而不是单个节点，这使得编写紧凑且更高效的查询更容易。

对于此示例，让我们定义两个标签：

- `Person`（应用于节点 `James` 和 `Scott`）
- `Object`（应用于节点 烛台套件）

## 关系

在这些节点之间可以识别出以下交互：

- `James` 是 `Scott` 的同事
- `Scott` 是 `James` 的同事
- `James` 买了一套烛台
- `Scott` 买了一套烛台

接下来，我将连接这些节点以展示它们的交互并完成图数据模型。标记为 `Person` 的节点可以通过 `同事` 关系连接。标记为 `Object` 的节点可以使用 `已购买` 关系与标记为 `Person` 的节点连接，如图 6-2 所示。

### 创建属性

节点本身不提供任何有用信息，也无法回答可能提出的问题。属性取决于节点可能需要的信息。例如：

- James 和 Scott 何时成为同事的？
- 这套烛台的价格是多少？
- James 和 Scott 从哪里购买了这套烛台？
- James 多大了？

添加以下属性有助于回答这些问题（请注意，属性以键值对形式添加），如图 6-3 所示。

```
               同事
Scott <------------------------> James
自: 2003-12-25                  自: 2003-12-25
姓名: Scott                     姓名: James
年龄: 53                         年龄: 37
   |                               |
   |                               |
   | 购买日期: 2015-02-19         购买日期: 2015-01-31 |
   |                               |
   v                               v
         一套烛台
         对象名称: 一套烛台
         价格: $50
         卖家: Amazon.com
```

*图 6-3. 基于 `Neo4j` 示例的图数据模型（含属性）*

让我们使用 `Neo4j` 查询语言 `Cypher` 将属性数据添加到数据库：

```
// 创建实体或节点
CREATE (James:Person { name: "James", age: 37 })
CREATE (Scott:Person { name: "Scott", age: 53 })
CREATE (sch:Object { Object_name: "一套烛台", price: "$50" })

// 创建关系
CREATE (Scott)-[:COLLEAGUE_OF { since: 1072339200 }]->(James)
CREATE (James)-[:HAS_BOUGHT { on: 1418976000 }]->(sch)
CREATE (Scott)-[:HAS_BOUGHT { on: 1420272000 }]->(sch)
```

请注意，使用的日期（`1072339200`、`1418976000` 和 `1420272000`）是`纪元时间`（是自 1970 年 1 月 1 日以来经过的秒数，不计算闰秒）。因此，如果将 `2003-12-25 08:00` 转换为`纪元时间`，您将得到 `1072339200`。

最后，这是一个示例查询，回答“一套烛台的价格是多少？”：

```
MATCH (sch:Object { object_name: "一套烛台" })
RETURN sch.price as price
```

总结一下，当数据满足以下条件时，可以使用图数据库：

- 具有复杂的关系，如社交网络数据
- 需要动态构建实体之间的关系，这些实体可能具有动态或变化的属性
- 所涉及的查询可能需要复杂或嵌套的连接
- 属于位置服务或推荐引擎

至此，我完成了关于如何根据您的数据处理需求选择合适的 `NoSQL` 数据库解决方案的讨论。接下来，我将讨论为了使您的应用程序适应 `NoSQL` 使用而需要对数据进行的更改。

### `NoSQL` 的并发性与安全性

对于 `NoSQL` 环境，并发性和安全性的概念（与 `RDBMS` 相比）有所不同。大多数 `NoSQL` 数据库不存在实现并发的机制（如锁定或事务隔离级别）。安全性需要使用第三方解决方案来实现，并且不与数据库集成。因此，`RDBMS` 默认可用的这些特性需要针对某些 `NoSQL` 环境进行模拟。这是 `NoSQL` 提供更好性能所付出的权衡之一。我现在将详细讨论这些概念。

### 并发性

当用户在 `RDBMS` 数据库中更新表中的数据时，其他用户无法修改相同的数据，因为它已被锁定（通过*排他写锁*）。在锁定数据以进行更新之前，`RDBMS` 会等待获得数据集的排他控制权，同时用户使用*共享读锁*读取数据。一旦没有共享锁，数据集将使用*排他写锁*进行锁定。并发性通过数据库锁定得到了有效处理。`RDBMS` 支持 `ACID`（原子性、一致性、隔离性和持久性）事务，这提供了数据的可靠性。

`NoSQL` 数据库不支持事务的 `ACID` 合规性，但有替代策略。*乐观并发控制*（`OCC`）就是其中之一。`OCC` 假设多个事务可以在不相互干扰的情况下完成。因此，允许事务使用数据资源而不获取锁。但是，每个事务都会验证其使用（读取或写入）的数据未被任何其他事务修改。如果存在冲突的修改，则提交的事务将回滚。`OCC` 只能用于数据争用较低的环境，否则重启事务的开销将抵消通过避免锁定所获得的性能优势和高吞吐量。

通常情况下，由于大多数 `NoSQL` 数据库遵循“单次写入，多次读取”的理念（尤其是开源数据库）。它们不期望并发更新，因此未设计为支持它们。默认情况下，大多数分布式数据系统支持*最终一致性*。任何具有处理读取请求的多个节点的系统，在处理读取请求时，如果要提供良好的性能（因为验证会涉及额外时间），则无法联系其他节点（以验证所提供的数据）。因此，提供的数据可能不是最新的；您最多只能期望节点同步并最终达到一致。这个概念也称为 `BASE`（基本可用）。

现在，如果您的应用程序需要某种程度的并发控制（也许不像 `ACID` 合规性那么严格），您该怎么办？以下是在 `NoSQL` 环境中实现并发性的一些其他方法：

- 您可以使用 `ZooKeeper`。`ZooKeeper` 的工作方式是通过使用法定人数实现分布式锁定。
- 您可以使用经过良好测试的分布式共识算法之一——例如，`Paxos` 结合 `MVCC`（多版本并发控制）。
- 如您所见，在符合 `ACID` 的数据库环境中锁定会导致读取（`SELECT`）和写入（`UPDATE`）彼此等待（完成）。这种情况通过使用 `MVCC` 来解决。一个*版本*是数据在某个时间点的快照。查询表时，读取者可以访问数据的当前版本，而更新可以同时（并行）发生。因此，稍后时间点的同一查询可能会使用更新的版本并产生不同的结果。
- 您可以使用 `CAP` 模型，该模型指出任何网络化共享数据系统只能拥有三个理想属性中的两个：一致性（`C`），意味着您获得数据的单个最新副本；高可用性（`A`）的数据（用于更新）；以及对网络分区（`P`）的容忍度。
- 尽管在设计者仍然需要在存在分区时在一致性和可用性之间做出选择，但随着当代网络系统的出现，处理分区以及从中恢复有了很大的灵活性。因此，修改后的 `CAP` 目标可以是最大化特定应用程序所需的一致性和可用性的组合。当然，这需要伴随着分区期间的连续性计划以及后续的恢复计划，从而克服 `CAP` 的感知局限性。

### 安全性

安全性是您甚至不会认为它是一个特性的另一个 `RDBMS` 功能。在开源 `NoSQL` 世界中，没有广泛集成的安全实现。没有内置的身份验证或授权。也没有内置的加密或掩码。所有这些功能都需要通过单独的应用程序或 `API` 实现，并且您需要确保这些应用程序或 `API` 得到良好集成。一些商业可用的 `NoSQL` 解决方案（例如，`10Gen` 的 `MongoDB` 或 `Datastax` 的 `Cassandra`）在其产品中包含了身份验证、掩码和加密功能，但它们仍然缺乏有效的授权或细粒度安全性手段。此外，并非所有商业 `NoSQL` 产品都提供这些功能。

回到开源产品，`Kerberos` 被广泛用于大量开源 `NoSQL` 解决方案的身份验证。`Kerberos` 由麻省理工学院开发，是一个易于获得的开源应用程序，可与多种 `Linux` 发行版以及 `HDFS` 配合使用。它也能很好地与 `HBase`、`Hive`、`Pig` 等 `Apache` 应用程序配合使用。大多数主要的 `Hadoop` 供应商发行版都与 `Kerberos` 配合使用，这就是为什么现在有些发行版包含了 `Kerberos`。由于 `Kerberos` 已经存在很长时间，因此有大量关于安装、配置、可能的问题以及解决方案的文档。

## 安全措施与监控工具

授权可以使用 HDFS ACL 或 Apache Sentry（如果您使用 Hive）来执行。此外，现在有像 Apache Knox 或 Apache Ranger 这样的组件可以提供全面的安全解决方案。您可以使用 Ranger（或 Knox）为各种 Apache 组件（如 HDFS、Hive 或 Hbase）创建访问策略（针对用户或组），这些策略提供细粒度（表级别）的权限。Knox 还提供 LDAP 集成，使得将 Hadoop 的安全性与您的企业安全性集成变得容易。

最后，大多数 Hadoop 供应商（以及一些 NoSQL 数据库）提供自己的定制授权工具。

数据加密在传输中以及*静态*（数据存储在物理磁盘驱动器上时）都可用，使用 Apache 基金会开发的加密和压缩 API。此外，还有像 eCryptfs 这样的开源加密文件系统，可以成功地与 Hadoop 和 NoSQL 解决方案一起使用。此外，大多数主要的 Hadoop 供应商都提供与第三方加密工具的接口。

最后，有像 Ganglia 和 Nagios 这样优秀的开源监控工具可用于监控系统资源和对 NoSQL 数据库的未授权访问。

总之，实施身份验证、授权、加密和监控工具的组合策略为 NoSQL 数据库提供了一个强大的安全选项。开源数据库主要使用开源工具，而商业可用的 NoSQL 数据库使用它们自己的定制工具来实现组合安全策略。

# 设计过渡模型

上一节讨论了选择合适的 NoSQL 数据库的标准。下一步，需要将关系数据库中的数据转换为 NoSQL 使用。这涉及反规范化，在某些情况下，在反规范化之前还需要转换为星型模式。无论哪种情况，都需要确保最终结果没有连接、没有关系，并且表数量很少。

另外，请注意，数据迁移的过程将取决于您选择的 NoSQL 技术。例如，将 RDBMS 数据迁移到列式数据库的过程将不同于迁移到键值存储（如 Riak）或文档存储（如 MongoDB）的过程。我接下来将详细讨论这些过程。

图 6-7 是一个通用销售分析系统的星型模式。`Sales_facts` 是一个事实表，您可以看到诸如 `Customer`、`Location`、`Date`、`Product` 和 `Sales_Reps` 之类的维度。

**图 6-7.** 销售分析星型模式示例

第一步是将维度表的相关部分与事实数据结合起来（以避免连接）。根据性能需求，可以很容易地得出结论，来自维度 `Customer`、`Location` 和 `Product` 的列需要添加到事实表中。因此，您可以从数据集中移除维度 `Sales_Reps`，因为它与此需求无关。接下来，您可以评估所考虑维度中的列，由于列 `ProductId`、`ProductSerialNum`、`LocationId`（来自 `Product` 维度）、`CustomerId`、`LocationId` 和 `CustomerSince`（来自 `Customer` 维度）与此数据集无关，它们也可以被移除。

最后，只有两个度量或事实，并且由于两者都与数据集相关，因此不需要移除任何一个。将需要二级索引来提升性能，可以为列 `CustomerName`、`ProductName`、`IndustryType`、`CustomerType`、`State`、`City` 等创建索引。

### 实现最终模型

我从将关系应用程序重构为 NoSQL 环境的设计原则开始。首先，我讨论了如何根据您的数据类型和目标应用程序选择 NoSQL 技术。然后，我讨论了 NoSQL 环境中并发性和安全性的实现。之后，我介绍了为关系数据设计过渡模型。作为最后一步，我将讨论实现这些过渡模型以针对您选择的 NoSQL 数据库。

广义上讲，重构过程涉及四个步骤：

1.  评估并选择最适合您数据/应用程序需求的 NoSQL 技术类型。尝试在一个小项目中使用所选技术，并验证功能/易用性。

2.  反规范化关系数据，并使用您选择的 NoSQL 技术（按需选用文档、键值、列或图）表示生成的模型。

3.  设计/开发 ETL（提取、转换、加载）逻辑，使用您选择的工具将数据从关系数据库迁移到 NoSQL 环境。

4.  重新设计应用程序查询，以从您的 NoSQL 数据库读取数据。

我将讨论如何使用列式 NoSQL 数据库作为目标以及过渡模型作为基础来实现最终模型。
