## 位图索引

*位图索引*适用于仅有少量不同值的列（例如性别、逻辑值（是/否）、类别或类型）。对于这些列，不同值的数量与表中行数的比值很小。这个比值被称为*基数*。

使用传统索引对一个大表进行完全索引会占用大量磁盘空间，而位图索引仅使用索引数据大小的一小部分。原因是，传统索引为包含给定键值的行提供了一个指针（指向表中的数据行），因此针对每个键值都包含一个行 ID 列表（对应于具有该值的行）。

然而，对于位图索引，每个键值使用一个位图来代替行 ID 列表。位图中的每一位对应一个行 ID。如果该位被置位，则表示对应的数据行包含该键值。通过一个映射函数将位的位置转换为实际的行 ID。此外，位图索引会对位图本身进行压缩。因此，对于少量不同的键值，位图索引能提供更好的压缩比。由于多个位图索引的位图可以轻松组合，你应该使用单列位图索引。与紧凑索引类似，为了使位图索引有效，你需要对要建立索引的列的数据进行排序——否则，将会读取位图索引中包含值的所有块。因此，你应该将属性 `hive.enforce.sorting` 设置为 `true`，并在 `CREATE TABLE` 语句中指明哪些列应当被排序。

由于（Hive 中的）位图索引本质上也是另一张表，你需要指定有效的存储格式和压缩方式（如果索引很大）。

其他索引类型用于 `ORCFile` 和 `Parquet` 格式，例如*存储索引*（一种最小值/最大值索引，如果某个值不包含在数据块中则可以跳过该块，适用于数值类型以及使用 `<`、`>`、`=` 运算符的查询），以及*聚合索引*（类似于一个预定义了聚合操作的表，例如针对特定列的 `count`、`sum`、`average`，并按该列进行分组）。

总而言之，你需要了解并评估你的数据以实现有效索引，同时还需要制定根据数据（源表）变化定期更新索引的机制。

### 选择 NoSQL 解决方案并优化数据模型

为你的环境（和数据）选择正确的 NoSQL 解决方案的重要性常常被忽视。例如，如果你的数据主要是非结构化的，并且数据量较小（大约 2-5 TB），那么列式数据库就不是一个合适的解决方案。

首先，你需要了解 NoSQL 数据库的主要类型、它们的特性、优缺点，以及它们在你需要的处理类型（基于你的业务需求）下的表现。你的选择将对环境的性能和所支持的功能产生巨大影响。

关于 NoSQL 数据库的类型、特性以及为你的环境（基于你的数据）选择合适 NoSQL 数据库的标准，请参见[第 6 章](http://dx.doi.org/10.1007/978-1-4842-1287-5_6)的“选择合适的 NoSQL 数据库”部分。

关于 NoSQL 需要强调的一点是：它确实已经（并将进一步）转变为 LimitedSQL，因为最初的 NoSQL 键值对、基于 MapReduce 的数据库正被下一代数据库所取代，这些数据库提供了（更简单的）基于 SQL 的接口，对分析很有用。此外，这些具备 LimitedSQL 能力的数据库在性能和功能方面也在不断改进。

回到 NoSQL，在选择了合适的 NoSQL 解决方案之后，下一步就是准备你的数据以迁移到 NoSQL。大多数情况下，`OLTP` 或 `OLAP` 系统会迁移到 NoSQL。随后，你需要转换你的数据，使其能在 NoSQL 数据库中优化运行。例如，存储在关系型 `OLTP` 环境中的数据定义了参照完整性，因此你需要执行连接操作来检索所需数据。关系型数据库通常在连接操作上表现良好，并拥有提升性能的特性，如索引、统计信息定义、数据和查询计划缓存等。如果你将关系型数据迁移到 NoSQL 环境，大部分 `RDBMS` 的特性就不复存在了。而且，NoSQL 数据库在连接操作上表现不佳。

因此，你需要重新设计数据模型并消除连接。你可能需要为此目的对数据进行反规范化，并且可能需要合并某些数据表以形成更大的表。需要采用不同的技术来将你的关系型（`OLTP`）或星型模式（`OLAP`）设计转换为适用于 NoSQL 的形式。更多信息请参见[第 6 章](http://dx.doi.org/10.1007/978-1-4842-1287-5_6)。

### 总结

性能调优本身就是一个庞大的主题，考虑到其涉及的各种子主题，其专业程度足以自成书。本章并非旨在涵盖所有方面。其目的在于吸引你关注可以调优 NoSQL 环境的不同方法。例如，MapReduce 或 HDFS 参数列表并非详尽无遗。请参阅 Apache 文档以获取完整的参数列表，并调优其他与环境更相关的参数。

或者，如果你考虑索引，请仔细审查你的查询需求，并添加你可能未涉及到的适当类型的索引。

同时，也要考虑硬件方面。像 Teradata 这样的大型公司主要专注于设计用于管理 PB 级数据的硬件。几年前，英特尔推出了其基于硬件的解决方案，以在不牺牲性能的情况下促进加密和解密。你可能不想（或没有资源）走得那么远。关于硬件优化的部分旨在提供通用指南，并帮助你优化计划用于实现方案的硬件。

你的环境会有特定的需求，但至少你有了一个良好的起点。当然，不可能考虑到所有类型的优化场景。

不同的组织在性能调优方面采用不同的方法。
