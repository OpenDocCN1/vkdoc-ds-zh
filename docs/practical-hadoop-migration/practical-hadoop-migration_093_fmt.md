# Hadoop 中的行式存储格式

Hadoop 生态系统中最流行的行式存储格式是文本文件、序列文件和 Avro。相信您之前一定使用过文本文件。CSV 文件易于使用，并且受到 Hadoop 生态系统中（以及外部）几乎所有工具的支持。序列文件在 Hadoop 生态系统内部也得到了广泛应用。

`Avro` 文件占用空间非常小，因此（与序列文件和文本文件相比）能提供更好的性能。但与另外两种行式文件格式相比，支持 `Avro` 的应用程序并不多。

## 文本文件

最简单、最常用的文件格式是文本文件。大多数数据库系统或应用程序都支持将数据导出为 CSV 或制表符分隔文件等文本格式。通常，这些文本文件包含 ASCII 或 UTF 字符，各个 `字段`（或列值）由称为 `分隔符` 的特殊字符（如逗号、分号、与号或制表符）分隔，记录之间用换行符分隔。

使用文本文件的优点如下：

-   它们可读性强且非常易于使用。
-   有大量可用于处理它们的工具。
-   大多数应用程序和数据库系统都可以接收（以及输出）文本文件。

尽管文本文件易于使用，但它们无法提供最佳性能。文本文件将所有字段值（包括数字或布尔值）存储为字符串。因此，如果您需要存储一个 `500` 的整数值，文本文件会将该值转换为等价的字符串（三个字符 `"500"`），然后再写入文件。

将所有数据存储为字符串存在几个问题：

-   数字和布尔值如果存储为字符串会占用更多空间（例如，`50,000,000` 作为字符串需要 `8` 个字节，但作为整数只需 `4` 个字节；布尔值 `"False"` 存储为字符串需要 `5` 个字节，但作为布尔值仅需 `1` 个字节）。这种空间占用增加会累积起来，导致文件体积庞大，需要更长时间才能加载（到内存），并对查询性能产生不利影响。
-   将字符串转换为适当的数据类型会为查询增加额外的工作。这对于 Hadoop 尤其重要，因为 Hadoop 生态系统中的大多数工具都遵循 `读时模式` 或读取时解析数据类型的理念。因此，每次执行查询时，都必须执行这种数据类型转换（除非您的所有数据真的是字符串或文本），这会减慢查询速度，并消耗额外的系统资源。

## 序列文件

序列文件是在 Hadoop 生态系统中广泛使用的文件格式（仅次于文本文件）。序列文件使用二进制格式，将数据存储为由键值对组成的记录。下面是序列文件的结构：

```
<文件头><键 1,(Doe,John,387-45-9876,1990-02-14,Chicago,IL)><同步标记>
```

因此，序列文件由一个文件头后跟记录（表示为键值对）组成。文件头包含关于文件和数据的元数据。同步标记用作记录终止符。Hive（以及 Impala）使用序列文件的简化版本，该版本忽略记录的键部分，并将每一行编码为字符串，使用特殊字符 `'\01'` 作为行分隔符。

例如，如果要对使用 Snappy 压缩方案的序列文件的 Hive 表数据进行压缩，请在 Hive 命令提示符下进行如下设置：

```
> set hive.exec.compress.output=true;
> set mapred.output.compression.type=BLOCK;
> set mapred.output.compress.codec=org.apache.hadoop.io.compress.SnappyCodec;
```

使用序列文件的主要优点是 Hadoop 生态系统中的所有组件都支持读写序列文件。不幸的是，Hive 和 Impala 使用序列文件的方式削弱了这种格式的许多优势，导致文件大小与文本文件相似（并因此带有与文本文件相同的问题）。

Hive 和 Impala（默认情况下）将数据以字符串形式存储在序列文件中。这意味着它们占用的空间与文本文件一样多，数字、布尔值和其他数据类型占用的空间超出了它们实际所需。此外，文件中的同步标记也会增加文件大小。

## Avro

`Avro` 是目前可用的最先进的行式格式，与文本或序列文件格式的区别如下：

-   `Avro` 在文件中包含或嵌入了数据（对应于表）的模式。这消除了每次在应用程序之间共享 `Avro` 文件时重新定义模式的需要。
-   `Avro` 根据字段的数据类型对字段进行编码（而不是将所有字段存储为文本）。这减少了（未压缩的）文件大小，并使得能够更有效地压缩文件。因此，网络传输时间和文件处理时间（用于数据类型转换）大大减少，为您的查询提供了更好的性能。
-   `Avro` 简化了模式变更（从而实现模式演化）。使用 `Avro`，可以更轻松地添加列，而无需重写底层数据以匹配新模式。如果您需要向数据中添加新列，可以通过在末尾包含附加字段并为旧记录提供默认值来实现。对于缺少此值的旧记录，Hive 将简单地使用默认值替换缺失值。

下面是 `Avro` 文件的结构：

```
<文件元数据><同步标记><数据块（对象计数，对象大小，数据）><同步标记>
```

该文件由一个文件头（包含序列化为 JSON 字符串的文件模式信息和压缩编解码器信息）后跟一个或多个数据块组成。每个数据块包含若干条记录和元数据（如记录数、记录大小等）以及实际数据，这些数据可以使用任何支持的编解码器进行压缩。以下代码使用 `Avro` 文件格式创建了一个 Hive 表（`Employee_avro`）：

```
> CREATE TABLE Employee_avro
(lastname STRING COMMENT '员工姓氏',
firstname STRING COMMENT '员工名字',
dept_code SMALLINT COMMENT '部门代码',
dob TIMESTAMP COMMENT '出生日期',
zip STRING COMMENT '邮政编码',
employee_since TIMESTAMP COMMENT '首次入职日期')
ROW FORMAT SERDE 'org.apache.hadoop.hive.serde2.avro.AvroSerDe'
STORED AS INPUTFORMAT 'org.apache.hadoop.hive.ql.io.avro.AvroContainerInputFormat'
OUTPUTFORMAT
'org.apache.hadoop.hive.ql.io.avro.AvroContainerOutputFormat'
TBLPROPERTIES ('avro.schema.literal'='{
"name": "employee_summary",
"type": "record",
"fields": [
{"name":"lastname", "type":"string"},
{"name":"firstname", "type":"string"},
{"name":"dept_code", "type":"int"},
{"name":"dob", "type":"string"},
{"name": "zip", "type": "string"},
{"name": "employee_since", "type": "string"}
]}');
```

从 `"name": "employee_summary"` 开始的部分是 JSON 模式定义，被包含在文件头中（作为文件元数据的一部分）。压缩编解码器的指定方式与为序列文件指定的方式完全相同。

`Avro` 也有一些缺点：

-   使用 `Avro` 格式可能比使用任何文本格式更复杂，并可能导致更长的开发时间。
-   （Hadoop 生态系统外部的）很少有应用程序支持或能读取这种格式。
-   对于 `Avro`，您需要在实际写入文件之前预先定义好模式，这在某些情况下是不可能的。

总而言之，`Avro` 对于使用全部或大部分列的查询来说是一个绝佳选择，因此对于数据仓库非常有用；尤其是那些包含数百列宽事实表的数据仓库。
