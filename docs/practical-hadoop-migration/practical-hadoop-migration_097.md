# 文档排版

## 性能优化与规划

一些组织从通用指南开始，只有在遇到具体问题时才考虑性能调优。这样，他们可以专注于问题领域并节省宝贵资源（时间和金钱）。这种方法的问题在于，当前问题虽然能快速解决，但能保证该领域或其他领域不会出现额外问题吗？当然不能。这就是为什么需要从良好的规划开始。执行压力测试，考虑数据增长（以及随之而来的使用量增加），同时还要考虑*边界条件*（最小值和最大值）。边界条件可能适用于你的硬件资源、NoSQL 解决方案、网络容量，甚至技术支持资源。

充分理解增长以及边界条件，将有助于你有效规划近期可能出现的任何性能问题。如你所知，随着技术的动态变化（尤其是在 NoSQL 领域），没有哪个系统能保证长久存在，但如果你主动出击并预测问题，而不是等问题出现才应对，至少可以避免近期内的问题。

## 第十一章  
## 案例研究：实现 Lambda 架构

Lambda 架构是大数据架构中最早出现的明确理念之一，像任何新架构一样，它既有追随者也有批评者。如何决定站在哪一边？我的答案很简单：这取决于该架构对你环境的适用性。Lambda 绝对不适合所有大数据用例。也许像 Kappa 或 Fast Data 这样的更新架构更适合你的环境。也许你甚至不需要基于架构的方法，可以直接从数据湖开始，按需设计分析。每个环境在某些方面都是独特的，需要特殊的设计考量，但诀窍是从通用方法开始，并且选择最合适的那一个。

为什么需要寻找新的数据架构方法？嗯，当前的基于 RDBMS 或 NoSQL 的系统并不具有韧性。由于大多数数据系统支持创建、读取、更新和删除（CRUD）操作，更新和删除操作可能导致数据损坏。例如，当你只想删除一行时，可能会删除大量行。软件错误或硬件故障也可能损坏数据。Lambda 架构中主数据的不可变性为此问题提供了有效的解决方案。

此外，对于当前的数据库系统，你总是在设计中需要做出权衡，因为要么优化数据存储（第三范式的规范化设计），要么优化查询处理（反规范化设计——通常是第一或第二范式）。Lambda 通过将主数据（使用第三范式存储）与查询层（存储为反规范化视图）分离，解决了这一难题。

那么，不可变数据存储如何捕获数据的变化？通过将数据划分为多个“事实”，并在时间维度上捕获这些事实的变化。因此，对事实的任何更改都会作为新的事实记录存储，并带有时间戳（指示更改发生的时间）。考虑一个员工记录。员工的地址是一个事实。每次员工搬家时，都可以添加一条新的事实记录，并附带一个时间戳，指示搬家时间。这保留了员工的居住历史（类似于数据仓库中的类型 2 维度）——但更重要的是，它保留了与员工相关的所有事实（就其地址而言）。当然，你可以根据需要以任何方式使用这些事实。

最后，Lambda 层如何促进近实时数据交付？我将通过一个真实案例研究进行讨论。我将简要讨论针对同一用例的 Kappa 和 Fast Data 设计变更。我将从描述业务问题开始。

## 第十一章 ■ 案例研究：实现 Lambda 架构

### 业务问题与解决方案

Yourtown Insurance 是一家汽车保险公司，最近不得不处理大量欺诈性索赔。随后，该公司增加了严格的指导方针和大量额外的索赔处理流程。这导致处理时间增加了两倍，拥有真实索赔的客户感到不满，并将业务转移到了其他保险公司。

Yourtown Insurance 聘请了业务流程（以及软件性能）专家，他们分析了过去的索赔（使用统计模型），并创建了一个预测模型来判断索赔是否可能具有欺诈性。如果确定索赔可能存在欺诈性，则将其定向到特殊队列，该队列执行额外处理，并在必要时启动调查。其余的索赔（被判定为非欺诈性的）则快速处理，就像在添加额外处理之前一样。

这一策略缩短了（真实）索赔的处理时间，同时仍然能够以约 80% 的准确率识别欺诈性索赔。顾问向 IT 部门保证，随着时间的推移，他们构建的预测模型将变得更加准确并提供更高的准确率。该模型基于许多因素构建，用于判断欺诈性索赔，例如：客户在去年提交的索赔数量、索赔提交时间、索赔提交时的天气状况、客户年龄、客户驾驶记录等。模型评估的结果确定，上述因素的某些值表明存在欺诈（或不存在欺诈）。

因此，需要针对汇总（或计算出的）客户数据实时检查索赔参数。由于索赔数据量非常大（30 TB，每月增长 1%），因此决定使用 Hadoop 进行数据处理，并且由于需要实时处理，因此选择了 Lambda 架构。根据数据量，同意批处理层应每周末重建一次，速度层应保存过去六天的数据。欺诈判断将基于历史数据（通过批处理层获得）和最新数据（通过速度层获得）进行。

本章将讨论使用适当的硬件、软件和需要开发的程序来设计和实现该解决方案。

#### 硬件

该系统的数据大小为 30 TB，每月增长 1%。未来四年，总增长约为 50%，即 15 TB。由于批处理层会反规范化数据，可以假设大约需要额外 30% 的存储空间，因此总空间需求为 60 TB。现在，如果你想在批处理层重建期间保持系统可用，则需要将空间*翻倍*（因为需要在删除旧视图之前构建新视图）。在本例中，可以假设在批处理层重建期间系统将不可用。因此，最终空间需求为 60 TB。
