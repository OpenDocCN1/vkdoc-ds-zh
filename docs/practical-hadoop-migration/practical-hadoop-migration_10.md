# 第六章 为 NoSQL 重新设计架构：设计原则、模型与最佳实践

我最近参加了一个由 Doug Laney 主讲的关于*数据货币化*的高德纳研讨会。Doug 谈到了一个有趣的概念，即为你组织历史上收集的数据赋予货币价值。他还谈到了*数据易货*的概念，以及用信息而不是金钱来缴税（显然他向几位 `IRS` 官员提过这个，并享受了他们的反应）。Doug 恰当地将数据经济学称为*信息经济学*。我认为，创建一个新学科来有效地将数据货币化，凸显了数据（和信息）在当今世界日益增长的重要性。

现在想想信息经济学背后的根本问题——你如何组织、整合、分析和呈现大量数据？由于这个概念涉及利用你组织多年来收集的所有数据，数据量将会很大。同时，像其他需要销售的东西一样，最终产品需要有用且具有可呈现性。大数据解决方案可以成功地用于组织和分析大量数据。当然，你需要为 `NoSQL` 的使用重新设计你的数据架构，因为关系数据不能直接用于 `NoSQL` 数据库。需要应用某些转换，我将在本章中讨论这些。

关系数据库有很多特性，你会想当然地认为任何数据库系统都具备。例如，定义细粒度的安全（或授权）、参照完整性约束或统计信息。此外，像并发更新或数据类型验证等事情都由 `RDBMS` 自动处理。

对于 `NoSQL` 数据库，只有部分这些特性可用，但通常需要附加组件（以及大量的额外工作来安装/配置/与其他组件集成）或涉及时间和资金的定制开发。例如，你必须转换数据以保持数据完整性（在没有参照完整性的情况下），或者在缺乏高级索引或统计信息的情况下提供更好的性能。`RDBMS` 在一个（相对）易于使用的包中为你提供了所有这些特性。

参照完整性的缺失促使数据反规范化。这让我们想起了数据仓库，尽管转换技术相似，但 `NoSQL` 通过完全消除任何连接操作，将这一点推向了更远。你可能还记得，对于星型模式，事实表需要与适当的维度表连接，以实现有效（且灵活）的数据过滤。而对于 `NoSQL` 数据库，即使是这些连接也是不可取的。因此，需要完全消除连接。

另一件要记住的重要事情是，许多数据完整性、验证或并发特性对于许多应用来说并非必需，这实际上促进了 `NoSQL` 数据库的发展——它们用这些特性换取了更好的性能和可扩展性。

还需要考虑一些非数据中心因素，例如安全性（认证/授权）或并发性，因为 `RDBMS` 默认提供这些特性，而在 `NoSQL` 解决方案中则不容易获得。

# 重新架构关系型应用到 NoSQL 环境的设计原则

作为总结性思考，你必须牢记 RDBMS 数据库设计与 NoSQL 数据库设计在功能上的区别。RDBMS 数据库设计是业务功能和流程的反映，而 NoSQL 设计本质上反映了数据访问模式及其性能优化（NoSQL 数据库中的数据被反范式化，以支持快速检索和处理）。

## 重新架构关系型应用到 NoSQL 环境的设计原则

NoSQL 数据库主要关注数据使用模式，并重新组织数据以优化性能。借助 `HDFS` 存储（在某些情况下），可扩展性和容错性默认可用。由于我在讨论迁移，因此假设存在一个现有的基于 `RDBMS` 的系统，该系统提供必要的业务功能。

因此，作为第一步，你需要审查需要迁移到 `NoSQL` 的现有数据和数据处理。如你所知，有几种类型的 `NoSQL` 数据库（`key-value` 存储、列式数据库、文档数据库和图数据库）。根据你的数据特征和处理需求，你必须决定哪种类型的 `NoSQL` 数据库最适合你的需求。

作为下一步，所选 `NoSQL` 数据库中的数据需要被**反范式化**、**聚合**和**呈现**，以支持分析和即席查询。我将详细讨论这些迁移方面的内容。最后，我将讨论 `NoSQL` 解决方案中非数据中心特性（如安全性或并发性）的实现。

### 选择合适的 NoSQL 数据库

首先，我假设你已经花了一些时间考虑是否真的需要在你的环境中使用 `NoSQL`，并根据第 1 章中讨论的各种因素做出了决定。请注意，`Hadoop` 和 `NoSQL` 操作的是**数据集**，而不是关系环境中的**数据库**和**表**。因此，你可以将 `NoSQL` 数据库视为数据集的集合。本节讨论 `NoSQL` 数据库的主要类型及其潜在应用。

### Key-Value 存储

这些数据库由全局的键值对集合组成。在这个上下文中，键值对意味着什么？假设一个包含全球销售详情的数据集在营销分析系统中被频繁访问，并且由于热门产品可能有数百万条销售记录，检索需要时间。如果这个数据集被缓存，将会有所帮助。因此，可以定义一个键，将数据集作为值，然后通过引用该键来确保快速数据检索。

一个常见问题是多个键指向同一个数据集。如果你能确保你的键存储中的所有值（数据集）都有唯一的键，那么你可以成功地像使用哈希表一样使用它。`key-value` 存储主要用作缓存存储或基于键的数据。

请记住，如果你尝试使用多个键查询相同的数据，会遇到问题。

使用 `key-value` 存储进行水平扩展很容易，可以通过对键进行哈希来实现。一些 `key-value` 存储会自动为你执行此操作。通常，`key-value` 存储非常适合执行大量小规模读写操作或连续流式处理的应用程序，因为内存处理带来了良好的性能提升。一些流行的 `key-value` 存储包括 `Memcache`、`Redis`、`Aerospike` 和 `Riak`。

你可以将 `key-value` 存储用于什么样的应用程序？考虑以下场景。

当你浏览零售网站时，一个随机的 `cookie` 值会与服务器上的一大块序列化数据相关联，通常为每个访问者创建。然后，这些 `cookie` 会持续数周，占用宝贵的数据库空间。可以使用 `key-value` 存储为访问者创建一个键条目，并设置 24 小时（或根据需要）的过期时间，从而自动释放空间。

另外，考虑一个简单的有上限的日志实现。你可以将项目附加到一个日志键（映射到捕获日志记录的文件）上，并仅保留最后几项。你可以使用它来跟踪系统状态，而无需扫描不断增长的日志信息。

总结一下，对于包含以下特征的数据，可以使用 `key-value` 存储：

- 大量的小规模读写操作
- 对多种数据结构的操作
- 数据类型多变，或需要灵活的列数

最后，你如何为你的应用程序使用 `key-value` 存储？以下是一个使用 `key-value` 存储 `Memcached` 的示例。一个典型的 `Memcached` 安装包含一个或多个服务器，这些服务器根据任何客户端的请求缓存数据（值）以及一个唯一的键。然后，可以使用该键在将来快速检索该数据。缓存的数据具有指定的过期时间，一旦达到该时间，就会从缓存中移除。如果有多个服务器可用，则可以缓存更多数据（因为所有服务器的内存都会被添加用于使用）。

由于 `Memcached` 调用和编程语言会根据使用的 API 而变化，我将使用伪代码来演示该概念。在此示例中，假设服务器 IP 是 `63.1.4.52`，使用的端口是 `2200`。那么，命令序列将类似于以下内容：

```python
# 伪代码：定义新的缓存和服务器
memcacheclt = new Memcache
memcacheclt:add_server('63.1.4.52:2200')
```

`Memcached` 可用于通过缓存频繁访问的数据来减轻 `SQL` 数据库的负载。当然，它不提供集中式查询缓存（正如 `RDBMS` 所提供的），也不使用任何中间件来实现缓存，因此在缓存失效时（可能由于数据更改）不会有重大问题。

```python
# 定义数据缓存（值）和 Sales 表中数据的键
sql = "SELECT * FROM Sales WHERE Product_id = ?"
key = 'SQL:' . Product_id . ':' . md5sum(sql)
```

如果你不熟悉 `md5sum`，它是一个计算和验证文件及字符串的 128 位 MD5 哈希的程序。MD5 哈希（或校验和）用作字符串或文件的紧凑数字指纹。尽管无限数量的文件（或字符串）可以拥有任何给定的 MD5 哈希，但任何两个非相同的文件（或字符串）拥有相同 MD5 哈希的可能性极低。这有助于确保键的唯一性。请注意，底层的 MD5 算法不再被认为是安全的（尽管它不需要特别安全，尤其是对于 `SQL` 字符串），但由于对字符串（或文件）的任何更改都会导致其 MD5 哈希发生变化，因此 `md5sum` 可用于验证文件或字符串的完整性。

```python
# 首先，检查键值对是否已定义
if (defined result = memcacheclt:get(key)) {
    return result
} else {
    # 执行 sql 以创建键值对
    handler = run_sql(sql, Product_id)
    # 由于你返回了一个 handler 或指针对象（在执行 SQL 之后），
    # 你需要将其转换为数组以便缓存
    final_array = handler:convert_to_an_array
}
```

## 缓存十分钟

`memcacheclt:set(key, final_array, 10 * 60)`

`return final_array`

当您缓存此产品的销售数据行时，最多十分钟内您将看到相同的数据。这意味着您所做的任何数据更改最多需要十分钟才能生效（除非您通过更改数据来主动使缓存失效）。通常，您可以为 Web 应用程序使用键值数据库，并保存用户配置文件/偏好、会话详细信息和购物车。

## 文档数据库

面向文档的数据库将数据存储为文档并进行管理。一个*文档*可以是一组结构化或半结构化数据。面向文档的数据库可以被视为键值存储的一个子类，因为数据的存储和检索方式相似，但数据的处理方式不同。对于键值存储，数据对数据库来说本质上是不可知的；它只是键对应的值。相比之下，面向文档的系统会读取数据（或文档）的内部结构以提取元数据，并将其用于进一步的处理和优化。

面向文档的数据库从数据本身提取类型信息，并将相关信息分组以便于使用。例如，XML 数据库（一个特定的子类）针对从 XML 文档中提取元数据进行了优化。此外，文档数据库通常也针对复杂的随机文本搜索（例如，`elasticsearch`）进行了优化。

使用面向文档的数据库，您可以灵活地使每个数据实例彼此不同，这为可选值以及更新提供了宝贵的支持。这就是为什么它们在 Web 应用程序中如此受欢迎的原因——这些应用程序经常更改，可能包含半结构化数据，并且还需要快速部署。接下来，让我通过一个示例讨论什么是文档。请看以下文本：

```
蓝色条纹衬衫
IL（美国）
```

尽管您可能清楚此文档包含服装商品的详细信息，但其他各个字段代表什么并不清楚。如果将此信息存储在键值存储中，语义内容（表示 Web 零售商的此库存商品）可能会丢失，并且数据库将无法有效地优化或索引这些数据。也许可以运用额外的逻辑将字符串分隔成字段并将字段分配给表中的列，但这并非易事。

如果没有元数据，解析像这样的自由格式数据可能会很复杂。现在考虑用伪 XML 标记的同一文档：

```
<Item>
  <ItemName>蓝色条纹衬衫</ItemName>
  <ItemType>男士衬衫</ItemType>
  <ItemSize>大号</ItemType>
  <ItemNumber>226453</ItemNumber>
  <Quantity>20</Quantity>
  <WarehouseNum>12345</WarehouseNum>
  <State>IL</State>
  <Country>US</Country>
</Item>
```

所以现在，文档既包含数据也包含元数据，并且元数据解释了每个字段。这样，就可以查询数据，例如“查找位于'IL'州的所有 `<Item>`”，或者为了性能而在`state`字段上设计索引。您可以像任何其他数据库一样组合搜索条件，但主要区别在于将元数据嵌入文档本身，这消除了预定义数据库字段的需要。它还提供了添加或删除某些字段的灵活性，因此数据库中的每个文档都可以有不同的格式。一个`<Item>`可能包含`<Size>`，而另一个可能只有`<Style>`。这并不会使之前查找伊利诺伊州商品的查询失效。

嵌入的元数据还允许更改文档格式而不影响现有文档。假设向新文档添加了一个新的`<ItemPicture>`字段。这不会影响任何现有文档——它们只是没有关联的图片。此外，通常，任何基于不属于某个文档的字段的查询都不会检索到它们。

文档的流行格式包括 XML、YAML、JSON 和 BSON。一些文档不包含明确定义的元数据（例如，PDF），而管理它们的数据库可能提供使用索引映射数据的方法，或者包含基于 XML 的预定义格式，如 MathML、JATS 或 DocBook。在某些情况下，使用模式语言如 DTD、XSD 或 Relax NG 将文档映射为更可用的格式。JSON 是许多面向文档的数据库最流行的格式（主要用于交互式基于 Web 的应用程序）。

文档可以使用唯一的键进行引用存储，并可以使用该键进行检索。键可以是字符串、URI 或路径。在键字段上创建索引有助于加快文档检索。可以创建更多索引以加快频繁搜索。大多数流行的面向文档的数据库都提供工具来提取和索引它们所管理的文档的几乎所有元数据以及数据内容。查询语言的支持进一步支持了查询，使用户更容易使用。

面向文档的数据库可用于包含以下内容的数据：

- 多种数据类型，可能有多种访问模式

- 需要构建 CRUD（创建、读取、更新、删除）应用程序

- 类似于 JSON、HTTP、REST、JavaScript 的数据类型，并与基于 Web 的应用程序一起使用

- 涉及大量小型（且可能易变的）连续读写操作的处理

- 不断变化的数据类型或需要灵活的列数（由于可选数据）

- 大型媒体（BLOB 类型）或半结构化数据

适用于文档数据库的应用程序包括事件日志记录、电子商务应用程序和内容管理应用程序。流行的面向文档的数据库系统有 MongoDB、CouchDB 和 OrientDB。

## 列式数据库

*列式*数据库按列而不是按行组织其数据。这重新定位了数据的焦点，有助于更有效地从硬盘存储读写数据，从而加快对数据集执行的查询速度。一个*数据列*由名称和值（有时还有时间戳）组成。每一行可以有不同数量的列。行键可用于查询，也可以使用（在列值上创建的）二级索引。

对于列式数据库，列值在物理上被分组在一起，而不是行。由于数据是按记录顺序存储的，因此列 1 的第 5 个条目和列 2 的第 5 个条目是同一记录的一部分。这使得作为一组按列访问单个数据元素（例如以下产品详细信息）成为可能，而不是逐行访问。

以下是产品表示例：

```
ID 产品名称        类别    数量  价格
1  绿茶包           茶      100  3.99
2  红茶包           茶      100  2.99
3  姜茶包           茶      100  4.99
```

对于面向行的数据库，数据将存储为：`1,绿茶包,茶,100,3.99;2,红茶包,茶,100,2.99;3,姜茶包,茶,100,4.99;` 对于面向列的数据库，数据将存储为：`1,2,3; 绿茶包,红茶包,姜茶包;茶,茶,茶;100,100,100;3.99, 2.99,4.99;` 但是为什么要按列组织数据呢？一个原因是它提供的存储压缩。因此，列操作（例如 `MIN`、`MAX`、`SUM`、`COUNT` 和 `AVG`）可以非常快速地执行。此外，由于列式数据库是自索引的，与关系数据库管理系统相比，它可以更有效地存储数据（就磁盘空间而言）。而且，列式数据库提供的数据压缩是一个很大的优势。这些特性的好处在大数据量下可见，此时数据访问性能至关重要。否则，对于较小的数据量，提供内存分析功能的数据库可以轻松地使面向行与面向列数据库的相对优势变得有些无关紧要，因为它们速度很快——尽管列式数据库提供的数据压缩仍然有用，因为内存很昂贵，而压缩可以帮助您使用更小的 RAM 容纳数据集。

什么样的应用程序可以使用列式数据库？如前所述，需要大数据量才能看到性能差异。此外，列式数据库非常适合于聚合在少数列中的大量数据。列式数据库不支持 ACID 事务，在可以容忍“最终一致性”的情况下更有用。

关于列式数据库的另一件要记住的事情是，它们在写入更频繁的应用程序中与在查询中一样表现良好。此外，这些数据库在应用程序需要一次只访问少数列（涉及大量行）时表现良好。列式数据库可以通过帮助您专注于必要的列而无需读取数千行来加快分析查询。

最后，列式数据库还可以用于依赖于时间的列（或具有过期时间的数据），因为可以设置在特定日期后自动使列过期。

虽然列存储的概念之前已作为关系数据库的一部分实现，但 RDBMS 不提供跨列族行不同的列的灵活性，而 NoSQL 列式数据库允许这样做（每行可以有不同数量的列）。

众所周知，列式数据库源自 Google 的 Big Table。流行的分布式横向扩展列式数据库包括 HBase 和 Cassandra。

总结一下，如果您的数据满足以下条件，可以使用分布式横向扩展列式数据库：

- 需要高可用性和冗余

- 需要跨越不同地理位置的数据中心，并且您需要一个能够处理长延迟的分布式、分区容忍的选项

- 有不需要任何一致性保证的连续数据流

- 具有不断变化的数据类型和动态字段

- 有可能达到真正的大数据量，例如数百 TB，并且需要对少数列进行聚合

通常，以下类型的应用程序可以从这种大数据处理能力中受益：

- 数据分析（用户行为、网络流量、日志文件）

- 生物信息学（遗传和蛋白质组数据）

- 股票市场分析（交易数据）

- 网络规模应用程序（搜索引擎）

- 社交网络服务

## 图数据库

图数据库起源于瑞士数学家莱昂纳德·保罗·欧拉提出的图论。图数据库的主要组成部分是*节点*和*边*（或*关系*）。节点和关系都可以具有与之关联的属性。此外，节点还可以用零个或多个标签进行标记。节点表示您可能想要监控（或查询）的实体，关系是节点之间存在的关系。属性（或特征）提供关于节点或关系的信息。

例如，如果“Practical Hadoop Security”是一个节点，则可以根据“Practical Hadoop Security”的哪些方面与特定数据库相关，将其与“书籍”、“安全参考资料”或“220 页”等属性关联起来。

对于大数据集上的复杂查询，图数据库通常比关系数据库更快，因为它们不需要昂贵的连接操作。由于它们不依赖于静态模式，因此对于频繁变化的数据以及不断演进的模式，它们表现更好。然而，对于具有大量数据元素的静态模式，它们（比关系数据库）表现不佳。当然，图数据库最适合于类似图的查询（例如计算两个节点之间的最短路径或计算图的直径）。

对于涉及各种节点（或实体）之间复杂相互关系（例如，涉及连接城市的多条高速公路、蛋白质与蛋白质之间的相互作用、员工与员工协作的查询）的场景，图数据库效果最好。这就是为什么图数据库非常适合以下类型的问题领域：

- 网络和 IT 基础设施管理
- 身份和访问管理
- 业务流程管理
- 产品和服务推荐
- 社交网络

关于图数据库需要记住的一件重要事情是，它们不擅长处理大量数据，因此对于涉及大规模图的应用程序（例如社交网络），通常使用列式（或其他合适的）数据库进行存储和检索，而图操作则作为一个增加性能的顶层处理层工作（例如，`Titan` 图数据库）。

我将以 `LinkedIn` 的架构为例。`LinkedIn` 混合使用 `Oracle`、`Voldemort`、`Espresso`、`Pinot` 和 `XML` 进行数据存储。数据库被水平和垂直分区（为了性能）。由于分区，无法实现引用完整性或跨域 `JOIN`。此外，使用了最终一致性模型，因此不能保证数据一致。`Voldemort` 和 `Pinot` 是键值存储。`Espresso` 是 `LinkedIn` 的在线分布式容错 `NoSQL` 数据库，被超过 30 个 `LinkedIn` 应用程序使用，包括会员档案、`InMail`（会员对会员消息系统）、主页部分内容、移动应用程序等。`Oracle` 因其成本而被谨慎使用。

`Voldemort` 是一个简单的键查找系统，用于快速查找小块数据（例如用户资料、*您可能感兴趣的工作*、*您可能认识的人*等数据）。`Pinot` 用于更大规模的键值查找，例如历史数据（*给我一月至三月所有的大数据工作*），并且可扩展以存储大量数据。

`Cloud` 是一个服务器，它将整个 `LinkedIn` 网络图缓存在内存中（`LinkedIn` 为此目的开发了一个专有的图数据库，它几乎位于每个操作的中心）。每个 `Cloud` 实例支持 2200 万个节点和 1.2 亿条边，需要 12 GB `RAM`。到 2008 年，生产环境中已有 40 个 `Cloud` 实例（我不确定现在有多少个）。`Cloud` 实例使用更新后的数据实时更新，并在关闭时持久化到磁盘。将所有内容放在 `RAM` 中是一个限制，但由于对图进行分区很困难，没有其他选择。

尽管 `Cloud` 缓存了整个 `LinkedIn` 网络，但每个用户只需要查看与他相关的信息，并且由于计算这些单个用户视图代价高昂，`LinkedIn` 仅在用户连接时进行计算并保持缓存。此缓存的网络视图在会话期间不会更新，除非用户自己添加/删除链接（此外，如果用户的任何联系人进行了更改，也不会更新）。

对于搜索，使用了 `Lucene` 搜索引擎的定制版本，并且由于搜索的是缓存数据，结果返回非常快。`Kafka` 和 `Databus` 用于数据复制，而 `Zoie`（使用 `Lucene` 的实时搜索和索引引擎）、`Bobo`（用于 `Lucene` 的分面搜索库，*分面*是用户的属性，如行业、前公司、专利等）和 `SenseiDB`（实时、分面、键值和全文搜索引擎）用于在线搜索。

### `NoSQL` 的并发性与安全性

对于 `NoSQL` 环境，并发性和安全性的概念（与 `RDBMS` 相比）有所不同。大多数 `NoSQL` 数据库不存在实现并发的机制（如锁定或事务隔离级别）。安全性需要使用第三方解决方案来实现，并且不与数据库集成。因此，`RDBMS` 默认可用的这些特性需要针对某些 `NoSQL` 环境进行模拟。这是 `NoSQL` 提供更好性能所付出的权衡之一。我现在将详细讨论这些概念。

### 并发性

当用户在 `RDBMS` 数据库中更新表中的数据时，其他用户无法修改相同的数据，因为它已被锁定（通过*排他写锁*）。在锁定数据以进行更新之前，`RDBMS` 会等待获得数据集的排他控制权，同时用户使用*共享读锁*读取数据。一旦没有共享锁，数据集将使用*排他写锁*进行锁定。并发性通过数据库锁定得到了有效处理。`RDBMS` 支持 `ACID`（原子性、一致性、隔离性和持久性）事务，这提供了数据的可靠性。

`NoSQL` 数据库不支持事务的 `ACID` 合规性，但有替代策略。*乐观并发控制*（`OCC`）就是其中之一。`OCC` 假设多个事务可以在不相互干扰的情况下完成。因此，允许事务使用数据资源而不获取锁。但是，每个事务都会验证其使用（读取或写入）的数据未被任何其他事务修改。如果存在冲突的修改，则提交的事务将回滚。`OCC` 只能用于数据争用较低的环境，否则重启事务的开销将抵消通过避免锁定所获得的性能优势和高吞吐量。

通常情况下，由于大多数 `NoSQL` 数据库遵循“单次写入，多次读取”的理念（尤其是开源数据库）。它们不期望并发更新，因此未设计为支持它们。默认情况下，大多数分布式数据系统支持*最终一致性*。任何具有处理读取请求的多个节点的系统，在处理读取请求时，如果要提供良好的性能（因为验证会涉及额外时间），则无法联系其他节点（以验证所提供的数据）。因此，提供的数据可能不是最新的；您最多只能期望节点同步并最终达到一致。这个概念也称为 `BASE`（基本可用）。

现在，如果您的应用程序需要某种程度的并发控制（也许不像 `ACID` 合规性那么严格），您该怎么办？以下是在 `NoSQL` 环境中实现并发性的一些其他方法：

- 您可以使用 `ZooKeeper`。`ZooKeeper` 的工作方式是通过使用法定人数实现分布式锁定。
- 您可以使用经过良好测试的分布式共识算法之一——例如，`Paxos` 结合 `MVCC`（多版本并发控制）。
- 如您所见，在符合 `ACID` 的数据库环境中锁定会导致读取（`SELECT`）和写入（`UPDATE`）彼此等待（完成）。这种情况通过使用 `MVCC` 来解决。一个*版本*是数据在某个时间点的快照。查询表时，读取者可以访问数据的当前版本，而更新可以同时（并行）发生。因此，稍后时间点的同一查询可能会使用更新的版本并产生不同的结果。
- 您可以使用 `CAP` 模型，该模型指出任何网络化共享数据系统只能拥有三个理想属性中的两个：一致性（`C`），意味着您获得数据的单个最新副本；高可用性（`A`）的数据（用于更新）；以及对网络分区（`P`）的容忍度。
- 尽管在设计者仍然需要在存在分区时在一致性和可用性之间做出选择，但随着当代网络系统的出现，处理分区以及从中恢复有了很大的灵活性。因此，修改后的 `CAP` 目标可以是最大化特定应用程序所需的一致性和可用性的组合。当然，这需要伴随着分区期间的连续性计划以及后续的恢复计划，从而克服 `CAP` 的感知局限性。

### 安全性

安全性是您甚至不会认为它是一个特性的另一个 `RDBMS` 功能。在开源 `NoSQL` 世界中，没有广泛集成的安全实现。没有内置的身份验证或授权。也没有内置的加密或掩码。所有这些功能都需要通过单独的应用程序或 `API` 实现，并且您需要确保这些应用程序或 `API` 得到良好集成。一些商业可用的 `NoSQL` 解决方案（例如，`10Gen` 的 `MongoDB` 或 `Datastax` 的 `Cassandra`）在其产品中包含了身份验证、掩码和加密功能，但它们仍然缺乏有效的授权或细粒度安全性手段。此外，并非所有商业 `NoSQL` 产品都提供这些功能。

回到开源产品，`Kerberos` 被广泛用于大量开源 `NoSQL` 解决方案的身份验证。`Kerberos` 由麻省理工学院开发，是一个易于获得的开源应用程序，可与多种 `Linux` 发行版以及 `HDFS` 配合使用。它也能很好地与 `HBase`、`Hive`、`Pig` 等 `Apache` 应用程序配合使用。大多数主要的 `Hadoop` 供应商发行版都与 `Kerberos` 配合使用，这就是为什么现在有些发行版包含了 `Kerberos`。由于 `Kerberos` 已经存在很长时间，因此有大量关于安装、配置、可能的问题以及解决方案的文档。

## 安全措施与监控工具

授权可以使用 HDFS ACL 或 Apache Sentry（如果您使用 Hive）来执行。此外，现在有像 Apache Knox 或 Apache Ranger 这样的组件可以提供全面的安全解决方案。您可以使用 Ranger（或 Knox）为各种 Apache 组件（如 HDFS、Hive 或 Hbase）创建访问策略（针对用户或组），这些策略提供细粒度（表级别）的权限。Knox 还提供 LDAP 集成，使得将 Hadoop 的安全性与您的企业安全性集成变得容易。

最后，大多数 Hadoop 供应商（以及一些 NoSQL 数据库）提供自己的定制授权工具。

数据加密在传输中以及*静态*（数据存储在物理磁盘驱动器上时）都可用，使用 Apache 基金会开发的加密和压缩 API。此外，还有像 eCryptfs 这样的开源加密文件系统，可以成功地与 Hadoop 和 NoSQL 解决方案一起使用。此外，大多数主要的 Hadoop 供应商都提供与第三方加密工具的接口。

最后，有像 Ganglia 和 Nagios 这样优秀的开源监控工具可用于监控系统资源和对 NoSQL 数据库的未授权访问。

总之，实施身份验证、授权、加密和监控工具的组合策略为 NoSQL 数据库提供了一个强大的安全选项。开源数据库主要使用开源工具，而商业可用的 NoSQL 数据库使用它们自己的定制工具来实现组合安全策略。

# 设计过渡模型

上一节讨论了选择合适的 NoSQL 数据库的标准。下一步，需要将关系数据库中的数据转换为 NoSQL 使用。这涉及反规范化，在某些情况下，在反规范化之前还需要转换为星型模式。无论哪种情况，都需要确保最终结果没有连接、没有关系，并且表数量很少。

另外，请注意，数据迁移的过程将取决于您选择的 NoSQL 技术。例如，将 RDBMS 数据迁移到列式数据库的过程将不同于迁移到键值存储（如 Riak）或文档存储（如 MongoDB）的过程。我接下来将详细讨论这些过程。

因此，我决定将这些实体（`claim_resubmission` 和 `claim`）与 `claim_line_item` 实体分开，后者保存索赔的详细信息和最新状态。在这种情况下，合并所有实体只会增加记录长度（从而增加访问时间），并且由于财产或重新提交列不经常访问，因此不会提供很好的价值。

此外，在这种情况下，将需要对列 `PolicyId`、`ClaimSubmissionDate`、`ClaimStatus`（针对表 `Claim` 和 `Claim_line_item`）以及列 `ClaimResubmissionDate` 和 `ReviewerEmployeeId`（针对表 `ClaimResubmission`）建立二级索引。

请注意，我仅演示了此应用程序的反规范化概念，如果您需要将数据迁移到 NoSQL 环境，总工作量（或所需的反规范化）可能会更大。此外，此应用程序是 OLTP，而基于 OLAP 的数据（或星型模式）的技术略有不同。

之后，你就可以使用该连接器进行导入/导出操作。例如，以下命令将从 MySQL 数据库服务器导入一个名为 `MyTbl` 的表到 HDFS 目录 `/MyData`：

```bash
$ sqoop import \
--connect jdbc:mysql://localhost/userdb \
--username root \
--table MyTbl \
--m 1 \
--target-dir /MyData
```

现在，上面的命令将从 MySQL 获取整个表的数据。但是，如果你只需要最近一天的数据呢？或者最近一周的？Sqoop 支持利用数据表中任意列的值进行增量数据加载。因此，如果 `MyTbl` 表有一个包含时间戳或最后修改日期的日期列（`modified_date`），你可以用它来获取最近一天的数据，如下所示（假设你在 2016 年 2 月 29 日进行增量加载，并希望加载 2016 年 2 月 28 日的数据）：

```bash
$ sqoop import \
--connect jdbc:mysql://localhost/userdb \
--username Myusr \
--password Mypwd \
--table MyTbl \
--m 1 \
--target-dir /MyData/incremental_table \
--check-column modified_date \
--incremental lastmodified \
--last-value 2016-01-27
```

但是，请注意，上面的命令将获取 `MyTbl` 表中自 2016 年 2 月 28 日 00:01 起所有新增（或修改）的行。因此，如果你的应用程序允许对现有记录进行更新或修改，此命令也会为你获取更新后的行。如果你只需要新添加的行呢？

Sqoop 提供了另一种增量加载模式，称为 `append`（而不是 `lastmodified`），它只会为你获取（某张表的）新追加的记录。显然，你不能在此模式下使用时间戳或最后修改日期。你需要使用一个具有递增值的 ID 列，并且需要知道上一次增量加载加载的最大值。例如，如果 `MyTbl` 有一个保存自增 ID 的 `MyId` 列，并且你确定上一次增量加载加载的最大 ID 值为 9834，那么以下命令将获取在该次加载之后添加的所有记录：

```bash
$ sqoop import \
--connect jdbc:mysql://localhost/userdb \
--username Myusr \
--password Mypwd \
--table MyTbl \
--m 1 \
--target-dir /MyData/incremental_table \
--check-column modified_date \
--incremental append \
--last-value 9834
```

## 增量导入模式总结

概括来说，Sqoop 支持两种类型的增量导入：`append` 和 `lastmodified`，可以与 `--incremental` 参数结合使用，以指定你需要执行的增量导入。如果你要导入某张表的新行，且新行的行 ID 值是递增的，你可以使用 `append` 模式。然后，你可以使用 `--check-column` 选项指定行 ID 列，并导入检查列的值大于 `--last-value` 指定值的行。

或者，如果你的表没有行 ID 列，但包含一个最后修改列，你可以使用 `lastmodified` 模式。在这种情况下，你可以将最后修改列与 `--check-column` 选项配合使用，并导入检查列的值大于 `--last-value` 指定的时间戳（或日期）的行。

在生产环境中，你需要创建一个脚本，该脚本首先确定上一次增量加载的 `--last-value`，然后将该值替换到你的 Sqoop 命令中，以获取所需的记录。然后，你可以将此脚本安排为增量加载的任务。

## 使用查询参数进行增量导入

最后，我将提及另一种增量加载数据的方法。你可以利用查询参数，使用 SQL select 语句将导入范围限制为仅包含新增或更改的记录，如下所示：

```bash
$ sqoop import \
--connect jdbc:mysql://localhost/userdb \
--username Myusr \
--password Mypwd \
--table MyTbl \
--m 1 \
--target-dir /MyData/incremental_table \
--query 'select * from MyTbl where modified_date > 2016-01-27'
```

你可以根据需要构建查询，以匹配增量加载需求或源数据表的结构。使用查询选项的好处是，你可以更好地控制需要导入的数据，并且可以指定多个条件来更有效地过滤数据。

# Flume 数据传输

## 使用 Flume 进行数据传输的优势

Flume（作为一种数据传输机制）的优势在于其处理流式数据和整合来自多个来源数据的能力。这就是 Flume 被用于事件和审计日志整合的原因。此外，Flume 与基于 Log4j 的日志记录配合良好，这种日志记录在 Hadoop 安装中非常流行。在排查作业问题或调查安全漏洞时，浏览各种 Hadoop 日志可能很困难，并且容易引入手动错误。定义一个 Flume 代理（及相关配置）可能需要一些初始时间，但你只需操作一次。后续对代理的修改会更简单快捷，最重要的是，整合（针对某个问题的）日志的过程会变得更容易、更快速。

在某些情况下，日志数据量可能非常庞大，而一个定义良好的 Flume 代理可以在无需人工干预的情况下过滤必要的数据。Flume 可靠、可扩展且易于定制。Flume 还支持动态配置和上下文路由。

## Flume 架构

Flume 架构围绕 `client`（客户端）生成 `event`（事件，由 Flume 传输的原子数据单元）以及 `agent`（代理）对其进行处理而展开。以下是关键术语的定义：

- `Client`（客户端）：产生事件并将其提供给一个或多个代理进行处理的实体。

- `Event`（事件）：Flume 从起点（源）传输到终点（目标）的原子数据单元。事件是一个带有（或不带）头部信息的字节数组。

- `Source(s)`（数据源）：事件数据接收器。数据源接收由事件（或从通道）生成的数据，并将其输出到一个或多个通道。例如，`Syslog` 可以用作数据源。

- `Channel`（通道）：临时数据管道。通道是事件从数据源接收后被输出到目标之前的一个临时存储区域。内存 (RAM) 或文件都可以用作通道。

- `Sink`（目标）：数据目的地。目标用作事件数据的目的地。最流行的目标之一是 HDFS，即日志或其他事件以文件形式存储在 HDFS 中。

- `Interceptor`（拦截器）：根据需要检查、转换或过滤事件。例如，时间戳拦截器为事件添加时间戳头部，或者 `regex_filter` 拦截器根据指定的正则表达式过滤掉事件。

- `Channel selector`（通道选择器）：根据头部信息将事件写入一个或多个已配置通道的过程。一个事件可以被 *replicated*（复制，写入所有通道）或 *multiplexed*（多路复用，根据端口等头部信息定向到不同通道）。例如，在端口 12345 上接收的事件进入 `channel1`，在端口 54321 上接收的事件进入 `channel2`，依此类推。

- `Sink processor`（目标处理器）：根据（选定的）负载均衡或故障转移策略，将事件写入（来自已定义的目标组的）目标的过程。

- `Agent`（代理）：一个进程或 Java 虚拟机 (JVM)，它利用拦截器（用于过滤事件）或通道（用于临时存储）等其他组件运行数据流，以将事件从数据源传输到目标。Flume 根据需要部署为一个或多个代理。

## 理解并使用 Flume 组件

上一节回顾了主要 Flume 组件的定义。我们还了解了每个组件在整体 Flume 架构中的位置。现在是时候详细讨论其中两个最重要的组件了。

### 数据源 (Source)

`数据源`是 Flume 中接收客户端事件数据并将其放置到一个或多个通道（记住，数据源需要至少一个通道才能运行）的组件。流行的数据源包括 `Syslog`、`Netcat`、`Exec` 等。

`Exec` 数据源在 Flume 外部运行一个命令，并将输出转换为 Flume 事件。要使用 `Exec` 数据源，我将定义一个数据源 `s1`，并在 Flume 代理配置文件（名为 `flume.conf`，位于 `/etc/flume/conf`）中设置其所有相关属性。

我将从 `type` 属性开始，并将其设置为 `exec`：

```
s_agent.sources=s1
s_agent.sources.s1.type=exec
```

Flume 中的所有数据源都需要使用 `channels`（复数）属性指定要写入事件的通道列表。这里我们将使用单个通道：

```
s_agent.sources.s1.channels=c1
```

唯一的另一个必需参数是 `command` 属性，它告诉 Flume 要向操作系统传递什么命令。例如，我们可以使用以下命令来打印 HDFS 审计日志中新增的行：

```
s_agent.sources.s1.command= tail -f hdfs-audit.log
```

请注意，Linux `tail` 命令的 `-f`（或 follow）选项会在文件增长时追加数据。默认情况下，输入文件（此处为 `hdfs-audit.log`）每隔一秒检查一次是否有增长，但你可以根据需要更改该时间间隔。你还可以为 `Exec` 数据源定义其他属性，有关不同 Flume 数据源的属性，请参阅：

[`flume.apache.org/FlumeUserGuide.html#flume-sources`](https://flume.apache.org/FlumeUserGuide.html#flume-sources)

总而言之，这就是我们如何为名为 `s_agent` 的代理配置单个数据源 `s1`。该数据源是一个 `exec` 类型的数据源，它将从 HDFS 审计日志文件 `hdfs-audit.log` 中提取作业的相关行。所有事件将被写入 `c1` 通道。

### 目标 (Sink)

`目标`是 Flume 中从通道取出事件并将其传输到下一个目的地（可能是另一个数据源）的组件。这种传输是事务性的，也就是说，代理使用事务交换来保证跨目的地的可靠交付——除非数据传输到下一个目的地成功，否则数据不会从通道中移除。目标需要恰好一个通道才能运行。以下是不同类型的目标：

- 终端目标：将事件存入其最终目的地（例如，HDFS、HBase）

- 自消费目标（例如，Null 目标）

- 用于代理间通信的 IPC 目标（例如，Avro、Thrift）

如果你的需求无法通过这些目标中的任何一个来满足，你可以通过扩展 `org.apache.flume.sink.AbstractSink` 类来编写自定义目标。

HDFS 是与 Flume 一起使用的流行目标。HDFS 目标可以用于在 HDFS 中打开一个文件，将流式数据写入其中，并在数据流结束或停止后关闭它。

要使用 HDFS 目标，你需要在命名目标上将 `type` 参数设置为 `hdfs`：

```
s_agent.sinks.sink1.type=hdfs
```

这为名为 `s_agent` 的代理定义了一个名为 `sink1` 的 HDFS 目标。你需要指定一些额外的必需参数，首先是要写入数据的 HDFS 路径：

```
s_agent.sinks.sink1.hdfs.path=/usr/flume/mydata
```

我使用了不包含服务器名称的绝对路径，但你可以根据需要包含服务器名称的绝对路径（`hdfs://namenode/usr/flume/mydata`）或相对路径（`mydata`）。HDFS 目标（或任何目标）的最后一个强制参数（`channel`）指定了它将从中读取数据的通道名称：

```
s_agent.sinks.sink1.channel=ch1
```

这告诉 `sink1` 目标从 `ch1` 通道读取事件。有关目标属性的完整列表，请参阅

[`flume.apache.org/FlumeUserGuide.html#flume-sinks`](https://flume.apache.org/FlumeUserGuide.html#flume-sinks)

`target.sinks.LogConsolidator.hdfs.rollCount = 10000`

`target.sinks.LogConsolidator.hdfs.rollInterval = 600`

请注意，数据在传输时使用的是 Apache AVRO 文件格式，Flume 在 4545 端口上监听（因为源代理正在向该端口发送数据）。输出端收集器通道 `mc1` 将文件条目写入 HDFS。Flume 在此通道中存储的最大事件数（此处为日志条目）为 500。这意味着，如果目标服务器崩溃，并且有超过 500 个日志事务被排队，则只有 500 个事务会被保存——除非你能清除该通道（通过将事务写入 HDFS）。如果你有足够的内存或磁盘空间，可以通过修改参数 `target.channels.mc1.capacity` 的值来增加这个限制。

作为最后一步，我需要同时在源服务器和目标 Hadoop 集群上启动 Flume 代理。在源服务器上：

```
$ /etc/flume/bin/flume-ng agent -c conf -f conf/flume-src.conf -n s_agent
```

在我的目标 Hadoop 集群上：

```
$ /etc/flume/bin/flume-ng agent -c conf -f /etc/flume/conf/flume-col.conf -n target
```

你可以添加更多的源并安装 Flume 代理，以便将文件发送到你的目标集群。Flume 本身不执行任何数据转换，但你可以根据需要使用 Linux shell 工具或诸如 Python 或 Scala 之类的编程语言对源数据应用转换。

### 总结

Hadoop 世界和大数据领域正处于一个非常活跃的时期，几乎每周都会增加新的 Apache 组件（以及商业解决方案）。这些解决方案中的许多都专注于分析。有些涉及实时分析，另一些则提供文本分析和情感分析。甚至有分析解决方案能够分析其他语言（如中文、德语或西班牙语）的社交媒体数据。还有数据发现解决方案，可以对敏感数据进行分类和脱敏，或为你的数据创建元数据。然而，在 Apache 的产品系列中，并没有针对 ETL 处理的新增组件。市场上确实有一些商业解决方案，但它们在价值上并不足以让你花费金钱和时间（用于重新培训你的团队）。

流式分析正变得越来越流行，`Kafka`、`Storm`、`Spark` 和 `Samza` 被广泛使用。这也是我简要介绍它们的原因，但在 ETL 领域，人们仍然高度依赖 `Sqoop` 和 `Flume`。这些组件的较新版本正在增加有用的功能，如果它们能在数据导入或导出之外执行一些真正的数据转换，那将是非常好的。与此同时，由于这些组件的成熟度，已经有大量现成的解决方案可用，并且会定期为 `Sqoop` 添加新的插件连接器。

如果你计划使用 `Flume`、`Sqoop`，甚至是 `Kafka`、`Spark` 和 `Storm`，在网上做一些关于你的 ETL 需求的研究将会对你有所帮助。

当然，你需要保持谨慎，不要被“Spark 狂热”冲昏头脑，因为 Spark 是用`Scala`开发的，用户随着时间的推移会发现很多问题。此外，从客观角度来看，`Scala`的市场饱和度为`0.5%`（与`Lisp`差不多），而`Java`为`21.5%`。事实上，随着`Java`（从 1.8 版本开始）引入原生函数式编程结构，使用`Scala`已经没有任何优势。再加上`Spark`（和`Scala`）引入了大量的传递依赖（与其他替代方案相比），这已经不是一个有吸引力的选择了。由于开发者需要掌握所有这些依赖关系才能对`Spark`有良好的工作理解，市场上真正的专家非常少。`Spark Python`现在也是一个流行的选择（因为它和`Scala`一样快），而且更多的数据科学家使用它感到很舒适。

那么，有哪些替代方案呢？`Apache Ignite`、`Apache Drill`、`Apache Kylin`、`Apache Geode`和`Apache Beam`都是很好的选择。如果你对处理流式数据感兴趣，应该研究一下这些组件。
