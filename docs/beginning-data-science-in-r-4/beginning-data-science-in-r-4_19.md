# 使用 `testthat`

`testthat` 框架提供了编写单元测试的函数，并确保每个测试都在一个干净的环境中运行（这样你就不会因为拼写错误等原因，导致一个测试中定义的函数泄露到另一个测试中）。它需要对你的 `DESCRIPTION` 文件和目录结构进行一些修改，但你可以通过运行以下命令来自动完成这些调整：

```
usethis::use_testthat()
```

这会将 `testthat` 添加到 `Suggests` 包中，并创建 `tests/testthat` 目录和 `tests/testthat.R` 文件。你可以查看这个文件，但它并不那么有趣。其目的是确保包测试（即运行 `tests/` 目录中的所有脚本）也会运行所有 `testthat` 测试。

所有 `testthat` 测试都应放在 `tests/testthat` 目录中，并且文件名应以 `test` 开头。否则，`testthat` 无法找到它们。为了便于阅读测试运行的结果，测试被组织在上下文（context）和测试（test）中——如果某个测试失败，你不仅想知道某个测试在某处失败了，还想知道是哪个位置的哪个测试失败了，而上下文就提供了这些信息。

在你的测试文件顶部，你可以使用 `context` 函数来设置一个上下文。它只是为接下来的一批测试指定一个名称。这个上下文会在测试期间被打印出来，这样你就可以看到测试的进度。如果你坚持每个文件只使用一个上下文，你就能看出测试失败的是哪个文件。

下一级的测试被封装在对 `test_that` 函数的调用中。该函数接受一个字符串作为第一个参数，该字符串应描述正在测试的内容；第二个参数是一个语句，它将是测试本身。这个语句通常不止一个语句，在这种情况下，它被包裹在 `{}` 大括号中。

在测试语句的开头，你可以创建一些对象或测试所需的任何东西，然后，你就可以进行实际的测试了。在这方面，`testthat` 提供了一整套用于测试的函数，例如测试值是否相等、是否近似相等、表达式是否生成警告、是否触发错误等等。所有这些函数都以 `expect_` 开头，你可以在 `testthat` 文档中查看它们的文档。

之前计算矩形面积和周长的测试，在 `testthat` 测试中看起来是这样的：

```
context("测试面积和周长")
test_that("我们计算了正确的面积和周长", {
  r <- rectangle(width = 2, height = 4)
  expect_equal(area(r), 2*4)
  expect_equal(circumference(r), 2*2 + 2*4)
})
```

尝试将这个测试添加到上一章练习中的 shapes 包中，看看它是如何工作的。尝试修改它以触发一个错误，看看效果如何。

在测试数字的相等性时，你应该时刻保持警惕，尤其是在处理浮点数时。计算机处理浮点数的方式与数学处理实数的方式不同。因为浮点数必须在有限的内存中表示，所以即使是数学上两个完全相同的表达式，你得到的确切数值也会取决于你计算它的方式。

对于我们之前用矩形进行的测试来说，这不太可能成为一个问题。我们测试的两个量，其计算方式并没有那么多，而且我们期望得到的就是这些确切的数字。但圆形的量又如何呢？

```
circle <- function(radius) {
  structure(list(r = radius),
            class = c("circle", "shape"))
}
area.circle <- function(x) pi * x$r**2
circumference.circle <- function(x) 2 * pi * x$r
test_that("我们计算了正确的面积和周长", {
  radius <- 2
  circ <- circle(radius = radius)
  expect_equal(area(circ), pi * radius²)
  expect_equal(circumference(circ), 2 * radius * pi)
})
```

在这里，我使用了内置的 `pi`，但如果实现中使用了其他东西呢？很明显，我们正在处理浮点数，不应该测试它们是否完全相等。好消息是，`expect_equal` 并不会这样做。它实际上是测试在一定的浮点数不确定度容差范围内是否相等——这可以通过向函数传递一个额外的参数来修改——所以一切都没问题。要检查精确相等性，你应该使用 `expect_identical` 函数，但你通常想要的是 `expect_equal`。

## 编写优秀的测试

为你的代码编写测试，最简单的方法是将你在开发代码时所做的实验立即转化为这样的单元测试——或者一开始就把你的检查放在一个单元测试文件中。在你编写函数的同时（或者至少是在编写函数之后立即）编写测试，你就不会积压未经测试的功能（而且，强迫自己之后专门花几个小时来写测试是非常困难的）。此外，将你在编写函数时用来检查函数的非正式测试，放入 `testthat` 文件并转化为正式的单元测试，并不会花费太多额外的时间。

如果你只做到这一步，那么至少你能知道，在你开发代码时经过测试的那些功能在未来依然存在——或者，如果它在某个时候出了问题，你会收到警告，因为这些测试将开始失败。

但既然无论如何你都要编写测试，不妨再系统化一些。我们总是倾向于检查常见的情况——即我们在编写函数时考虑到的情况——而忽略了特殊情况。然而，特殊情况往往是 bug 藏身之处，因此，将它们也纳入你的单元测试总是一个好主意。

特殊情况包括空向量、空列表或作为列表的 `NULL`。如果你实现了一个接受向量作为输入的函数，请确保当该向量为空时它也能正常工作。如果该输入对于函数来说没有意义，并且你无法想象当输入为空时该返回什么合理的值，那么请确保该函数抛出错误，而不是做一些它未被设计去做的事情。

对于数字，特殊情况通常是零或负数。如果你的函数能处理这些情况，那太好了（但一定要测试！）；如果它们无法处理这些特殊情况，就抛出错误。

对于 shapes，非正数的维度是没有意义的，所以，在我的实现中，如果遇到这种情况，我会抛出一个错误。对于矩形，一个针对此情况的测试可能如下所示：

```
test_that("维度必须是正数", {
  expect_error(rectangle(width = -1, height = 4))
  expect_error(rectangle(width = 2, height = -1))
  expect_error(rectangle(width = -1, height = -1))
  expect_error(rectangle(width = 0, height = 4))
  expect_error(rectangle(width = 2, height = 0))
  expect_error(rectangle(width = 0, height = 0))
})
```

在开发代码和相应的单元测试时，多思考一下可能存在的特殊情况，并确保你有测试来验证如何处理这些情况，这总是一个好主意。
