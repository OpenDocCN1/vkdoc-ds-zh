# 14. 测试与包检查

没有测试，几乎无法保证您的代码能够正常运行。您在编写代码时可能通过使用几个选定的参数调用函数来进行测试，但要构建健壮的软件，您需要更严格地进行测试。并且为了防止错误随着时间推移悄悄潜入代码，您应该经常测试。理想情况下，每当您对代码进行任何修改时，都应该检查所有代码。

软件测试有不同的方式——软件测试本身几乎就是一门科学——但我们为了确保刚编写的代码能按预期工作而进行的那种测试，称为单元测试。而为了确保对代码的修改不会破坏任何原有功能所进行的测试，称为回归测试。

## 单元测试

之所以称为单元测试，是因为它测试的是功能单元——在 `R` 语言中，这基本上意味着单个函数或几个相关的函数。每当您编写一个新的功能单元时，也应该为该单元编写测试代码。测试代码用于检查新代码是否确实按预期工作。而且，如果您编写的测试能够稍后自动运行，那么您也同时为这个单元创建了回归测试。每当您对代码进行任何修改时，都可以运行所有自动化测试，这将检查每个单元，确保所有功能都和以前一样正常工作。

大多数程序员不喜欢编写测试。编写新功能是件令人兴奋的事，但探查新特性的错误则乏味得多。然而，您确实需要测试，并且从长远来看，您会为拥有它们而感到高兴。不要等到编写完所有函数之后才编写测试。那会把最困难的部分留到最后，这可不是激励自己编写测试的好方法。相反，您可以在编写函数的同时编写单元测试；有些人甚至建议在编写函数之前就编写测试，这种方法被称为测试驱动开发。其核心理念是：您编写的测试会规定函数应如何工作，当函数通过了为其编写的测试时，您就知道它按预期工作了。

我个人从未觉得测试驱动开发对自己有多大用处。它不符合我的工作方式——我喜欢在实现函数的同时探索其不同的接口和用法——但有些人更喜欢这种方式。不过，我确实会以另一种方式将测试与编程结合起来：我会编写一些小的脚本来调用我的函数，并在试验这些函数的同时将它们整合起来。我编写这些代码时，会使其易于将我的试验结果提取出来，并在以后用作自动化测试。

以我们之前做过的形状（shape）练习为例，该练习要求编写计算不同形状面积和周长的函数。我这里有一个用 `width` 和 `height` 来定义矩形的版本。对这两个函数的测试可能如下所示：

```r
area <- function(x) UseMethod("area")
circumference <- function(x) UseMethod("circumference")
rectangle <- function(width, height) {
    structure(list(width = width, height = height),
              class = c("rectangle", "shape"))
}
area.rectangle <- function(x) x$height * x$width
circumference.rectangle <- function(x) 2 * x$height + 2 * x$width
r <- rectangle(width = 2, height = 4)
area(r)
## [1] 8
circumference(r)
## [1] 12
```

面积是 2 × 4，周长是 2 × 2 + 2 × 4，所以看起来没问题。但我是在通过调用函数并观察打印输出来测试代码。我不想永远用这种方式测试——因为我必须盯着输出来看，所以这种方式无法实现自动化。不过，这些测试本身是没问题的。我只需要将它们自动化即可。

### 自动化测试

自动化测试只需在代码中检查函数的结果，而不是用肉眼看。因此，下面这样的代码就是自动化测试：

```r
r <- rectangle(width = 2, height = 4)
if (area(r) != 2*4) {
    stop("Area not computed correctly!")
}
if (circumference(r) != 2*2 + 2*4) {
    stop("Circumference not computed correctly!")
}
```

是的，代码稍微多了一点，但它本质上还是同样的测试，而且这是以后可以自动运行的东西。如果没有报错，就说明测试通过，一切正常。

您可以按这种方式编写自己的测试，将它们放在名为 `tests/` 的目录下（这是 `R` 期望测试代码存放的位置），然后每当您想检查代码状态时——即对代码进行修改后——就可以运行这些测试。

`tests/` 目录中的脚本也会在您对包进行一致性检查时自动运行（我们稍后会回到这个话题）。

当您在 `RStudio` 右侧的 `Build` 标签页中点击 `Check`，或在 `Build` 菜单中选择 `Check Package` 时，就会触发这个过程，但这不仅仅运行测试，它还会做更多事情，因此并不是运行测试最高效的方式。

在 `R` 中有一些用于规范化此类测试的框架。我使用的框架叫做 `testthat`。使用这个框架，可以轻松运行测试（无需进行完整的包检查），并且能以更结构化的方式编写测试——当然，代价是每个测试需要编写更多的代码。

如果您还没有安装它，现在请安装：

```r
install.packages("testthat")
```

# 使用 `testthat`

`testthat` 框架提供了编写单元测试的函数，并确保每个测试都在一个干净的环境中运行（这样你就不会因为拼写错误等原因，导致一个测试中定义的函数泄露到另一个测试中）。它需要对你的 `DESCRIPTION` 文件和目录结构进行一些修改，但你可以通过运行以下命令来自动完成这些调整：

```
usethis::use_testthat()
```

这会将 `testthat` 添加到 `Suggests` 包中，并创建 `tests/testthat` 目录和 `tests/testthat.R` 文件。你可以查看这个文件，但它并不那么有趣。其目的是确保包测试（即运行 `tests/` 目录中的所有脚本）也会运行所有 `testthat` 测试。

所有 `testthat` 测试都应放在 `tests/testthat` 目录中，并且文件名应以 `test` 开头。否则，`testthat` 无法找到它们。为了便于阅读测试运行的结果，测试被组织在上下文（context）和测试（test）中——如果某个测试失败，你不仅想知道某个测试在某处失败了，还想知道是哪个位置的哪个测试失败了，而上下文就提供了这些信息。

在你的测试文件顶部，你可以使用 `context` 函数来设置一个上下文。它只是为接下来的一批测试指定一个名称。这个上下文会在测试期间被打印出来，这样你就可以看到测试的进度。如果你坚持每个文件只使用一个上下文，你就能看出测试失败的是哪个文件。

下一级的测试被封装在对 `test_that` 函数的调用中。该函数接受一个字符串作为第一个参数，该字符串应描述正在测试的内容；第二个参数是一个语句，它将是测试本身。这个语句通常不止一个语句，在这种情况下，它被包裹在 `{}` 大括号中。

在测试语句的开头，你可以创建一些对象或测试所需的任何东西，然后，你就可以进行实际的测试了。在这方面，`testthat` 提供了一整套用于测试的函数，例如测试值是否相等、是否近似相等、表达式是否生成警告、是否触发错误等等。所有这些函数都以 `expect_` 开头，你可以在 `testthat` 文档中查看它们的文档。

之前计算矩形面积和周长的测试，在 `testthat` 测试中看起来是这样的：

```
context("测试面积和周长")
test_that("我们计算了正确的面积和周长", {
  r <- rectangle(width = 2, height = 4)
  expect_equal(area(r), 2*4)
  expect_equal(circumference(r), 2*2 + 2*4)
})
```

尝试将这个测试添加到上一章练习中的 shapes 包中，看看它是如何工作的。尝试修改它以触发一个错误，看看效果如何。

在测试数字的相等性时，你应该时刻保持警惕，尤其是在处理浮点数时。计算机处理浮点数的方式与数学处理实数的方式不同。因为浮点数必须在有限的内存中表示，所以即使是数学上两个完全相同的表达式，你得到的确切数值也会取决于你计算它的方式。

对于我们之前用矩形进行的测试来说，这不太可能成为一个问题。我们测试的两个量，其计算方式并没有那么多，而且我们期望得到的就是这些确切的数字。但圆形的量又如何呢？

```
circle <- function(radius) {
  structure(list(r = radius),
            class = c("circle", "shape"))
}
area.circle <- function(x) pi * x$r**2
circumference.circle <- function(x) 2 * pi * x$r
test_that("我们计算了正确的面积和周长", {
  radius <- 2
  circ <- circle(radius = radius)
  expect_equal(area(circ), pi * radius²)
  expect_equal(circumference(circ), 2 * radius * pi)
})
```

在这里，我使用了内置的 `pi`，但如果实现中使用了其他东西呢？很明显，我们正在处理浮点数，不应该测试它们是否完全相等。好消息是，`expect_equal` 并不会这样做。它实际上是测试在一定的浮点数不确定度容差范围内是否相等——这可以通过向函数传递一个额外的参数来修改——所以一切都没问题。要检查精确相等性，你应该使用 `expect_identical` 函数，但你通常想要的是 `expect_equal`。

## 编写优秀的测试

为你的代码编写测试，最简单的方法是将你在开发代码时所做的实验立即转化为这样的单元测试——或者一开始就把你的检查放在一个单元测试文件中。在你编写函数的同时（或者至少是在编写函数之后立即）编写测试，你就不会积压未经测试的功能（而且，强迫自己之后专门花几个小时来写测试是非常困难的）。此外，将你在编写函数时用来检查函数的非正式测试，放入 `testthat` 文件并转化为正式的单元测试，并不会花费太多额外的时间。

如果你只做到这一步，那么至少你能知道，在你开发代码时经过测试的那些功能在未来依然存在——或者，如果它在某个时候出了问题，你会收到警告，因为这些测试将开始失败。

但既然无论如何你都要编写测试，不妨再系统化一些。我们总是倾向于检查常见的情况——即我们在编写函数时考虑到的情况——而忽略了特殊情况。然而，特殊情况往往是 bug 藏身之处，因此，将它们也纳入你的单元测试总是一个好主意。

特殊情况包括空向量、空列表或作为列表的 `NULL`。如果你实现了一个接受向量作为输入的函数，请确保当该向量为空时它也能正常工作。如果该输入对于函数来说没有意义，并且你无法想象当输入为空时该返回什么合理的值，那么请确保该函数抛出错误，而不是做一些它未被设计去做的事情。

对于数字，特殊情况通常是零或负数。如果你的函数能处理这些情况，那太好了（但一定要测试！）；如果它们无法处理这些特殊情况，就抛出错误。

对于 shapes，非正数的维度是没有意义的，所以，在我的实现中，如果遇到这种情况，我会抛出一个错误。对于矩形，一个针对此情况的测试可能如下所示：

```
test_that("维度必须是正数", {
  expect_error(rectangle(width = -1, height = 4))
  expect_error(rectangle(width = 2, height = -1))
  expect_error(rectangle(width = -1, height = -1))
  expect_error(rectangle(width = 0, height = 4))
  expect_error(rectangle(width = 2, height = 0))
  expect_error(rectangle(width = 0, height = 0))
})
```

在开发代码和相应的单元测试时，多思考一下可能存在的特殊情况，并确保你有测试来验证如何处理这些情况，这总是一个好主意。

# 在测试中使用随机数

另一种良好的测试方法是使用随机数据。在我们手动设置的测试中，我们往往会避免极端情况，因为根本无法想到它们。随机数据则没有这个问题。因此在测试中使用随机数据可能更高效，但这当然也会使测试不可重现，从而导致调试变得极其困难。

当然，你可以设置随机数生成器的种子。这会使测试具有确定性和可重现性，但这从一开始就违背了进行随机测试的初衷。

我对此并没有完美的解决方案，但有时会使用这个技巧：选择一个随机种子并记住它，设置该种子，既然现在知道了随机种子是什么，那么如果测试失败，我就可以再次设置它并从那里开始调试。

你可以通过将种子放入测试名称中来保存它。这样如果测试失败，你就可以从错误信息中获取种子：

```r
seed <- as.integer(1000 * rnorm(1))
test_that(paste("测试在种子", seed, "下有效"), {
  set.seed(seed)
  # 使用随机数的测试代码
})
```

## 测试随机结果

当处理随机数时，另一个出现的问题是关于函数返回的期望值应该是什么。如果函数不是确定性的，而是依赖于随机数，那么我们不一定有预期的输出。

如果在这种情况下我们所能做的只是对结果进行统计测试，那么这正是我们必须做的。如果一个函数在完成有用的工作，它很可能不是完全随机的，这意味着我们可以对其进行一些测试，即使该测试有时可能会失败。

作为一个玩具示例，我们可以考虑通过从一组数据中抽样来估算其均值。这是一个愚蠢的例子，因为在这个例子中，直接计算均值可能要快得多，但为了有趣，我们还是来考虑一下。

如果我们抽取了 `n` 个元素，均值的标准误差应为 `s / sqrt(n)`，其中 `s` 是样本标准误差。这意味着真实均值与样本均值之间的差异应服从 `N~(0, s/sqrt(n))` 分布，并且这是我们可以进行统计测试的（尽管不能进行确定性测试）。

在以下代码中，我将两个均值间的距离除以 `s / sqrt(n)` 进行归一化，这应使其服从 `Z ~ N~(0, 1)` 分布。然后我选择一个显著性阈值，该阈值在千次中仅会出现一次。实际上我选择的阈值，在两千次中才出现一次，但我只测试了 `Z` 的正值，所以在分布的负端还隐含着一千次中的另一侧情况：

```r
seed <- as.integer(1000 * rnorm(1))
test_that(paste("样本均值接近真实值，种子", seed), {
  set.seed(seed)
  data <- rnorm(10000)
  sample_size <- 100
  samples <- sample(data, size = sample_size, replace = TRUE)
  true_mean <- mean(data)
  sample_mean <- mean(samples)
  standard_error <- sd(samples) / sqrt(sample_size)
  Z <- (true_mean - sample_mean) / standard_error
  threshold <- qnorm(1 - 1/2000)
  expect_less_than(abs(Z), threshold)
})
```

这个测试预计每千次中会失败一次，但结果实际上是随机的时，我们无法获得绝对的确定性。如果这个测试只失败了一次，我不会担心；但如果我发现它失败了好几次，那么这就不太可能只是侥幸，这时我会去探究发生了什么事情。

## 检查包的完整性

你可以通过在 `RStudio` 右侧 `Build` 选项卡中点击 `Check`，或通过 `Build` 菜单中的 `Check Package` 来执行包检查，这会运行你的单元测试，但还会做更多事情。

它会调用一个脚本，该脚本会运行大量一致性检查，以确保你的包处于最佳状态。它会验证所有函数是否都有文档说明，代码是否符合某些标准，文件是否在正确的目录中（以及不应该有文件的地方是否有文件），是否提供了所有必要的元信息，以及许多、许多其他事情。你可以查看 `http://r-pkgs.had.co.nz/check.html` 来获取包检查时执行的更长的测试列表。

你应该尝试对你的包运行检查。它会输出大量信息，并在最后告诉你发现了多少错误、警告和注意事项。

在输出中，每个未被声明为 `OK` 的测试都是你应该留意的内容。它可能不是错误，但如果检查标记了任何问题，你将不允许将其发布到 `CRAN`——至少在没有一个非常好理由的情况下是不允许的。
