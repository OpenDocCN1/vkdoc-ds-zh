# 13. 构建 R 包

现在我们已经知道如何在 R 中编写函数和创建类，但函数和类都不是我们用来收集和分发 R 代码的单位。这个单位是包。当你编写以下代码时，加载并导入到命名空间中的就是包：

```
library(something)
```

而当你编写以下代码时，下载的就是包：

```
install.packages("something")
```

本章的主题是如何创建你自己的包。在有限的篇幅内，我只能对 R 包的结构做一个非常宽泛的概述，但这应该足以让你入门。如果你想了解更多，我强烈推荐 Hadley Wickham 的著作 *R Packages*。

## 创建 R 包

我假设你使用 RStudio 来完成这项工作。如果你不使用它，可以查看 `devtools` 包。它提供了执行我们通过 RStudio 图形界面所能完成的所有操作的函数。

要创建一个新包，请前往菜单栏的 `File` 并选择 `New Project…`，此时会弹出一个对话框，询问你的新项目是应该放在新目录中、现有目录中，还是从版本控制仓库中检出。请选择 `New Directory`。

之后，你可以在空项目、包或 Shiny 应用程序之间进行选择。不出所料，你应该在这里选择 `R Package`。

现在你会看到一个对话框窗口，可以在其中设置包的详细信息。你可以选择包的类型（这里可以在普通包和使用 Rcpp 制作 C++ 扩展的包之间做出选择），可以指定包的名称，还可以提供要包含在包中的现有源文件。此外，你需要选择放置新包的位置，以及是否要为该包使用 `git` 仓库。

选择一个普通包，并点击同意创建一个 `git` 仓库（我们稍后会再回到 `git` 的话题）。现在你只需要选择一个名称和一个存放包的位置。放在哪里由你决定，但包的名称有一些指导原则。

### 包名称

包名称可以由字母、数字和“.”组成，但必须以字母开头，并且不能以“.”作为最后一个字符。你不能使用其他字符，如下划线或破折号。

每当你构建打算让别人能够使用的软件时，都要小心选择名称。给它起一个容易记住且便于在谷歌上搜索的名称。

对于包的实验性操作，你可以只创建一个名为 `test` 的包。

创建一个新包，然后查看结果。

### R 包的结构

在 RStudio 为你创建的目录中，你应该有两个目录：`R` 和 `man`；三个文本文件：`.Rbuildignore`、`DESCRIPTION` 和 `NAMESPACE`；以及一个项目文件（其名称将是你的包名后跟 `.Rproj`）。

这些文件中的最后一个由 RStudio 使用，你只需要知道，如果你在 RStudio 中打开这个文件，就会得到上次处理该项目时项目状态的打开版本。

在 `R` 目录内，有一个示例文件 `R/hello.R`；在 `man` 目录内，有一个示例文档文件 `man/hello.Rd`。

这些文本文件以及这两个目录是 R 包外观的一部分，并且它们必须始终以这些确切的名称存在。还有一些其他目录也具有标准名称，但它们不是必需的，目前我们这里没有这些目录。

### .Rbuildignore

你创建的目录包含包的源代码，但它并不是实际的包。包是需要你从这些源代码构建并安装的东西。我们很快就会介绍如何操作。

`.Buildignore` 文件告诉 R 在构建包时不要包含哪些内容。未在此处提及的文件将自动包含在内。这本身并不是什么大问题，但它会导致包变得混乱，不利于他人使用，而且如果你将包上传到 CRAN，那里的过滤器会强制要求严格的目录和文件结构，你将不允许包含不符合该结构的文件或目录。

自动生成的 `.Buildignore` 文件内容如下：

```
^.*\.Rproj$
^\.Rproj\.user$
```

这两个是正则表达式，用于防止 R 将 RStudio 文件包含在已编译的包中。

这里的 `^` 字符匹配文件名的开头，而 `$` 匹配结尾。未转义的 `.` 匹配任意字符，而转义的 `\.` 匹配实际的点号。`*` 表示前面的符号可以重复任意次数。因此，第一个正则表达式匹配任何以 `.Rproj` 结尾的文件名，第二个表达式匹配任何以 `.Rproj.user` 结尾的文件名。

## Description

该文件包含关于你的包的元信息。如果你将包命名为 `test`，并且与我同一天（2015 年 11 月 11 日）创建它，那么它现在应该看起来像这样：

```
Package: test
Type: Package
Title: What the Package Does (Title Case)
Version: 0.1
Date: 2015-11-22
Author: Who wrote it
Maintainer: Who to complain to 
Description: More about what it does (maybe more than one line)
License: What license is it under?
LazyData: TRUE
```

你需要更新它以描述你的新包。

接下来我对这些元数据做一个简短描述，但你也可以在 Hadley Wickham 的 *R Packages* 一书中阅读更多相关内容。

### Title

标题字段不言自明。你需要为你的包提供一个标题。这里的 `(Title Case)` 表示你需要像对待书籍标题一样，对单词的首字母使用大写。

如果你在 CRAN 上阅读某个包的文档，它看起来会像这样：`packagename: This is the Title`。请勿在此处将包名包含在你的标题中；包名会自动添加到文档页面中。你只需要标题本身。

### 版本号

这个数字仅用于追踪用户安装的软件包版本。每当您对包进行更改并发布时，该数字都应递增。

版本号不仅用于表明您更新了版本，有时也是指定包之间依赖关系的必要条件。如果某个功能是在 1.2 版本引入的，而在 1.1 版本中并不存在，那么使用此功能的其他包就需要知道它们是否能访问到 1.2 或更高版本。我们稍后将再讨论依赖关系。

版本号有一些约定俗成的规则，但并非强制要求。这里的惯例是，发布的版本采用 `主版本号.次版本号.补丁号` 的编号方案，因此版本 1.2.3 意味着主版本号为 1，次版本号为 2，并且这是补丁版本 3。补丁通常是较小的更改，典型如错误修复等，而次版本修订通常包含一些新功能。对于何为次版本、何为主版本的界定非常主观，但只要接口发生变化——即，您更改了函数的调用方式，以至于旧的调用类型不再正确——您绝对应该增加主版本号。

如果您正在分发包的开发版本，供那些敢于尝试测试版的用户使用，惯例是额外添加一个开发版本号。那么版本号就像这样：`主版本号.次版本号.补丁号.开发编号`，按照惯例，最后的数字从 9000 开始，每次新发布时递增。

您刚刚开始开发新包，所以请将版本号改为 `0.0.0.9000`。

### 描述

此字段应描述该包。通常是一段简短的描述。如果描述跨越多行，为了让 R 正确解析 `DESCRIPTION` 文件，您必须在 `Description:` 之后的行进行缩进。

### 作者和维护者

删除这两个字段。有一种更好的方法来指定相同的信息，可以确保信息以更结构化的形式提供。您应该使用一个名为 `Authors@R:` 的新字段来代替。`Author` 或 `Maintainer` 字段本身并没有问题，您可以保留它们而不产生任何麻烦；新字段只是让您能够更简洁地提供相同的信息。

该字段接受一个 R 表达式，用于指定一个或多个作者，其中作者信息通过调用 `person` 函数提供——这样我们就能确保信息结构化恰当。查看该函数的文档 (`?person`) 以获取更多细节。

您是唯一的作者，因此您应该使用类似这样的内容：

```
Authors@R: person("名", "姓",
email = "your.email@your.domain.com",
role = c("aut", "cre"))
```

这里的角色表示作者和创建者。`person` 函数的文档列出了其他选项。

如果有不止一个人作为作者、维护者或其他类型的贡献者参与，您可以通过使用 `c` 函数连接多个 `person` 来创建一个序列。

### 许可证

此字段指定软件包发布时所采用的软件许可证。它实际上可以是任何内容，但如果您希望将包放到 CRAN 上，则必须选择 CRAN 接受的许可证之一。

您可以通过其缩写来指定要使用的已认可许可证。例如，要指定您的包依据 GPL 第 2 版许可证发布，您可以这样写：

```
License: GPL-2
```

### 类型、日期、LazyData

`Type` 和 `LazyData` 字段并非必需。如果您愿意，可以删除它们。`Type` 仅仅是说明您有一个包，但我们大致已经知晓这一点。`LazyData` 告诉 R，如果您的包中包含数据，它应该惰性加载。再次强调，这并不是特别重要（除非您计划在包中包含极其庞大的数据集；如果那样做，请搜索 `LazyData` 的文档）。

`Date` 当然包含日期。这应该是您最后一次修改包的日期，即您最后一次更新版本的日期。

### URL 和 BugReports

如果您有包的网页和用于报告 Bug 的 URL，这些就是您需要使用的字段。它们对包来说不是必需的，但对用户来说当然非常有用。

### 依赖关系

如果您的包有依赖项，您可以使用三个字段来指定它们：`Depends`、`Imports` 和 `Suggests`。

使用 `Depends`，您可以同时指定包运行所需安装的其他包，以及包运行所需的 R 版本。但对于包而言，使用 `Imports` 和 `Suggests` 比 `Depends` 更好，因此请仅使用 `Depends` 来指定您所需的 R 版本。

您可以这样指定：

```
Depends: R (>= 4.1)
```

这表示您需要 R 才能工作（这不足为奇，但语法对包同样适用），并且 R 版本必须至少是 4.1。

依赖关系的语法是一个以逗号分隔的包名（或如前所述的 `R`）列表，可选的版本号要求放在包名后的括号中。

`Imports` 和 `Suggests` 字段可能看起来像这样：

```
Imports:
ggplot2,
dplyr (>= 1.0.7),
pracma
Suggests:
testthat,
knitr
```

指定我们导入了三个包：`ggplot2`、`dplyr` 和 `pracma`，并且如果 `testthat` 和 `knitr` 可用，我们会在某些函数中使用它们。我们要求 `dplyr` 至少是 1.0.7 版本，但对其他包的版本不作要求。（这里对 `dplyr` 的版本要求完全是任意的；仅仅是我在撰写本文时安装的版本。不要过度解读。）

`Imports` 和 `Suggests` 之间的区别在于：`Imports` 中的要求必须在安装您的包时已经安装（或者如果您告诉 R 安装依赖项，它们也会被安装），而 `Suggests` 中的要求则不必。

### 使用导入的包

`Imports` 或 `Suggests` 列表中的包并不会像您调用 `library(package)` 那样被导入到您的命名空间中。这是为了避免污染您的包命名空间，您不应通过自己调用 `library` 来打破这一规则。如果您想使用其他包中的函数，必须通过其包命名空间显式访问，或者在单个函数级别显式导入。

在不导入包命名空间的情况下访问另一个包的函数的方法是使用 `::` 符号。如果您想在不导入 `dplyr` 的情况下使用 `dplyr` 中的 `filter` 函数，您可以使用名称 `dplyr::filter` 来获取该函数。

如果您访问一个您已在 `Imports` 字段中列出的包中的名称，那么您知道它存在（即使它没有被导入到您的命名空间中），因此您只需要使用完整名称即可。

另一种导入函数的替代方法是使用 Roxygen——我们稍后将讨论——通过它，您可以为单个函数导入另一个包的命名空间，或仅导入另一个包中单个函数的名称。

### 使用建议包

要访问建议包中的函数——即`Suggests`字段中列出的包——需要使用`::`符号，就像处理导入包一样。但有一个额外的麻烦：该包可能并未安装在您包所在的计算机上。这就是建议依赖项与将其放入`Imports`字段声明必要依赖项之间的区别。

建议包而非导入包的目的在于：您的包所提供的功能并不严格依赖其他包，但如果存在建议包，您可以实现更多功能或更高效地完成工作。

因此，您需要在使用某个包之前检查它是否已安装，而实现这一检查的函数就是`requireNamespace`。如果您请求的命名空间（包）已安装，它会返回`TRUE`，否则返回`FALSE`，因此您可以这样使用它：

```
if (requireNamespace("package", quietly = TRUE)) {
  # 使用包的功能
} else {
  # 执行不涉及该包的操作
  # 或者放弃并使用 stop() 抛出异常
}
```

`quietly`选项用于阻止其打印警告信息——既然您已经在处理包未安装的情况，就没必要让它多此一举了。

### 命名空间

`NAMESPACE`文件提供了关于您包中实现的哪些函数应在用户执行`library(test)`时导出到用户命名空间的信息。

每个包都有自己的命名空间。这类似于每个函数在其函数体内都有一个命名空间，我们可以在其中定义和访问局部变量。您在包中编写的函数会先在包命名空间中查找其他函数，然后再到全局命名空间中查找。

想要使用您包的用户可以通过以下方式加载函数到他们的命名空间：

```
library(test)
```

或者显式请求您命名空间中的函数：

```
test::function_name()
```

但他们只能访问到被显式导出的函数（和其他对象）。^(²⁷) 如果一个函数未被显式导出，那么它就被视为包的实现细节，包外部的代码不应能够访问它。

`NAMESPACE`文件正是您指定应从包中导出哪些内容的地方。^(²⁸)

自动生成的文件内容如下：

```
exportPattern("^[[:alpha:]]+")
```

它会导出所有名称由字母组成的内容。这显然导出了过多内容，但我们暂时先忽略这个问题。我们不会手动编辑这个文件，因为按照下文所述，使用 Roxygen 可以更轻松地导出函数（以及所有其他对象）。

### `R/` 和 `man/`

`R/`目录是您放置所有 R 代码的地方，而`man/`目录用于存放包的文档。在 RStudio 生成您的新包后，两个目录中各有一个示例文件。您可以看一下它们，然后将其删除。

您为包编写的所有 R 代码都应放在`R/`目录下的文件中，以便加载到包中。所有文档都将放在`man/`中，但我们不会手动在那里编写文档。相反，我们将使用 Roxygen 来记录函数，然后 Roxygen 会自动生成`man/`目录下的文件。

### 检查包

在介绍 Roxygen 并开始为包添加功能之前，我希望您先检查一下包是否处于一致状态。包需要满足许多一致性要求，主要涉及文件名、命名约定等方面，最好经常检查您的包是否正常。要进行检查，请进入**构建**菜单并选择**检查包**。您也可以在命令行中使用`devtools`包来执行此操作：

```
install.packages("devtools")
```

然后使用`check()`函数：

```
devtools::check()
```

它会运行一系列检查——似乎每次更新`devtools`时检查项都会增加——但最终会告知您的包是否正常。如果现在运行，您应该会得到零错误、零警告和零提示。

当我们开始修改包时，请不时运行`check()`。如果某些操作破坏了包的一致性，尽早发现会更好，这样您就能知道破坏了哪些部分并轻松修复。如果您做了大量更改，事后追溯是哪次更改导致的问题可能会更加困难。

### Roxygen

Roxygen 是一个为包编写文档的系统，如果您熟悉 Javadoc，您会认出它的语法。不过，它还做了更多事情，包括处理命名空间的导入和导出，我们稍后会看到。

要使用它，首先需要安装，因此运行：

```
install.packages("roxygen2")
```

现在进入**构建**菜单并选择**配置构建工具…**。在那里，选择**构建工具**并勾选**使用 Roxygen 生成文档**，然后在弹出的对话框中勾选**构建并重新加载**。这可以确保使用 Roxygen 生成文档，并且在构建包时文档也会生成。这还能确保 Roxygen 处理命名空间的导入和导出。

#### 为函数编写文档

我们可以通过一个示例来了解 Roxygen 如何工作：

```
#' 两个数相加
#'
#' 此函数将两个数相加。
#'
#' @param x 一个数字
#' @param y 另一个数字
#' @return x 和 y 的和
#'
#' @export
add <- function(x, y) x + y
```

函数`add`的文档写在函数上方的注释中，但注释以`#'`开头，而不是普通的`#`。这告诉 Roxygen 这些注释是需要处理的文档的一部分。

第一行会成为函数文档的标题。其后应跟一个空行（仍然在`#'`注释中）。

接下来的文本是对函数的描述。对于这个简单函数而言，文档显得有些多余，但通常您会在这里写几段文字，描述函数的功能及其使用方法。您可以根据需要编写任意长度的文档。

以`@`标签开头的行——例如`@param`和`@return`——包含提供给 Roxygen 的信息。这些信息用于生成文档中的各个部分。

`@param`标签用于描述参数。该标签后跟参数名称，然后是参数的简短描述。

`@return`标签提供函数返回值的描述。

在用 Roxygen 注释编写了一些文档后，可以通过菜单**构建**并选择**编辑文档**来构建文档。Roxygen 不会覆盖现有的`NAMESPACE`文件，因为该文件并非由它生成，因此请在运行**编辑文档**之前先删除它。这样 Roxygen 就可以自由写入该文件。此操作只需执行一次；此后，Roxygen 就会识别出该文件是由它控制的。

构建文档后，请查看`NAMESPACE`文件和`man/`目录。在`NAMESPACE`文件中，您应该会看到该函数已被导出：

```
# 由 roxygen2 生成：请勿手动编辑
export(add)
```

而在`man/`目录中，应该会有一个名为`add.Rd`的文件，用于记录该函数。

### 导入与导出

在`NAMESPACE`文件中，您应该看到您文档化的函数被显式地导出了。这是因为我们在文档中提供了`@export`标签。它告诉`Roxygen`从包命名空间中导出该函数。

这是处理命名空间导出的最简单方法。因此，即便仅为此，您也应该使用`Roxygen`，而不是手动编辑`NAMESPACE`文件。

如果您使用`@export`标签，`Roxygen`还会确保多态函数和其他类型的对象被正确导出——这在`NAMESPACE`文件中通常需要不同类型的命令。只要您使用`Roxygen`，就不必为此担心。

`Roxygen`还可以处理命名空间的导入。请记住，您在`DESCRIPTION`文件的`Imports`字段中列出的包，在安装您包的计算机上会被确保已安装，但这些包的命名空间并不会被自动导入。您必须使用`::`符号来访问它们。

有了`Roxygen`，您可以在函数中使用`@importFrom package object`标签，将`object`（通常是一个函数）导入到该函数的命名空间中。对于普通函数，我个人认为使用此功能意义不大，因为它并不比直接使用`::`符号更简短。不过，对于中缀函数来说，这样做会让它们更易用，因为您实际上可以将中缀函数作为中缀运算符来使用。

因此，在下面的函数中，我们可以使用`dplyr`包的`%>%`运算符，因为我们显式地导入了它。否则，您无法直接使用中缀运算符。

```r
#' Example of using dplyr
#'
#' @param data A data frame containing a column named A
#' @param p   A predicate function
#' @return The data frame filtered to those rows where p is true on A
#'
#' @importFrom dplyr filter
#' @importFrom dplyr %>%
#' @export
filter_on_A <- function(data, p) {
  data %>% filter(p(A))
}
```

如果您编写了一个大量使用某个包功能的函数，您也可以导入该包的整个命名空间。这类似于使用`library(package)`，通过`@import`标签完成：

```r
#' @import dplyr
#' @export
filter_on_A <- function(data, p) {
  data %>% filter(p(A))
}
```

### 包作用域 vs. 全局作用域

关于使用`library(package)`加载包时的命名空间，有必要快速说明一下。我之前提到过，但这里想彻底澄清。一个包拥有自己的命名空间，其中存放着它的函数。当从包内部编写的其他函数中调用函数时，会先在包的命名空间中查找，然后再去全局命名空间中查找。

如果您编写了一个使用了包内其他函数的函数，而有人在加载您的包之后，在全局命名空间中重新定义了该函数，这并不会改变函数在您包内被找到的结果。

无论函数是被导出的还是包内部的，该机制都有效。`R`总是会先查看包的命名空间，然后再查看全局命名空间。

### 内部函数

您可能不想导出包中编写的所有函数。如果有些函数您认为是包设计的实现细节，就不应该导出它们。如果导出了，其他人可能会开始使用它们，而当您后续优化包时，可能想修改这些功能，这显然不是您希望看到的。

让函数成为内部函数非常简单。您只需不使用`@export`标签即可。这样，当包被加载时，它们就不会从包命名空间中被导出，因此也无法从包外部访问。^(²⁹)

### 文件加载顺序

通常，将包功能分布在多少个文件中并不重要。通常，为每个（主要）函数或类创建一个文件，更便于找到要编辑的文档，但这主要还是个人喜好问题。

各种函数（无论是内部的还是导出的）放在哪些文件中通常也不重要，因为它们都会出现在包的命名空间中。并且，只要您坚持使用函数（以及`S3`多态函数），构建包时文件处理的顺序也不会产生影响。

但对于`S4`类等则确实有影响。万一您遇到这个问题，我快速提一下：包文件是按字母顺序处理的。不过，这个“字母顺序”取决于您所处的环境，因为字母顺序实际上取决于您使用的语言，所以您不应依赖于此。

相反，您可以使用`Roxygen`。它也能确保某个文件在另一个文件之前被处理。您可以使用`@include`字段来声明函数与另一个文件之间的依赖关系：

```r
#' @import otherfile.R
```

我自己从未有过这方面的需求，您可能也不会有，但至少您知道有这种方法。

### 为包添加数据

包中包含一些数据并不罕见，这些数据要么用于包的实现，更常见的是用于示例目的。

这些数据应存放在`data/`目录中。您的新建包中可能没有这个目录，但如果您想在包中包含数据，数据就应该放在这里。

数据不能使用任意格式。它必须存放在`R`能够读取的文件中，通常是`.RData`文件。不过，添加数据文件最简单的方法是使用`devtools`包的功能。如果您尚未安装它，请执行：

```r
install.packages("devtools")
```

然后，您可以使用`use_data`函数来创建数据文件。

例如，我在`admixturegraph`包中有个小的测试数据集，是使用以下命令创建的：

```r
bears <- read.table("bears.txt")
devtools::use_data(bears)
```

这些数据在包加载后不会立即可用，但您可以使用`data`函数来获取它们：

```r
library(admixturegraph)
data(bears)
bears
```

您不能直接在数据文件中添加文档说明，因此需要将文档放在`R/`目录下的一个`R`文件中。我通常有一个名为`data.R`的文件，用于记录包中的数据集。

对于`bears`数据，我的文档如下所示：

```r
#' Statistics for populations of bears
#'
#' Computed $f_4(W,X;Y,Z)$ statistics for different
#' populations of bears.
#'
#' @format A data frame with 19 rows and 6 variables:
#' \describe{
#'  \item{W}{The W population}
#'  \item{X}{The X population}
#'  \item{Y}{The Y population}
#'  \item{Z}{The Z population}
#'  \item{D}{The $D$ ($f_4(W,X;Y,Z)$) statistics}
#'  \item{Z.value}{The blocked jacknife Z values}
#' }
#'
#' @source \url{http://onlinelibrary.wiley.com/doi/10.1111/mec.13038/abstract}
#' @name bears
#' @docType data
#' @keywords data
#'
NULL
```

### NULL

文档后面的`NULL`是必需的，因为`Roxygen`需要在文档注释后跟一个对象，但实际上是`@name`标签告诉它，这段文档是为`bears`这个对象服务的。`@docType`标签表示我们正在记录的是一个数据集。

`@source`标签说明数据来源；如果您是为自己的包生成的数据，则不需要此标签。

`@format`标签是这里唯一比较复杂的标签。它描述了数据（一个数据框），并且使用的标记语言与`Roxygen`的文本标记看起来非常不同。`R`使用的文档实际上更接近（La）TeX，而不是我们一直使用的格式，数据描述就体现了这一点。

您必须将描述内容放在用`\description{}`标记的花括号内，并且对于数据框的每一列，都有一个条目。其格式为`\item{列名}{列描述}`。

# 构建 R 包

## 步骤与功能

在 RStudio 右上角的面板中，您应该会看到一个名为“构建”（`Build`）的标签页。点击它。

在该标签页内，工具栏中有三个选项：`Build & Reload`、`Check` 和 `More`。它们的功能正如其名：第一个用于构建并（重新）加载您的包；第二个用于检查包——即运行我们之前见过的一致性检查；第三个则通过下拉菜单提供其他各种选项。

当您对包进行修改后，使用 `Build & Reload` 来重新编译它。它会加载您所有的 `R` 代码（以及其他各种内容）来构建包，然后安装该包并将其重新加载到终端中，以便您可以测试新功能。

通过这种方式构建并安装的包，之后也可以在其他项目中使用。

当您需要将包发送给他人时，可以在 `More` 下拉菜单中选择制作一个 `源代码包`。它会创建一个存档文件（`.tar.gz`）。
