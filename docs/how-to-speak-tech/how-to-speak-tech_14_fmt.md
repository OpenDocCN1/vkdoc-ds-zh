# 11. 性能与可扩展性

作为一名充满热情的企业家，你密切关注着 `MyAppoly` 的使用情况，并立即处理任何问题。你花时间仔细审阅团队的分析报告，并注意到了成功的迹象。你的用户数量正在呈滚雪球式增长。很快，你的团队来找你，讨论如何改进网站，因为网站正在吸引前所未有的流量。一些工程师指出，某些页面的加载速度远低于其应有的水平，并且当前的架构无法支持更多用户，尤其是考虑到指标所显示的增长速率。例如，每台服务器每秒只能处理一定数量的请求，因此当前网站加载时间过长。这些都是“好问题”，但仍然需要解决。

`性能` 关乎网站的速度：加载速度有多快，传输了多少字节，以及任何衡量用户接收请求信息速率的指标。

`可扩展性` 指的是 Web 应用程序适应不断增长的工作量的能力。它关乎你的网站能够容纳更多用户、更多数据和更多计算——不仅仅是多一个或几个，而是数千甚至数百万个。

你可以看到，这两者并非同一回事，但可能同时出现。如果你的用户群在增长，你需要确保网站尽可能高效地运行。你的团队准备了一份关于他们希望实施技术的入门指南。这份清单并非详尽无遗，但能让你了解公司通常如何处理这些问题。

## 提升性能的实践方法

可以通过优化后端和前端来提升性能。然而，后端只占页面加载时间的一小部分。大部分时间都花在下载用户界面的组件上——例如，为给定网页上出现的各种元素发出 HTTP 请求。这可能会影响你确定优先顺序和分配资源的方式，尽管页面加载时间只是性能的一个方面。

### 后端方面的考量

应用已经提及的良好设计原则可以提升效率。例如，抽象化技术允许你在应用程序的不同部分有效地重用代码。

此外，许多成功的科技公司会重写代码以提高效率。优化数据库查询和其他操作（例如用于确定 Netflix 电影推荐的算法）是第一步。另一步则是完全用不同的编程语言重写应用程序。回想一下，更底层的语言能提供更高的效率（第 3 章）。因此，许多科技公司会重写其应用程序以利用这些语言。例如，Twitter 从 Ruby on Rails 迁移到了 Scala 和 Java。Facebook 通过程序化方式将其 PHP 代码转换为高度优化的 C++ 代码。这样的例子不胜枚举，但由于将代码迁移到不同的语言是一个艰巨的过程，公司需要仔细权衡，判断当前使用的编程语言是否已不再适合其任务。

### 前端方面的考量

当用户访问你的网站时，只有很少的时间花在 HTML 文档的初始 HTTP 请求上。大部分时间都花在下载与该特定网页相关的各种资源上。本节将重点介绍一些实践、工具和方法，供所有前端开发者在以性能为目标时加以考虑。

#### 减少 HTTP 请求

减少下载页面资源所需的 HTTP 请求次数可以缩短页面加载时间。有多种方法可以减少请求次数，例如合并脚本和样式表。我们将讨论两种与图片相关的特定方法：使用 `CSS 精灵图` 和 `图片地图`。

假设你想在网站左上角展示 Logo 的左半部分，在右上角展示 Logo 的右半部分。一种方法是设计两个元素分别代表每一半，这需要两次请求才能显示。与其采用这种方法，我们可以只对整个 Logo 发出一次请求，然后使用不同的 CSS 属性来隐藏我们不想显示的那部分图像。这就是 `CSS 精灵图`，它有助于减少我们可能需要的请求次数。

现在假设你想在网站上包含一张团队成员的照片，点击其中任何一张脸都会将用户重定向到其领英主页。如果使用单独的照片，浏览器需要对每张图片发出单独的 HTTP 请求。但是，通过使用集体照，你可以使用 `图片地图` 将不同的链接关联到图片的不同区域，从而将图片的 HTTP 请求次数减少到一次。

#### 缓存

如果你的用户反复访问同一页面，让他们每次重新请求该页面的所有资源意义不大。你每次和最好的朋友见面时，不会都问他们要一次电话号码，对吧？在某些时候，他们会让你直接存下来。同样，你的浏览器也厌倦了反复向服务器请求，而是将网页存储在 `缓存` 中。缓存资源的例子包括图片、CSS 文件和 JavaScript 文件，与 HTML 相比，这些文件变化频率相对较低；你可能想在你的网站上添加一段新的信息段落，但不太可能频繁更改 Logo 或页面样式。将 CSS 和 JavaScript 放在外部文件中可以实现对其的缓存。

#### 压缩

如果你曾下载过大型文件，可能会注意到它是以体积更小的 `.zip` 文件形式下载的，需要解压才能使用。创建这种文件的过程被称为 `压缩`。通过减小响应体积，文件从服务器传输到浏览器所需的时间也会缩短。请记住，压缩会带来一定的代价。在服务器上压缩文件以及浏览器解压文件都需要额外的处理能力。因此，并非对所有资源进行压缩都是合理的。

另一种压缩手段是 `精简`，即删除文档中所有不必要的空格、注释和字符。编写软件时，缩进和注释能让代码更具可读性。然而，当代码从服务器传输到浏览器时，这些内容会增加大量不必要的负担。

#### 脚本与样式表的位置

请记住，样式表（`CSS` 文档）和脚本（`JavaScript` 文档）通常以外部链接的方式嵌入到 `HTML` 文档中。这些文档的链接位置将决定页面的加载方式。假设一个页面需要五秒加载完成。第一种情况是，屏幕在整整五秒内保持空白，随后整个页面瞬间呈现。第二种情况是，页面在五秒内逐步加载，直至完成。哪种方式更好呢？许多人会选择后者，因为用户对无响应的状态感到不适，他们更希望看到加载过程。要实现这种被称为 `渐进式加载` 的效果，你应将样式表链接在 `HTML` 文档的顶部，而脚本链接在底部。由于许多浏览器会等到样式表处理完毕后才加载元素，以避免重新绘制，因此将样式表放在顶部速度更快。脚本则应放在末尾，因为脚本下方的内容在脚本完全下载之前会停止渲染。

## 基础设施变更

大多数网络应用项目（例如 MyAppoly）都始于一台具有固定存储容量的服务器，该服务器与一个数据库相连。随着越来越多的用户开始使用你的应用，你需要增加服务器来响应他们所有的请求。然而，当更多用户加入并开始相互交互时，将所有收集到的数据写入数据库会变得极其缓慢。为了与数据库快速交互，我们会 `复制` 数据库，即创建多个可供交互的副本。

复制数据库的过程颇为复杂。如果查询只是"读取"操作——即用户想要访问数据库中存储的信息——那么多个数据库副本能够满足日益增长的用户群需求。但如果用户想要"写入"或更改数据库中存储的内容——例如添加一个好友——该怎么办呢？你必须确保所有数据库都得到更新。将"新朋友"添加到所有数据库副本中可能效率低下，因此，你通过指定一个主数据库作为写入数据库来解决这个问题，所有更新必须仅由该数据库处理。其他所有数据库副本则纯用于读取。通过这种方式，数据库可以具备可扩展性。

在添加了更多服务器和数据库之后，如何实际引导用户访问不同的副本呢？你可以使用 `负载均衡器`，以分散请求的方式将用户请求发送至可用的服务器。负载均衡器可以采用各种复杂的算法来决定最优的分配模式。最简单的是轮询法，它按固定模式将新用户引导至服务器。将一位用户发送至服务器 A 后，下一位用户发送至服务器 B，再下一位发送至服务器 C，以此类推。然而，这种方法可能并非最优，因为它没有考虑服务器的实际可用性。你可能会意外地将两个高负载用户分配到同一台服务器，而其他服务器的负载却较轻。基于使用情况的分配方式可能效果更好。负载均衡器能为你的系统提供可靠性，因为当某台服务器宕机时，它可以重新路由流量。

## 结论

你最终会认识到性能至关重要，并且现在了解了开发者如何思考改善加载时间。你意识到，随着网络应用开始扩展，为了支持更多用户，你将需要为更多资源付费。额外资源需要在成本与性能之间进行权衡——这是一个不错的问题。随着你不断发展，你会发现自己存在一个盲点：安全性。下一章将向你介绍一些重大攻击及其防范方法。
