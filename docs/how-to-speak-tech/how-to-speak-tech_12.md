# 9. 软件开发：调试与测试

2009 年，丰田汽车被指控部分车型油门踏板存在卡滞问题，并于 2010 年 1 月召回 410 万辆汽车进行维修。该缺陷是汽车产品中的一个*缺陷*或瑕疵。我们可以将丰田的产品与任何互联网公司的产品进行类比。Facebook、谷歌和 MyAppoly 都有过、并且将来也还会有各种各样的缺陷，但优秀的团队会在产品面向客户发布之前，在开发过程中发现它们。

期望团队编写的每一行代码在第一次运行时都能正确工作是不现实的。正如出版前的校对和编辑是写作过程中的关键环节一样，*调试*——即排除错误的过程——也是编写代码过程中的重要一步。这些错误不仅包括拼写错误等语法相关问题，还包括代码结构或代码间交互方式的问题。由于团队和用户会定期发现产品中的缺陷，调试是一个持续的过程，且所需时间不可预测。随着 MyAppoly 规模扩大、工程师人数增加，快速定位缺陷源头将变得越来越困难。从概念层面理解工程师如何进行调试，将有助于你认识到这个过程有多么依赖于试验和变量。

## 缺陷的一生

简而言之，*缺陷*就是一个错误。这个不寻常的术语背后有一段有趣的历史。在计算机使用穿孔卡片编程的年代，著名计算机科学家格蕾丝·赫柏注意到了一些不寻常的现象。经过调查，她发现一只死飞蛾干扰了一张穿孔卡片——这成了计算机科学史上的第一个“bug”（程序缺陷）！

如今，bug（程序缺陷）是由程序员（无意中）制造的，而不是由真实的虫子造成的，并且并非所有缺陷都容易修复。缺陷分两种：语法缺陷和语义缺陷。

- *语法缺陷*源于违反编程语言的规则。你的程序员可能遗漏了分号、拼错了变量名，或者试图使用编程语言不提供的结构。这类缺陷通常容易修复，因为编译器、解释器或其他工具可以找到它们。如果把代码比作 Microsoft Word 文档，这些错误可以通过拼写和语法检查来发现。

- *语义缺陷*包含两种类型。第一，*运行时错误*会导致程序崩溃并停止执行。例如，程序试图打开一个不存在的文件。第二，*逻辑错误*不会中断程序的完成，但会产生意外结果，比如该做减法时做了加法。如果你在文章中自相矛盾，就犯了逻辑错误，但只要语法和拼写正确，拼写检查器就不会标出它。因此，语义错误比语法错误更难捕获、定位和解决。

尽管所有缺陷都是程序员造成的，但并非都源于疏忽。有些缺陷的出现是因为更新后的代码与之前的逻辑不再兼容。有些缺陷则是因为两位工程师合并代码时，两个新功能无法完美协作。存在缺陷并不意味着必须有人为此承担责任。

## 调试过程

本节阐述的六步调试法，是对 Grötker 及其 Synopsys 公司同事提出的“调试 13 条黄金法则”¹¹的提炼。这六个步骤并非权威标准，但当你团队中的工程师说他们正在“调试”某个问题时，你可以确信他们大致遵循的是这些步骤的某种变体。

### 1. 追踪问题

为了有效管理 MyAppoly 的错误，首先就要追踪所有缺陷。对遇到的每一个缺陷都保留适当的文档记录，可以帮助你更快地解决未来的问题。此外，追踪缺陷还能帮助整个团队在问题及其解决方案上保持步调一致。许多现成的追踪系统运行方式如下：当发现一个缺陷时，系统会创建一个描述该缺陷的问题或“工单”。其状态在解决前保持为*开启*，解决后则切换到*已关闭*。期间还存在一些中间状态，例如*处理中*，并且工单可以作为委派方式分配给不同的团队成员。

什么才是适当的文档记录？由于任何程序输入都可能影响缺陷，所有可能导致问题的因素都应被记录下来。这包括用户执行的具体操作、操作系统、浏览器、实际行为、预期行为，以及你能想到的几乎所有可能相关的信息。这些变量要么是*静态的*——即与配置和兼容性相关的、不会改变的属性，例如操作系统和浏览器；要么是*动态的*——即与内存和网络相关的、频繁变化的方面，例如同一时间运行的其他程序数量。

### 2. 复现问题

在获知一个缺陷并记录其详细信息后，下一步就是复现该问题。这包括重建环境，并检查行为是否与所报告的一致。这个过程起初有点手工操作，但你需要重新制造出程序的故障，以便使用相同的测试来确认问题是否已被妥善修复。



### 3. 运行测试

每次调整代码后，请尝试复现故障，以确认上次更新是否解决了问题。手动复现问题会令人疲惫，因此，更好的方法是实现测试自动化，以便你能够识别问题。有几种技术可以实现这一点；每种技术的可用性取决于你所使用的编程语言、整个系统的规格以及你愿意购买的工具有哪些。

科学方法将为你的调试工作提供指导：提出假设，相应地编辑代码，测试，评估，并根据需要重复。每次调整代码后对程序进行测试，记录更改以创建审计跟踪，这样你可以在需要将代码恢复到原始状态时进行回溯。此外，为每一次更改创建不同版本的文件也是一个好习惯。

在发布新版本之前，你将如何测试 `MyAppoly` 的功能？你不能浪费任何时间，因为你希望尽快替换已发布给用户的含有缺陷的代码。你运行的测试通常会在三个层级之一进行：表示层、功能层或单元层。

虽然你可以从任何层级进行测试，但你通常会根据执行的难易程度、交互的便利性以及结果评估的简易性等因素来选择其一。我们快速了解一下。

*表示层* 是我们在模型-视图-控制器描述中应用的视图组件。从表示层进行测试时，你像普通用户一样，使用鼠标和键盘与应用程序交互。假设在 `MyAppoly` 上检查某个账户余额时存在一个缺陷。存入 100 美元后，账户余额仍然显示为 0 美元。你可以通过刷新网页并查看账户余额，使用表示层来检查你是否修复了该缺陷。在这一层进行测试通常是可行且快速的。即便如此，可见性是有限的，因为你光看最终数值不一定能看到后端是如何进行计算的。

*功能层* 包含所有定义程序功能的代码——本质上是 `MyAppoly` 的控制器和模型部分。为了在这一层进行测试，程序员通常会编写一个与更大应用程序中的代码进行交互的较小程序。例如，程序员可能想编写一个小程序来创建一个假账户并向其中存入 100 美元，检查存款后的账户余额是否确实是 100 美元。运行这些功能测试通常和点击浏览器上的刷新按钮一样简单，并且自动化允许进行大规模测试。创建这些测试可能看起来很容易，但开发人员编写每个测试都需要一些初始成本。然而，如果你预计会频繁运行同一测试，那么这项投资可能是值得的。

最后一层是 *单元层*。如果你能将整个程序分解成小的、一次操作一个的代码块，你就得到了一个单元。在账户示例中，以下每一项都可能代表一个单元：获取旧账户余额、获取存款金额、计算新账户余额以及存储新值。测试这些特定单元可以通过脚本实现自动化。这些测试让程序员能够最详细地了解程序在构建块层面的运行情况。通常这些测试是等式测试，意味着它们将测试预期输出是否等于实际输出。如果相等，测试将继续；否则，将报告错误。这样，缺陷可以立即被追溯到程序的特定区域。在当前示例中，有几个单元。首先，你可以检查账户将要变化的数值。如果你输入了 100 美元，请确保后端确实将其解释为 100 美元。现在，获取你账户的现有余额。你读取的账户是正确的吗？最后，你可以将 100 美元添加到现有账户余额中以获得最终值。最终值正确吗？通过将其分解为逐步分析，你可以确定故障发生的具体步骤。

你的程序员拥有各种工具和技术来帮助他们追踪和测试缺陷。一种简单的调试方法涉及 `print` 函数，它可以显示你告诉它显示的任何内容。在更新你的 `MyAppoly` 账户余额的例子中，你可以在每一行代码之间添加 `print` 语句。你可以打印旧账户余额、你想要改变的金额以及新账户余额。如果其中任何一个数字有误，你就能确切地看到哪里出了问题。通过这种方式，`print` 函数可以用来创建单元测试。但可以想象，在你的代码中到处添加 `print` 语句既混乱又繁琐，因为你必须阅读大量输出来查找每个缺陷。幸运的是，有更好的方法。

你可以使用的一种工具是 *调试器*。调试器本质上会暂停程序的执行，以便程序员进行观察。通过设置 *断点*，程序员可以在代码的某个位置暂停，并查看所有相关变量的值。调试器还允许程序 *跟踪* 代码，在每一行之后暂停，这样程序员就可以确定接下来将执行哪一行代码以及变量应如何变化。可以想见，如果发生错误，程序员将能够识别错误发生的位置，并且通过与计算机一起跟踪代码逻辑，程序员可以更容易地发现缺陷。你可能听说过的一个调试器示例是 GNU 调试器 `GDB`，它在命令行中运行，通常与 C 编程语言相关联。

### 4. 解释测试结果以识别缺陷根源

每一次测试，你都更接近理解缺陷的根本原因。如果你问你的程序员，没有什么比找到造成巨大困扰的逻辑错误或缺失语句更令人有成就感了。请记住，缺陷可能存在于任何地方，无论是在你的源代码中，在编译器中（如果你使用的是编译型语言），还是在第三方库或 API 中。

### 5. 在本地修复缺陷

既然你已经找到了缺陷，是时候修复它了。即使修复需要你重新编写整个功能，你也知道程序崩溃的*原因*。修复缺陷后，你的团队将运行回归测试，以测试网站的所有其他功能是否仍然正常工作。修复一个缺陷却引入另一个缺陷，这绝不是一个正确的解决方案。你也可以编写额外的测试，以确保下次这样的缺陷不会再悄无声息地溜过去。假设你的回归测试通过了，你就可以有信心，你已经消除了威胁，同时没有制造更多的混乱。

### 6. 交付修复后的产品

一旦你修复了缺陷并运行了确认测试，`MyAppoly` 团队将更新该站点的公共版本，这样用户就不会再访问一个有缺陷的应用程序了。这遵循了第 8 章概述的发布管理流程。

## 结论

现在你已经对你的团队将用来使 `MyAppoly` 达到完美状态的过程和技术有了更多了解。有了这些工具，你的团队已经构建、测试、调试并发布了一个可运行的 `MyAppoly` 版本。改进产品始终是一个目标，但下一章要讨论的是一个关键任务：获取用户。
