# 软件开发：团队协作

厨师多了烧坏汤。这句谚语同样适用于编程，除非你以正确的方式组织你的工程师。

你花了最近几周的时间组建了一个由雄心勃勃的工程师组成的小团队。他们了解后端、前端和数据库的交互方式，并已准备好开始为 `MyAppoly` 编写程序。在开始之前，你需要制定协作指南。他们将如何合作？两个人可以同时处理同一个文件吗？一位工程师如何理解另一位工程师的工作？

这些问题对于任何技术性工作来说都很重要。各种设计原则和工具支持团队化编码，使其更快、更安全。为了与你的工程师进行有效沟通，你需要理解这些原则和工具的术语——尤其是版本控制系统。

## 文档

工程师向队友解释其代码最简单的方式就是注释代码。每种编程语言都允许程序员在特定代码行或代码块旁边编写注释，以解释代码的工作原理或功能。示例注释包括“更改用户密码”或“将用户添加到数据库”。有了这些注释，新工程师可以快速了解代码库，程序员也可以有效地为那些他们不太熟悉的代码做出贡献。注释还能让管理者更高效地审查代码，因为英文陈述提高了代码的可读性。注释是**文档**的一种形式，文档是对某个过程或功能的一系列描述和说明。文档通常采用段落形式，以帮助工程师更快地理解重要功能的设计和实现。如果你负责 `MyAppoly` 的首席工程师构建了一个允许应用处理信用卡支付的新功能，他们可能想写几段文字，解释该功能如何与程序的其余部分集成、代码如何工作、代码保存在哪里、逻辑如何运作、他们使用了哪些 API 等等。

除了这些外部文档外，编码风格对团队也至关重要。这里的**风格**，我指的是命名约定（如何在程序中命名变量）、缩进和空格的使用、注释的结构以及其他方面。想象一下，一段代码要求用户输入姓名，然后将其保存到数据库中。一位工程师可能会格式化文本，并将存储用户姓名的变量命名为 "name"，而另一位工程师可能会把它命名为类似 "var293" 这样含义模糊的名字。显然，前者比后者更容易理解。这些编码风格很重要；因此，制定一份供所有工程师使用的标准风格指南是一种常见做法。许多编程语言本身也带有各自的风格指南或约定，可以作为起点。如果 `MyAppoly` 的工程师遵循这些约定，那么所有功能的格式和标签都将保持一致，新工程师也将能够更轻松地协作和审查代码。



## 程序架构

组织 MyAppoly 代码的方式有多种。在第 3 章到第 5 章中，你学习了代码如何执行程序逻辑、构建用户所见界面以及与数据库交互。如果所有这些代码都混杂在一起，程序就会变得缓慢且难以管理：试想一下，如果程序的所有代码都塞进一个文件里，工程师要如何在数百万行的文件中确定从何处开始编辑？

幸运的是，编程已是一门成熟的学科，聪明的人们已经开发出了更好的代码组织方式。这些设计原则不仅能提高效率和代码性能，还有助于团队协作和代码的可维护性。

最常见的组织方式之一是多层应用程序架构，其中应用最广泛的是三层架构。这三层大致对应了第 3 章至第 5 章的主题：一层涉及与数据库相关的所有内容，通常称为模型（第 5 章）；中间层是控制器或应用处理层，包含程序逻辑，与程序的后端相关（第 3 章）；最后一层是用户所见的所有内容：视图或表现层（第 4 章）。还有其他一些架构，但我会重点讨论这些架构存在的根本原因，而非深入介绍每种架构的具体差异。

首先，这些架构支持并行工作（这一设计原则通常被称为*关注点分离*）。一名工程师可以专注于 MyAppoly 的表现层，而另一名工程师可以同时处理模型层。控制器工程师可以告诉模型工程师：“我不关心你怎么实现，但我需要用户的姓氏。”这样，视图工程师和控制器工程师就可以假设自己已有某种方式来获取用户名，从而继续编码，无需担心真正去数据库查询姓名的代码。模型工程师可以给另外两名工程师提供一个简单的描述：“如果你想获取姓名，就调用 `getUserName` 函数；如果你想获取用户的位置，就调用 `getUserLocation`。”然后，模型工程师就可以用任意方式编写与数据库交互的代码。从这个例子可以看出，应用程序的三个部分可以相对独立地进行开发，因为每位工程师无需关心其他部分的具体实现细节。

其次，这种设计支持可维护性。假设控制器工程师告诉模型工程师，他们需要用户的姓名、地址和邮政编码。模型工程师编写三个函数从数据库中获取这些数据，并将它们交给控制器工程师。控制器工程师可以对这些数据进行处理后，再交给视图工程师显示给用户。三个月后，工程师们发现模型层从数据库获取信息的效率太低。幸运的是，视图和控制器工程师无需做任何更改，模型工程师只需更新其函数以提高性能，应用程序的其他部分无需变动。如果团队没有采用定义明确的架构，这些数据库代码可能散落在任何文件中，找出并修改所有与数据库相关的代码将会困难得多。

选择这种架构的第三个理由是代码的可复用性。假设视图工程师想在每个页面上都显示用户名。低效的做法是在整个网站的每一个网页上都重写获取用户名的数据库代码。相反，视图和控制器工程师可以调用同一个 `getUserName` 函数，该函数进入模型层并执行查询以获取姓名。这种抽象使得工程师能够更高效、更经济地使用代码。

这三个优势的总和显而易见：缩短了开发时间。产品可以更快地构建和维护，宝贵的工程时间可以投入到更多高附加值的活动中去。

## 版本控制

程序的架构有助于分离功能，以便多位工程师能同时在一个项目上工作。但仅仅分离功能并不能解决所有问题。一个工程师团队如何有效协调编程工作？一个人如何通知团队他们已更新了某个特定文件？他们要把新更新的文件通过邮件发送吗？如果你是一名正要更新文件的工程师，你如何确保自己正在处理的是最新版本？也许你在代码中引入了一个缺陷或错误，想要回退到旧版本。这些困扰该如何解决？*版本控制*（也称为*修订控制*或*源代码管理*）指的是对文档变更的管理。你的团队很可能会使用像 Git 或 Mercurial 这样的版本控制系统来解决这些问题。下面我们来讨论版本控制系统的一些特性及其优势。

### 冲突解决

当多位工程师协作一个项目时，解决冲突的两种主要方式是文件锁定和版本合并。

*文件锁定*是一种防止对某个文件进行并发访问的方法。想象一份包含文章的标准文档。如果两个人同时编辑这篇文章，我们如何决定采纳谁的修改？能否合并它们？文件锁定将“写入”权限（编辑文件的能力）授予第一个打开该文件的人，并为其他用户锁定该文件。如果其他用户试图打开这个被锁定的文件，该文件将仅能被查看（“读取”权限）。

文件锁定的好处是避免了合并对同一文件的两组编辑的复杂问题。当工程师 2 打开一个已被工程师 1 编辑的文件时，他会收到通知。然而，这种解决方案也存在缺点。工程师 2 必须等待工程师 1 完成编辑，这会导致流程延迟并拖慢开发速度。设想一个最坏的情况：工程师 1 打开一个文件后请了几天病假。要么工程师 2 在几天内无法使用该文件，要么需要请上级强制解锁文件，这个过程称为*文件解锁*。另一个缺点是，这个系统可能给人一种虚假的安全感。两个相互依赖的文件可能被不同的工程师锁定，并以损害其兼容性的方式被修改。

另一种主要的冲突解决方法是*版本合并*，它允许多个用户同时编辑一个文件。当多位工程师完成对同一文件的修改后，系统会协助合并这些更改。当工程师们都在同一个文件的不同部分工作时，合并很容易，就像一个编辑可以修改文章引言，而另一个编辑则修改结论。相反，如果两位工程师以不同的方式修改了文件的同一部分，就会产生*冲突*，必须手动解决。虽然“冲突”这个词听起来令人紧张，但许多人认为这种系统运行起来更流畅，因为浪费的时间更少。只要工程师们不修改文件的相同部分，就几乎不会出现冲突，合并过程也能无缝进行。这种方法适用于文本类文档，如代码或文档，因为文本易于比较和合并。而对于不易比较的音乐或艺术文件，文件锁定则是更好的选择。



### 集中式与分布式

版本控制系统分为集中式和分布式两种。采用**集中式**系统时，所有代码都存储在一个称为主**仓库**的中央服务器上。工程师每次打开或保存文件时，都必须连接到网络以访问中央服务器。这种模式被称为客户端-服务器模型，与获取网站的模型类似。虽然客户端（即工程师的计算机）上可以保存完整的代码副本，但所有变更的历史记录都保留在主服务器上。如果中央服务器因任何原因宕机，代码及其历史记录就会丢失或暂时不可用，这构成了单点故障。

在分布式模型中，项目工程师的计算机上存在整个代码库及其历史记录（仓库）的多个副本。他们可以在未连接网络时打开和保存文件，并且执行操作的速度更快。每位工程师都拥有一个本地仓库（简称 `repo`），该仓库会随着变更而更新，尽管分布式系统也可以使用中央服务器。每个本地副本（或称工作副本）实际上都相当于一份备份。正是由于这些原因，业界已显著转向更多地采用分布式模型。

### 版本控制的优势

版本控制允许工程师提交代码变更，并且独立、有序地跟踪每一次变更。因此，工程师可以查看文件编辑的完整时间线，并能快速**回退**到文件甚至整个代码库的先前版本。此外，每次编辑都附有工程师解释变更内容的注释。未来的工程师可以轻松查看每次变更的责任人，并在需要时寻求进一步澄清。

版本控制系统速度很快，因为它们只跟踪对文件的变更，即**差异**。例如，如果你只是在一本书中添加了一个句子，那么通过指明插入句子的位置以及添加的内容来描述你的编辑，会比复制整个新版本要快得多。类似地，版本控制系统跟踪两件事：变更的行号和实际的变更（无论是添加的代码还是删除的代码）。一旦保存，差异就会发送到代码库的主版本，这意味着其他工程师将始终能够访问最新的代码库版本。

另一个重要优势是，两名工程师可以使用各自的副本独立开发不同的功能。如果这些功能不编辑相同的代码，则可以轻松合并。否则，版本控制系统会有一个冲突管理系统，使合并两个功能的代码变得容易，或者会使用文件锁定来从一开始就防止冲突。

版本控制还允许工程师在各种状态下为代码库**打标签**。回想一下，版本控制系统允许查看任何历史时刻的代码库。你可能希望在某些时间点对代码库进行标记。例如，你可能希望将已发布的代码库标记为“version 1.0”。同样，你可能希望将经过充分测试但未发布的代码标记为“beta”，或将最新的变更标记为“latest”，以便于访问。

## 结论

团队编程可能会带来若干障碍，但有了合适的风格指南、程序架构和版本控制系统，团队成员将能够更有效地协作。下次有人告诉你“厨子多了做坏汤”时，告诉他们去用 `Git`。
