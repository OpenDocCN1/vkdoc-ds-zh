# 6. 利用现有代码：API、库与开源项目

想象一下，如果没人能利用他人的发明来设计新产品，社会发展的速度会多么缓慢。利用他人的创新成果进行新发现至关重要。或许一种为治疗某种疾病开发的药物，可以改良后用于治愈另一种疾病；也许为制造更耐用器皿而发明的柔性玻璃，可以用来制作摔不碎的手机屏幕。我们不断追求更好的事物，但如果总从零开始，就很难有所发现。

幸运的是，`MyAppoly`也无需从零开始。现有许多方式可以让`MyAppoly`利用现有代码。比如，您想在`MyAppoly`中添加一个地图。鉴于其他公司已投入时间和金钱完成了这项工作，您的团队从头构建地图几乎得不偿失。谷歌允许开发者使用谷歌地图，这体现了推动 Web 2.0 时代网站和应用快速普及的关键动力。那句广为流传的格言“不要重复发明轮子”正是技术界的写照，并催生了信息共享的文化。互联网公司固然会谨慎保护自身信息，但总体而言，它们比过去的组织更乐于分享发现。这种协作文化在一定程度上解释了硅谷非凡的增长、活力与财富。

您应聚焦于`MyAppoly`的独特之处，而非重建其他公司已提供的代码。那么，这些现成的工具究竟是什么呢？本章将阐述*应用程序编程接口*（`API`）^(⁵) 的要点，并探讨开源运动及其重要性。

## 应用程序编程接口

假设您想在地图上向用户展示最近的自动柜员机（ATM）位置，并在`MyAppoly`上接受信用卡支付。您的团队要么从头构建这些功能（这会大幅延长开发时间），要么利用他人的成果，例如谷歌地图和 Stripe。有些`API`是免费的，有些则需要付费。谷歌地图允许您在`MyAppoly`内免费使用其地图服务，而 Stripe 会针对其处理的每笔信用卡支付收取少量费用。这种通过将一个公司的产品集成到另一个产品中来实现轻松技术整合的能力，使得初创公司得以快速成长，并在相对较短的时间内变得成熟。`MyAppoly`不仅能受益于他人的`API`，也能通过发布自己的`API`获益。如果其他公司开始依赖`MyAppoly`的`API`所提供的数据和功能，您的业务将更具吸引力。



### 使用他人 API

使用 API 的显著优缺点包括：

**优点**：

- **比较优势**：使用他人的 API 可以让你专注于自己的核心竞争力与价值主张。就像传统企业可能将文档编辑或报销等非核心工作外包一样，你也可以将支付处理、地图功能等工作外包出去。
- **节省开发时间**：通过使用其他公司的 API 将非核心工作外包，能够节省开发团队的时间。无论是构建功能还是后续维护，都能节约时间。
- **借助他人的专业能力**：公司通常会在其核心能力领域发布 API。无论这些 API 提供信息还是功能，这些公司往往投入了大量时间进行开发。即便你的团队也能做得很好，为何不将责任交给一家纯粹专注于解决该问题的公司呢？
- **获取信息**：许多 API 提供数据访问权限。这些数据通常可在公司网站上获取，但格式不利于大规模采集。API 能以更易于处理的格式提供相同数据。例如气象 API：网站可能显示某个城市随时间变化的每日天气，但假设你正在进行全球变暖研究，需要收集过去 50 年十个城市的每日数据，手动从网站复制每个数字将非常繁琐。而 API 允许你一次性访问并下载所有所需数据。

**缺点**：

- **依赖性**：如果 API 背后的公司决定更改政策或关闭服务，你的 Web 应用将无法正常运行。这种风险是任何依赖第三方的业务都存在的。他们是否有许多大客户？运营状况如何？API 是否已稳定运行一段时间？这些问题的答案有助于预测其可靠性。
- **非定制化**：市场上也可能没有完全满足你特定需求的 API。API 提供通用解决方案，但可能无法完美适配你的网站。因此，在为了上述优点而适应 API 功能，与从头构建完整功能以获得全部能力之间，可能存在权衡。

在权衡这些利弊后，你的最终选择将取决于具体的 API 及其功能。请记住，利用现有代码是行业趋势，过度保守可能会让你的 MyAppoly 落后于竞争对手。

### 发布一个 API

假设 MyAppoly 允许用户将随机笔迹样本与特定个人匹配。你可能正在为法医调查、电子支付验证或历史研究构建这个工具。实现所有这些场景的一种方式是发布 MyAppoly API。发布 MyAppoly API 的优点包括：

- **规模化客户集成**：如果你想向不同的潜在合作伙伴提供数据或功能访问权限，为每个合作伙伴构建定制解决方案会耗费大量时间和资源。何不将接口标准化为 API，让合作伙伴在你设定的参数范围内访问所需内容？
- **他人对你的依赖**：如果你的 API 成为多家公司运营的关键部分，你就为公司创造了额外的价值来源。他人依赖你。想想那些建立在 Facebook 之上的第三方应用。如果 Facebook 消失，想象会有多少其他公司随之崩溃。其他公司对 Facebook 的依赖无疑支撑了其估值与成功。
- **多样化的分发方式**：API 可以将你已通过应用呈现的相同信息，提供给那些希望以不同方式消费的人们。通过提供这种替代访问方式，你正在扩大市场。
- **收入来源**：向他人收取 API 使用费可以成为可观的收入来源。
- **更多数据**：每次有人调用你的 API，你都可以记录该信息。这些数据可能帮助你识别行业趋势或新功能的机会。
- **品牌价值**：即使你选择免费提供 API，广泛使用所产生的价值也会以品牌和声誉的形式回馈给你。这有助于确立你在该领域的领导者地位及知识分享倡导者的形象。

你还必须考虑缺点：

- **资源消耗**：API 会带来额外的工程和维护挑战。每当你的数据源发生变化，你必须确保 API 正常工作。例如，如果将数据集扩展到包含音频文件，你必须相应更新 API。最后，试图将你的 API 集成到自己应用中的开发者可能需要客户支持以及解释可用功能的文档。缺乏支持的 API 会导致开发者沮丧并最终放弃。如果你打算发布 API，请预先警告，这可能会是一个资源密集的过程。
- **安全性**：API 允许用户访问你的数据。这个入口可能暴露漏洞，导致你不想共享的其他信息被不当访问。不过，API 的广泛流行表明这些风险是可避免或可管理的。
- **成本**：每次开发者使用你的 API（通过进行 API“调用”或“请求”），MyAppoly 都必须采取行动。谁来支付处理这些请求的费用？是你！在发布 API 之前，你需要一个计划来承担处理请求的费用。

你的 API 成功与否，将取决于开发者学习、使用和集成的难易程度。

### API 如何工作？

API 背后的技术细节可能很复杂，但其基本原理很简单。API 是软件与软件之间的接口。应用程序无需你参与即可相互通信。例如，如果 MyAppoly 需要显示天气，软件可以与气象 API 通信（“发起调用”）以获取最新天气预报，然后再展示给用户。

获取天气的一种方式是通过天气网站（直接访问）。或者，你也可以通过 API。你不是通过浏览器直接访问天气，而是编写代码，利用 API 获取所需信息。但你怎么知道该写什么代码？API 提供了*文档*，告诉你哪些是有效的请求以及如何准确编写，这类似于编程语言。因此，在阅读 API 的说明和规则后，你使用其`getWeather`函数来指定你想要天气数据。当你将该函数提供给 API 时，它会与服务器交互以检索你请求的信息。然后 API 以易于解析的格式（通常是 XML 或 JSON，详见本章“JavaScript 对象表示法”部分）将结果返回给你。根据 API 允许的操作，理论上你可以通过 API 获取所有所需信息，再也不必通过浏览器访问该网站。

从这个例子可以看出，API 是为软件开发者设计的，可定义为“一组例程（通常是函数）以及使用这些函数的随附协议，为软件开发提供构建模块”。它们允许用户通过安全通道连接到应用，然后使用代码运行函数以获取信息或借用功能。

两种更流行的 API 类型——*表述性状态转移*（REST）和*简单对象访问协议*（SOAP）——将在接下来的章节中描述并进行比较。



#### REST

`REST` 是一种由 Roy Thomas Fielding 开发的架构风格，旨在提高 Web 的可扩展性。每个请求包含两部分：端点（即 URL）和包含请求的消息。该消息由几个部分组成，包括开发者 ID 或“密钥”（如果需要的话，这有助于 API 跟踪谁在发起请求以及频率）、所需操作（例如 `getWeather`），以及提供更多请求信息的参数（例如，仅查询今天和昨天的 `getWeather`）。所有这些信息都编码在 URL 中，并通过 HTTP 的 `GET` 方法发送给 API。随后，API 解码请求，与服务器交互以完成所需操作，然后将响应返回给用户。

#### SOAP

`SOAP` 始于 1997 年微软的一项倡议，是另一种使用 HTTP 从远程服务器请求数据的方式。`REST` API 将请求的具体信息编码在 URL 中，而 `SOAP` 则将请求的详细信息放在一个 XML 文档中发送。构成消息的 XML 文档必须满足 *Web 服务描述语言*（`WSDL`）文件中概述的规范。在某种程度上，`SOAP` 就像把请求装进信封里发送（隐藏了请求的细节），而 `REST` 则像是把请求写在明信片上发送（所有人可见）。不过，两者都通过邮件（即 HTTP）进行传输。

#### 比较 REST 与 SOAP

`REST` 和 `SOAP` 在以下方面存在差异：

*   *开销*：由于 `REST` 请求限于一个 URL，而 `SOAP` 请求则由整个文档描述，因此后者往往体积更大，需要更多开销，并在消息的不同部分包含更多进一步定义请求的信息。
*   *透明度*：延续明信片与信封的类比，`REST` 的一切都是公开的，因此更容易被监控；而 `SOAP` 则只有地址（端点 URL）可见。
*   *开发时间*：`REST` API 通常比 `SOAP` API 开发得更快，这取决于你团队成员的程序员技能。
*   *灵活性*：由于 `SOAP` 使用 XML 文档作为消息，因此 `SOAP` 请求中可以包含比 `REST` 请求更多的信息，这使得 `SOAP` API 具有更高的灵活性。

### 身份验证

正如本章开头部分所讨论的，你可能希望跟踪谁在使用你的 API 以及他们在请求什么。你也可能希望与 API 用户进行通信，以确认数据的准确性和连接的安全性。身份验证的方法包括以下几种：

*   *开放 API（无身份验证）*：使用 API 没有任何障碍，代码可以更自由地分发，并且你无需管理请求（前提是你不在意追踪单个用户）。如果你只关心匿名的聚合数据，而不关心特定用户的行为或控制 API 的访问权限，那么开放 API 是一个有吸引力的选择。
*   *基于消息的身份验证*：可以将凭证（例如唯一的开发者密钥）作为消息的一部分包含在 API 请求中传递。或者，信息也可以通过传入请求的 HTTP 头部传递。
*   *SSL 端点*：该方法帮助客户端跟踪服务器。在收到服务器证书后，客户端可以检查它是否发生变化。如果发生变化，则信息很可能来自服务器以外的源头，因此不可信。这种身份验证方法可以防止攻击者冒充你期望的服务器。由于 `SSL` 端点方法无法帮助识别客户端，因此它需要与本文列出的其他方法之一结合使用。
*   *客户端证书*：你可以配置 API 来创建证书，并通过安全通道将其提供给客户端，以便客户端在每次发出请求时出示该证书进行身份验证。虽然客户端证书被认为是处理身份验证的强大方法，但这种身份验证形式可能会显著降低速度。

### JavaScript 对象表示法

除了 XML（第 4 章和第 5 章）之外，你可能会遇到的另一种格式化语言是 *JavaScript 对象表示法*（`JSON`），它使用一组可以嵌套的名称/值对。例如，一本书（对象）可以包含许多描述其作者、标题和出版年份的名称/值对。许多 API “返回”（以某种格式传递响应）`JSON` 而不是 XML。这些都是对相同信息进行结构化处理的不同方式。

## 库

*库* 是定义常用功能（如下拉菜单或动画弹出窗口）的代码集合。例如，你可以创建一个包含数学变量和函数的库。你可以共享你的库，这样任何其他想在程序中使用数学功能的人都可以导入你的共享库，从而节省大量时间。共享代码和库可以减少开发时间以及所需的开发人员数量。

另一方面，你对自己系统可靠性在多大程度上依赖于他人贡献的软件有多大信心？这里没有对错之分，但你的最终决策需要为你团队的程序员们做出良好的判断。



## 开源

与通过 API 和库传播信息相关的是*开源*项目的增长。*开源*的最佳解释可通过审视软件开发的历史来获得。

尽管难以想象，但曾有一段时间，所有软件开发都归研究人员所有，并在大学中开发；研究成果可以不受任何限制地共享。毕竟，所有研究都是为了公共利益。在 20 世纪 60 年代，IBM 等公司借鉴了这一传统；当它们推出首批大规模商用计算机时，其软件是免费提供的。随着技术的发展、竞争的加剧以及硬件价格的下降，公司开始将软件视为可以支撑其业务的替代收入来源。软件变成了商业化的专有财产，任何未经公司知晓的复制行为都属非法。

麻省理工学院的理查德·斯托尔曼对这种文化变迁感到不满。由于担心麻省理工学院会控制他的新项目及其分发，斯托尔曼离开了大学，继续开发他的 GNU 软件——一个完全由自由软件组成的计算机操作系统（例如，相当于免费版的 Windows 或 Mac OS）。随着斯托尔曼的开发，他对商业化的反对以及对平等获取的倡导启发了他人。1985 年，他创立了自由软件基金会（FSF）以支持 GNU 项目。FSF 于 1988 年颁布了《通用公共许可证》（GPL），旨在保护基于*著佐权*原则的自由使用和自由获取。与保护财产权（版权）不同，“著佐权保护的是复制、分发和修改产品的自由”。

GPL 的宣言挑战了专有软件的商业观念，而在 20 世纪 90 年代，对*自由*一词的误解也随之出现。FSF 中的“自由”指的是自由，而非价格。

根据 FSF 的定义，“如果程序的用户拥有以下四项基本自由，则该程序是自由软件”：^(⁶)

*   出于任何目的运行程序的自由（自由 0）。
*   研究程序如何工作并为其需求修改程序的自由（自由 1）。因此，用户必须能够访问源代码。
*   重新分发副本以便帮助邻居的自由（自由 2）。
*   改进程序并向公众发布改进版本，从而使整个社区受益的自由（自由 3）。同样，确保这项自由也需要能够访问源代码。

通过其公共教育努力——FSF 使用了诸如“言论自由，而非免费啤酒”这样的口号——FSF 试图纠正人们认为它反对商业软件的误解。

回顾第 3 章，构成程序的代码被称为*源代码*。为了能够被阅读、理解和修改，源代码必须对公众开放——因此有了*开源*这个术语。然而，源代码的可访问性是程序被视为*开源*的必要条件，但并非充分条件。任何人都必须能够不受限制地在自己的创作中使用该代码。成立于 1988 年的开源促进会（OSI）颁布了“开源定义”，内容如下：^(⁷)

*开源不仅仅意味着访问源代码。开源软件的分发条款必须符合以下标准：*

1.  *免费再分发*：许可证不得限制任何一方将软件作为包含来自多个不同来源程序的聚合软件分发的一部分进行销售或赠送。许可证不得对此类销售收取版税或其他费用。
2.  *源代码*：程序必须包含源代码，并且必须允许以源代码形式和编译形式分发。当某种形式的产品未随附源代码分发时，必须有一种广为人知的方式，以便以不超过合理的复制成本获取源代码，最好是免费通过互联网下载。源代码必须是程序员修改程序时首选的形式。禁止故意混淆源代码。
3.  *衍生作品*：许可证必须允许修改和衍生作品，并且必须允许在原始软件许可协议的相同条款下分发。
4.  *作者源代码的完整性*：许可证只有在允许随源代码一起分发允许在构建和编译时修改程序的“补丁文件”时，才能限制以修改后的形式分发源代码。许可证必须明确允许分发基于修改后的源代码构建的软件。许可证可以要求衍生作品使用与原始软件不同的名称或版本号。
5.  *不歧视个人或团体*：许可证不得歧视任何个人或群体。
6.  *不歧视特定领域*：许可证不得限制任何人在特定领域使用该程序。例如，它不得限制该程序用于商业用途或基因研究。
7.  *许可证的分发*：附属于该程序的权利必须适用于所有程序被重新分发的对象，无需这些对象执行额外的许可协议。
8.  *许可证不得特定于某个产品*：附属于程序的权利不得依赖于该程序是某个特定软件分发的一部分。如果该程序从该分发中提取出来，并按照程序许可协议的条款使用或分发，那么所有被重新分发给该程序的对象都应享有与原始软件分发所授予的相同的权利。
9.  *许可证不得限制其他软件*：许可证不得对与许可软件一起分发的其他软件施加限制。例如，许可证不得要求同一介质上分发的所有其他程序都必须是开源软件。
10. *许可证必须技术中立*：许可证的任何条款不得基于任何特定的技术或接口风格。

大约在这个时候，Red Hat 成立，这是一个致力于改进 Linux（一个开源计算机操作系统）并教育他人如何使用它的组织。它是第一家整个商业模式都专注于著佐权产品的公司。开源系统开始挑战包括微软在内的大型软件公司的地位。^(⁸)

自那以后，许多其他开源许可证被创建出来，例如网景公司的 Mozilla 公共许可证。如今，开源的不断发展体现在大约 50 种经 OSI 批准的特定开源许可证中，这些许可证大致分为以下两类：

1.  *学术许可证*：在这些许可证下，大学将其研究成果分发给公众，并允许其软件和源代码被使用、复制、修改和分发。伯克利软件分发（BSD）许可证是典型代表，体现了“不附带任何条件”的方式。所有在学术许可证下许可的代码都被添加到一个通用代码池中，可用于任何目的，包括创建商业软件。你可以从这个代码池中借用代码，而无需回馈任何内容。



## 互惠许可

根据这些许可，代码将被纳入开源软件库。任何人都可以出于任何目的使用该库中的代码，但如果你选择传播自己新创建的代码，则必须以相同的许可协议进行分发。换句话说，你可以利用这些代码来创作新作品，但必须将你的新作品贡献到代码库中以供他人使用。`GPL` 就是互惠许可的一个例子。

许多人担心开源代码的质量。一种评估标准包括可靠性、性能和总体拥有成本。其他用于评估质量的指标包括可移植性、灵活性和自由度。无论你选择哪种指标，关键在于，利用现有代码的诸多优势可能会被依赖他人代码和系统所带来的固有风险所抵消。尽管如此，一些开源项目已经达到了与商业软件相同的复杂度和质量标准。

## SDK

顺便提一下，你可能会在 `MyAppoly` 办公室听到 SDK（即软件开发工具包）这个术语，尤其是在团队讨论移动应用开发时（第 13 章）。为了方便开发人员为某个平台（例如驱动苹果 iPhone 的 iOS 软件）进行开发，平台提供商可能会提供一个 SDK。这个 SDK 可以下载，其中包含开发人员为该平台构建应用所需的一切，可能包括文档、第 3 章讨论的集成开发编辑器、API 及其他有用的库，以及相关工具（例如用于调试——查找错误——或跟踪性能）。目标是让事情变得简单，因此能够可靠利用的构建块越多越好。

## 结论

随着对 API 和其他利用现有代码方式的更深入理解，你的团队制定出了一个完整的开发计划。使用一些关键的 API 和共享库有助于加快进度，但团队计划逐步减少对其中一个库的使用，因为它无法提供 `MyAppoly` 所需的全部功能。由于其他一些贡献库和工具的性能差且不可靠，团队已将其排除在外。你必须在自主开发和外包之间取得平衡，既然已经做出了决定，你的团队就可以开始开发 `MyAppoly` 了。但他们将如何协作构建它呢？
