# 5. 数据库：模型

由于数据的价值，一些公司收集的信息本身就是一种资产。我曾在一家专门为本地企业提供数据的初创公司工作，主要负责收集本地企业（主要是餐馆）的菜单。通过建立一个包含餐馆出售的所有食品及其价格的数据库，我得以了解一些有趣的事实！旧金山的披萨平均价格是多少？我酒店方圆五英里内，哪些餐厅的菜单上有泡菜？没问题。收集独特的数据可能会让你回答以前无法回答的问题。

你需要熟悉的“典型”应用的最后一个组件是`数据库`，通常也称为`模型`。`MyAppoly` 的用户需要输入他们的信息才能注册你的服务。你必须将他们的数据存储在某处。从用户名和密码，到用户登录次数，随着你的网站越来越成功，你想要保存的信息量将呈指数级增长。本章将为你做好准备，以便你参与团队关于使用哪种类型数据库以及如何组织数据的讨论。虽然本章不讨论如何以编程方式在数据库中添加和更新数据，但它会回顾数据库通常是如何结构化以及它们之间的区别。

## 数据库系统

我们大多数人都熟悉某种记录保存系统。有些人保存收据是为了准备纳税。企业主可能会跟踪他们的销售额和支出，以确保达到目标。医生会保存所有病人的档案，通常按姓名字母顺序排列。数据库系统是文件柜的电子版本，而“请求”则是与文件柜的交互，包括添加、删除、更新或检索文件（或称`记录`）。

你可能会收集哪种类型的数据？通常，你会希望保存将来对你有某种价值的数据。这被称为`持久化数据`，因为它会在一天结束后或用户注销后被保存下来。由于数据和数据分析的力量能够解锁效率、洞察力和机遇，数据库对当今所有企业都至关重要。

### 数据库的四个组成部分

数据库由四个部分组成：数据、硬件、软件和用户。

#### 数据

数据是数据库的“必要条件”——即保存在数据库中的实际信息。除了数据之外，数据库还存储关于数据和数据库本身的元信息。例如，记录由多条信息组成，因此知道记录的哪一部分对应的是用户名（举个例子）是很有用的。这种`元数据`保存在`目录`中——以备你需要刷新记忆，了解你在收集什么以及它如何被存储。

#### 硬件

数据物理上存储在硬件的某个组件中——通常是辅助存储器，例如磁盘。存储硬件可按以下几种方式分类：主存储器、辅助存储器和三级存储器。

`主存储器`提供对数据的快速访问，因为计算机的中央处理单元（CPU）直接与之交互。CPU 执行计算机程序的指令，因此可以将其视为处理过程的大脑或程序的执行者。当计算机执行您请求的任务时，它首先访问主存储器以获取具体操作指令，然后 CPU 再执行。与主存储器相关的术语包括`寄存器`、`高速缓存`（也称为静态随机存取存储器或 SRAM）以及`动态随机存取存储器`（DRAM）或主存。这些不同部分关联着不同的任务，但它们都服务于同一个目的：使 CPU 正在使用的数据和程序保持就绪状态以便执行。我们说主存储器是易失性的，因为当机器关闭或断电后，其中的内容会丢失。然而，主存储器成本高昂，因此其规模往往有限。

相比之下，`辅助存储器`是非易失性的、成本更低，且不被 CPU 直接访问。由于数据在计算机关闭后仍能保留，并且我们通常希望数据的安全性不依赖于计算机的电源状态，因此辅助存储器作为我们的海量存储场所也就不足为奇了。CPU 无法直接访问辅助存储器中的内容；数据必须先复制到主存储器中才能执行，这一事实也凸显了为何访问辅助存储器的速度通常较慢。硬盘驱动器、闪存和软盘都是辅助存储器的例子。

`三级存储器`与辅助存储器类似，同样不被 CPU 直接访问。它用于海量数据存储，且速度远慢于辅助存储器。

区分这三类存储器的关键权衡因素是访问时间与费用，本章末尾的“优化”部分将对此进行探讨。

#### 软件

当用户与 `MyAppoly` 交互时，他们会执行一些操作，而您需要将这些操作保存到数据库中。一个`数据库管理系统`（DBMS）负责定义数据库，并在用户和应用程序之间对数据进行存储、操作和共享。

可以将 `DBMS` 视为文件管理的总管，负责管理所有 `MyAppoly` 访客的请求。当用户在 Facebook 上点击“接受好友”时，系统会创建一个请求并发送至数据库。`DBMS` 在将这些请求发送到数据库之前，会先进行接收和分析，随后这些请求被`解释`（转换为数据库能够理解的请求）并执行。代表 `DBMS` 实际访问数据库的代码被称为数据子语言；其中一种流行的是 `SQL`。

`DBMS` 提供了一种方法来控制`并发`（同时向数据库发出的多个请求）、`冗余`（同一信息在数据库中被多次存储）、`安全性`、`恢复`（防止某种数据库故障）以及`优化`（及时处理请求）——这些方面极大地提升了开发人员的价值。

#### 用户

您的最终用户是 `MyAppoly` 的用户，他们通过与应用程序交互，在后台生成对数据库的请求。当新用户注册时，系统会发出一个数据库请求，要求 `DBMS` 向数据库中添加一个新用户。

## 三层架构

您还会听到数据库系统被描述为一种由三部分组成的`架构`：物理层、逻辑层或概念层，以及外部层。物理层是数据存储的地方，逻辑层包含 `DBMS` 如何与应用程序交互，而外部层则包括用户与数据库的交互。

数据库系统的三个层次、三层或三种模式与我们之前对数据库的描述类似，但理解这些在数据库系统上下文中可能出现的术语是很有帮助的。现在也更容易解释数据库独立性原则了。`DBMS` 提供了一种抽象形式，使用户无需了解数据存储的细节即可与数据库交互。因此，任何一个层次的实现在不影响整个系统的情况下都可以更改。假设您的程序员将应用程序编码为以列表形式显示所有 `MyAppoly` 用户的姓名。而您希望所有用户显示在图表上。让程序员重写对数据库的请求来获取信息会很麻烦。

得益于数据独立性原则，您的程序员可以将列表更改为图表，这不会影响程序员与系统其他部分的交互方式。该更改仅影响可视化层，与您如何获取数据或数据如何存储无关。总之，系统将数据的管理与数据的实际使用分离开来，这具有多项优势。有人可能会说，请求经过中间人（`DBMS`）处理后到达数据库这一过程会减慢处理速度，但收益远大于延迟成本。

## 分类

对数据库管理系统进行分类的标准包括以下几点，后续小节将分别予以讨论：

*   `数据模型`：数据需要以准确且高效的方式存储，以描述真实世界。下一节将讨论不同类型的模型。

*   `站点数量`：`集中式`和`分布式`是您可能之前就遇到过的流行术语。它们与数据库的关系将在“集中式与分布式”一节中讨论。

*   `成本`：解决方案的成本范围很广。存在免费开源解决方案，例如`MySQL`。对于希望获得更可定制系统的大型企业，也提供商业解决方案。

### 数据模型

在数据库中有多种高效且有组织地存储数据的方式。以下各小节将讨论四种最常见的数据模型：关系模型、非关系模型、面向对象模型和对象关系模型。

#### 关系模型

1969 年，埃德加·F·科德提出了一种名为`关系模型`的模型，该模型此后一直成为事实上的标准。`关系`不过是表格的数学术语，因此仅凭这一点，我们就能确定关系模型使用表格来表示数据。

在关系模型（也称为实体-关系模型）中，任何存在的事物，如汽车、班级或商店，都是一个实体。每个实体都有属性，即表中的列：汽车有颜色，班级有名称，商店有位置。表中的每一行代表一个特定的实体（也可称为对象或记录）。在我们的用户表中，每一行描述一个`MyAppoly`的用户。这些列可以是名、姓、密码、地址和电子邮件地址等项。表通常有一个主键，即每一行的值都唯一的列，通常是为该实体分配的唯一 ID。`MyAppoly`表中的唯一用户 ID 能让我们引用单个客户而不会产生重叠。大多数网站要求用户名唯一，这意味着用户名可以作为主键，而不是用户 ID。

既然数据库能很好地为我们的实体及其关系建模，那么我们如何与数据库交互呢？通常，数据库及其特定表是通过使用 `DBMS` 及其数据子语言（用于与 `DBMS` 通信的语言）提供的特定操作符来修改的。与所有语言一样，子语言要求严格，需要以特定方式格式化请求，因此你必须非常清楚地说明你想要什么。例如，`结构化查询语言`（`SQL`）是由 IBM 开发的一种专有查询语言（数据子语言），它现在是事实上的国际标准，并受到大多数关系型系统的支持。在 `SQL` 中，这些操作符包括`INSERT`（向表中添加条目）、`DELETE`（从表中删除行）、`SELECT`（检索已存储在数据库中的信息）和`UPDATE`（修改现有行）。

有几个值得了解的命令可以实现更复杂的操作。一个例子是`JOIN`，它与`SELECT`配合使用。假设你有一个如上所述的用户表，以及一个名为 `pets` 的独立表，其中存储了所有用户的宠物数据。`pets` 表中的每一行代表一只宠物，列包括名称、主人、颜色和类型。在这个例子中，`pets` 表的所有者列应对应于用户表中的一个用户。如果我想回答以下问题：“所有将蟒蛇作为宠物的用户的地址是什么？”这个请求涉及访问 `pets` 表以检索所有拥有蟒蛇的主人，然后将你主人列表中的每个主人提供给用户表以获取他们的地址。通过使用`JOIN`操作，可以简化这个两步过程，该操作本质上是基于一个共享列将两个表合并。（在这个例子中，共享列是 `user` 和 `owner`。）这个例子说明，鉴于关系型系统的结构，请求可能会变得复杂，但存在相应的操作让开发者找到他们问题的答案。

# 数据模型与概念

刚才描述的查询语言和操作符是非过程性的，这意味着用户可以指定他们想要什么，但不一定指定 DBMS 应如何执行请求。我不确定你是否会对数据具体如何检索有强烈的看法，但从速度角度来看，这可能会很重要。

为了全面起见，让我们回顾几个其他概念和术语。构成特定任务的一系列请求称为一个*事务*——例如，注册一个用户及其宠物所需的所有请求可以定义为一个事务。存在一些事务规则，这些规则并非关系型系统所独有，但将在此简要讨论。首先，事务是*原子性*的，这意味着它们是全有或全无的——要么用户完全注册成功，要么数据库保持不变。因此，即使过程因任何原因中途失败，表仍然保持一致，这意味着没有不完整的行或部分更新的记录。其次，事务是*持久性*的，意味着它们会立即更改数据库，并且更改在事务执行完成后立即可用。事务在数据库中反映的任何延迟都会对网站的整体体验产生负面影响；想象一下，每次你接受一个新朋友，你的 Facebook 好友列表更新需要一周时间。第三，事务是*隔离性*的，意味着 DBMS 会将两个事务视为相互独立。设计一个符合所有这些约束的数据库很困难，但这些描述应该有助于你理解 DBMS 如何处理请求。

最后一个要提到的术语是*规范化*，它指的是消除数据库中冗余的过程。让我们回到用户和宠物表的例子。如果开发人员在宠物表中创建了一个名为“主人地址”的列会怎样？该信息不是已经保存在用户表中了吗？在这种情况下，地址列将是冗余的并浪费空间。虽然规范化可以帮助数据库用户节省内存，但它也可能需要更长的时间来获取查询结果。如果我经常提出之前关于所有拥有蟒蛇的人的地址的问题（那个我不得不使用`JOIN`的问题），我的立场可能会不同。`JOIN`操作可能代价高昂，因为 DBMS 必须合并两个表，然后找到信息，根据表的大小，这可能是一个成本高昂的过程。创建一个冗余列可能更简单、更经济。这类决策可以由*数据库管理员*（DBA）做出，他们精确地了解请求是如何执行的。

## 非关系模型

*非关系模型*，你可能已经猜到，不使用表格作为主要的数据结构。因此，这一类别涵盖了很多，包括网络型、层次型（想想家谱）和列表型。

有一个值得特别提及的术语是`NoSQL`。关系型系统适用于更复杂的数据，其中的查询会涉及实体之间的关系（例如，用户与其宠物之间的关系）。相比之下，`NoSQL`系统往往非常适合存储大量简单数据，例如键值对（`firstName: Vinay`）。对于这些简单的用例，`NoSQL`提供了出色的性能和可扩展性。如果你的团队认为如此严格的关系型结构并非必要，并且你正在处理大规模数据的存储和检索，而存储项之间的关系不那么重要，那么`NoSQL`数据库管理系统就非常有用，可以说更有效。开源`NoSQL`数据库，如 MongoDB 和 Cassandra，值得探索。

### 面向对象模型

*面向对象* *数据库*围绕着面向对象编程语言中的*对象*概念（第 3 章）。这些对象描述实体，每个对象包含一系列描述其自身的属性或特征，以及一组可在每个对象上执行的操作（例如，描述宠物主人的对象可能能够购买宠物）。与之前一样，每个对象必须具有唯一性，因此通常使用`Object ID`。你可以通过以下方式理解对象间的关系编码：描述宠物主人的对象可能存储了描述宠物详情的宠物对象的`Object ID`。因此，如果你想获取用户 X 的宠物详情，可以访问用户 X 的对象，获取对应的`pet ID`，然后访问宠物对象。这些对象可以分层排列，以赋予系统更多结构，并利用继承及其他与面向对象模型相关的特性。

面向对象模型功能强大，因为它们允许保留某些对象的复杂特性。此外，它们有助于将对象的结构与可应用于对象的操作分离开来。这些模型如何运作的细节留待更专业的技术著作阐述，但“关系模型”中讨论的许多术语也适用于此模型。例如，面向对象模型也有一种查询语言：*对象查询语言*（`OQL`）。

### 对象关系模型

面向对象的特性已融入关系型系统，形成了*对象关系模型*，融合了两种模型的优点。例如，在对象关系系统中，你可以定义自己的数据类型。

### XML

如第 3 章和第 4 章所述，`XML`是一种标记语言，可用于为文档赋予结构。因此，它可用于定义数据结构，也是 Web 上数据通信的主要方式。

### 集中式与分布式

客户端-服务器架构描述了最终用户与 DBMS 之间的关系。客户端包括所有与 DBMS 交互的应用程序，而 DBMS 则是处理和执行业务请求的服务器。

实际存储一切的计算机本质上可以是*集中式*或*分布式*。采用集中式时，所有请求都发往一个容纳所有数据的单一服务器。如果此服务器因任何原因宕机，依赖它的应用程序将无法工作，这使得该服务器成为单点故障。因此，随着通信和数据库技术的发展，组织意识到分布式系统能带来诸多好处。与其只用一个中央数据库服务器，何不使用多个可以相互通信的服务器呢？在分布式系统中，单个请求的不同部分可以在分布式数据库服务器网络中的不同机器上执行。尽管数据可能驻留在由软件通过网络管理的多个站点，但对应用程序的用户而言，数据库的运行方式如同集中式系统。回到我们的例子，`users`表和`pets`表在理论上可以存储在不同的服务器上。

典型的分布式系统具有若干特性，其中一些最重要的特性包括：本地自治（每个站点应相互独立）、无中心站点、位置独立（用户无需知道数据存储在哪里），以及几乎所有其他使其功能与集中式系统完全一致的属性。

从技术领域中*分布式*一词的流行程度可以看出，分布式处理已变得非常流行，且理由充分。其优势包括：

- *卓越的合理性*：想想典型的组织，数据往往已经呈分布式。无论是跨地理办事处分布，还是在内部按部门划分，数据库都有逻辑区分。因此，如果其他优势足够吸引人，为何不保留这种分布特性？这可以让每个团队独立管理自己的数据，而不必设法将所有数据合并到一个中央服务器中。例如，百事亚洲公司将其部分数据存储在亚洲可能是合理的。

- *更高的效率和性能*：直观上，数据在离请求发出站点最近的地方进行处理时效率最高。因此，数据应存储在访问最频繁的用户附近。分布式系统有助于实现整个组织数据的最有效分配。此外，当查询分布在多台机器上执行时，性能也能得到提升。

- *更高的可靠性*：由于信息存在于多台计算机上（也可创建多个副本），整个系统在任意时刻宕机的概率远低于集中式系统。

- *可调节的扩展性*：分布式系统是水平可扩展的，这意味着很容易向系统添加更多计算机。假设你的 MyAppoly 目前在美国使用五台计算机存储信息，添加第六台计算机比垂直扩展（例如，为特定计算机增加内存）容易得多。诸如 Amazon Web Services（第 2 章）之类的服务之所以如此受欢迎，是因为它们允许组织根据需求增减服务器。这种无缝的扩展和缩减方式使组织能够更有效地使用资源。如果只在偶尔的情况下（例如，网站有促销活动时）才用到那么大的容量，就没必要买下那么多容量。

这种系统的缺点较少，但确实存在。首先，由于数据可能驻留在多个站点，需要跨服务器整合数据的查询处理会耗费更多时间。其次，与集中式系统相比，`DBMS`提供的各种功能（安全性、并发管理等）在分布式系统中往往技术实现上更为复杂。

## 其他主题

其他数据库管理需求涉及并发、安全和优化，将在接下来的章节中依次讨论。

### 并发

你不希望多个数据库用户发出相互冲突的请求。如果一位 Facebook 好友在你给他发消息的同时将你屏蔽，Facebook 会如何处理？这涉及*并发*问题。

在数据库语境中，*并发访问*意味着多个用户可以同时访问数据库，或者多个事务可以同时被处理。由于 DBMS 支持并发，它们也需要能够控制在多个事务试图同时修改数据库时可能出现的潜在困境。

例如，Yelp 如何处理两位用户同时向 Yelp 上的一家餐厅添加推荐？知道 DBMS 能管理这种情况就够了，但若要了解更多细节，以下是一些并发问题：

- *丢失更新*：当两个事务试图更新同一个值时，其中一个更新可能会丢失。

- *未提交依赖*：一个事务可能访问到另一个事务已更新但尚未最终确定的值。

- *不一致分析*：当两个事务的目标相互冲突时，它们的执行步骤可能彼此不一致。

这些问题通常通过一种称为*锁定*的概念来解决，即特定对象或值被锁定，仅允许一个进程访问。锁定会在每个进程之间增加等待时间，以确保没有两个事务发生冲突或相互干扰。

### 安全性

数据库安全漏洞正日益频繁地发生。任何网站的用户都需要一定程度的保护，而公司必须确保其数据的安全。

`DBMS`通过以下两种方式保护数据，防止未经授权的访问和不恰当的修改（从而维护数据的*完整性*）：

-   *自主控制*：在这种模型中，每个用户都被授予对数据库中不同对象的适当访问权限。自主控制通常是两种控制类型中更为灵活的一种。

-   *强制控制*：在强制控制下，数据库中的每个对象都被分配一个安全级别，每个用户也被赋予一个许可级别。用户只能访问其许可级别内的数据对象集合。

本质上，`DBMS`可以相应地标记用户和数据，以确保任何未经授权的人都无法访问或操纵私有数据。作为额外的检查，`DBMS`会记录事务、事务时间以及发起请求的用户。这些日志可用于追踪可疑活动（参见第 12 章）。

# 数据库与大数据技术概述

可能会出现一些通过此处描述的控制系统似乎无法立即解决的复杂情况，尽管 `DBA` 可以使用 `DBMS` 和其他工具来防范它们。一个例子涉及到信息从“有”到“无”的流动。例如，可能会出现这样一种情况：一个拥有更高许可级别的用户以某种方式修改数据，从而使一个较低许可级别的用户能够访问该数据。这种信息流动必须受到控制。

另一个问题与 `干扰` 有关，这是统计数据库面临的一个难题。`MyAppoly` 可能使用统计数据库，这些数据库不会向用户提供关于其他用户的特定信息，但会提供关于一个用户群体的汇总统计数据。那些不愿意让他人知道其薪资、年龄或其他个人指标具体信息的个人用户，如果这些信息仅以统计数据的形式匿名访问时才可见，他们可能会更愿意分享信息。一个问题是，特定的筛选操作可能允许某人推断出关于特定用户的信息，这是不应该被允许的。例如，如果你请求剑桥所有蟒蛇宠物主人的平均薪资，但只有一个人符合这个描述，那么请求返回的平均薪资将是一个人的薪资。`DBMS` 应该防止这种情况发生。

`数据加密` 是一种用于保护存储在互联网上或通过互联网传输的数据的方法（第 12 章）。重要或敏感的信息，例如社会安全号码或信用卡信息，应始终通过限制访问和加密信息两种方式进行保护。

总而言之，存在 `DBMS` 和其他工具来保护数据。没有完美的解决方案，这就是安全存在风险的原因。安全系统的目标是通过使侵入系统的成本大于潜在收益来阻止入侵。

## 优化

有多种方法可以优化数据库系统，以占用更少的空间并更快地返回或更新信息。一种方法是设计更高效的查询。例如，如果你想了解有多少人居住在加利福尼亚州并拥有蟒蛇，那么在几千名蟒蛇主人中搜索加利福尼亚州居民，比在数百万加利福尼亚州居民中查找蟒蛇主人要快得多。

数据库可以优化的另一个领域（尤其是在空间方面）是冗余。当信息之间的冗余被消除时，数据被称为是集成的。例如，将患者的姓名、保险计划和地址写在文件中的每一张纸上是很浪费的。集成数据意味着这种重复被消除，并且在关系型数据库的情况下仅保存在一个表中。

除了大多数其他考虑因素之外，数据库设计必须智能化。它应该反映出你需要最快访问或最频繁更新的内容。否则，无论查询编写得多么好，或者使用了什么工具，有缺陷的数据库设计都将不是最优的，并会导致时间、金钱和空间的浪费。你应该只存储你需要的信息，并且应该以逻辑方式组织它，使相关信息保持在一起。你存储信息的方式应由你预期之后如何使用它来决定。

## 大数据

`大数据` 与普通数据有何不同？其实，即便在计算机出现之前，各类组织也一直在积累信息，但如今可收集和存储的数据量已呈爆炸式增长。当前收集的数据规模已远超传统处理方法的承载能力。关系型数据库因成本高昂且限制过多正被边缘化，更具扩展性和灵活性的非关系型数据模型逐渐崭露头角。为了让您直观感受其规模与增长，据估计，2010 年全球产生了 1.2 皆字节（1.2 × 10²¹ 字节）的数据。^(⁴) 作为对比，地球上沙子的数量估计在 `10²⁰` 到 `10²⁴` 粒之间。想象一下要筛遍所有沙粒的场景！假设我们的数据量每两年翻一番，那将需要建造大量的数据中心。

在讨论如何着手研究如此海量数据之前，先了解几个描述数据的术语。第一个是 `数据量`，这也是“大数据”一词最直观的体现。信息量庞大是首要难题，这促使工程师思考如何利用分布式系统来应对。第二个是 `数据速度`，指新数据产生的速率。例如，Facebook 的数据生成速度可能远高于 `MyAppoly`。面对每天海量的交互，Facebook 必须做出重要决策：哪些数据该保留，哪些该丢弃？在线购物网站也面临类似困境。每当用户点击商品或输入搜索词，企业都必须决定是否保存该信息。然而，保存更多信息可能会影响将数据转化为洞察的速度。如果零售商因数据处理延迟而无法快速为用户定制个性化网页体验，那么更敏捷的竞争对手很可能会胜出。最后是 `数据多样性`。若数据来源多样、形式各异，则会带来一系列更为复杂的处理难题。

现在，您可以去找您的数据团队，告诉他们数据多样性增加了存储难度，当前的数据速度已超出有限的服务容量。用更通俗的话说，您可能只需一句：“我们需要更多预算！”

假设您拥有海量且高度多样化的数据。单纯靠肉眼观察得出有效信息的可能性微乎其微，尤其当数据没有明显模式时。在“大数据”领域，您可能会遇到一个词——`Hadoop`，这是一个软件框架，允许组织对数据进行测试以寻求答案。如前面章节所述，分布式架构是存储和处理海量信息的关键。Hadoop 通过将数据分散到一组并行工作的强大处理器上来帮助组织理解数据。Hadoop 使用的主要方法称为 `MapReduce`，包含两个部分：映射（`map`）和归约（`reduce`）。假设您想从数据集中解决某个问题，工程师编写了一个理论上可得出正确答案的函数。`映射` 会将任务拆分为多个部分，并分发到多台机器上。此阶段完成后，`归约` 会将每台机器的结果合并为单个任务，从而完成分析。任何单台机器都无法及时完成如此庞大的工作量，因此 Hadoop 的分而治之策略是一个极其强大的工具。其他工具，如 `Spark`，也正日益流行。
