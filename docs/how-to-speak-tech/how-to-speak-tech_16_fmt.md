# 13. 移动基础

特别感谢 **Ashi Agrawal** 和 **Cheenar Banerjee** 为本章做出的贡献。

到目前为止，我们都假设 MyAppoly 仅作为一个网络应用程序存在，但现实是，许多产品——比如 Snapchat 或 Lyft——部分或完全以移动形式存在。这些公司优化了其应用程序在你手机上的体验。手机是一种随身携带的小型设备，配备了一套与传统计算机不同的工具。我们之前讨论的许多结构仍然相关，但一个成功的移动应用程序所做的不仅仅是复刻桌面体验：它是专门为移动设备构建的。那么，让我们深入探究移动开发的复杂性吧！

## 简要介绍

自 20 世纪 70 年代手机发明以来，手持计算机的能力迅速增长。黑莓设备在 21 世纪初因其超越短信和通话的能力（包括对电子邮件的关注）而声名鹊起。随后，随着智能手机的出现，用户能做的事情呈爆炸式增长，远不止拨打电话。现在，我们通过这些极其便利的设备追踪健康、设置闹钟、呼叫拼车服务。本章重点讨论智能手机，但移动设备也包括手持计算机。

移动应用构成了一个蓬勃发展的市场。2018 年，全球手机用户数量突破了 50 亿大关。^(²⁴) 在网站方面，移动设备带来的流量超过了桌面设备，^(²⁵) 预计到 2020 年，移动应用每年将带来近 2000 亿美元的收入。^(²⁶) 这令人兴奋，但究竟什么是移动应用？它是特意设计并编写、在移动设备上运行的程序。正如我们将看到的，移动应用可以打开新的机遇之门，但也带来了新的考量因素和限制条件。

## 为何要为移动平台开发

在深入探讨*如何*开发移动应用之前，你需要理解*为何*以及*何时*开发移动应用。在某些情况下，这是显而易见的——例如，拼车和地图应用具有明确的移动使用场景，这对成功至关重要。对于其他产品来说，情况并非如此非黑即白，但在产品路线图中考虑移动端通常是合理的，因为它可以使功能和用户群多样化并得到增强。以 MyAppoly 为例，你的团队决定需要单独的移动端存在来吸引新用户。

虽然 MyAppoly 首先构建了一个桌面网络应用，但有些应用则默认将移动端特有的功能和限制作为设计基准。这个过程被称为**移动优先开发**，它能带来更好的移动用户体验，以及更简洁、更极简的桌面设计。移动端设计在屏幕上容纳更少的元素，这很容易转化到桌面端；但从桌面端转向移动端意味着设计者必须思考要移除什么。

## 移动应用 vs. 桌面应用

移动应用与我们一直在讨论的网络应用非常相似。与传统网络应用一样，移动应用也有前端和后端。两者也都使用 API 和其他外部资源。在本章中，我们将传统网络应用称为**桌面网络应用**。也有一些可以下载的桌面应用，比如文字处理器或电影剪辑软件，但本文主要比较移动应用与桌面网络应用。

为移动设备开发和为桌面设备开发之间存在显著差异。让我们概述这些差异，以理解为什么需要创建单独的移动端。这两个平台主要有四个方面的差异：尺寸、交互方式、功能特性及便携性。让我们逐一深入探讨。

-   **尺寸**：移动设备屏幕比桌面屏幕小得多，这限制了每页的内容量。移动应用的用户界面必须相应调整。例如，许多移动应用采用可折叠菜单来节省屏幕空间，而桌面网络应用则显示大型菜单栏以展示所有选项。

-   **交互方式**：我们与移动设备的交互方式也与桌面设备不同。我们使用鼠标或触控板在桌面屏幕上导航，并使用单独的物理键盘打字，而现代智能手机我们则使用触摸操作。

-   **功能特性**：移动设备配备了一套与传统笔记本电脑不同的本地或内置功能。这通常包括摄像头、定位服务、蓝牙和推送通知系统。因此，我们可以为移动应用创建一套完全不同的功能，例如，Instagram 最初在移动设备上推出，因为大多数人主要使用手机拍照。

-   **便携性**：便携性意味着人们会随身携带并在任何地方使用他们的智能手机。因此：(a) 内容的呈现需要简洁，(b) 存在更多实时用例，以及 (c) 蜂窝数据与宽带互联网不同。让我们进一步详细探讨这些点。人们通常会在短时间内浏览手机，因此用户交互需要快捷。菜单层级在桌面网络应用中能提供更多选择，但对于时间紧张的人并不实用。由于人们会随时查看手机，移动应用可以专注于实时操作，比如拼车。最后，应用通常通过蜂窝数据访问互联网，这可能比 Wi-Fi 或以太网更慢且更不可靠。因此，移动应用可能需要针对速度进行优化。由于有众多移动应用争夺用户的时间，用户可能会在等待一个缓慢的应用时转而使用其他应用。

由于这些差异，我们在创建移动内容时，必须批判性地思考移动开发所带来的限制，以及其拓展出的可能性和机遇。

## 移动应用的类型

主要有三种类型的移动应用：**网络应用**、**原生应用**和**混合应用**。这三种都很常见，而最适合开发的应用类型取决于产品本身。本节将讨论每种类型的技术基础及其向用户呈现的方式。

### 网页应用

移动网页应用，即用户通过 Safari 或 Chrome 等浏览器打开 URL 来访问的网页应用，与桌面网页应用最为相似。它们通常有一个更熟悉的称呼：移动网站。对于许多产品而言，这类应用只是使用不同的前端封装层来调用与桌面网页应用相同的后端。其他产品则采用一个响应式网站来同时适配桌面和移动设备。响应式网站会根据设备屏幕尺寸（可能是平板电脑或旋转后的移动设备）而变化。屏幕上的元素会自动缩放、隐藏或移动，以在不同设备上提供良好的用户体验。

尽管移动网站通常可以相对轻松地在桌面网站基础上进行开发，但它们运行速度相对较慢，因为它们在浏览器内运行，而不是直接在设备本身上运行。此外，它们对原生功能的访问权限有限，而这些功能往往正是移动应用强大之所在。因此，许多公司开始开发独立的移动应用。

### 原生应用

原生应用是为直接在手机操作系统上运行而编写的应用程序。两种最流行的操作系统是 Android 和 iOS，分别由谷歌和苹果公司开发。虽然部分手机运行基于 Windows 或 Linux 的操作系统，但绝大多数手机运行的是 Android 或 iOS。原生应用通常通过应用商店下载，并在手机屏幕上显示为图标。由于原生应用直接在手机上运行，它们无需使用浏览器作为中介，因此运行速度比移动网页应用更快。

开发者编写原生应用的一个主要原因是易于利用额外功能，包括摄像头和 GPS。与外部后端或 API 不同，这些功能可以在离线状态下访问，从而使应用具备离线能力。原生应用还可以使用本地设备存储来保存一个在应用多次使用间持续存在的离线数据库。这类应用会跟踪并保存用户交互，在提供像本地存储的照片或笔记等内容时无需网络服务——想想相册应用或音乐播放器。

此外，这个本地数据库在提供个性化内容方面也很有用。虽然桌面网页应用可以存储信息用于个性化，但它们通常使用用户账户（例如，将你所有的历史购买记录关联到一个奖励会员账户）。由于人们会使用多个浏览器或电脑，但通常只使用一部手机，因此移动应用的用户账户通常仅代表在该特定手机上发生的交互集合。结果，许多移动应用可以移除强制登录，而这往往是新用户使用的障碍。

关于原生应用的最后一点是，它们比网页应用拥有更多内置的安全防范措施。移动操作系统会为独立应用提供额外的安全措施，而这些措施无法给予移动网站。此外，应用必须通过审核流程才能有资格在应用商店中提供下载，而移动网站则没有这样的验证系统。^(²⁷) 然而，原生移动应用也为攻击者提供了更有价值的目标，因为它们比移动网站能访问更多功能。无论是移动应用还是移动网页应用，都存在安全漏洞的风险，因此无论你选择哪种方式，保持警惕都是有益的。

### 混合应用

移动应用的最后一类是混合应用，它结合了原生应用和网页应用的特性。与移动网站类似，混合应用也通过网页浏览器运行，不过这里的浏览器是通过 `web view` 内嵌到应用中的。因此，混合应用的速度不如原生应用。然而，它们具备一些原生优势，例如可以访问摄像头和 GPS 等设备特定功能。此外，混合应用从应用商店下载，并在手机屏幕上显示为独立的图标。一些混合应用是使用桌面网页技术编写的，这意味着如果已有桌面网页应用，编写起来会更容易。

虽然混合应用可以利用原生技术且更容易编写，但它们也带来了一系列不同的缺点。使用独立的 `web view` 速度较慢，且无法访问所有设备功能。此外，由于这些 `web view` 使用网页技术，它们的设计通常不符合设备的设计规范。即使 `web view` 遵守了这些规范，它们也可能难以使用。公司常常在开发周期早期创建混合应用，以便快速搭建一个轻量级应用，然后再长期转向原生应用。对于拥有网页开发经验但缺乏特定移动平台专长的团队，或者对于可以牺牲速度的简单应用来说，混合应用也是受欢迎的选择。

既然我们已经讨论了网页应用、原生应用和混合应用之间的高层差异，接下来我们将讨论独立应用（原生应用和混合应用）的开发，因为它们使用的技术与桌面应用不同。

## 独立应用开发

独立应用是指通过其自身图标而非网页浏览器来访问的应用。这类应用可以专门为它们所运行的操作系统编写，也可以更通用地适用于所有智能手机。本节将概述每种方法及其相对的优缺点。

### Android 与 iOS

如前所述，原生移动应用直接在手机操作系统上运行。同时为 Android 和 iOS 进行开发是一项繁重的任务，因此许多公司会先集中精力构建一个平台。选择聚焦哪个平台可能颇具挑战性，所以下面我们将概述关键差异。Android 和 iOS 主要在三个方面有所不同：用户基础、开发流程和应用部署。

# 对于大多数产品而言

选择平台的首要考虑因素是用户群体。虽然 iOS 在西方消费者中占据主导地位，但 Android 在全球拥有更多用户。凭借其高昂的产品定价和品牌形象，iOS 吸引了那些在应用和应用内购买上花费更多的消费者。

当然，从技术层面来看，两者的开发也截然不同。Android 应用使用 `Java` 或 `Kotlin`，在 `Android Studio` IDE 中开发；而 iOS 应用则使用 Apple 创建的编程语言 `Swift`，在 `XCode` IDE 中开发。`Java` 享有广泛普及度，而 `Kotlin` 和 `Swift` 则是相对较新的成员，使用范围更有限。你的团队成员可能更有可能已经熟悉 `Java`。此外，`XCode` 仅原生运行于 Mac 设备上，这意味着开发过程会受到设备类型的限制；而 `Android Studio` 则可在所有类型的计算机上运行。由于 Apple 的政策，iOS 应用开发受到更多限制。另一方面，Android 是开源的，开发者可以查看源代码以更深入地理解该平台。

由于运行着不同设备和操作系统版本，Android 应用的开发时间更长。运行 iOS 的设备相对较少，且全部由 Apple 制造，因此它们之间的差异极小。相比之下，Android 设备由超过 1000 家不同公司生产。^(²⁸) 这种差异意味着开发者在创建 Android 应用时，必须考虑极为广泛的屏幕尺寸和设备规格。由于 Google 并非生产所有 Android 设备，它无法强制用户和设备制造商向消费者推送最新的操作系统。更新操作系统对设备制造商来说可能是一个麻烦，因为他们必须确保新系统能与其手机配置良好兼容。因此，他们往往不会向消费者推送最新版本，导致移动设备碎片化：Android 用户分散在不同的操作系统版本上。Android 开发者因此必须确保他们的应用能在多个操作系统版本上良好运行。正如我们在第 12 章中讨论的，过时的软件也可能导致安全风险增加。许多黑客利用 Android 设备碎片化，将恶意代码瞄准 Android 设备。

最后，Android 和 iOS 在将应用部署到各自的应用商店方面也存在差异。虽然两者不发布收到的应用提交数量统计，但据传闻，Android 似乎比 iOS 接受了更高比例的应用进入其应用商店。因此，应用更有可能被 Apple App Store 拒绝，而不是 Android Play Store。

Android 和 iOS 各有优缺点。在决定重点开发哪个平台时，产品通常会最优先考虑用户基础和开发便利性。如果你仍然无法选择其一，或者希望同时向两个平台发布，那么跨平台开发或许是合适的路径。

### 跨平台开发

尽管真正的原生应用能提供最佳性能，但为 Android 和 iOS 编写和维护它们需要相当多的开发投入。不仅每个平台需要不同的代码库，而且应用的每次更改都需要单独的更新和测试。因此，跨平台解决方案越来越受欢迎。跨平台移动开发是指开发者编写单个应用以在多个移动操作系统上运行的过程。现有多个框架支持跨平台移动开发，其中许多允许开发者完全使用 JavaScript 和其他 Web 技术进行编码。这些框架可用于创建原生应用或混合 Web 应用。

原生移动应用是使用框架编写的，这些框架为开发者提供了通用组件，这些组件会在每个设备上被转换为原生组件。流行的工具包括 `React Native`、`Flutter` 和 `Xamarin`。这三者在将平台无关的代码转换为原生代码的方式上存在差异，但最终结果都是移动应用的运行速度几乎与完全原生应用一样快。根据所需功能的不同，这些应用可能仍然需要特定于平台的代码。然而，大部分代码库保持不变。

混合跨平台移动框架包括 `Ionic`、`Apache Cordova` 和 `Onsen UI`。请记住，混合应用结合了桌面 Web 应用的易用性和原生移动应用的功能。与原生移动应用的框架类似，这些框架将平台无关的代码转换为混合代码。此外，这些框架使开发者能够访问原生功能，如前所述。

### 原生开发 vs. 跨平台开发

对于许多产品而言，跨平台开发因为其在三个方面（开发效率、开发者可及性和用户覆盖度）的众多优势而具有意义。

原生开发和跨平台开发之间最显著的区别在于整个开发周期中效率的极大提升。由于开发者只需编写和维护一个代码库，发布新更新的速度要快得多。Web 技术的使用也能带来更快的开发速度。原生代码在运行前需要编译，而 Web 代码可以在更改后立即刷新（称为`热重载`）。尽管编译时间从几秒到几十分钟不等，但这些延迟会随着时间的推移而累积。

Web 技术的使用也使更多开发者能够进行跨平台开发。由于诸如 JavaScript 之类的基础 Web 技术相对广为人知，新开发者可以更快地熟悉项目。此外，跨平台解决方案消除了公司为每个代码库分别聘请 iOS 和 Android 专家的需要。

最后，跨平台开发是推动用户采纳的绝佳工具。通过采用跨平台开发流程，你可以同时向 Android 和 iOS 用户推出应用，而不必在开始时只专注于其中一个平台。

跨平台开发也有其缺点，许多知名公司（如 Facebook 和 Airbnb）已经弃用了它。它可以加快开发周期，但移动应用本身的速度会受到影响。设备需要将跨平台代码转换为原生代码，这会消耗额外时间。对于需要快速运行的、对时间敏感的应用来说，这可能会破坏用户体验。此外，通过跨平台开发的应用无法充分利用原生代码结构。虽然这些框架涵盖了每个平台的大部分工具，但它们无法捕捉到每个平台的所有细微差别。因此，更复杂的产品仍然需要相当大量的特定于平台的代码。最终，这可能会感觉像是在支持三个平台而不是两个，从而削弱了跨平台开发所宣称的快速迭代速度。最后，由于跨平台解决方案仍然相对年轻，它们在发展成成熟框架的过程中，更有可能给开发者带来充满错误的体验。跨平台开发可以很好地服务于一个初出茅庐的产品，但它绝不是解决移动开发难题的万能药。

## 结论

最终，何时专注于桌面端、何时专注于移动端，取决于你的产品路线图。许多产品希望快速上线，因此采用跨平台方案来创建混合应用；而有些产品则专注于优化用户体验，从而开发完全原生的应用。对于其他产品来说，一个移动网站就已足够。选择哪条路取决于你的资源投入和优先级。虽然为用户创造有意义的移动体验需要额外的投入，但它能够推动用户增长并提升满意度。
