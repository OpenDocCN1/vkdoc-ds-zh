# 8. 软件开发：过程

2011 年，在花了三年时间就组织资源和设计流程方面为创业者提供建议后，埃里克·莱斯在他的著作《精益创业》中阐述了他的方法论，该书的出版引发了精益创业运动。其哲学阐述了一种持续且以反馈为导向的产品开发方法，本章将围绕此展开。

你们公司的首席技术官表示，`MyAppoly` 必须有一个定义明确的流程来开发产品。你应该致力于每个月发布一个新功能吗？应该有人在向团队展示新功能之前先构建并测试它吗？软件开发的流程应该是什么样的，如何管理它？本章不直接涉及 Web 应用的技术层面，但任何软件开发流程都必须考虑到软件生产的复杂性和不可预测性。对软件开发团队如何运作有一个高层次的理解将使你成为一名更好的管理者。你的团队向你介绍了他们为软件开发流程（即构建产品的方式）所做的设计。没有商定好的流程，开发就会变得混乱并以失败告终。幸运的是，你的工程师们对此颇有见地。

## 瀑布模型

瀑布开发模型由一系列顺序执行的、不同的阶段组成。假设你正在市场上寻找新房子。恭喜你！你找不到任何满意的房子，所以决定自己建造一栋。

首先，你与建筑师会面，确定你的时间表和需求。这些需求包括所用材料、卧室和浴室的数量等细节。在最终确定需求后，你与建筑师一起制定蓝图。接下来，你召集一个施工队，破土动工建造房子。总承包商告诉你十个月后回来，届时整栋房子将建好。完工后，你去查看房产并参观一番。从某种意义上说，你是在对其进行测试，以确保它按照规格建造完成。假设墙壁上没有大洞，楼梯也没有缺失，那么你就有望搬进新房，并邀请我参加你的乔迁派对。此开发过程遵循了瀑布模型的五个阶段：需求、设计、实施、验证和维护。

在这个模型中，输入和输出都有明确定义，而回溯到更早的阶段代价极其高昂。例如，如果在建筑的**实施**阶段你想改变房子的布局，想象一下拆除、重新设计然后重新实施项目所需的成本。因此，瀑布模型建议在进入下一阶段之前，必须确认整个项目的每一个细节。

## 更合适的方法

如果你接触过软件开发，你就会知道，从一开始就了解整个项目的每个细节是绝无可能的。谁知道几个月后会出现什么新技术呢？也许我们会想用它。如果代码的某些方面不能像我们预期的那样正确工作怎么办？我们可能不得不采用不同的方法进行工程处理。如果我们发现最初的页面布局太过混乱怎么办？所有这些情况都会经常发生，因此，长期且顺序执行的流程不一定适用于软件。此外，与房屋建设不同，软件有更多进行快速迭代的空间。软件开发通常不需要像房屋建造那样大的资本投入。因此，支持瀑布模型的那些特性并不适用于软件。



### 迭代与增量开发

20 世纪 60 年代，一种被称为*迭代与增量开发*的演化模型问世，并最终被众多软件开发人员采纳。它将长期期的瀑布模型分解为多个名为迭代的小型项目。例如，我们可以将`MyAppoly`的构建拆解为其各项功能的开发，包括转账、上传照片以及将数据导出至电子表格。这些迭代共同构成了整个项目，但每一次迭代都是最终目标的一个完整、独立的方面。从工程角度看，导出到电子表格的功能应与照片上传功能相互独立。每一次增量迭代都会为现有产品增添新内容，而“优化”迭代则会增强原有功能。

在迭代与增量开发的总框架下，许多开发理念倾向于建议一次迭代的周期在一到六周之间。这些迭代设有截止日期，这种做法被称为*时间盒*。1955 年，西里尔·帕金森阐述了他同名的定律，即“工作会膨胀，以便填满完成它所可用的时间”。^(¹⁰) 根据帕金森定律，如果你有一周时间去做一件你深知只需两天就能完成的事，整个迭代仍将耗费一周，因为你将会效率低下。`Timeboxing`旨在防止这种拖延。`Timeboxing`也能防止工作范围扩大。假设某项功能的时间盒定为一周，但最终发现其技术复杂性更高。通过将花在此功能上的时间限制在一周内，我们可以在时间盒结束时重新评估，并仅在其属于优先事项时才决定完成它。

为了适应软件开发固有的不可预测性，快速迭代是必要的。你可以对单个方面进行多次迭代，因此这种开发模式不像瀑布模型那样严格按顺序进行。如果你将这一流程应用于房屋建造，一次迭代可能只包含一间卧室。后续的迭代可以添加不同的卧室，甚至根据前几次迭代的反馈重新改造某一特定卧室。

IID 流程的一个关注点是优先级排序。如果某人将一个大项目分解为多个迭代，那么应该先处理哪些迭代呢？IID 流程有两种优先级排序方法：风险驱动和客户驱动。风险驱动方法建议先处理项目中最具风险的部分。这些迭代可能包含应用中最核心的部分，或者最复杂、最可能失败的部分。通过优先构建这些部分，你可以更有信心地认为项目是可行的，并能按预期推进。客户驱动方法，顾名思义，认为客户的反馈和需求应影响优先级的排序。这种基于反馈的决策制定在本质上被认为是*进化式的*和*适应性的*，因为它提供了开发者所珍视的灵活性，以替代瀑布模型的僵化。这些优先级排序策略并非相互排斥，但对于在团队内部构建讨论框架而言非常有用。

*交付*与*迭代*之间存在区别：并非每次迭代都必须交付（即让客户可用）。例如，你可能希望在发布新版本前先构建好几个功能。话虽如此，来自交付的反馈可以为未来的迭代和交付提供信息，因此，定期向客户发布迭代版本在战略上是有利的。

### 敏捷开发

如今，许多公司已转向*敏捷*方法论。敏捷开发，与前面提到的 IID 一样，是一种组织和管理理念。有人认为它是 IID 的一种类型，而另一些人则认为它借鉴了 IID，但对其进行了显著扩展。无论你持何种立场，从行业巨头到新兴的 Web 初创公司，几乎每个人都希望宣称自己拥有*敏捷开发流程*。

敏捷开发展现出许多与 IID 相同的特性。产品待办事项列表包含了所有尚未完成的事项，并根据某种优先级排序方法进行组织。团队每次处理几个迭代，一旦迭代完成就会立即发布给用户以获取反馈，这比大多数 IID 创造了更多的客户与开发者之间的协作。这些反馈会为产品待办事项列表添加新条目并重新排列优先级。*敏捷*并非指团队流程速度的提升，而是指描述构建产品方法论的核心理念。它包含四个核心原则：

*   个体和互动高于流程和工具
*   可工作的软件高于详尽的文档
*   客户协作高于合同谈判
*   响应变化高于遵循计划

敏捷开发强调团队动力和整体工作环境。我不去罗列特点，而是根据我在一家初创公司对敏捷文化的亲身经历来描述它。敏捷开发提倡团队协作和开放空间，可能更倾向于开放式办公布局而非格子间，以激发创造力并消除僵化。白板随处可见，以便自我管理的团队能够勾勒想法、交流思路，并将其拍照留存以供将来使用。这些头脑风暴会议力求简单，因为敏捷开发流程鼓励所有方面的简约。与其使用复杂的幻灯片和电子表格来阐述观点，不如随手记下、拍照并发送出去。

这些公司的特点是拥有自我管理的团队，权威从管理者转移到了团队本身。这些团队为下一次迭代集思广益，自行分配任务，分组攻克难题，重新召集以检查进度，并相互问责。旧式的管理观念认为人们不喜欢工作、逃避责任，只能通过负面激励来驱动。敏捷开发从根本上不同意这种观点，它根植于更自然的管理理论，该理论认为人们在团队中会感到被赋权，乐于攻克难题，并享受工作。合适的环境会激励团队提高生产力并交付更好的产品。项目经理不是发号施令必须做什么，而是提供资源、维护愿景、清除障碍，并推广有利于团队采纳敏捷文化的原则。

## 优势

敏捷开发的优势显而易见。快速迭代使团队能够管理复杂性并完善协同工作的方式，从而提高效率。逐步增加功能并重新审视旧功能的能力降低了整体风险，并能更快地向客户交付产品版本。客户喜欢持续改进的产品，公司可以利用快速且持续的反馈来指导产品开发，进而改善用户体验。通过频繁交付变更，你的团队会感到被赋权。他们的认同会带来更高的生产力，最终，企业和客户都将受益。由于开发过程为产品带来了生产力和质量上的提升，敏捷开发正迅速普及。



## 发布管理

迭代版本是如何交付给客户的？向公众发布或*推送*代码的流程必须经过深思熟虑，以最大限度降低出现缺陷或错误更新的风险。*交付*和*推送*代码含义相同，即让代码“上线”供客户使用。主要涉及以下三种环境或服务器。

首先是*开发环境*，所有编码和测试都在此进行。新功能部署在独立的服务器上，公众无法访问。因此，任何错误都仅限于公司内部，最坏情况也仅是拖慢开发进程。开发环境中的代码不会影响网站的“线上”版本。

当迭代版本准备发布时（以更新或新版本的形式），新代码必须上传到*预发布环境*，这是另一台与线上应用完全一致的服务器。并非所有产品都使用预发布服务器，但在此环境中进行测试可作为一个额外检查，以确认新功能已准备好最终交付。

如果代码在预发布环境中运行完美，这个更新就准备进入*部署*阶段。它会被迁移到生产环境，即服务于公众网站、响应用户访问的服务器。发布流程的设计旨在确保此服务器仅更新运行正确的无缺陷代码。当然，没有任何流程是完美的，有时漏洞还是会悄然出现。

## 结论

与团队讨论后，你决定实施本章中讨论的某一种开发模型。同时你与工程师们合作，打造一套有效的发布管理系统，为发布的每一步都设置多重检查。然而，在向客户推出新功能之前，谨慎的做法是确保这些功能没有缺陷，并且不会造成比它们解决的问题更多的混乱。你的下一个任务是学习你的团队是如何实现这一目标的。
