当你使用默认环境评估诸如`x + y`这样的表达式，以获取变量所引用的值时，我们将这一过程称为*标准求值*。当你显式指定环境，并使用默认环境之外的其他环境时，我们称之为*非标准求值*。虽然显式环境求值自有其用途，但一般情况下你很少需要这么做——不过请记住，每当我们求值某个需要了解变量所指代对象的表达式时，都涉及某种形式的表查找过程。

## 环境与函数

当我们加入函数后，情况变得更有趣了。对于函数而言，我们同时拥有全局环境和局部环境。

在以下代码中，我们有两个名为`x`的变量。一个是全局变量，指向一个向量；另一个是函数参数。在函数内部，有一个引用`x`的表达式。当我们评估该函数时，表达式需要先判断`x`是函数参数而非全局变量，然后才能获取该变量所引用的值：

```
x <- 1:10
f <- function(x) sqrt(sum(x))
f(x²)
```

当我们调用函数时，同样有一个引用名为`x`的变量的表达式，但这里的`x`与函数内部的`x`不同。这里的`x`是全局变量，因此当评估函数调用表达式时，R需要判断`x`指向全局变量，然后查找*这个*变量所引用的值。

我们可以通过重命名变量使其唯一来厘清这一点。将全局变量命名为`gx`，参数变量命名为`px`：

```
gx <- 1:10
f <- function(px) sqrt(sum(px))
f(gx²)
```

运行这段代码后，全局作用域知道`gx`（代表序列1:10）和`f`（代表函数）这两个名称，但不会知道`px`。在函数调用内部，当我们评估`sqrt(sum(px))`时，我们*确实*知道`px`。那么这究竟是怎么回事呢？

我们仍然拥有全局环境，并且可以通过`globalenv()`检查，确认`f`和`gx`存在于其中。然而，当我们调用`f`时，函数调用也会获得一个新的环境——即局部环境。

正如我们可以使用`globalenv()`获取全局环境一样，我们也能使用`environment()`函数获取局部环境：

```
gx <- 1:10
f <- function(px) as.list(environment())
f(gx²)
```

```
## $px
## [1] 1 4 9 16 25 36 49 64 81 100
```

我使用`as.list()`将环境转换为列表，以便查看其中的内容。

`environment()`函数在全局作用域中同样有效，并且会返回全局环境，因为在全局环境中，当前环境*就是*全局环境。

从上面的例子可以看出，函数中的局部环境包含了参数`px`。通常，函数调用的局部环境会包含参数以及你在函数内部赋值的任何变量：

```
f <- function(x) {
  res <- sqrt(sum(x))
  as.list(environment())
}
x <- 1:10
f(x²)
```

```
## $res
## [1] 19.62142
##
## $x
## [1] 1 4 9 16 25 36 49 64 81 100
```

因为我对`res`进行了赋值，该变量现在也位于局部环境之中。

这里，我还将参数名改回了`x`，但此`x`会映射到`f`内部局部环境中的参数，而不是全局环境中的`x`，这就是全局`x`和局部`x`不会产生冲突的原因。当我们调用函数时，有两个环境在起作用：包含局部变量的局部环境，以及包含全局变量的全局环境；参见图4-1。函数内部的代码会在局部环境中查找变量所引用的值，而全局代码则在全局环境中查找。

你可能现在会好奇，函数`f`似乎也知道的`sqrt()`和`sum()`这些名称。它们并不在局部环境中。（它们也不在全局环境中；你可以用`as.list(globalenv())`验证一下。）那么函数是如何找到它们的呢？我们现在来看，环境中还有一个巧妙之处，用于处理在直接作用域中找不到的变量，以及这个技巧如何解决刚才的问题。

## 环境链、作用域与函数调用

在R中调用函数时，首先会为该函数创建一个空环境。这个环境将存储其参数，函数内赋值的任何局部变量也会存放在这里。每当R需要查找某个值，它都会在这个环境中寻找。如果找到了变量，你就获得这张表中的值。但如果没找到，R并不会就此放弃，而是会继续搜索。

环境不仅仅是表，更是表组成的链条。每个环境都有一个“父环境”（你可以使用`parent.env()`函数获取它），如果在一个环境中查找失败，R就会去父环境中查找。如果在父环境中也找不到，它会尝试祖父环境，并且只要还有更上层环境，就会一直向上追溯。

思考以下代码：

```
f <- function(x) {
  sqrt(sum(x + y))
}
x <- 1:10
y <- 1:10
f(x²)
```

```
## [1] 20.97618
```

我们在全局环境中定义了三个变量：`f`、`x`和`y`，其中`f`是一个函数。然后我们调用该函数，创建了一个局部环境，用于存放`f`的参数`x`；参见图4-2。

**图4-2.** 局部环境和全局环境通过父指针相互关联

局部环境和全局环境中的`x`指向不同的值。如果在函数内部查找`x`的值，我们会得到局部环境中的那个值；参见图4-3。函数体内使用的`sqrt`、`sum`和`y`这些名称并未在局部环境中定义。如果环境仅仅是表格，我们就无法运行这段代码。然而，父环境允许我们查找非局部变量。当R在局部环境中找不到`y`时，它会去父环境（即全局环境）中查找，并在那里找到它；参见图4-4。

`sqrt`和`sum`变量也未在局部环境中定义，因此R也会去父环境中查找，但它们同样不在全局环境中。尽管本书后续内容不会深入全局环境之外的结构，但环境链实际上要比这更深。在全局环境之后，你会遇到包含已加载包中名称的环境，这就是为什么你可以使用包中的函数。当你遍历完这些环境后，就会到达所谓的“基础环境”，那里存放着R的基础函数（你可以通过`baseenv()`函数获取这个环境），最后是一个终止搜索的空环境。正是在这个基础环境中，我们找到了`sum`和`sqrt`；参见图4-5。这个机制在整条链上都是相同的，所以如果你理解了函数与全局环境之间的工作方式，你也就能理解所有环境的工作原理 1.

## 作用域、惰性求值与默认参数

了解变量如何映射到值的规则，也有助于我们理解：为什么在定义函数时，可以在默认参数的表达式中使用函数参数，但在调用函数时却不能。

如果我们定义一个函数，其默认参数设置为引用另一个参数的表达式：

```
f <- function(x, y = 2 * x) x + y
```

我们可以这样调用它：

```
a <- 2
f(x = a)
## [1] 6
```

但*不一定*能这样调用：

```
f(x = a, y = 2 * x)
```

在这两种情况下，我们首先都会为函数创建一个环境，并在其中存储从`x`和`y`到值的映射。不过，函数参数并非直接传值，而是通过惰性求值来传递。你可以将这种惰性求值理解为类似本章前面提到的`quote(x + y)`表达式。我们传递给函数的是未经求值的表达式，只有在必要时才会对其求值。

因此，在这两种情况下，`f`的环境都会将`x`映射到`a`，将`y`映射到`2 * x`。然后我们尝试对`x + y`求值，这意味着需要触发`a`和`2 * x`这两个表达式的求值，而这两种调用的区别就体现在这里。

函数参数*也*拥有一个关联的环境。从这个意义上说，它们*并非*完全等同于 `quote(x + y)` 表达式。在第一种情况下，`x` 由用户提供，而 `y` 使用默认值：`x` 的表达式 `a` 知道它应在全局作用域（其中定义了 `a`）中求值，但默认参数 `y = 2 * x` 则应在局部环境中求值；参见图 4-6。因此，当我们尝试对 `x + y` 求值时，我们会在全局环境中对表达式 `a` 求值以获取 `x` 的值，然后在局部变量（它知道 `x` 的值）中对表达式 `2 * x` 求值以获取 `y` 的值，这样我们就得到了所需的变量值。

然而，在第二种情况下，`x` 和 `y` 都需要在全局环境中求值，因为这两个表达式都来自全局环境。我们仍然可以对 `a` 求值以获取 `x`，但全局环境中可能不存在 `x` 变量，导致无法对 `2 * x` 求值；更糟的是，全局环境中可能存在一个 `x`，但值却是错误的，这样我们得到的结果就会与预期不符。

在函数调用内部对参数求值时，所使用的环境取决于参数被提供的位置。默认参数会在局部环境中求值（参见图 4-6），而其他参数则会在调用作用域中求值（参见图 4-7）。

**图 4-6.** 使用默认参数进行求值

**图 4-7.** 使用显式参数进行求值

我们可以利用惰性求值来提取表达式（而非值），然后根据需要在不同的环境中对它们求值。对此的完整探讨超出了本书范围，但一个简短的示例如下：

```
f <- function(expr, ...) {
  expr <- substitute(expr) # 将参数转换为纯表达式
  env <- list2env(list(...)) # 从 '...' 创建环境
  parent.env(env) <- parent.frame() # 从调用者环境中获取其余参数
  eval(expr, env) # 在新环境中对表达式求值
}

a <- 22
f(a)
## [1] 22

f(a + b, b = 13)
## [1] 35
```

你可以使用 `substitute()` 函数剥离参数的环境，仅获取其表达式。在函数内部，我们使用 `list2env` 将 `...` 参数转换为一个环境，然后通过 `parent.frame`（获取调用者的环境而非函数的局部作用域）将这个环境的父环境设置为调用作用域，最后在新环境中对表达式求值。这使我们能够传入额外的参数（如 `b = 13`），并利用它们代替局部环境进行求值。

类似这样的技巧在 Tidyverse 包生态系统中被广泛使用。如果你想进一步探索，`rlang` 包是一个绝佳的起点。它提供了多个高级工具，用于操控参数并在替代环境中对它们求值。不过，关于非标准求值的讨论就到此为止。

## 嵌套函数与作用域

到目前为止，我们只考虑了全局环境和局部环境这两种环境，因此你很可能会认为局部环境的父环境始终是全局环境（并可能好奇既然如此，为什么还需要这一整套机制）。但事实并非如此。这仅仅是到目前为止我们定义函数的位置所导致的结果。

考虑下面这个稍显古怪但足够简单的函数：`f <- function() environment()`

当我们调用 `f()` 时，它会返回其局部环境，这并没有什么新意。然而，`environment()` 函数可以接受一个参数——一个函数——如果你用一个函数调用它，它返回的将不是当前环境，而是该函数被定义时的环境。我们在全局环境中定义了 `f`，所以 `environment(f)` 会返回全局环境：

```

## <environment: R_GlobalEnv>
```

现在应该很清楚了，这与我们在函数体内得到的环境是*不同*的：

为了进一步说明这一点，我们尝试在 `f` 内部定义一个函数：

```r
f <- function(x) {
  print(environment()) # 打印局部环境
  g <- function(y) x + y
  g
}
```

由于 `f` 仍定义在全局环境中，`environment(f)` 依然是 `R_GlobalEnv`，但我们在调用 `f` 时内部定义的函数 `g`，则是在局部环境中定义的：

```r
environment(f)
## <environment: R_GlobalEnv>

g <- f(2)
## <environment: 0x7fe435b7a0a8>

environment(g)
## <environment: 0x7fe435b7a0a8>
```

如我们所见，在调用 `f()` 时打印的环境，与函数调用结果所关联的环境是同一个。

需要特别注意的是，函数的``环境``与我们``调用``函数时获得的局部环境是不同的。函数的环境是我们定义函数时已存在的环境，而局部环境是在调用函数时新创建的环境。如果这一点清楚了，那么 R 设置父环境的规则就很简单了：当你调用函数时，新的局部环境会将函数的环境作为其父环境。

## 闭包

我们在这里编写的 `g` 函数是一个所谓的*闭包*的示例：一个函数可以在创建它的函数调用环境中找到它所需的某些变量。通过闭包，我们可以将同一个函数放入不同的环境链中，从而使其适应不同的数据。

使用之前的 `f`，我们可以编写：

```r
h1 <- f(1)
## <environment: 0x7fe446992678>

h2 <- f(2)
## <environment: 0x7fe4777ada20>

h3 <- f(3)
## <environment: 0x7fe477056128>
```

从而得到三个不同的函数，一个给输入加 1，一个加 2，一个加 3，所有这些都来自同一段代码。变量 `x` 将在三个不同的环境中找到——这些环境是在我们调用 `f` 时创建的，分别将 `x` 映射为 1、2 或 3。

```r
sapply(1:5, h1)
## [1] 2 3 4 5 6

sapply(1:5, h2)
## [1] 3 4 5 6 7

sapply(1:5, h3)
## [1] 4 5 6 7 8
```

闭包在函数式编程中经常使用，因为它们提供了一种将数据与函数打包在一起的方式，使我们能够将领域信息与通用代码分离。之前，我们使用三个闭包调用了 `sapply()`（它代表简化版的 apply）。`sapply()` 函数对序列中的每个元素调用其参数函数。它不关心函数具体做什么，但该函数必须能接受一个参数调用。通过使用闭包，我们将一个执行加法的函数适配为已经绑定了其中一个加法参数的函数。通过这样做，我们将加法适配到了 `sapply()` 提供的接口。

我们也不需要特意编写返回闭包的函数。每当你定义一个函数，你就赋予它访问定义时作用域内所有变量的权限。所以如果你编写这样的代码：

```r
# 将 x 中所有元素增加 inc
inc_all <- function(x, inc) {
  sapply(x, \(a) a + inc)
}

inc_all(1:5, 3)
## [1] 4 5 6 7 8
```

你仍然创建了一个函数（本例中我们没有命名，它是函数 `\(a) a + inc`），该函数知道增量是多少，因此 `sapply()` 可以使用它，而无需将增量作为额外参数。

当然，一个向量表达式：

```r
1:5 + 3
## [1] 4 5 6 7 8
```

会比使用 `sapply()` 更简洁、更高效，但我们的需求往往比简单的加法更复杂。也许我们需要检查数据中的哪些元素可以在某个数据库中找到——一个简单的示例如下：

```r
## foo qux bar
## TRUE FALSE TRUE
```

由于 `sapply()` 不了解数据库，我们需要将数据库打包到我们提供的函数中。如果我们在函数内部这样做，`sapply()` 将无法访问数据库变量，但我们创建的函数 `\(key) key %in% database` 可以。该函数会从 `sapply()` 获取 `key`，并从其作用域中获取 `database`。

## 访问最内层作用域之外

当我们使用 `<-` 运算符给变量赋值时，我们修改的是当前环境链顶部的环境，即局部环境。那么，这段代码会做什么呢？

```r
make_counter <- function() {
  x <- 0
  count <- function() {
    x <- x + 1
    x
  }
}

counter <- make_counter()
```

这个函数的意图是创建一个函数（一个闭包），该函数每次调用时返回一个递增的数字。它不是纯函数，但可能对我们有用。在上一章编写的深度优先编号算法中，我们不得不在递归调用中传递当前数字，但如果我们有这样的计数器，就可以在每次需要时*用它*来获取下一个数字。

然而，它并不工作。

```r
counter()
## [1] 1

counter()
## [1] 1

counter()
## [1] 1
```

我们可以解包该函数，看看具体发生了什么。当我们创建计数器时，调用 `make_counter` 函数，该函数创建了一个环境，其中 `x` 被设置为 `0`，然后返回 `count` 函数。

当我们调用计数器函数时，它会通过闭包知道 `x` 的存在，因此可以计算 `x + 1`，并将结果赋值给 `x`。问题就出在这里。在计算 `x + 1` 时使用的 `x` 是通过沿环境链向上搜索找到的，但函数所赋值的 `x` 被放入了计数器函数自身的环境。函数返回后，该环境就消失了。下一次调用 `counter` 时，会创建一个新的函数实例，从而产生一个新的环境。来自 `make_counter` 函数的变量 `x` 永远不会被更新。

当你使用 `<-` 时，如果局部变量不存在，就会创建一个新的局部变量。即使变量名在环境链更深层被发现，也没有影响。赋值始终是针对局部环境。

要赋值给环境链中更深层的变量，你需要使用运算符 `<<-`。这个运算符会像 R 语言确定表达式求值方式一样，沿环境链向上搜索，并在找到该变量的环境中进行更新（如果环境链中找不到该变量，则将其添加到全局环境中）。

我们来看一下将示例中的赋值运算符更改后会发生什么：

# Make_counter 与闭包

`Make_counter <- function() {
  x <- 0
  count <- function() {
    x <<- x + 1
    x
  }
}

counter <- make_counter()
counter()
## [1] 1
counter()
## [1] 2
counter()
## [1] 3`

这次，当我们进行赋值时，发现外层环境中存在一个 `x`，即我们在调用 `make_counter` 时初始化的那个 `x`。因此，该赋值针对的是那个环境，而不是局部环境。每次调用 `counter` 时，我们都会创建一个新的函数实例环境，但所有实例都链接到同一个外层环境，因此每次调用该函数时，我们都会更新同一个环境。

我们可以结合使用这个计数器函数和 `<<-` 运算符，来创建 `depth_first_numbers` 函数的一个更简单版本，这样就不需要在递归调用中传递数据了。我们可以在最外层作用域中创建一个表格和一个计数器函数，然后直接使用该计数器并通过 `<<-` 对表格进行赋值：

```
depth_first_numbers <- function(tree) {
  table <- c()
  counter <- make_counter()
  traverse_tree <- function(node) {
    if (is.null(node$left) && is.null(node$right)) {
      dfn <- counter()
      node$range <- c(dfn, dfn)
      table[node$name] <<- dfn
      node
    } else {
      left <- traverse_tree(node$left)
      right <- traverse_tree(node$right)
      new_node <- make_node(node$name, left, right)
      new_node$range <- c(left$range[1], right$range[2])
      new_node
    }
  }
  new_tree <- traverse_tree(tree)
  list(tree = new_tree, table = table)
}

result <- depth_first_numbers(tree)
print_tree(result$tree)
## [1] "((A,B) ,D)"
result$table
## A B D
## 1 2 3
```

如果我们想用深度优先编号范围来标注所有节点，我们仍然需要在这里创建一个新树；我们仍然不能修改数据，但是可以在递归函数内部使用外层作用域中的变量。

## 词法作用域与动态作用域

这种根据函数定义时所处环境来查找变量值的规则，被称为词法作用域，是最常见的作用域标准。之所以这样称呼，是因为原则上你可以通过代码判断表达式中的变量是在哪里定义的。首先，你检查变量是否在当前局部环境中设置，可以是局部变量或函数参数。如果没有，你会查看外围代码，检查该变量是否在该环境中。外围代码可以是全局环境，也可以是另一个函数。如果它是一个函数且变量未定义，你会沿着函数定义处的代码继续向外查找。如果变量到值的映射取决于函数被调用的位置而非定义的位置（即所谓的动态作用域），那么仅通过阅读函数定义处的代码，你无法确定变量名所引用的到底是哪个变量。

R 语言支持两种作用域，其中词法作用域是默认的（标准求值模式）。尽管如此，通过修改环境链，你可以访问调用函数的作用域（在非标准求值模式下）。在某些情况下，非标准求值可以为你的代码提供更简洁的接口，但在大多数项目中，你应该坚持使用标准的词法作用域，因为它是最容易处理的。

需要动态作用域和非标准求值的一个常见场景是，当你需要对表达式求值，而表达式中的数据部分存在于变量中，部分存在于数据框中时。在这里，如果你能像使用标准变量一样使用数据框变量，就能获得更简洁的接口。因此，我将给出一个如何实现这一点的例子。

我们将编写一个函数，它接受一个表达式和一个数据框作为输入，并在一个环境中对该表达式求值，该环境会优先在数据框中查找变量。如果找不到，它会在调用者（而非函数）的环境中查找。

该函数看起来像这样：

```
df_eval <- function(expr, df = list()) {
  x <- substitute(expr)  # 剥离 expr 的环境；现在只是引号内的表达式
  env <- list2env(df, parent = parent.frame())
  eval(x, env)
}
```

我们使用 `substitute()` 函数来剥离 `expr` 的环境。它将 `expr` 转换为原始表达式，就像我们可以用 `quote()` 创建的那样。我将其存储在变量 `x` 中，是为了稍后说明一个要点；通常情况下，我可能仍会称它为 `expr`。

无论如何，接下来我们根据数据框创建一个新环境。数据框也是列表，因此 `list2env()` 会创建一个环境，其中数据框中的每个变量都存储为环境变量。新环境的父环境是 `parent.frame()`，即调用者的环境。这样设置会将数据框放在前面，因此我们在查找父框架之前，会先使用数据框中的变量。如果在数据框中找不到某个变量，我们就会在调用者的环境中查找。最后，我们在新环境中对 `x` 进行求值。

让我们设置一些数据来进行实验：

```
x <- 1:3
y <- "foo"
df <- data.frame(y = 2:4, z = 3:5)
```

我们在调用者的环境中有一个 `x` 和一个 `y`，在数据框中有 `y` 和 `z`。我们希望函数选择这个 `x`（而不是 `df_eval` 内部的 `x`），并且如果我们调用 `df_eval` 并传入 `df` 作为数据框，我们不应该选择变量 `y`，而应该选择数据框中的 `y`。

让我们测试一下。首先，仅使用 `x` 调用它：

```
df_eval(x)
## [1] 1 2 3
```

我们没有提供数据框，因此使用了默认参数，但这次调用的目的是展示我们选择了全局环境中的 `x`，而不是函数内部的 `x`。

现在，让我们看看它是否会优先选择数据框中的 `y` 而不是这里的变量：

```
df_eval(y+z, df)
## [1] 5 7 9
```

是的，它按预期工作。

R 中有几个内置函数以这种方式进行非标准求值——在求值表达式时将数据框放入当前环境中——这是一种利用环境机制的合理方式。不过，不要过度使用。
