# 第 5 章：高阶函数

**高阶函数**这个术语指的是那些以函数作为参数或返回函数的函数。我们在前一章中用来创建闭包的函数就是高阶函数。

在 R 中，高阶函数经常被用来替代循环控制结构，我们将在下一章中详细介绍如何做到这一点。在转向使用函数操作函数的更有趣的内容之前，我先在这里给出一个简单的例子。

我们在上一章中看到的 `sapply` 函数，允许你对列表或向量中的所有元素调用一个函数。你应该主要在 R 的交互式使用中用这个函数，因为它有点不安全。它会根据你给出的输入和函数的行为来猜测你想要的输出类型，这里有更安全的替代方案，`vapply` 和 `lapply`，它们的输出类型分别是预定义的类型或始终是列表。

无论如何，如果你想对向量中的所有元素求值一个函数，你可以编写如下代码：

```r
sapply(1:4, sqrt)
## [1] 1.000000 1.414214 1.732051 2.000000
```

这会对向量 `1:4` 中的所有元素求值 `sqrt` 并给出结果。它是向量化表达式的一种类比，如果你的表达式可以向量化，向量化版本可能总是更优的。向量表达式更易读，并且如果涉及调用内置函数，通常会快得多：

```r
sqrt(1:4)
```

但是，当你想要调用的函数没有被向量化时，你可以使用 `sapply` 对序列中的所有元素求值该函数。事实上，我们在第一章中看到的 `Vectorize` 函数就是使用 `sapply` 的表亲 `lapply` 实现的。

我们可以像这样实现自己的版本：

```r
myapply <- function(x, f) {
  result <- x
  for (i in seq_along(x))
    result[i] <- f(x[i])
  result
}

myapply(1:4, sqrt)
## [1] 1.000000 1.414214 1.732051 2.000000
```

这里，我通过复制`x`创建了一个长度正确的结果向量。对这个向量的赋值可能会创建副本。第一次赋值肯定会，因为我们正在修改一个向量，R 通过制作副本来避免这种情况。后续的赋值可能会再次进行此操作，以转换结果的类型。尽管如此，其工作原理仍然相当简单明了，并且如果输入和输出具有相同类型，它将以线性时间运行（取决于对`f`的函数调用次数，而`f`本身可以具有任意时间复杂度）。

使用像`sapply`或`myapply`这样的函数，或者它们的任何同类，让我们可以用一个函数调用来替换循环，而在循环中，可能会发生各种我们不希望发生的对局部变量的赋值。我们只需要将循环体包装在另一个我们可以传递给 apply 函数的函数中。

如果我们需要将某些信息传递给函数，闭包与 apply 函数结合使用会特别有用。例如，让我们考虑一个需要对向量中的元素进行缩放的情况。我们在第一章中编写了这样一个函数：

```r

rescale <- function(x) {

  m <- mean(x)

  s <- sd(x)

  (x - m) / s

}

rescale(1:4)

## [1] -1.1618950 -0.3872983  0.3872983  1.1618950

```

这个函数是用向量表达式编写的，这是正确的做法，但让我们看看可以用 apply 函数做什么。显然，我们仍然需要计算`m`和`s`，然后需要一个计算`(x - m) / s`的函数：

```r

rescale <- function(x) {

  m <- mean(x)

  s <- sd(x)

  f <- function(y) (y - m) / s

  myapply(x, f)

}

rescale(1:4)

## [1] -1.1618950 -0.3872983  0.3872983  1.1618950

```

其实没有必要给函数命名然后再传递它；我们也可以这样写：

```r

rescale <- function(x) {

  m <- mean(x)

  s <- sd(x)

  myapply(x, \(y) (y - m) / s)

}

rescale(1:4)

## [1] -1.1618950 -0.3872983  0.3872983  1.1618950

```

我们传递给`myapply`的函数`\(y) ...`知道它被创建时的环境，因此它知道`m`和`s`，并且可以在从`myapply`调用时使用这些变量。

## 柯里化

我们经常会遇到这样一种情况：有一个两个参数的函数，你想要绑定其中一个参数，并返回一个以第二个参数为参数的函数。例如，如果我们想使用函数

```r

f <- function(x, y) x + y

```

我们可能想要使用`myapply`将其应用于一个序列，给每个元素加上 2。再次强调，这个例子只是为了向你展示一种通用技术，当你可以用向量表达式解决问题时，永远不应该做这些事情。尽管如此，让我们暂时假装我们没有向量表达式。那么我们需要为其中一个参数（比如`y`）创建一个函数，然后在调用时求值`f(2, y)`。

显然，我们可以这样写：

```r

g <- function(y) f(2, y)

myapply(1:4, g)

## [1] 3 4 5 6

```

或者更简洁地写成：

```r

myapply(1:4, \(y) f(2, y))

## [1] 3 4 5 6

```

如果我们只需要给序列中的所有元素加 2，这就足够了。如果我们想要一个更通用的解决方案，我们需要一个函数来创建我们需要的函数，一个记住`x`并且可以用`y`调用的闭包。编写这样的函数稍微复杂一点；我们只需要一个返回如下函数的函数：

```r

h <- function(x) \(y) f(x, y)

myapply(1:4, h(2))

## [1] 3 4 5 6

```

函数`f`和`h`最终做的是同一件事，唯一的区别在于我们如何向它们提供参数。函数`f`需要同时提供两个参数，而函数`h`一次只接受一个参数：

```r

f(2, 2)

## [1] 4

h(2)(2)

## [1] 4

```

像`h`这样的函数，它不是通过单个函数调用接收一系列参数，而是通过一系列函数调用，每个调用接受一个参数并返回一个新函数，这被称为*柯里化*函数。我们将`f`转换为`h`的过程称为对`f`进行*柯里化*。这些名称源自逻辑学家哈斯凯尔·柯里，函数式编程语言 Haskell 的名字也来源于他。

我们手动完成了从`f`到`h`的转换，但我们可以编写一个转换函数的函数：一个接受函数作为输入并返回另一个函数的函数。因此，我们可以编写一个通用的柯里化函数的函数——另一个高阶函数。一个用于柯里化两个参数的函数的函数可以这样编写：

```r

curry2 <- function(f) \(x) \(y) f(x, y)

```

参数`f`是我们想要柯里化的函数，返回值是函数

```r

\(x) \(y) f(x, y)

```

它需要先使用参数`x`调用，然后使用参数`y`调用，之后它将返回值`f(x, y)`。这里的变量名无关紧要，它们只是名称，不必与`f`实际使用的变量名有任何关系。

使用这个函数，我们可以自动从`f`创建`h`：

```r

h <- curry2(f)

f(2, 3)

## [1] 5

h(2)(3)

## [1] 5

```

由于`+`在 R 中只是一个函数，我们也可以直接使用*它*，而无需先编写函数`f`：

```r

h <- curry2(`+`)

h(2)(3)

## [1] 5

```

因此，可以用如下代码实现给序列中所有元素加 2 的操作：

```r

myapply(1:4, curry2(`+`)(2))

```

## [1] 3 4 5 6

你觉得这个写法是巧妙还是过于简洁而难以理解，全凭个人品味。它显然不如向量表达式优雅，但一旦你熟悉了柯里化的作用，解析起来也并不困难。

话虽如此，我本人还是更喜欢任何一天都使用`myapply`，因为我发现那个版本更易读。但我们还是继续深入探讨一下柯里化。不过请注意，所有这些不同的方法都在做同一件事：通过绑定第一个参数，将二元运算符`+`转化为一个单一函数。

```r
myapply(1:4, \(y) 2 + y)
## [1] 3 4 5 6
```

我们为柯里化编写的函数只适用于恰好接受两个参数的函数。我们显式创建了一个返回函数的函数，而这个返回函数最终返回最终值，因此柯里化版本必须能处理接受两个参数的函数。但在 R 中，函数是可以被检查的数据，所以我们可以创建一个通用的版本，能够处理任意数量参数的函数。我们只需要知道函数接受的参数个数，然后创建一个函数序列来处理每一个参数。

完整实现如下所示，在函数列表之后我会详细解释：

```r
curry <- function(f) {
  n <- length(formals(f))
  if (n == 1) return(f) # 无需柯里化
  arguments <- vector("list", length = n)
  last <- function(x) {
    arguments[n] <<- x
    do.call(f, arguments)
  }
  make_i <- function(i, continuation) {
    force(i) ; force(continuation)
    function(x) {
      arguments[i] <<- x
      continuation
    }
  }
  continuation <- last
  for (i in seq(n-1, 1)) {
    continuation <- make_i(i, continuation)
  }
  continuation
}
```

首先，我们获取函数`f`接受的参数个数：`n <- length(formals(f))`

我们可以使用`formals`函数获取这些参数。它返回一个所谓的“配对列表”（pair-list），本质上是一个链表，类似于我们在第三章中看到的那种，它在 R 内部使用，但在实际的 R 编程中并不常用。你可以把它当作列表来对待，除了一些运行时性能差异外，其行为相同。我们只需要知道这个列表的长度。

如果`f`只接受一个参数，我们就直接返回它。这样它就已经是最大程度的柯里化了。否则，我们创建一个列表，用于在调用函数链时存储变量：

```r
arguments <- vector("list", length = n)
```

我们需要收集传递给所创建的各个函数的参数。我们不能像在`curry2`中那样简单地使用形式参数`x`和`y`，因为在我们检查输入函数`f`之前，不知道需要多少个参数。无论如何，我们需要动态创建名称以确保它们不会冲突。将参数保存在一个列表中更简单，而且由于它是一个列表，我们可以将作为参数传递的任何类型的值放入其中。

现在，我们需要创建实际要返回的函数。我们分步进行。我们创建的最终函数应当使用所有参数调用`f`。它将最后一个参数作为输入，因此我们需要将其存储在`arguments`中——由于这意味着修改实际函数作用域之外的列表，我们需要使用`<<-`赋值运算符。为了使用参数列表调用`f`，我们需要使用`do.call`函数。它允许我们以列表形式指定函数的参数，而不是直接用逗号分隔的参数来传递。

```r
last <- function(x) {
  arguments[n] <<- x
  do.call(f, arguments)
}
```

其他每个函数也需要存储一个参数，因此它们需要知道对应的索引，然后返回柯里化链中的下一个函数。我们可以这样创建这些函数：

```r
make_i <- function(i, continuation) {
  force(i) ; force(continuation)
  function(x) {
    arguments[i] <<- x
    continuation
  }
}
```

参数`i`是索引，我们用它来为参数赋值；参数`continuation`是那个在最终结果能从`last`函数返回之前仍需被调用的函数。它是柯里化函数的延续。在返回函数之前，我们需要在`make_i`内部对这两个参数进行求值。否则，我们会遇到惰性求值问题：当我们最终调用函数时，变量的值可能已经在我们创建函数后改变了。我们通过调用`force`来处理参数。

现在我们只需将所有部分绑定在一起。我们以降序方式操作，这样在创建下一个函数时，我们始终拥有所需的延续函数。第一个延续函数是`last`函数。它应该是最后一个被调用的函数，并将返回整个柯里化链的期望结果。每次对`make_i`的调用都会返回一个新的延续函数，我们将其提供给链中的下一个函数（按降序排列）：

```r
continuation <- last
for (i in seq(n-1, 1)) {
  continuation <- make_i(i, continuation)
}
```

最终创建的延续函数就是柯里化后的函数，这就是我们在`curry`末尾返回的内容。

现在，我们可以使用这个`curry`函数将任何函数转换为柯里化版本：

```r
f <- function(x, y, z) x + 2*y + 3*z
f(1, 2, 3)
## [1] 14
curry(f)(1)(2)(3)
## [1] 14
```

这与直接调用`f`的语义并不完全相同；我们在将表达式赋值给参数列表时就对其进行了求值，因此惰性求值在这里并不适用。编写一个能处理参数惰性求值的函数需要大量涉及环境和表达式的复杂操作，这超出了本书的范围。

不过除此之外，我们已经编写了一个通用函数，用于将普通函数转换为其柯里化形式。

反向转换（即自动将柯里化函数转换为非柯里化形式）要困难得多。当我们得到一个函数时，我们无法知道需要调用它多少次才能得到一个值——即使调用次数与传递给它的参数无关——因此我们无法确定应该为非柯里化版本的函数获取多少个参数。

`curry`函数并非完全通用。我们无法处理默认参数——柯里化版本中必须提供所有参数——而且我们也无法创建这样一个函数：其中部分参数被固定，而其他参数不固定。柯里化版本始终需要按照原始函数接受参数的精确顺序来接收参数。

### 一个参数绑定函数

我们已经拥有所有必要的工具，可以编写一个函数，用于绑定函数的一组参数，并返回另一个函数，在该函数中我们可以提供剩余参数并获得结果：

```r
bind_parameters <- function(f, ...) {
  remembered <- list(...)
  function(...) {
    new <- list(...)
    do.call(f, c(remembered, new))
  }
}
```

```r
f <- function(x, y, z, w = 4) x + 2*y + 3*z + 4*w
f(1, 2, 3, 4)
## [1] 30
g <- bind_parameters(f, y = 2)
g(x = 1, z = 3)
## [1] 30
h <- bind_parameters(f, y = 1, w = 1)
f(2, 1, 3, 1)
## [1] 17
h(x = 2, z = 3)
## [1] 17
```

我们从第一次函数调用中获取参数，并将其保存到一个列表中，然后返回一个闭包，该闭包可以接收剩余参数，将它们转为列表，合并已记忆的参数和新参数，并通过 `do.call` 调用函数 `f`。

我们之前已经见过所有的构建块，现在只是将它们组合起来，将一个函数转换为另一个函数。

在这里使用 `list` 来记忆来自 `...` 的参数，意味着我们正在对参数进行求值。我们在该函数中明确关闭了惰性求值。保持惰性求值的语义也是可能的，但这需要更多工作。我们需要使用 `eval(substitute(alist(...)))` 技巧来将未求值的参数放入一个列表中——我们在第一章中见过这个技巧——但这会让我们在列表中得到原始表达式，并且需要小心地在正确的环境链中对这些表达式求值，才能使其正常工作。我把这作为练习留给读者，或者你可以查看 `pryr` 包中的 `partial` 函数，了解它是如何实现的。

这种部分绑定函数在 R 中并不常用。编写闭包来绑定参数同样简单，而且通常更易读，因此在使用部分绑定时需谨慎。

## 续延传递风格

我们用来创建 `curry` 的技巧涉及创建一个函数链，其中每个函数返回下一个应被调用的函数，即*续延*（*continuation*）。这种将计算的剩余部分作为一个可最终调用的函数的想法，可以应用于许多其他问题。

考虑一个简单的任务：对列表中的所有元素求和。我们可以通过以下三种方式编写函数来实现：

# 续延传递：将非尾递归转换为尾递归

第一个函数以直观的方式处理计算：将当前元素与递归调用的结果相加。第二个函数使用累加器来构建一个尾递归版本，其中累加器在递归过程中携带部分和。第三个版本同样提供了一个尾递归函数，但这次是通过一个续延函数来实现的。该函数的作用类似于第二个函数中的累加器；它只是将计算包装在一个函数内，该函数在递归调用中被传递下去。

在这里，续延捕获了向下递归过程中的部分和——这与第二个函数中累加器的作用相同——但表示为尚未求值的函数。该函数最终会被递归其余部分的和值所调用，因此在该递归位置的任务仅仅是接收最终会提供的值，加上当前值，然后调用先前传递给它的续延以完成计算。

对于“对列表中的数字求和”这样简单的任务，续延传递当然是杀鸡用牛刀。如果你需要尾递归，累加器版本更简单、更快；而且无论如何，你只是用续延向上传递的函数调用替换了向下遍历向量的递归（不过后续会看到这个问题的一种解决方案）。尽管如此，在一个简单的例子中看到这三种递归方式——直接递归、累加器递归和续延传递递归——有助于理解它们的工作原理及区别。

## 将非尾递归转换为尾递归：树大小计算

续延的一个常见用途是将非尾递归函数转换为尾递归函数。举个例子，我们回到第 [3 章](https://doi.org/10.1007/978-1-4842-9487-1_3)中用于计算树的大小的函数。在那个解决方案中，我们需要处理内部节点：先递归调用左子树，再调用右子树，获取它们的大小，然后将它们相加并加 1（表示内部节点自身）。因为我们需要两次递归调用的结果，所以无法直接使该函数变成尾递归。使用续延，我们可以做到。

这个技巧是传递一个续延，用它来包裹其中一次递归，而我们可以通过尾递归调用来处理另一次递归。解决方案如下所示：

```r
size_of_tree <- function(node, continuation = identity) {
  if (is.null(node$left) && is.null(node$right)) {
    # 叶子节点，大小为 1。
    # 告诉续延根据该值计算后续部分。
    continuation(1)
  } else {
    # 创建一个续延，将在获得左树大小时被调用
    left_continuation <- function(left_result) {
      # 当获得左树大小时，创建一个续延，
      # 用于合并左树和右树（并将其传递给续延）
      right_continuation <- function(right_result) {
        continuation(left_result + right_result + 1)
      }
      # 计算右树的大小
      size_of_tree(node$right, right_continuation)
    }
    # 计算左树的大小
    size_of_tree(node$left, left_continuation)
  }
}

tree <- make_node("root",
                  make_node("C", make_node("A"),
                            make_node("B")),
                  make_node("D"))
size_of_tree(tree)
```

## [1] 5

该函数在调用时接受一个延续，负责计算“后续需要完成的工作”。如果我们当前查看的节点是叶子节点，就用 `1` 调用它——因为叶子节点的大小为 1——然后它会执行任何所需的计算，以算出先前已遍历并封装在延续参数中的树的大小。

默认延续是恒等函数：

```r
function(x) x
```

因此，如果我们仅用叶子节点调用该函数，会得到值 `1`。但当我们遇到内部节点时，会修改延续，以封装那些因尚未掌握计算所需的全部信息而无法立即完成的部分计算。

对于内部节点，我们这样做：

```r
# 创建一个延续，该延续将接收左子树的大小
left_continuary <- function(left_result) {
    # 当我们获得左子树的大小时，创建一个组合左、右子树的延续（并将其传递给延续）
    right_continuation <- function(right_result) {
        continuation(left_result + right_result + 1)
    }
    # 计算右子树的大小
    size_of_tree(node$right, right_continuation)
}
# 计算左子树的大小
size_of_tree(node$left, left_continuation)
```

我们创建一个延续，只要给它左子树的大小，它就能计算出整棵树的大小。当该延续被调用时，它接收左子树的大小作为参数，但自身需要计算右子树的大小。为此，它需要一个能获取右子树大小的延续，而当 *那个* 函数被调用时，我们就可以返回内部节点的大小：左子树大小加右子树大小再加一。它通过调用延续来返回结果，该延续随后会处理从递归返回时必须进行的后续操作。

`left_continuation` 用这个 `right_continuation` 对右子树发起递归调用，从而将右子树的大小传入 `right_continuation` 函数。但在调用 `left_continuation` 之前，我们先调用 `size_of_tree(node$left, left_continuation)` 来获取左子树的大小。当遍历完左子树后，`left_continuation` 会随其大小被调用。

由于它是尾递归的，我们可以用循环替换递归调用。这次，我们需要记住在创建新延续时强制求值该延续，因为循环时我们在修改局部参数。除此之外，其形式与你期望的将尾递归函数转换为循环函数的通用模式一致。

### 进一步优化：使用循环

```r
size_of_tree <- function(node, continuation = identity) {
    repeat {
        if (is.null(node$left) && is.null(node$right)) {
            return(continuation(1))
        }
        new_continuation <- function(continuation) {
            force(continuation)
            function(left_result) {
                size_of_tree(
                    node$right,
                    function(right_result) continuation(left_result + right_result + 1)
                )
            }
        }
        # 模拟递归调用
        node <- node$left
        continuation <- new_continuation(continuation)
    }
}

size_of_tree(tree)
```

## [1] 5

不过，这里有一个问题。我们避免了向左的深层递归，但我们创建的延续会像之前递归那样调用同样深度的函数。向右的递归调用仍然是函数调用——我们在那里还需要另一个延续，并且还不能覆盖左延续。此外，每次我们通常递归调用时，都会将一个函数包裹在另一个函数内部，当这些函数需要被求值时，我们仍然会面临深层嵌套的函数调用。

将此类函数转换为纯循环仍然是可能的，但要求 *所有* 尾调用（即我们立即返回其结果的那类函数）都得到优化。某些编程语言实现了这一点，这在纯函数式编程语言中很常见，但 R 语言并不支持。

不幸的是，我们自己也很难将其重写为一个循环函数。

不过，有一个利用闭包的技巧可以绕过这个问题。它不会让我们获得用循环替代递归所带来的性能提升，实际上反而会稍微慢一些，但它能让我们编写包含多个递归调用的函数，而无需担心递归调用过深。如果你的算法需要递归，或者递归能带来更简单的实现，并且你并不迫切需要高性能，就可以使用这个通用技巧。

### 延迟求值与蹦床

解决递归过深问题有两个关键部分。第一部分叫做“thunk”（延迟计算体）。它本质上是一个不接受参数、仅返回值的函数。它用于封装一小段计算，供日后求值。我们可以像这样将一个函数及其参数转换为一个 thunk：

```
# 一个可以直接调用的函数，例如 f(1, 2)
f <- function(x, y) x + y

# thunk 将会调用 f(1, 2)
thunk <- \( ) f(1, 2)

f(1, 2)
## [1] 3

thunk()
## [1] 3
```

我们将对`f`的调用`f(1, 2)`封装在一个不接受任何参数的函数`\( ) f(1, 2)`中，这样在不调用`f`的情况下，我们创建了一个函数`thunk`，它`如果`被我们调用，就会求值`f(1, 2)`。这有点像函数参数的惰性求值。

如果你所处的环境中`f`后续可能会绑定到其他值，你可以进一步处理。你不希望使用`\( ) f(1, 2)`，因为那会在你调用`thunk()`时调用当前的`f`（无论其为何值），但你可以通过类似下面的方式将`f`置于一个不会改变的环境中：

```
make_thunk <- function(f, ...) {
    # 确保变量在我们返回后不会改变
    force(f)
    params <- list(...)
    # 然后返回 thunk
    \( ) do.call(f, params)
}

g <- make_thunk(f, 1, 2)
g()
```

```
## [1] 3
```

通过调用`force(f)`，你确保 thunk 环境中的`f`保持不变；而通过立即求值`...`参数（将其放入列表中），你确保变量会被绑定到创建 thunk 时所持有的值，而不是在调用 thunk 时可能持有的值。

第一种结构更简单，但如果存在非纯函数且变量会发生变化，那么第二种更安全。

如果你好奇为什么这类函数被称为 "thunk"，以下是《黑客词典》中的解释：

> 历史注记：关于这个术语的起源，流传着几个拟声词神话。

>

> 最常见的一种说法是，它模拟了数据撞击堆栈的声音；

>

> 另一种说法认为，它模拟了数据撞击累加器的声音。

>

> 还有说法认为，它模拟了表达式在参数求值时被解冻的声音。

>

> 实际上，根据发明者的说法，这个术语是在他们意识到

>

> （经过数小时讨论后的凌晨时分）可以通过一点编译时的思考

>

> 提前推算出 Algol-60 中参数的类型，从而简化求值机制后

>

> 才被创造出来的。换句话说，这个想法“已经被想到过了”（already been thought of）；

>

> 因此它被命名为 thunk，这就像是“凌晨两点时‘think（想）’的过去式”。

我们将把递归调用封装到 thunk 中，每个 thunk 执行递归中的一步。每个 thunk 求值一步，并返回一个新的 thunk，该 thunk 将求值下一步，依此类推，直到某个 thunk 最终返回一个值。这种求值方式被称为“蹦床”（trampoline），其形象比喻是：每个 thunk 在蹦床上弹跳一次，完成一步求值，然后作为下一个 thunk 再次落回蹦床。

蹦床只是一个不断求值 thunk 直到获得值的函数，其实现如下：

```
trampoline <- function(thunk) {
  while (is.function(thunk)) thunk <- thunk()
  thunk
}
```

为了理解如何结合 thunk 和蹦床来避免递归，我们首先考虑计算数字阶乘这一更简单的例子，而不是计算树的大小。

我们在第 3 章中编写了递归阶乘函数，非尾递归版本如下：

```
factorial <- function(n) {
  if (n == 1) 1
  else n * factorial(n - 1)
}
```

使用累加器的尾递归版本如下：

```
factorial <- function(n, acc = 1) {
  if (n == 1) acc
  else factorial(n - 1, acc * n)
}
```

为了得到 thunk-蹦床版本，我们首先将其重写为连续传递风格（continuation passing style）。这基本上就是将尾递归版本中的累加器转换为用于计算最终结果的延续：

```
cp_factorial <- function(n, continuation = identity) {
  if (n == 1) {
    continuation(1)
  } else {
    cp_factorial(n - 1, \(result) continuation(result * n))
  }
}
```

```
factorial(10)
## [1] 3628800

cp_factorial(10)
## [1] 3628800
```

这个函数与累加器版本功能相同，并且由于没有尾递归优化，它会从`n`直到`1`一直调用`cp_factorial`，然后对延续函数进行同样多次的求值。我们可以让它对`n`值最高大约达到一千左右还能工作，但超过这个值后，就会达到递归栈的极限。在我们达到这个极限之前，R 中的数字就已经大到无法用浮点数表示，但这不是重点；重点是递归调用的次数可能会多到我们无法处理。

因此，我们希望每个“递归”调用不再进行递归，而是创建一个 thunk。这将创建一个执行下一步并返回下一步 thunk 的 thunk，但它不会调用下一步，因此不会产生递归。我们需要为递归和延续两者都创建这样的 thunk。实现很简单：我们只需将递归替换为对`make_thunk`的调用：

```
thunk_factorial <- function(n, continuation = identity) {
  if (n == 1) {
    continuation(1)
  } else {
    # 新的延续是一个返回 thunk 的函数。
    # 该 thunk 将通过调用延续来运行计算的下一步
    new_continuation <- \(result) \() continuation(n * result)
    # 我们尚未调用阶乘递归，只是返回一个准备好执行计算第一步的 thunk
    \(() thunk_factorial(n - 1, new_continuation)
  }
}
```

用`1`调用此函数会直接得到一个值：

```
thunk_factorial(1)
```

```
## [1] 1
```

用`2`调用会创建一个 thunk。我们需要调用这个 thunk 来向下递归到基本情况；这将为我们提供一个针对该处延续的 thunk，并且我们需要求值该 thunk 以得到值：

```
# 将我们向下递归一步，但不会向上返回
thunk_factorial(2)()
```

```

## <bytecode: 0x7fe42629e860>
## <environment: 0x7fe4263bcb38>
```

```
# 下一步调用将我们向上返回一个结果

```

```

```

对于递归中的每一步，我们因此会多得到两个 thunk：一个用于向下递归，另一个用于求值该 thunk。但最终，我们将求值所有 thunk 并得到一个值：

```
thunk_factorial(3)()()()()()
## [1] 6

thunk_factorial(4)()()()()()()
## [1] 24

thunk_factorial(5)()()()()()()()()
## [1] 120
```

当然，我们不想显式调用所有这些 thunk；这正是蹦床的用途：

```

```


我们可以编写另一个高阶函数，将这种 thunk 化的函数转换为一个使用蹦床进行计算的函数，如下所示：

```
make_trampoline <- function(f) \(...) trampoline(f(...))
factorial <- make_trampoline(thunk_factorial)
factorial(100)
```

```
## [1] 9.332622e+157
```

为了计算树的大小，我们只需做同样的事情。这里使用的延续执行的操作更复杂——它会在右子树上调用深度优先遍历，而不是直接计算一个表达式——但这并不影响，因为它只是一个延续，我们只需将其包装成一个 thunk：

```
thunk_size <- function(node, continuation = identity) {
  if (is.null(node$left) && is.null(node$right)) {
    continuation(1)
  } else {
    left_continuation <- function(left_result) {
      # 右侧延续为我们返回一个 thunk，该 thunk 返回当前树的大小（左 + 右 + 1）。
      right_continuation <- function(right_result)
        \(() continuation(left_result + right_result + 1)
      # 返回用于向右递归的 thunk
      \(() thunk_size(node$right, right_continuation)
    }
    # 返回用于向左递归的 thunk
    \(() thunk_size(node$left, left_continuation)
  }
}

size_of_tree <- make_trampoline(thunk_size)
size_of_tree(tree)
```

# 5

我们实现蹦床版本的方式与阶乘函数*完全*相同。我们先将递归改写为续延传递风格，然后把直接递归调用转换为 thunk，并让续延返回 thunk。使用蹦床后，我们永远不会遇到调用栈溢出的问题；我们从不进行递归调用，而是在原本需要调用函数的地方即时创建 thunk。
