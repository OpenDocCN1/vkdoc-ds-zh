# 接口设计

不仅通用函数具有多态性。任何仅通过通用函数操作数据的函数同样具有多态性。我们使用栈实现的逆转函数将空栈作为参数，而这个空栈决定了我们实际使用哪个栈的实现。在该函数中，我们没有在任何地方引用任何具体实现的细节。如果相反，我们在这个函数内部创建了一个空栈，那么，尽管在其他地方只通过通用函数的接口访问实现，该函数也将被绑定到单一实现上。

为了最大程度地发挥多态性的优势，你需要尽可能地设计你的函数使其具备多态性。这需要做到两点：
1.  除非确实必要，否则不要引用具体实现。
2.  任何需要引用具体类型实现细节的时候，都通过通用函数来实现。

逆转函数具有多态性，因为它没有引用任何具体实现。选择使用哪个具体的栈是由参数决定的，并且它对特定栈实现执行的所有操作都通过通用函数进行。

在编程时，很容易一时冲动违反这些规则。使用参数来决定算法中使用的数据结构并不是那么困难，但如果你编写的算法使用了多个不同的数据结构，你可能不希望将所有不同的具体实现都作为参数。然而，你真的应该这样做。如果你不想记住所有需要该算法的具体数据结构位置，只需编写一个封装该算法并提供实现的函数即可。这样你就可以两全其美。

更多时候，你可能会想要访问具体实现的细节。例如，假设你想弹出元素，直到看到某个特定元素为止，但前提是该元素在栈上。如果我们习惯于处理栈的向量实现，那么很自然地会写出这样的函数：

```
pop_until %
push(1) %>%
push(2) %>%
push(3) %T>% print
## [1] 3 2 1
## attr(,"class")
## [1] "vector_stack"
pop_until(vector_stack, 1)
## [1] 1
## attr(,"class")
## [1] "vector_stack"
pop_until(vector_stack, 5)
## [1] 3 2 1
## attr(,"class")
## [1] "vector_stack"
```

这里我们使用 `%in%` 函数来测试元素是否在栈上（我们使用 `magrittr` 管道操作符为测试创建了一个栈）。只要栈是向量栈，这工作得很好，但如果栈是以链表形式实现的，它将无法工作。你不会得到错误信息；`%in%` 测试将总是返回 `FALSE`，所以如果你更换了栈的实现，你会得到一个错误的代码，甚至不会告诉你它没有正常工作。

依赖实现细节是破坏多态对象接口所能做的最糟糕的事情。你不仅将自己绑定到单一实现，而且还将自己绑定到该具体数据的确切实现方式。如果该实现发生变化，使用它的算法就会崩溃。所以现在你既不能改变实现，又必须在实现改变时修改使用它的算法。如果运气好，如果破坏了接口你可能会收到错误信息，但就像我们刚刚看到的情况（如果你不相信我，可以自己试试），你可能连这个都得不到。该函数将总是返回原始的栈，即使你想要弹出的元素就在栈上。

```
list_stack %
push(1) %>%
push(2) %>%
push(3)
pop_until(list_stack, 1)
```

如果你编写一个操作多态对象的算法，尽可能坚持使用其已有的接口。对于 `pop_until` 函数，我们可以很容易地仅使用栈接口来实现它。

```
pop_until <- function(stack, element) {
s <- stack
while (!is_empty(s) && top(s) != element) s <- pop(s)
if (is_empty(s)) stack else s
}
```

如果使用该接口无法实现你的需求，你应该对其进行扩展。你总是可以编写适用于某个类的新通用函数。

```
contains <- function(stack, element) {
UseMethod("contains")
}
contains.default <- function(stack, element) {
.NotYetImplemented()
}
contains.vector_stack <- function(stack, element) {
element %in% stack
}
```

你不需要为抽象数据类型的所有实现都添加具体函数来实现一个通用函数。如果你有一个返回错误的默认实现——并且对你使用的任何代码都有适当的单元测试——那么如果你的算法尝试使用尚未实现的函数，你会收到错误，并且你可以在那时添加它。

如果抽象数据类型来自另一个包，添加新的通用函数不如一开始就使用原始接口理想。如果那个包中的实现在后续发生变化，你的新通用函数可能会崩溃——并且可能是静默崩溃。尽管如此，结合适当的单元测试，这仍然比简单地在其他函数中访问详细实现要好得多。

## 设计最小化且功能强大的接口

设计接口是一门艺术。当你创建自己的抽象类型时，你需要仔细考虑该类型应该具备哪些操作。你不想拥有太多操作。这会让实现该类型其他版本的人感到困难；他们需要实现所有操作，并且根据这些操作是什么，这可能涉及大量工作。另一方面，你不能有太少的操作，因为那样使用该类型的算法将经常不得不破坏接口来获取实现细节，这会破坏这些算法的多态性。

算法课程中学到的抽象数据类型是*最小化且功能强大*的接口的绝佳例子。它们定义了完成有用工作所需的最少数量的操作，同时仍然使具体的栈、队列、字典等的实现成为可能，且工作量最小。

在设计你自己的类型时，努力实现同样类型的最小化接口。



## 多态性的实用价值

多态性不仅适用于传统意义上的抽象数据结构。多态性为实现抽象数据结构提供了手段，使得算法可以基于抽象接口工作，无需了解其操作的具体实现。然而，泛型函数在许多我们通常不视为数据结构的场景中也同样实用。

在 R 语言中，经常需要将统计模型拟合到数据上。这类模型并非真正的数据结构，但它们拥有一个抽象接口。例如，你可能拟合一个线性模型这样的具体模型，但一旦获得拟合模型，就会有许多对所有模型都通用的操作。你可能需要预测新数据的响应变量，或者获取拟合值的残差。这些操作对所有模型都是相同的——尽管不同模型实现这些操作的方式各异——因此它们都能受益于泛型机制。事实上确实如此。实现这两项操作的函数 `predict` 和 `residuals` 都是泛型函数，每种模型都可以提供自己的实现版本。

存在一个广泛应用于拟合模型的标准函数列表，所有这些函数都是作为泛型实现的。如果你编写的分析代码仅使用这些泛型函数来操作拟合模型，那么你可以在任何时候更换模型，并复用所有代码而无需修改。

打印和绘图函数也是如此。`print` 和 `plot` 都是泛型函数，它们针对不同的数据类型（通常也针对不同的拟合模型）都有具体的实现。我们日常可能不太会思考这个问题，但如果没有这类泛型函数，我们就需要使用不同的函数来显示向量和矩阵等。

在不同数据类型之间转换也是常见的操作，同样多态性非常有用（并且在 R 语言中频繁使用）。要将数据结构转换为向量，你可以使用 `as.vector` 函数——这个名字容易引起误解，因为它看起来像是泛型函数 `as` 针对 `vector` 的特化版本，但实际上它是一个名为 `as.vector` 的泛型函数。要将因子转换为向量，被调用的是具体实现 `as.vector.factor`。

一个需要将某些输入数据转换为向量的算法，可以使用 `as.vector` 函数。这样，只要该数据类型实现了 `as.vector` 函数，算法就不必关心实际数据是以何种形式实现的。

## 多态性与算法编程

多态性作为算法设计，特别是算法实现的一个组成部分，在课程和教科书中并不常被提及，但它对于编写可复用软件至关重要。你可能不会将 R 语言视为实现算法的语言，但每当你编写数据分析流程、操作数据框或拟合模型时，都可以将其视为在实现或使用一个算法。我们希望数据分析高效，因此希望算法高效，同时也希望编写可以多次使用的代码以避免重复。这意味着我们需要编写能够处理不同数据的代码，而这通常涉及将具体数据隐藏在泛型接口之后。

以排序函数这样简单的功能为例。对于许多排序算法，要对元素排序，你需要能够判断一个元素是否小于另一个元素。如果你在一个算法实现中硬编码了整数或浮点数比较，那么你只能排序这些类型的对象。一般来说，如果你硬编码了比较操作，那么每种要排序的元素类型都需要一个不同的实现。

因此，大多数语言在其运行时库中提供了泛型排序函数，允许你指定应使用的比较功能，通常是通过向函数提供一个比较函数，或者允许你为新的数据类型指定比较函数。遗憾的是，R 语言中的 `sort` 函数不属于这种类型——它确实允许你为新类型定义排序规则，但它要求输入为原子形式，因此你不能给它传递复杂数据类型的序列——任何超出简单数值型、布尔型或字符串型的内容。通常，你可以将数据转换为矩阵或类似结构来进行排序，但如果你实际拥有一个复杂数据列表，则无法使用它。

不过，我们可以轻松地实现自己的函数来完成这个任务，我们可以将其命名为 `sort_list`——注意不要与内置函数 `sort.list` 混淆，后者实际上并不是对列表进行排序……



### 列表排序

归并排序的一种直观实现可能如下所示：

```
merge_lists <- function(x, y) {
if (length(x) == 0) return(y)
if (length(y) == 0) return(x)
if (x[[1]] < y[[1]]) {
c(x[1], merge_lists(x[-1], y))
} else {
c(y[1], merge_lists(x, y[-1]))
}
}
sort_list <- function(x) {
if (length(x) <= 1) return(x)
start <- 1
end <- length(x)
middle <- end %/% 2
merge_lists(sort_list(x[start:middle]),
sort_list(x[(middle+1):end]))
}
```

它能够完成任务，但由于合并函数在进行像 `x[-1]` 和 `y[-1]` 这样的下标操作以及在递归调用中合并结果时会复制列表，因此其运行时间是二次的。我们可以实现一个稍微复杂一点的函数，采用迭代而非递归的方式进行合并，从而在线性时间内完成操作：

```
merge_lists  length(x)) {
result[k:n] <- y[j:length(y)]
} else {
result[k:n] <- x[i:length(x)]
}
result
}
```

在排序函数的递归调用中，我们仍然在进行复制，但复制量不会超过后续将要合并的量，因此至少其渐近运行时间是可以接受的。

使用这个函数，我们可以对元素列表进行排序，前提是能够使用 `"<"` 来判断一个元素是否小于另一个。然而，内置的 `"<"` 函数并不一定能在你自定义的类上正常工作。

```
make_tuple  1 and only the first element will be
## used
## Warning in if (x[[i]]  1 and only the first element will be
## used
## Warning in if (x[[i]]  1 and only the first element will be
## used
## [[1]]
## [1] 1 1
## attr(,"class")
## [1] "tuple"
##
## [[2]]
## [1] 1 2
## attr(,"class")
## [1] "tuple"
##
## [[3]]
## [1] 2 0
## attr(,"class")
## [1] "tuple"
```

我们有几种方法可以解决这个问题。一种选择是定义一个用于比较的泛型函数：我们可以称之为 `less`，然后在合并函数中使用它。

```
merge_lists  length(x)) {
result[k:n] <- y[j:length(y)]
} else {
result[k:n] <- x[i:length(x)]
}
result
}
less <- function(x, y) UseMethod("less")
less.numeric <- function(x, y) x < y
less.tuple <- function(x, y) x[1] < y[1] || x[2] < y[2]
sort_list(x)
## [[1]]
## [1] 1 1
## attr(,"class")
## [1] "tuple"
##
## [[2]]
## [1] 1 2
## attr(,"class")
## [1] "tuple"
##
## [[3]]
## [1] 2 0
## attr(,"class")
## [1] "tuple"
```

不过，对于所有我们希望排序的类型，我们都需要定义 `less` 的具体实现。另一种方法是告诉 R 如何处理我们自定义类型的 `"<"` 操作，我们将在后续章节中看到如何操作。采用那种方法，我们将为所有能以此方式比较的对象获得排序功能。第三种可能性是将 `less` 设为排序函数的一个参数：

```
merge_lists <- function(x, y, less) {
# 函数体与之前相同
}
sort_list <- function(x, less = `<`) {
if (length(x) <= 1) return(x)
result <- vector("list", length = length(x))
start <- 1
end <- length(x)
middle <- end %/% 2
merge_lists(sort_list(x[start:middle], less),
sort_list(x[(middle+1):end], less),
less)
}
unlist(sort_list(as.list(sample(1:5))))
## [1] 1 2 3 4 5
tuple_less <- function(x, y) x[1] < y[1] || x[2] < y[2]
sort_list(x, tuple_less)

##

```

我们将默认的 `less` 函数设为 `"<"`，但对于该比较函数不适用的类型，可以提供另一个函数。

### 算法灵活实现的通用建议

作为一般规则，你希望通过提供多态性的处理机制来使你的算法实现具有适应性，这可以通过为某些函数提供选项（如上文对 `less` 所做的那样）或为抽象数据类型使用泛型函数来实现。

在为特定用途实现算法时，你可能能够试验最优的数据结构和操作实现，但通过提供修改函数的处理机制，你可以使代码更具可重用性。即使在算法对不同应用都能正确执行的情况下，你可能仍希望提供灵活性；算法的性能通常取决于具体使用场景。在渐近分析中，我们通常偏好具有理论更佳运行时间的实现，但在实践中，我们想要最快的代码，而那并不一定是渐近最快的算法。当我们使用"大 O"分析时，我们隐藏了常数因子，但这些常数很重要，所以你希望你的实现用户能够替换算法实现中使用的数据结构和操作。

要确定如何在你的实现中最好地提供这种灵活性，通常需要进行一些实验。对于抽象数据结构，泛型函数通常是最佳方法。对于像上面排序例子中的比较操作，所有三种解决方案（泛型函数、运算符重载，或提供一个具有良好默认值的函数）可能都同样好。但正如设计良好软件接口需要进行实验和思考一样，算法编程中也是如此。

## 关于 `UseMethod` 的更多内容

`UseMethod` 函数是我们用来定义泛型函数的，它负责使用我们之前看到的名字查找机制来找到合适的具体实现。不过，关于 `UseMethod` 有一些我之前省略的细节。

首先，它的行为并不像一个普通的函数。它看起来像一个函数，在很大程度上也确实是一个函数，但如果你把它当作任何其他函数来对待，可能会得到意想不到的效果。

其次，你可以在调用 `UseMethod` 之前赋值局部变量，从而将它们传递给具体实现。让我们考虑一个简单的情况。

```
foo <- function(object) UseMethod("foo")
foo.numeric <- function(object) object
foo(4)
## [1] 4
bar <- function(object) {
x <- 2
UseMethod("bar")
}
bar.numeric <- function(object) x + object
bar(4)
## [1] 6
```

这里 `foo` 函数使用了我们之前看到的模式。它只是调用 `UseMethod`。然后我们定义了一个具体的函数，如果 `foo` 在数字上被调用时就会使用。数字是有类的，其类是 `numeric`。（从技术上讲，数字的类不止这个，但现在我们无需担心。）`foo` 没有异常行为。

然而，对于 `bar`，我们在调用 `UseMethod` 之前赋值了一个局部变量 `x`。当调用 `bar.numeric` 时，这个变量是可见的。对于普通的函数调用，你需要采取措施才能访问调用作用域，因此在这里 `UseMethod` 的行为不像普通函数。

在调用 `UseMethod` 时，它的行为也不像普通函数。你不能将 `UseMethod` 用作表达式的一部分。

```
baz <- function(object) UseMethod("baz") + 2
baz.numeric <- function(object) object
baz(4)
## [1] 4
```

当 `UseMethod` 被调用时，具体函数完全接管，调用 `UseMethod` 永远不会返回。在这方面，它类似于 `return` 函数。正因为如此，你将 `UseMethod` 放入的任何表达式都不会被求值，你在 `UseMethod` 调用之后可能放置的任何代码也永远不会被求值。

`UseMethod` 函数除了泛型函数的名字外，还接受第二个参数。这是用于分派泛型函数的对象——其类型决定将被调用的具体函数的对象——如果你不想基于调用 `UseMethod` 的函数的第一个参数进行分派，可以使用这个参数。由于基于函数第一个参数的类型进行分派是一种非常常见的模式，在调用 `UseMethod` 时使用另一个对象可能会引起混淆，因此我建议除非有非常充分的理由，否则不要这样做。
