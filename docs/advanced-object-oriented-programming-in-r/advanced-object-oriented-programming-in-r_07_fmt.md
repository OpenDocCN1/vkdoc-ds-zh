# 3. 实现复用

最容易编写的代码是已经存在的代码。如果你能重用现有代码，这总是比编写新代码要好。你无需花费时间编写代码，而且如果现有代码已经存在了一段时间，它很可能是经过良好测试的，因此比引入的新代码更可能正确。所以，作为程序员，你的目标应该是编写尽可能少的新代码，尽管这听起来有些矛盾。

然而，重用代码的方法并不是将现有代码块从程序的一个地方复制粘贴到另一个地方。这样你确实重用了代码，但最终你会得到两份相同的代码。如果将来某天你发现需要修改这段代码（也许是因为尽管经过了测试，里面还是隐藏着一个 bug），你必须记得在两个地方都进行修改。当你有这样重复的代码时，很难记住这一点，而如果这两份拷贝开始出现差异，维护起来将是一场噩梦。

重用代码的方法是编写可以在许多不同上下文中使用的函数。编写专门处理单个问题并能出色解决问题的函数，同时对你调用它们的上下文做尽可能少的假设。用小巧、可重用的构建块来构建程序，会使你的代码更易于维护，也更易于扩展。

然而，在面向对象编程中，我们通常还会为代码重用增加另一个方面。当一个类定义了泛型函数时，该类及其所有子类的实现都必须实现这些泛型函数。如果每个类都以独特的方式实现所有泛型函数，那么重用的机会就很少，但所有实现都完全独特的情况很少见。通常，对于一个给定的问题，存在一些适用于大多数类的良好默认解决方案，只有少数类才需要实现专门的函数。在面向对象编程中，你应该在类层次结构中尽可能高的层级上实现函数，并让子类在可能的情况下通过调用通用函数（而不是提供它们自己专门的函数）来重用这些实现。层次结构中的任何类都可能需要对一部分泛型函数进行特化，而任何子类都应该使用其层次结构中其上级最特化的函数。但总的来说，子类只应在所需功能与其超类中定义的版本不同的情况下，才定义自己的泛型函数版本。其余的函数它应该直接重用。我们说它从其超类中`继承`了这些函数，而泛型函数的查找机制在很大程度上实现了这一过程的自动化。

在日常的 R 编程中，深层类层次结构很少被用到。与其编造一个对实际代码来说不现实的人为例子——也为了避免给出那些大部分代码与类层次结构介绍无关的例子——我将使用抽象的例子。如果你对面向对象编程在 R 中的实际应用更感兴趣，我在第 4 章中给出了一个实际的例子，尽管那只是一个单层深度的类。

## 类层次结构中的方法查找

正如我们之前所见，对于泛型函数 `f`，调用 `f(x)` 会使 R 查找名称源自 `class(x)` 的函数。如果 `class(x)` 是单个字符串，例如 `"A"`，它将查找 `f.A`。如果 R 找到了这样的函数，就会调用它；如果没找到，则会查找 `f.default` 并调用它。否则，若没有 `f.default`，R 将放弃并返回错误。这是当对象类为单个字符串时 R 的行为。如果它是一个类名序列，R 则会遍历这个序列，并依次尝试为序列中的每个类查找函数。

考虑下面定义的三个类 `A`、`B` 和 `C`。

```r
A <- function() {
structure(list(), class = "A")
}
B <- function() {
structure(list(), class = c("B", "A"))
}
C <- function() {
structure(list(), class = c("C", "B", "A"))
}
```

由于类仅由字符串表示，我们并没有真正显式地定义它们；我们只有三个函数来创建设置了类属性的对象。创建对象的函数被称为构造器，对于 S3 系统来说，这实际上是定义类的唯一方式。

我们可以创建这些类的实例并检查它们的类。

```r
x <- A()
y <- B()
z <- C()
class(x)
## [1] "A"
class(y)
## [1] "B" "A"
class(z)
## [1] "C" "B" "A"
```

如果我们定义一个只有默认实现的泛型函数：

```r
f <- function(x) UseMethod("f")
f.default <- function(x) print("f.default")
```

对所有三个对象调用它只会得到默认行为。

```r
f(x)
## [1] "f.default"
f(y)
## [1] "f.default"
f(z)
## [1] "f.default"
```

另一方面，如果我们定义一个具有默认实现和 `A` 类实现的泛型函数，那么对这三个对象调用它都会调用 `A` 函数。

```r
g <- function(x) UseMethod("g")
g.default <- function(x) print("g.default")
g.A <- function(x) print("g.A")
g(x)
## [1] "g.A"
g(y)
## [1] "g.A"
g(z)
## [1] "g.A"
```

对于 `x`，我们明白为什么会这样。R 查找 `g.A` 并找到了它。而对于 `y`，R 查找 `g.B` 却未找到。如果 `y` 的类只是 `"B"`，那么查找就会结束，R 会调用 `g.default`。但 `y` 的类既是 `"B"` 又是 `"A"`，所以当 R 找不到 `g.B` 时，它会转而查找 `g.A`。由于 `g.A` 确实存在，R 就会调用它。类似地，当我们调用 `g(z)` 时，R 首先查找 `g.C`，未找到；接着查找 `g.B`，也未找到；最后发现 `g.A` 存在，于是调用它。因此，这三个调用都指向同一个 `g.A` 函数。类 `B` 和 `C` 从类 `A` 继承了 `g` 的实现。

现在，我们尝试添加一个同时对 `A` 和 `B` 类有实现的泛型函数。

```r
h <- function(x) UseMethod("h")
h.default <- function(x) print("h.default")
h.A <- function(x) print("h.A")
h.B <- function(x) print("h.B")
h(x)
## [1] "h.A"
h(y)
## [1] "h.B"
h(z)
## [1] "h.B"
```

在这种情况下，调用 `h(x)` 会调用 `h.A`——显然，`x` 的唯一类是 `A` 且 `h.A` 已实现——而调用 `h(y)` 和 `h(z)` 都会调用 `h.B`。在这两种情况下，类序列中类 `B` 出现在类 `A` 之前，并且因为 `h.B` 存在而被调用，匹配函数的查找就此停止。虽然 `h.A` 函数存在，但我们在首次匹配后就停止了查找，所以永远不会到达它。

为了完整性，如果我们添加一个对这三个类都有实现的函数，那么每个类都会被调用其最专门的函数。

```r
i <- function(x) UseMethod("i")
i.default <- function(x) print("i.default")
i.A <- function(x) print("i.A")
i.B <- function(x) print("i.B")
i.C <- function(x) print("i.C")
i(x)
## [1] "i.A"
i(y)
## [1] "i.B"
i(z)
## [1] "i.C"
```

## 在构造器中正确建立层次结构

当我们上面创建三个类 `A`、`B` 和 `C` 时，我们在每个构造器中显式创建了代表类层次结构的类列表。对于像这里这样的小型层次结构（所有三个类彼此邻近定义，且我们知道它们应该协同工作）来说，这没问题。但如果代码增长到更复杂的情况，它确实会引入潜在的错误来源。例如，我们可能希望在某个时候将另一个类插入到 `A` 和 `B` 之间的层次结构中。我们或许记得更新 `B` 的类列表，但我们是否也会记得更新 `C` 的呢？如果 `C` 在不同的文件中，而且我们已经多年没有修改过它了呢？

由于类层次结构完全由这些类列表表示——没有显式的层次结构，只有这些隐式列表——我们必须格外小心，以确保我们的代码始终符合我们的设计。我们应该避免在每个构造器中显式地表示层次结构。

确保这一点的一种方法是，在定义新类时，始终调用其直接超类的构造器。R 对类层次结构一无所知，并且在您创建 `class` 列表之前，它也不知道您拥有哪个超类。因此，没有自动的方法来做到这一点；你必须手动调用超类的构造器，以这种方式获取一个对象，然后将新的类名添加到其 `class` 列表的前面。

```r
A <- function() {
structure(list(), class = "A")
}
B <- function() {
this <- A()
class(this) <- c("B", class(this))
this
}
C <- function() {
this <- B()
class(this) <- c("C", class(this))
this
}
```

使用这种编程惯用法还能让您避免另一个潜在的错误来源。类的构造器通常会创建一个带有属性的对象，并期望这些属性在其函数中处于一致的状态。如果您不调用超类的构造器，而是在子类的构造器中设置这些属性，就可能违反超类所依赖的不变约束。在编写子类构造器时，您可能会小心避免这样做，但超类的实现将来可能会被更改。一旦发生这种情况，子类的实现就可能被破坏。尝试调试因代码在其他完全不相关的位置发生更改而出现的错误，简直是地狱般的体验。

通常，更好的做法是始终调用超类的构造器，然后在返回子类对象之前对生成的对象进行修改。

## `NextMethod`

当专化泛型函数时，我们并不总是需要从头实现所有功能。有时我们可以复用更抽象类中的实现；只需对它们的结果稍作调整。我们可以使用函数的全名显式调用超类的函数，但这仅在类实际实现了自己的版本时才有效。如果类只是继承了它，则此方法无效，并且每次修改类层次结构时都必须小心，以免破坏此类直接调用所依赖的假设。

更好的解决方案是使用`NextMethod`函数。此函数允许你以类似`UseMethod`的方式调用继承的函数，并使用`class`序列。`NextMethod`函数在魔法程度上与`UseMethod`类似。它知道你正在实现哪个泛型函数——尽管像`UseMethod`一样，你可以覆盖这一点——并且它会搜索你函数第一个对象的`class`序列。同样，你可以覆盖这一点，但这是一个非常常见的惯用法，你可能不应该这样做。与`UseMethod`不同，它不会终止你调用它的函数，并且你可以使用它返回的值。

例如，我们可以考虑上一章末尾讨论的书目对象。这里我们有超类`"publication"`和两个子类`"article"`和`"book"`，并且我们有一个用于格式化引文的泛型方法`format`。我们可以为`publication`类编写一个`format`函数，用于格式化姓名和作者列表，并在方法的专化中调用`NextMethod`来获取此字符串，并用子类中可用的信息扩展它。

```r
format.publication <- function(publ) {
paste(name(publ), authors(publ), sep = ", ")
}
format.article <- function(publ) {
paste(NextMethod(), journal(publ), pages(publ), sep = ", ")
}
format.book <- function(publ) {
paste(NextMethod(), publisher(publ), ISBN(publ), sep = ", ")
}
```

当我们调用`NextMethod`时，R 将搜索`class`序列——从上次搜索结束的地方开始——寻找一个实现了我们当前正在评估的泛型函数的类。

我们可以使用`A`、`B`和`C`类来实际查看这一点。如果我们定义所有都调用`NextMethod`的函数，并对这三个类中的每一个对象进行评估，我们将看到`A`对象`x`会评估`A`方法和默认函数；`B`对象`y`会评估`B`函数，然后在默认版本之前继续评估`A`函数；而`C`对象`z`会评估所有函数。

```r
f <- function(x) UseMethod("f")
f.default <- function(x) print("f.default")
f.A <- function(x) {
print("f.A")
NextMethod()
}
f.B <- function(x) {
print("f.B")
NextMethod()
}
f.C <- function(x) {
print("f.C")
NextMethod()
}
f(x)
## [1] "f.A"
## [1] "f.default"
f(y)
## [1] "f.B"
## [1] "f.A"
## [1] "f.default"
f(z)
## [1] "f.C"
## [1] "f.B"
## [1] "f.A"
## [1] "f.default"
```

如果我们实现另一个函数，其中我们只为`A`和`C`类实现版本，而不为`B`实现，我们将看到`C`对象评估`C`版本，然后评估`A`版本；由于没有`B`版本，调用`NextMethod`时的搜索将找不到它，因此将继续到`A`版本。

```r
j <- function(x) UseMethod("j")
j.default <- function(x) print("j.default")
j.A <- function(x) {
print("j.A")
NextMethod()
}
j.C <- function(x) {
print("j.C")
NextMethod()
}
j(x)
## [1] "j.A"
## [1] "j.default"
j(y)
## [1] "j.A"
## [1] "j.default"
j(z)
## [1] "j.C"
## [1] "j.A"
## [1] "j.default"
```

所有方法分派——即查找泛型函数实现的技术术语——完全基于`class`属性中的类列表。类层次结构并未显式表示，确保`class`列表反映出你所设想的类层次结构设计是你的责任。如果我们反转`class`列表的顺序，R 同样可以轻松地处理它。

```r
f(z)
## [1] "f.C"
## [1] "f.B"
## [1] "f.A"
## [1] "f.default"
class(z) <- rev(class(z))
f(z)
## [1] "f.A"
## [1] "f.B"
## [1] "f.C"
## [1] "f.default"
```

如果我们反转类的顺序，`UseMethod`中对第一个函数的搜索只是从最抽象的类开始，并沿着列表向下工作，直到找到实现。在这种情况下，它会立即找到它，并且对`NextMethod`的调用会像之前一样，从`UseMethod`或先前`NextMethod`调用结束的地方继续搜索。默认函数总是在最后，因为一旦你遍历完列表，就会调用默认函数。如果`A`类是一个`C`专化的抽象类，这当然会给出不正确的行为。你将调用抽象函数而不是专化函数。但是将泛型函数解析为具体类的机制并不了解类层次结构，因此它只会搜索列表。

这也意味着你可以编写不同的类，这些类认为其他类的层次结构完全不同。如果一个`class`列表是`c("A", "B", "C")`，另一个是`c("B", "C", "A")`，第一个认为`C`是最抽象的，`A`是最衍生的类，而第二个认为`A`是最抽象的，`B`是最衍生的。R 寻找要调用函数的机制足够简单，但如果你开始编写代码，其中你的类层次结构取决于你所查看的对象，那么你就走上了疯狂之路。
