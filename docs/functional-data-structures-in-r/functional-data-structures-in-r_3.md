# 结论

R 语言并非真正意义上的算法编程语言。它的设计初衷是提供灵活性，让统计分析与数据可视化变得简便，而非追求运行速度。借助现代编译器与运行时系统技术，它本可以比现在快得多，但基础速度从未被列为优先事项。编程时间（即你实现一项分析所需的时间）被置于比运行时间（即计算机完成分析所需的时间）更高的优先级。对许多应用场景而言，这是合理的选择——不值得为了节省一天的运行时间而多花一周去编程。既然程序员的时间比计算机的时间更宝贵，通常不值得用一周的编程时间来换取一个月的运行时间节省。

你应投入多少额外时间优化代码运行速度，取决于你预期代码运行的时间长短与频率。如果你正在编写一个期望被频繁使用的分析包，就应考虑优化代码；但如果你只是在编写一次性分析流程，或许不必费心——至少不必花太多时间进行优化。

就高效代码而言，最大的性能提升来自精心选择算法与数据结构。将平方时间算法改为线性时间算法，即使是中等规模的数据集也能显著提速；将对数时间检查集合成员关系替代线性时间检查，也能达到同样效果。若你觉得代码运行过慢，首先应该从算法和数据结构入手。对实际代码进行微观优化（“贴上速度红线、画上加速条纹”）或许能带来两到十倍的性能提升，但改变算法或数据结构却能带来渐进式的改进。在 R 语言编程中，微观优化很少值得投入精力，但切换数据结构却可能大有裨益。尤其是当你通过多态接口访问数据结构时，更换数据结构只需对代码进行微小改动，却能带来巨大的性能提升。

R 语言并没有丰富的数据结构库可供选择。这再次印证了性能并非该语言发展的核心驱动力。但我们可以构建自己的库，并使其可复用。每次改进一个库，都能让下一位程序员以最少精力获得更高效率。我略尽绵力，在 GitHub 上实现了本书所述的数据结构，仓库地址为 [`https://github.com/mailund/ralgo`](https://github.com/mailund/ralgo)。欢迎在你的分析中使用我的代码，也期待收到优化改进的拉取请求。

本书并未穷举所有函数式数据结构。数据结构有诸多变体，许多都可以转化为持久化/函数式版本。我希望未来能在 R 包中看到更多这样的实现，也期望本书能激励你尝试实现其中一些。若你确实付诸实践，我愿闻其详。
