# 18. 某英国大型电信公司访谈实录

## 关于本次访谈

| 访谈对象 | 匿名架构师 |
| 时间段 | 2013–2019 |
| 项目管理框架 | 瀑布模型与敏捷开发 |
| 涉及公司 | 某英国大型电信公司 |

### 背景介绍

本次访谈对象来自一家英国大型电信公司（TC）。为便于发布，我们必须对该公司及受访人进行匿名处理。

匿名受访人（P1）是首席数据架构师。他已在该公司工作二十年，多年来随着公司从一项技术转型到另一项技术，他一直担任架构师。他负责从传统数据库到大数据及机器学习架构的全方位数据管理工作。他拥有工商管理硕士学位（MBA）。



### 启动计划

从数据工程的角度来看，组织应保持高度的灵活性。应避免过于完整地定义最终状态或最终外观。组织对最终状态的看法会因技术或业务原因而改变。P1 表示，“感觉我们处于一种持续的进化状态中，我们大致了解已经发布的产品以及正在生产中的内容，但不太确定下一步会是什么。” 架构需要支持数据科学家完成工作所需的渐进式变化和技术创新。预测这些变化是架构师的职责。

创建架构需要一种微妙的平衡。它要求使用产品的各个工作组了解他们的真实需求。一旦对用例和理想的工作流程有了充分理解，P1 就必须审视现有技术以发现任何差距。这些差距可能存在于技术特性方面，也可能出现在处理规模和处理完成时间上。“这项工作涉及尝试、迭代，然后逐步发展，直到取得成功。”

当数据团队刚刚起步时，最棘手的部分是弄清楚如何协同工作。P1 建议从仅两个项目开始。这能“与负责构建的团队、负责消费的团队，以及可能为你提供数据的团队建立共识。你可以获得足够的能力，让每个人都理解自己的角色和职责。” 自此，事情将开始发展演变。

### 与业务部门合作

TC 一直拥有深厚的研究与开发背景。因此，他们从一个应用研究团队起步，该团队由深厚的定量数学背景演变而来，并提升了编程技能。这使得 TC 能够创建集中式的数据科学能力，公司内的其他部门可以在其中找到电信领域高度专业化的技能。

由此，越来越多的业务部门在其内部配备了二到六名数据科学家。这些业务部门包括消费者营销、网络运营和投资组合规划。数据工程和架构的工作就是为这些团队提供他们现在及未来所需的工具。

他们数据分析演进的一个例子是旨在优化呼叫中心能力。传统上，他们有静态的专家系统，仅能查找来电者所说的关键词。在数据科学家创建了更复杂的模型后，通话时间从 40 分钟缩短到了 5-10 分钟。将所有这些数据与需要集成的各种系统连接起来存在工程上的困难，而从业务部门获取想法并在多个不同部门之间进行协调则存在组织上的困难。呼叫中心项目通过缩短通话时间，既节省了成本，又改善了客户服务。

### 数据科学家与数据工程师

对 P1 而言，最大的差距在于数据工程师应如何与数据科学家合作。在大型企业中，由于需要集成的系统数量庞大，数据工程变得困难重重。为了获得客户的 360 度全方位视图，工程师必须整合多个设计初衷并非相互集成的不同系统。除了这种架构上的困难，还面临着“购买还是自建”的决策难题。公司能否购买一个现成的产品来满足需求，从而以最小的定制化程度大幅加快项目进度？加上分布式系统带来的额外复杂性，这个决策变得更加困难。

### 为企业提供支持的模型

与较旧形式的数据产品相比，现代机器学习模型被企业使用的时间往往更长。企业必须以超过十年的周期进行思考，因此其模型也必须具有同样的长久性。大多数企业都为软件工程和外部供应商关系制定了较短的流程。而现在，企业必须为模型制定长期计划。将模型长期部署在关键功能（如网络自动化）中，本身就存在巨大的风险。

因此，P1 表示，TC“更倾向于使用我们自己构建的解决方案，因为我们可以精心构建它，并针对我们特定的客户群和产品集进行更深入的调优。我们可以构建比外部人员更好、更准确的模型。” 通过创建自己的服务系统，他们还能够更快、更具扩展性地将模型投入生产。这些自建系统还使得数据科学家能够构建模型，确保良好的数据产品不仅服务于模型构建，也用于数据发现和探索。

TC 还必须面对一个长期问题：每个模型应由谁长期支持？TC 传统的运营支持团队缺乏此类支持所需的技能。这项任务可能会落到数据工程师身上，需要教会他们模型如何工作以及应如何正常工作。他们会为置信区间分配一个容忍度，并确保所有评分都落在该容忍度范围内。如果模型未能做到，数据工程师会收到关于如何重新训练模型的指示。最后，他们会获得一个故障安全状态计划，即当一切崩溃无法工作时该怎么做。



### 从概念验证迈向生产环境

Scrum 团队或小队存在陷入孤岛的风险。团队可能过度专注于自身的项目，而忽视组织其他部门的需求或工作。当一个组织从定义明确、分割清晰的项目，转向将数据作为服务或产品提供时，这种项目导向的思维就会成为问题。

为了处理更多概念验证和探索性工作，TC 创建了其大数据平台和数据产品，并采用了“非常简单的标准化服务产品以及非常清晰的定义。这很像经典的福特模式。在这个平台上，你可以拥有任何你喜欢的东西，只要它符合这些标准之一，并附带半 TB 的存储空间、一个启用了抢占功能的容器，并且你的作业可能被终止。” 这个大数据平台在推出时没有采用计费模式，这有助于规定其使用规则。

这种模式对于快速引入团队效果很好。但对基础设施团队来说，这是一个巨大的变化，因为他们过去习惯于创建虚拟机后就再也不去管它们。运营一个平台或服务意味着基础设施团队必须了解正在运行的内容并监控这些进程。了解运行内容至关重要，因为“我们面临着所谓的‘噪音噩梦’，平台上有一些未受过充分教育、技能欠佳、并在整个生产环境中制造问题的租户。” 因此，运营服务平台需要思维方式的转变。

概念验证工作的一个权衡是，设置过多的工程规则或服务等级协议（SLA）会抑制创新。P1 说：“我认为我们成功做到的一件了不起的事情是，大幅降低了进行相当探索性的数据发现或洞察的门槛，比如一个小团队想要理解某个问题，或者进行一次性的分析，判断我们应该在哪里投资。这与大型项目形成对比，后者有相当清晰的需求、资金支持以及非常明确的收益预期。但我们必须在同一种基础设施上兼顾这两类需求，这本身就带来了挑战。”

随着产品走出概念验证阶段，企业必须思考如何将基础设施投入生产。对 TC 而言，他们“天真地以为可以把所有东西都放在一个集群上，但显然这行不通。” 现在，他们为大多数用例使用专用集群。这样，TC 就能防止有人“突然过来编写一些疯狂的作业，破坏整个系统的稳定性。” 创建这个生产集群包括了制定其 SLA。这些 SLA 需要同时满足用例的业务需求和技术需求。通过启动多个集群，大型组织在处理运维问题时可以运用“宠物与牲畜”的类比。单一的整体式集群意味着你必须像养宠物一样维护它。而有了多个集群，你就可以像管理牲畜一样对待它们。

### 构建企业基础设施与运营

TC 大数据之旅的第一阶段是多租户环境。他们最初的目标是创建一个实现数据和用例民主化的场所。这使得业务部门能够开始创建和运行分析。当业务部门开始将这些分析和工作负载投入生产时，问题就出现了。业务部门开始依赖这些“生产”数据流，并期望数据工程和运营团队通过 SLA 来支持它们。但当时团队仍在创建流程和工作流以实现 SLA。

团队能力与业务预期之间的这种脱节，促使 TC 投入更多精力来汇总业务需求：对数据产品以及该数据产品的业务需求进行清晰定义。TC 建立了一个流程，让业务经理能够以清晰的方式定义他们的业务需求和所需的数据产品。随后，他们运行概念验证，定义技术需求，并创建最小可行产品（MVP）。这个过程包括与业务部门的定期接触点，让业务部门能够决定功能是否符合、超出还是低于预期。这个迭代过程会持续演进，直到业务部门确信数据产品满足其需求。

业务和技术人员都需要理解的一个关键微妙之处在于，数据产品与典型的编程工件（如模块、API 端点和软件库）有何不同。为了帮助业务部门理解这种差异，TC 设立了一个集中式数据工程团队，同时在业务部门内部也设有独立的数据工程团队。集中式数据工程团队会审查每个业务部门团队的提案，确保其遵循最佳实践。验证业务部门提案的过程是迭代的。它不仅仅是一次性的提交给委员会审批。相反，业务部门可以得到集中式团队的全方位配合和智力支持，共同迭代提案，直到双方都满意为止。

TC 一直拥有非常丰富的数据。然而，他们过去只保留不到 1% 的数据，而丢弃了另外 99%。这是因为团队只关注数据的某一种用例，而该用例仅需要那 1% 的数据。在这个用例中，数据仅用于处理故障。由于另外 99% 的数据被丢弃，后续的用例只能研究故障，而无法利用那些被丢弃的数据可能带来的价值。

因此，TC 开始捕获所有数据，以便能够处理各种类型的用例。这使得数据的适用性从单一的特定技术用例，扩展到可以服务于业务的其他部门。

### 项目管理框架

TC 的大部分 IT 项目都采用瀑布式方法论。这些项目通常以三个月为交付周期。之所以采用瀑布式，是因为它允许一次性发布大型项目，并便于各个团队协调更大规模的发布。使用数据团队平台的团队更关注可预测的时间表，而非敏捷性。平台的租户希望获得可预测的性能，对新增或更新的组件需求较低。

目前正在着手努力，为数据团队开始采用敏捷方法论。为了满足那些希望少变化甚至无变化的租户需求，公司正在将他们的项目迁移到单独的专用基础设施上。其他希望采用更快、更敏捷方法的团队则继续留在当前的基础设施上。



### 给其他人的建议

`TC` 认识到，在数据项目中取得成功的关键在于人才。他们努力招聘那些真正有经验的人。许多人声称自己能构建大数据系统，但实际上从未动手实践过。他们的知识全是理论性的，而拥有实际经验的人至关重要。当人们缺乏实践经验时，他们是在一个可能并未完全理解的根基上构建系统，也无法理解自己的决策对架构或运营带来的影响。从长远来看，这类根本性错误将代价高昂。

对于任何组织而言，在开启大数据之旅之前，获得业务部门的正确支持与投入至关重要。业务部门必须从一开始就投资组建合适的数据团队和人员。如果仅凭单人或小组包揽一切，最终改进效果或`ROI`都将微乎其微。组织将无法实现利用数据的目标。

`P1` 建议管理层理解并内化分布式系统领域不断变化的技术格局。一项技术的有用生命周期正变得越来越短。在短短时间内，`P1` 已经目睹了多项技术的兴起，随后又被更新、更好的技术所取代。`P1` 表示：“我的印象是，规划的周期变得越来越短，而业务部门却希望越来越快。他们希望现在就能把事情搞定。”

业务部门要求变革的速度正迫使数据团队做出改变。数据团队必须思考如何快速将某个想法落地，然后将其产品化，从而使模型具备可扩展性。某个团队可能想在一个业务单元内实施某个方案，但同样的想法或工作流程完全可以广泛应用到组织的其他部分。`P1` 总结道：“从小处着手，快速推进，迅速上线。”
