# 数据工程

二号学士喜欢搭建飞机模型、编程、数据和分布式系统。欢迎了解数据工程团队！

将实验室中的数据科学转化为企业中大规模运行的数据科学并非易事。你需要有人能够创建可维护且可持续的数据系统，并且这些系统能被非专业人员使用。这需要具有工程背景的人才能做好。

数据工程团队负责构建数据管道，为整个组织（包括数据科学家）提供数据。数据工程师需要具备创建符合以下要求的数据产品的技能：

-   洁净
-   有效
-   可维护
-   可大规模使用
-   可持续扩展与改进

有时，数据工程团队会重写数据科学家的代码。这是因为数据科学家专注于研究，缺乏时间或专业知识来最有效地使用编程语言。

数据工程师还负责选择运行数据的基础设施。这些基础设施因项目而异，通常由名称奇特的开源项目，或云服务商提供的相关工具组成。这也是数据团队容易陷入困境、选错方案或实施错误而偏离正轨的地方。

我对数据工程师的一句话定义是：

-   数据工程师是那些专门围绕大数据创建软件解决方案的人。

这个团队对你的成功至关重要。确保你拥有合适的人选和适当的资源来有效指导你。在这个初始阶段，关于数据工程师，你需要了解几个主要方面：

-   他们出身于软件工程背景。
-   他们专精于大数据领域。
-   他们的编程技能至少达到中等水平，理想情况下是专家级别。
-   他们可能需要被要求对数据科学家施加一些工程规范。

这些数据工程师——本质上——是软件工程师，拥有随之而来的一切优点和缺点。他们同样需要他人来弥补自身的不足。因此，数据工程团队本身就是一个多学科团队，除了与其他团队密切互动外，其成员主要由数据工程师组成，但也可能包含其他职位。这些额外的人员将填补数据工程师不具备的角色或技能，或完成难度较低、可与数据工程师协作的任务。

## 运维

三号学士喜欢准时运行的火车、硬件、软件和操作系统。欢迎了解运维团队！

在生产环境中运行分布式系统框架，其稳定程度从坚如磐石到反复无常不一而足。你的代码行为也大致如此。谁来负责让这些技术持续运行并发挥作用？你需要一个运维团队来推动这艘船前行，确保一切顺利运转。

组织通过两种不同的方式来实现其运维目标。

第一种是更传统的运维路线。由一个团队负责让一切保持运行。该团队并不真正接触数据工程师的代码。他们可能参与自动化工作，但不编写管道代码。

第二种更像是一种实践而非一个团队。这种实践融合了数据工程和运维职能。同一个团队既负责数据管道代码，也负责其持续运行。选择这种方法是为了防止长期存在于开发与运维人员之间的典型的“甩锅”问题——开发人员创建了质量存疑的代码，而运维团队被迫处理由此产生的问题。当开发人员负责在生产环境中维护自己的代码时，他们就需要让代码坚如磐石，而不是把质量问题当成别人的事。

无论是作为一个独立团队还是作为工程部门的一个职能，运维团队都负责保持一切正常运行。这个“一切”的清单相当长，凸显了运维的必要性。这些事项包括：

-   负责数据工程师和数据科学家（可能也包括其他人）编写的定制化软件在生产环境中的运维工作
-   保持网络优化，因为你正在处理大量数据，而且绝大多数数据通过网络传输
-   修复任何硬件问题，因为硬盘和其他物理硬件会发生故障（在云环境中较不常见，但偶尔仍需要故障排查知识）
-   安装和修复定制代码可能需要的辅助软件
-   安装和配置操作系统以优化其性能

这份清单听起来像是所有运维工作都包含的内容，但让我再补充一些真正让大数据运维团队超负荷运转的事项。他们必须：

-   负责已投入运维的集群软件及其他大数据技术的平稳运行
-   比通常情况更熟悉正在运行的代码，并能理解其输出日志
-   熟悉传入数据的预期数量、类型和格式

我对运维工程师的一句话定义是：

-   运维工程师是拥有运维或系统工程背景，专门从事大数据运维，理解数据，并学习了一些编程知识的人。

在这个初始阶段，关于运维工程师，你需要了解几个主要方面：

-   他们出身于系统工程或运维背景。
-   他们专精于大数据领域。
-   他们必须理解通过各种系统传输或访问的数据。

重要的是要知道，数据工程师和运维工程师之间确实存在不同的思维方式。我屡见不鲜。维护和保持系统运行，与创建或研究最新的大数据框架，确实需要不同类型的人。
