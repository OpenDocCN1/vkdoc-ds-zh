# 14. 埃里克·科尔森与布拉德·克林根伯格访谈

## 关于本次访谈

| 人物 | 埃里克·科尔森与布拉德·克林根伯格 |
| --- | --- |
| 时间跨度 | 2011–2019 |
| 项目管理框架 | 定制化 |
| 涉及公司 | Stitch Fix |

### 背景说明

Stitch Fix 是全球领先的线上个人造型服务商——通过数据科学与人工判断相结合，为客户提供符合其独特品味、生活方式和预算的服装、鞋履及配饰。该服务覆盖美国女性、男性和儿童，以及英国女性和男性。Stitch Fix 的目标是帮助客户展现并成为最好的自己。

埃里克·科尔森于 2012 年创立了 Stitch Fix 的数据团队。他的官方头衔是首席算法官，现已转为荣誉职务。加入 Stitch Fix 前，他曾任 Netflix 数据科学与工程副总裁、雅虎分析经理。埃里克拥有经济学学士学位、信息系统硕士学位，以及管理科学与工程硕士学位。

布拉德·克林根伯格现任 Stitch Fix 首席算法官，是埃里克的继任者。他是 Stitch Fix 数据团队的早期成员。布拉德曾在 Google、Netflix 及其他金融公司担任数据科学家，拥有斯坦福大学统计学博士学位。

### 起点

当埃里克来到 Stitch Fix 创建算法部门时，他是从零开始的。当时，公司的技术栈看起来就像一个典型的 Ruby Web 开发栈，包含一个 Ruby Web 应用程序、一个数据库和 Web 服务器。所有数据都来自 Web 团队或内部系统（如库存管理系统等）。

在典型的 Web 开发者模式下，每当发生变更时，许多字段都会被覆盖。例如，当一件衣服的价格发生变化时，以前的历史价格并不会被保存。这个故事凸显了 Web 开发者和数据团队成员之间的一个重大差异。如果由数据科学家决定，数据将永远不会被删除或更新。这也展示了组织在发展初期必须经历的一些成长和变化。为了让数据科学家开始创建定价模型，Web 工程团队需要创建所有价格的历史数据集。

Web 开发者为数据科学家提供的一个巨大优势是高质量的数据模型。Stitch Fix 早期就将数据的完整性和真实性作为优先事项。数据通过一个具有直观且一致模式的关系型数据库暴露出来。关系型数据库的使用中存在一些需要改变的可变性担忧，例如不保留历史价格，因为历史价格会被直接覆盖。除了可变性的问题外，这种高质量的数据意味着数据科学家可以专注于创造价值，而不是试图判断他们是否能够信任这些数据。当数据出现异常时，数据科学家可以专注于找出异常的业务原因以及如何利用它，而不是试图找出数据存在缺陷的技术原因。所有数据都妥善地存储在数据库中，数据科学家无需进行大量修改就可以直接使用。

### 成长与招聘

起初，埃里克亲力亲为。他很快就意识到需要创建一个团队。他最初招聘的三个人都是数据科学家。第一个员工最初专注于为业务提供基础洞察。第二个员工则被聘用来从事商品销售领域的工作。第三位数据科学家布拉德被聘用来处理造型算法，并改进埃里克早期的一些模型。

由于公司刚起步，数据量起初是可控的。算法部门不需要做太多的数据工程工作，因为他们可以借助 Web 工程师已经创建的系统。因此，数据科学家复制了 Web 工程师使用的 PostgreSQL 数据库，并创建了自己的实例。从那时起，所有分析处理都可以在内存中通过单台计算机使用`Python`或`R`来完成。

随着团队规模扩大到 20 到 24 人，埃里克和团队不得不思考如何创建组织结构。他们不想简单地照搬前公司的默认管理或组织领导策略。相反，团队在封闭会议上从构建部门的基本原则开始讨论。他们辩论了诸如“层级的作用是什么？”以及“我们在设计组织时优化的是什么？”之类的话题。他们决定构建一个为创新而优化的组织结构。^(³⁰) 他们对此非常明确，并认识到这意味着他们在系统稳定性或执行预制需求等其他领域将不那么擅长。但他们知道，在这些领域做出牺牲，换取更多的创新，是非常值得的。

为了契合这一目标，他们建立了一种动手型管理者的文化，这些管理者喜欢亲自参与数据科学工作，而不是主要从事行政管理工作。每位管理者最初只带少数直接下属（最初上限约为五人），以便管理者能保持成就感并在智力上参与到真正的数据科学能力中。布拉德是最早的动手型管理者之一，并持续专注于业务中的造型部分。

仅仅创建管理结构并不能保证生产力或实现组织目标。他们提出了“充满信心地授权责任”这一说法，以此来证明引入层级结构的合理性。这意味着人员管理角色的存在是为了拥有整个算法能力（或一组能力），包括所有技术职能（`建模`、`ETL`、实施、度量等）以及人员职能（招聘、管理、提供反馈等）。这种对能力的垂直聚焦，而不是对技术职能的水平聚焦，使得团队能够扩展到超过 100 名数据科学家，同时保留了快速行动所需的自主权。此外，这种组织结构使他们能够在促进自下而上的创新的同时，交付业务成果。

在实践中，这种方法意味着数据科学家必须拥有多样化的技能才能管理整个能力。他们必须成为通才，并被期望自己完成建模、`ETL`和部署工作。这对于避免与更专业化的劳动分工相关的交接和排期挑战是必要的。这些能力成为组织的基础。相关的能力被组合在一起形成团队，团队再组成部门。以这种方式组织人员，为每个团队创造了自主权，因为它们向上融入组织的其他部分。

最终，部门规模变得足够大，需要增加一层管理层。那时，埃里克招聘了几位总监级别的人员来监督各个团队。这使得团队能够继续扩展。当布拉德接管团队后，他进一步扩大了规模，如今算法团队拥有超过 125 名数据科学家和平台工程师。

### 主要划分：数据科学与平台团队

最终，完全在内存中使用`Postgres`进行处理的方式开始触及数据库和服务器的硬件限制。团队不得不处理 PB 级数据，并需要为算法处理开发一个定制平台。此外，他们还需要提供清晰的接口（`API`），将算法结果交付给各个生产系统。这些活动更需要计算机科学家的技能，而不是数据科学家的技能。因此，Stitch Fix 的算法部门由两个主要小组组成：*数据科学*和*算法平台*，两者都向首席算法官汇报。数据科学团队基本符合本书中设定的定义，只是编程能力要求更高，并涉及更多运维工作。而平台团队则构建基础设施和工具，使数据科学家能够保持自主性。

#### 数据科学团队

数据科学团队进一步划分为与公司主要职能相对应的中心。

##### `商品销售算法`

该中心开发算法来管理库存，并就如何采购和为客户创造最佳产品做出决策。

##### `造型算法`

该中心专注于为造型推荐引擎提供支持的算法。更广泛地说，该中心处理一套将客户与产品进行匹配的算法，包括服装推荐、造型师选择算法以及库存定向。

##### `客户算法`

该中心专注于在服务中为客户个性化体验，独立于服装本身。例如，有些算法可以个性化地决定何时以及如何与每位客户互动。

##### `运营算法`

该中心专注于协调整个公司资源流动的算法，确保劳动力（仓库工人、客服人员、造型师等）的供应与需求相匹配。

# 客户服务算法

该中心专注于管理客户互动（例如路由工单、推荐回复等）的算法。

数据科学家负责自行编写`ETL`、训练模型并将其部署到生产环境。Stitch Fix 希望他们的数据科学家尽可能贴近业务问题——与业务部门合作，验证某个模型或新方法是否真正解决问题或改善指标。在某些情况下，数据科学家就是业务本身，肩负着直接影响营收及其他指标的责任。

## 平台团队

平台团队负责搭建开发和运行算法所需的一切基础设施和工具。实际上，他们让数据科学家无需深入了解运行算法所需的大量高级计算机科学概念——如容器化、分布式处理、自动故障转移等。这样一来，数据科学家便可以在更高的抽象层级上编写代码，乐得不知后台发生的分布式与并行化处理。这使他们能够专注于将科学应用于业务问题，同时避免将工作交接给他人。

通过为数据科学团队和平台团队招聘合适的人才，并让各自专注于自己擅长的领域，管理者可以让数据科学家的工作效率大大提高。借助该平台，数据科学家可以拥有并创建解决整个业务问题的方案。Eric 在描述该平台时表示：“它真正让数据科学家能够掌控他们正在处理问题的方方面面——从思考如何构建模型，到获取数据、设计算法、训练模型、因果性地衡量影响，以及与业务部门的合作伙伴协作，全程无需将工作移交或交接给其他职能部门。”

运营职责由平台团队和数据科学团队共同承担。Stitch Fix 已建立对生产系统的广泛监控，这有助于他们快速定位问题根源。根据问题的明显根源，负责该系统的团队会收到需要运营支持的警报。每个算法都有不同的`SLA`，具体取决于其成熟度和风险因素。团队不希望采用一刀切的`SLA`，因为在许多领域，他们更看重创新而非稳定性。

Stitch Fix 的架构完全在云端运行。他们从云计算中获得的主要优势是敏捷性。数据科学家和平台工程师能够随时启动新集群来尝试新想法。如果该想法未能产生预期效果，这些资源也可以同样迅速地关闭。这减少了对围绕尝试哪些想法建立大量流程的需求。

## 自下而上的方法

我发现 Stitch Fix 创造算法的方法非常吸引人。在大多数组织中，事情往往采取自上而下的方式。某位高管下达指令，每个人执行该指令，或者一个业务部门资助特定功能的工作。相比之下，Stitch Fix 鼓励数据科学采用一种自发涌现或自下而上的方法。

“这源于一个事实，即这类算法无法预先设计；它们必须边进行边学习，”Eric 分享道。公司很早就意识到数据科学的工作流程与其他学科不同。“你不能预先指定一个模型，而必须让数据和机器学习`揭示`模型。”业务部门不能仅仅制定一个需求规格，就指望数据科学家去实现它。

由于这种开放的学习方式，数据科学家自己就能发现通过模型进行改进或优化的需求或可能性。“那些最接近数据、日复一日与数据打交道的人，会发现别人发现不了的东西。我们许多算法能力并非被要求的，”Eric 说。“这些想法并非来自业务人员或甚至我本人或 Brad 的自上而下指令。这些想法来自数据科学家自己。”

Eric 声称，是好奇心驱使数据科学家去探索一个想法。“他们在数据中看到了关联，这暗示了更高效执行某事的方法，或者构建一个全新能力的方法，”Eric 说。“他们情不自禁。一旦观察到，他们就会被迫去追查。”借助对数据的访问权限以及平台提供的几乎无限的计算资源，数据科学家近乎零成本地探索这些想法。“我称之为`低成本探索`。他们无需请求许可就可以探索这些想法。”

但这种好奇心并非臆测；它有数据和统计的支持。“他们有证据——`AUC`（曲线下面积）和其他统计指标——让他们知道何时走在正确的道路上。并非所有想法都会产生好结果。但是，数据和统计提供的证据可以告知你，你究竟是走进了死胡同，还是正在接近可能颠覆游戏规则的东西。” 由此，数据科学家可以将他们的发现提交给团队其他成员，以展示其探索的潜在影响。

Brad 说：“团队中的大多数人都是热衷于解决业务问题、并寻找将数据和算法应用于业务的方法的人。在很多方面，我认为我们最大的成功来自于那些重新思考我们如何运用数据和算法运营业务不同部分的人所带来的突破。这既是解决业务问题，也是解决数学问题。”

当我们谈到这种自发性时，我假设 Stitch Fix 正在推行类似谷歌 20% 项目时间政策的做法，即每个人可以将五分之一的时间用于与日常工作不直接相关的项目。Stitch Fix 决定不这样做，因为他们担心创造某物的过多结构和压力实际上可能对创新不利。他们担心每个人会觉得只需要研究“惊天动地”的想法，而许多简单的想法同样可能有效。

于是，Eric 和 Brad 决定继续让创新由好奇心驱动。“数据科学家几乎总是被好奇心困扰。那种痒必须得挠，”Eric 说。“我最近和团队里的几个人聊天，问他们‘是什么让你想出了那个没人要求但你却做到了的伟大能力？’他们的回答几乎总是‘因为我不得不这样做。’‘我必须弄清楚它为什么不能分解。’或者，‘我必须解释那个异常现象，’又或者，‘我必须验证这个假设是否成立。’”

尽管好奇心是他们进行研究的主要基础，但数据科学家仍然需要对业务有良好的基本了解。Eric 说：“我们的数据科学家具备丰富的业务背景，因此他们可以自行判断某件事的价值有多大。他们可以访问数据来验证自己的想法，并且具备业务背景，知道一个新能力能产生多大的影响。”

数据科学家并非唯一有能力让新想法涌现的人。平台工程师同样受观察驱动。他们并非从数据科学家那里获取需求，而是观察他们的工作方式，并构建框架来使数据科学家更加高效——即使数据科学家并未提出这样的要求。

### 项目管理

要找到一个完美适配数据科学工作中研发环节的项目管理框架实属不易。因为团队无法预料且无法规划的情况实在太多，充满了太多曲折与变数。正因如此，Stitch Fix 并未采用 `Scrum` 或看板这类项目管理框架。他们采用的模式，我将其描述为更接近埃里克·S·雷蒙德在《大教堂与集市》一书中描述的开源项目实践。

通过组建小型团队并配备亲力亲为的管理者，团队便无需复杂的项目管理架构。他们可以更快速、更非正式地推进工作。布拉德表示：“我们采取的方法更像是做一个园丁，你只需要创造让人们能做好工作的环境，偶尔需要修剪一下枝杈，或为新树苗腾出空间，但总的来说，你只需努力营造合适的条件，然后顺势而为。”

埃里克补充道：“这个过程堪称神奇，在我看来，它与当今大多数数据科学公司的运作方式截然不同，那些公司更倾向于自上而下的管理。” 在其他那些自上而下的公司里，通常由数据科学团队之外的人发号施令或构思创意，然后指派数据科学团队的人去执行这些想法。“最好的创意应该来自数据科学家。他们是最接近数据的人。他们能看到我们其他人看不到的模式和异常。”

### 数据的竞争优势

Stitch Fix 身处零售业中竞争异常激烈的细分领域。他们依靠数据来维持竞争优势。“Stitch Fix 的商业模式提供了与众不同的客户体验。但正是这种模式所提供的数据，造就了我们的差异化。它使我们能够比其他零售商实现更好的个性化服务，”埃里克说。Stitch Fix 专注于建立积极的反馈循环和洞察力，以便更好地服务客户。

对于实体零售商而言，许多潜在的反馈循环无法建立。例如，如果有人把衣服留在试衣间，零售商就无法追踪到这件衣服被试穿和拒绝的信息。电商公司能获取更多关于自身业务的数据，但只能从客户挑选的商品中学习。而 Stitch Fix 则专注于闭环这些反馈循环。例如，Stitch Fix 能够让客户尝试他们自己可能不会挑选的衣服。这使得他们能够捕捉到关于合身度、风格、尺码等方面的偏好数据——即使客户最终退回了部分商品。关于客户为何不喜欢某件商品的数据，通常与为何喜欢的数据同样宝贵。这些数据不仅帮助 Stitch Fix 向客户推荐未来的商品，还为他们提供采购哪些库存的决策依据，甚至能让他们设计新款服装。

Stitch Fix 通过数据与客户建立了互惠互利的关系。客户向 Stitch Fix 提供关于自己尺码和风格偏好的宝贵数据；Stitch Fix 则向客户提供高度相关的服装——甚至包括他们从未想过的款式。这种通过数据建立的共生关系使双方都能受益，并为客户分享真实想法创造了绝佳理由。这是采用更传统模式的零售商难以复制的。

通过真正拥有数据的竞争优势并加以利用，算法团队对业务产生了直接影响。“我认为我们算法部门的一个新颖之处在于它对业务的直接影响程度，”埃里克说。“布拉德的部门要对各项指标的实际影响负责，无论是增加收入还是优化降低成本。除了自身影响外，他们还与公司几乎每个部门（营销、商品采购、运营、造型设计等）合作，提供嵌入这些职能中的算法能力。这在 Stitch Fix 非常独特：那是一种真正的责任感。”

Stitch Fix 因其采用的`人在回路中`算法而闻名。在某些情况下，他们需要机器学习的能力，结合人类判断的细微差别能力。例如，用于为客户挑选衣物的造型算法就是如此。然而，在其他情况下，人类判断无法增加价值，只需要机器计算即可。他们称之为`机器对机器算法`。例如，如何将库存分配到各个仓库，或如何为客户匹配造型师。这些算法最初可能是`人对机器`，但一旦对算法有足够信心，就可以将人完全从回路中移除。

要让组织信任并接受“机器对机器”算法，确实非常困难。布拉德说：“这是艺术与科学的结合——人类与机器协同工作。有时会有张力，但那是健康的张力。目标不仅仅是将人类能做的事情自动化，而是让算法能够完成人类自身无法完成的事情。存在一些非常有趣的案例，有时机器和人类意见相左。这就带来了赢得信任和信誉的挑战。但随着时间的推移，当我们能证明机器可以产生非常好的结果时，那就很了不起。尤其是在像 Stitch Fix 这样的公司里赋能员工时，你可以通过实验和数据来实证地证明这一点，表明这确实能让客户更满意。”

埃里克说：“我们的商业模式天生就适合进行实验。我们开展随机对照试验，从而了解事物之间的因果关系。这让我们得以了解决策的结果。而且，事实证明这常常令人感到谦卑！我们了解到，我们的直觉经常出错。我们的许多好主意最终都被证明是错的；它们要么毫无效果，要么甚至会产生反效果！” 秉承数据科学的风格，团队有时会写下他们对各种实验结果预测。实验结束后，他们会拿实际结果与预测进行比较。“通常，我们会发现我们之中没有一个人，甚至连方向上的预测都是对的。看到我们的预测差得有多远，着实令人警醒。但我们必须学会这一点。很可能在商业史上，情况一直都是如此。只是在我们有能力进行恰当的对照实验之前，我们从来不知道决策的结果。无知即是福啊！”

### 给其他公司的建议

我曾与全球各地的管理层交流，他们声称像`Stitch Fix`这样的公司之所以能取得成就，是因为它们位于旧金山。这些管理者认为，世界其他地区的公司无法同等程度地利用数据、招聘优秀人才或高效执行。我将这个问题直接抛给了埃里克和布拉德。

“我确实认为，工作和数据科学总体上并非地理均匀分布。但除了旧金山湾区或纽约之外，也在涌现出越来越多的中心。远程工作的兴起，对全国各地的人们来说可能是个好趋势，”布拉德说。

“聪明人会被其他聪明人所吸引。这使得人才得以聚集，反过来又会吸引更多的公司——尤其是那些真正重视顶尖人才并提供更多创新岗位的公司。这种良性循环将人才集中在相对较少的地方。所以，如果你的公司不在这类地方，这确实是个挑战，”埃里克说。

基于这一挑战，我请他们给那些行动缓慢的大型企业提出建议。

埃里克说：“嗯，我不想太悲观，但对一家老牌守旧的公司来说，这是一条上坡路。公司往往抗拒变革。流程和价值观在初创期就已确立，并成为组织固有的一部分，有点像公司的 DNA。如果这种 DNA 不包含经验主义、实验精神、创新等要素，那么成功引入数据科学团队将会很困难。这就像向体内注入一个外来物种；防御机制会排斥它。并非不可能，但要在一家现有公司做出如此根本性的改变，将会非常艰难。”

布拉德建议：“尝试在公司内部找到这样一个位置：既能提供解决问题所需的数据，又具备使用数据的意愿。理想情况下，你需要一个团队，它不仅利用数据获取洞察或撰写报告，而是真正想要利用数据和算法来做出决策。我认为很少有组织真正倾向于这个方向。但在一个大型组织内部，也可能存在一些团队或能力单元，让你拥有更多机会。”

埃里克补充道：“在一家成熟的现有公司中增加数据科学，远比从一开始就拥有它并让其自然成长要困难得多。作为现有公司的一项新尝试，数据科学团队很可能需要事先声明其计划，甚至要引用投资回报率（ROI）的估算。相比之下，在`Stitch Fix`，数据科学从一开始就是公司架构的一部分。这使得数据科学团队能够探索机会，并在事后认识到投资的回报。也就是说，我们允许先对许多新想法进行试验，在它们被证明成功之后，再投入额外的人力。这消除了事先为单个想法声明 ROI 估算的压力。数据科学解决方案本身存在大量不确定性；最好的方式是通过大量的试错进行广泛探索。”

`Stitch Fix` 在旧金山湾区的人才市场上面临激烈竞争。他们专注于招募背景多样的数据科学家，例如化学、生物学、神经科学领域，偶尔也直接从博士项目中招聘人选。为了找到合适的人，布拉德说：“解决难题，并且真正接受过用科学方法处理问题的训练，这是一套相当通用的技能。我们通常发现，那些具有解决科学问题并运用技术和数据背景的人，做得相当不错。”

我问他们，如果公司能为数据团队提供来自最高管理层（C-level）的大力支持，企业将如何受益。

`Stitch Fix` 早在初期就获得了这种来自管理层的支持。埃里克曾是首席算法官，也是最高管理层成员。“从一开始，我们就将数据科学确立为一等实体，拥有高管代表和专门部门，”埃里克说。布拉德后来接替了他的职位，与 CTO 和 CFO 同属最高管理层。

布拉德补充道：“让所有团队成员向一位最高管理层汇报，会带来若干好处。对于团队而言，我认为这为我们提供了一个非常出色的社区，以及更好的机会和职业发展。” 由于布拉德身居最高管理层，他能够决定数据团队的组织结构。“至于团队向最高管理层成员汇报，我认为在决策层拥有一席之地至关重要。这意味着我们不仅仅是在执行其他团队的想法，而是在真正帮助改变公司思考数据、不确定性以及运用算法的方式。正如埃里克提到的，我认为`Stitch Fix`成功的一部分原因正是我们所拥有的、非常强调经验主义的数据优先文化。而在很大程度上，我将此归功于埃里克——尤其是他在首次加入公司后的许多年里，一直担任最高管理层高管。”

### 事后反思的教训

我问他们，如果以事后诸葛亮的智慧，会做出什么改变或采取不同做法。

埃里克说：“随着数据科学家快速开发模型，我们曾带来一些困扰。模型投入了生产，但可能没有以最稳健的方式编码，所以最终不得不在它们上线运行后进行替换。因此，当然，如果当时能拥有现在的认知，我们一开始就会以正确的方式编写所有算法，这样就不必重写了。但这说来轻松，不过是事后反思罢了！”

布拉德声称他不会做太多改变。“我认为，那些让团队表现得如此出色的通用原则，在相当多的环境中都能奏效：推崇自下而上的创新，雇佣擅长界定问题的通才，并真正让人们能够自主负责。”

我问埃里克和布拉德，他们认为自己在哪些方面做得非常出色。

埃里克说：“我们在算法上下了如此大胆的赌注。事实证明，这对我们的商业模式至关重要。我们的成功很大程度上归功于一开始就拥有一张白纸，能够以正确的方式建立一切。你在职业生涯中会学到东西——通常是从自己的错误中——但原地纠正这些错误可能非常困难。你常常需要一张白纸重新开始。例如，在 Netflix，我的团队内部存在劳动分工，将分析或商业智能团队与数据科学团队分开。两个团队都向我汇报，但他们的工作被分割开来，以利用他们各自的技能组合。这导致了上下文、工具和基础设施的碎片化。我想解决这个问题，但这样做意味着要拆解多年的遗留代码和流程，以及不得不更换大部分团队成员。在同时交付公司优先事项的同时，这样做尤其令人望而却步。但是，在 Stitch Fix，我拥有一张白纸。没有什么需要拆解的。我能够从一开始就建立正确的组织原则。当然，有些东西必须边做边学。但是，我们非常小心地保留可选性，并避免那些难以逆转的事情。”

其他明智的选择包括“尽早引入平台团队，与我们共同成长”以及“为我们自身建立一定的自主权”。将平台团队纳入自己的组织，使他们能够设定自己的方向并统一原则。埃里克回忆道：“我们不想必须把数据科学家的需求‘移交’给工程师去实现。移交限制了快速迭代的能力。相反，我们的算法平台团队构建了一个基础设施，使数据科学家能够自己实现解决方案。”事实证明，这对他们来说是绝妙的一步。埃里克进一步回忆道：“我记得我们风格算法的第一个版本。它是在历史数据上训练的，看起来非常有前景。到了实施的时候，我们有选择：我们可以构建 API 来与工程团队对接，或者他们来做。最终我们决定自己做，这是一个极好的决定。通过拥有 API，我们可以让工程团队完全脱离我们所有的实验和迭代。如果我们没有自己构建它，我们就需要为每一次变更与他们协商，将其纳入他们的路线图。这将会非常困难，因为他们有自己的重要优先事项。”

他总结道：“工程团队和算法团队之间的接口变得相当清晰。部分原因是两个团队使用了完全不同的技术栈：工程团队使用`Ruby`；算法团队使用`Python`和`R`。这导致了良好的解耦，这对我们非常有利。”

# 德米特里·里亚博伊访谈录

## 关于本次访谈

| 人物 | 德米特里·里亚博伊 |
| --- | --- |
| 时间段 | 2011–2019 |
| 项目管理框架 | Scrum |
| 涉及公司 | Twitter, Cloudera, Zymergen |

### 背景

德米特里·里亚博伊创立了 Twitter 的数据工程平台，曾在当时还是小型初创公司的 Cloudera 实习，目前担任 Zymergen 的软件工程副总裁。他拥有分布式系统和数据库方向的硕士学位。

### Twitter 的招聘经历

德米特里是 Twitter 雇佣的第四位做分析工作的人。当时，公司有一位分析经理和两名工程师。数据工程职能是从分析部门而非核心工程团队中脱胎而出的。

起初，团队包揽了一切：既做分析，又创建所需的基础设施。团队的经理更侧重分析，但能够编写分析所需的高级`SQL`。团队其他成员则是被要求做分析的程序员。其中有些程序员本身就有分析背景，因为他们之前曾是分析团队的成员。

在早期阶段，一些分析问题是棘手的分布式系统问题，而另一些则是更基础的分析问题。德米特里说：“公司陷入了一个思维陷阱，认为‘哦，我们找三个深度学习专家，你知道，付给他们大把钞票，他们就能创造奇迹。’但实际上，他们根本没有数据。他们能做什么？公司的期望是错位的。”没有合适的数据或系统，数据分析师将无所事事。

第四和第五位员工拥有深厚的分析背景。Twitter 当时开始构建其营收平台，这项工作是从分析团队中剥离出来的。为了扩大团队规模，Twitter 收购了另一家名为 `BackTape` 的初创公司，这家公司专注于工程与分析的融合。

随着公司需求的增长，人们开始自然而然地分化为我们通常所说的分析团队和数据工程团队。这种分化大约在一年后开始出现。德米特里开始着手建立数据工程团队，寻找那些能够帮助创建基础设施的人。那时，德米特里并没有正式的头衔是经理，很多事情也尚未形成书面文件。整个分析部门仍然只有一位经理。随着团队壮大，显然一位经理已经无法顾及所有人。那时，德米特里被正式提拔为数据工程经理。

到了 2012 年，德米特里的整个团队大约有 20 人。此时，Twitter 进行了一次重组，将分析团队划归财务部门，将数据工程团队划归工程副总裁管理。德米特里说：“让我的团队转入核心工程团队很重要，尽管这意味着将工程与分析分离开来。一方面，让做分析的人和为他们准备数据、探索不同数据呈现方式的人保持良好的协作至关重要。但是，让懂工程的经理来评审和评估数据工程师更为重要。如果数据工程师不属于核心工程组织，他们未必会被视为一个真正的工程学科。分析师未必能准确判断什么困难、什么容易。组织中离你越近的人，往往在思维和文化上与你越一致。”

德米特里将数据工程团队分成了三个子团队。一个团队负责传统数据库技术，另一个专注于`Hadoop`计算引擎，第三个则是平台工程团队，使用`Hadoop`构建产品和全公司范围的报告系统。平台工程团队原本在组织的另一个部门，但 Twitter 决定将他们与数据工程团队合并。到 2014 年，德米特里的团队已有 50 人。他们还为数据工程团队增加了另一个小组，名为“流式计算”。

随着技术在整个组织内被采用，思考谁应该拥有这些技术变得至关重要。在抑制创新和技术采用与试图让员工工作更轻松或使某些用例成为可能之间，存在着艰难的权衡。“你要避免那些实际上并不理解平台的伪平台团队，他们的工作成功不依赖于交付你的平台，而且他们的本职工作另有其事，只是兼职做平台团队。他们应该是平台工程师，并且应该专注于那份平台工作。”

推特曾收购了一家名为`BackTape`的公司，该公司创建了一种名为`Storm`的分布式流处理技术（后来捐赠给了阿帕奇基金会，成为`Apache Storm`）。之后，推特又收购了另一家公司，卡蒂克·拉马萨米曾在那家公司工作。他的团队将`Storm`重写为一个名为`Heron`的新项目（后来捐赠给了阿帕奇基金会，成为`Apache Heron`）。`Heron`保持了与`Storm`的`API`兼容性，使推特免于重写大量调用`Storm API`的代码。

2015 年，德米特里离开了数据工程团队，转而负责`AB`测试平台。

### 数据与分析的挑战

从表面上看，对推文进行分析似乎很容易。可一旦加入分析需求，数据工程就会变得更加困难。将数据工程团队隶属于工程团队，使得关于如何进行软件变更及其对分析影响的必要讨论变得更加容易。数据工程团队不再是在最后一刻或根本不知道变更，而是可以从一开始就参与到关于重新架构或进行重大系统变更的讨论中。

这样一来，数据工程团队就不会感觉像是在与公司其他部门对抗以创建数据产品。相反，他们能够说：“我理解你在做什么，我理解发生了什么。我们需要改变它；让我们共同思考这在数据方面将如何运作。”

数据产品有一个关键的细微差别，这在软件工程中不那么常见。当系统升级到新版本时，数据工程团队不能仅仅忘记旧版本的数据。他们必须为所有之前版本的数据维护归档兼容性。德米特里说：“数据工程师仍然必须处理两年前遗留下来的混乱记录。你要么付出巨大代价进行重写，因为你面对的是 PB 级的数据；要么你设置某种垫片（`shim`）。如果选择后者，你必须记录相关逻辑。而且，无论过去多少年，你仍然会遇到那些看起来与较新数据不同的怪异数据。所以这很困难。当你属于同一个组织，并且将整个工程任务视为一个完整的功能集，而不是把问题推给别人、留给分析师去弄清楚时，这些讨论就更容易进行。”

当分析职能和数据工程职能分属于两个不同的组织时（就像推特曾经那样），就会出现不同类型的问题。由于这两个团队必须继续紧密合作，他们仍然需要保持良好的关系。“保持人与人之间的联系，并记住对面是一个活生生的人，这绝对有帮助。他们不是凭空出现的随机工单，你处理完就行了。尽管如此，拆分职能导致了更多的形式化。我们变得更加严肃，分析师不能再随便走到一个他们碰巧认识的工程师面前，要求修改`SQL`查询或做其他事情。分析师需要提交工单。我们有工作流程，需要确定优先级，所有这些都引入了摩擦，并减缓了创新。分析师方面对此有些沮丧。他们想说，‘我知道那个文件在哪里，你只需要这么做就行。’而我们不得不说，‘呃，现在不是那样运作的了。’”

流程中的一些变化并非数据或数据团队所独有；有些只是源于公司的成长。“老员工基本上知道所有东西在哪里以及为什么。所以他们觉得很有权力去直接更改东西，因为他们能理解所有上下文。这导致新员工说，‘你到底在干什么？我们有 500 个新东西是建立在（这个）能力之上的，你怎么能直接改呢？’这些关于组织距离及其导致的复杂性增加的问题永远不会消失。梳理这些流程是一个持续不断、永无止境的工作。”

### 任务归属结构

数据工程团队不得不更清晰地划分基础设施团队及其职责与分析团队及其职责之间的界限。

在硅谷，大多数人一份工作只会干几年。这意味着两年后，你的团队中有一半或更多的人员是完全不同的。一些离开的人创建的系统或项目已经过了试验阶段并投入生产。德米特里指出，人员变动迫使人们进行谈判，“谁来拥有它？在调试问题到什么程度时，可以叫数据工程师介入？”

他继续说道：“调试这类问题，我认为是产生大部分摩擦的地方。问问工程师问题是什么，他们会耸耸肩说，‘嗯，你给系统喂了它无法识别的东西是什么？数据可能是有偏差的，但在你做更多工作之前我帮不了你。’”当任何一方都不清楚自己的职责相对于另一方的界限在哪里时，事情就会变得混乱——尤其是在每个人都压力大且过度劳累的时候。

为了减少职责重叠带来的摩擦，团队思考了“所有权是什么样的，支持又是什么样的。我们确定了具体需求，并构建了一些工具来实现它们。”因此，数据工程团队构建了报告来帮助排查任务问题。他们告诉分析师任务日志的位置，以便他们自己就能读取错误信息。每个任务都有一个所有者字段，所有警报都会发送给他。这有助于明确角色和职责，因此当问题出现时，谁该修复它们就变得一目了然。

### 选择技术栈与构建分布式系统的难点

选择自行编写分布式系统是一个非常艰难的决定。这需要深厚的技术投入、丰富的专业知识和高度专业化。Twitter 就曾自行开发了多个分布式系统。

Twitter 最初使用 `MySQL`，但数据库已不堪重负。DBA（数据库管理员）对需要处理的运维开销感到不满。于是他们开始考虑用 `Cassandra` 替代 `MySQL` 的部分工作负载。但当他们意识到主要的性能问题源于一种名为“比较并交换”的复杂数据库操作时，他们决定创建一个名为 `Manhattan` 的新型分布式事务数据库系统来应对这一挑战。

Dmitriy 的团队是 `Manhattan` 的首批生产用户之一。他们用该系统处理计数器（例如，推文计数）和监控任务。团队对 `Manhattan` 的改进进行了持续迭代。“在分布式系统中，轻松搞定 80% 的功能部分，只相当于持续十年漫长拉锯战的 20%。” 解决最后 20% 的难点（即长尾问题）极其耗时且困难。`Manhattan` 团队并没有试图打造一个通用系统，而是“非常明智地寻找那些‘当前容易实现的特定功能子集’就足够用并能带来价值的用例”。

我问 Dmitriy，在自行编写分布式系统和使用现有系统之间该如何抉择，他会给出什么建议。当时，对于大规模实时分布式系统而言，“市面上还没有像 `Storm` 这样的系统。但即便是 `Storm`，一旦达到 Twitter 的规模，也会出现一些严重问题。我们重写它是正确的选择，因为当时没有其他人会做这件事。” Dmitriy 思考了重写 `Storm` 的替代方案，他说：“我们本可以把所有人都迁移到 `Flink` 上，但这是一次相当大规模的迁移，并且涉及诸多问题。”

重写 `Storm` 和 `Heron` 并非仅有的重大变革。“我们最终停用了 `Pig`，因此只能支持 `Scalding`。这惹恼了一些人，并且由于大家需要重写任务，我们可能在分析侧损失了多个周期，但我们挺过来了。这让我们得以探索更现代的 `SQL` 引擎。我们最终引入了 `Presto`，现在它已经是公司内部的一个重要组件了。”

“一个重要的提醒：像 Twitter、Facebook、Google、Pinterest 这样的大公司，与小型公司面临的问题是不同的。大公司为自己解决问题，或许会开源自己的成果，但这些系统是为解决它们独有的问题集而构建的。这些工具或许能解决它们在大规模场景下的问题，但这并不意味着这些工具适合所有人。”

他继续说道：“我认为你必须现实且清醒地看待权衡与收益。让那些没有花费七年时间投入某个特定系统的人参与进来，帮助做出决策。然后下定决心，贯彻到底。”

我想向各个组织指出，切换分布式系统是不可避免的。即便是像 Twitter 这样人才济济、资源丰富的公司，也无法全知全能，或者在选择分布式系统时能做到“一劳永逸”。随着技术和业务需求的变化，他们必须持续迭代。

### 数据工程师、数据科学家与运维工程师

我问 Dmitriy 对数据科学家的定义。他回答：“我认为，数据科学家是那些既充满好奇，又严谨地深入数据、探究数据能告诉他们什么的人。他们通过多种途径获得技能。有些人完全是自学成才，有些人则拥有机器学习、统计学或相关领域的博士学位。我认为他们必须对业务感兴趣，并理解业务侧问题的价值。比如，我们为什么要问这个问题？有时，这意味着需要做一些数据工程工作。”

Dmitriy 对数据工程师的定义是：“软件工程师，只不过他们关注的是静态数据，以及如何最好地组织数据，使其在回答问题和构建数据产品时发挥最大效用。”

当被问及对运维工程师的定义时，他说：“我认为所有工程师都是运维工程师。只是有些工程师比其他工程师更专注于这方面。如果你负责在生产环境中运行的代码，你就是运维工程师。如果你的产品是实时在线的、一个不断变化演进的系统，你就是运维工程师。”

我问他在数据科学家和数据工程师之间，他更偏好什么样的比例。他说：“这取决于你拥有什么样的数据科学家和什么样的数据工程师。”有些数据科学家对工程学非常精通，而另一些则只懂 `R`。“我认为这个比例正在发生变化，因为托管平台可以实现更多功能。现在你不需花费那么多精力去搭建基础设施，但你仍然需要知道自己在做什么。”

比例问题的一部分也取决于数据工程师的经验水平。“你需要有经验的人，以及真正对该领域感兴趣的人，而不是只有感兴趣的初级员工和有经验、能摸索方向、知道要警惕什么以便构建系统的高级员工。”

他提出：“平台即服务降低了对运维人员的需求。我认为它更加强调了架构和编程方面的重要性。”

他接着讲了一个关于招聘的小故事。“我按字面意思理解了我上级给我的指示。他们规定了需要多少数据工程师，但随后又说：‘去招聘数据科学家——我们会告诉你什么时候停止。’我做了件经典的事：招聘了一堆数据科学家，却没有增加数据工程师的数量。结果你猜怎么着？我们的数据科学家就成了我们的数据工程师。自然，他们抱怨道：‘为什么让我干这个？我不知道怎么做。我要辞职了。’”

“当然，”他解释道，“CEO 并不是字面意思上说的‘招聘一个数据科学家’。他是想说：‘我想要一个能正常运作的数据科学组织。把它建立起来。’我们现在的情况好多了，因为我们招聘了所需的工程师。我们有了非常棒的数据工程师。”

### 项目管理框架

当被问及项目管理时，Dmitriy 回答：“我们使用 `Scrum`。我看的是大局，因此我认为你使用什么框架其实并不重要。去读读 [敏捷宣言](https://www.agilealliance.org/agile101/the-agile-manifesto/) ，关注它的核心思想。而不是那些机制和所有围绕它的流程。宣言呼吁‘个体和互动高于流程和工具’，然后团队转头就去死板地定义敏捷流程。别担心这个。如果流程不能服务于目的，就把它扔掉。我认为这同样适用于数据科学和工程。我曾听到有人争辩说不能用这种方式做数据科学，但实际上是可行的。”

### 业务与数据团队的互动

建立 KPI 至关重要，这能让数据团队明确优先级并评估是否达成了目标。Dmitriy 承认常见的技术 KPI 围绕“可预测性、稳定性等”，但数据团队的最佳 KPI 关乎他们对业务产生的影响。“数据工程和数据科学的目的都是创造业务价值。所以，围绕业务价值来定义他们的 KPI。”

业务方总是有源源不断的请求，远超数据团队能完成的时间。Dmitriy 的团队设置了一个单一的漏斗，所有人都通过它提交请求。“我们会与数据科学团队的负责人以及项目经理开会，分析这些请求的内容，以及它们与其它请求和优先级的关系。” 基于此，他们规划出下一年的路线图。

### 数据团队成功的关键

德米特里表示，管理者需要“尽可能提升数据验证的重要性。这意味着要与非数据团队及其他工程团队合作。这样才能为成功奠定基础，而不是像仓鼠踩轮子一样徒劳地试图修补问题。成功的另一面，同样在于关注业务价值。不要为了解决问题而解决数据问题。”

数据团队管理需要成为“决策制定过程中的合作伙伴”。

管理层的职责是与组织内其他部门“建立并理顺关系”。“如果你固步自封，不与工程团队的其他成员交流，只专注于某一类问题，你或许能擅长解决这类问题，但对其他事情及其发生的原因一无所知。这种认知差距会让你成为更差劲的工程师。”

他建议管理层要“深刻理解技术问题”。管理层还需要具备沟通和领导能力才能成功。“你需要深思熟虑，尤其是在考虑组织设计和结构时，这些并非直接关乎技术，却需要长时间才能显现的元效应。你构建团队的方式会影响谁与谁沟通。结构的选择决定了摩擦会在哪里产生或不会产生。当结构失效时，你必须愿意改变它。这其中很大一部分工作，是把合适的人放到能够让他们听到并参与正确对话的环境中。建立信任有助于促进人际连接。”
