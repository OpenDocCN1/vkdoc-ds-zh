# 17. 对 Harvinder Atwal 的访谈

## 关于本次访谈

| 人员 | Harvinder Atwal |
| :--- | :--- |
| 时间段 | 2012–2019 |
| 项目管理框架 | `Scrum`, `Kanban`, `Waterfall` |
| 涉及公司 | `Moneysupermarket` |

### 背景

Harvinder Atwal 是 `Moneysupermarket` 的数据战略与高级分析主管。他拥有运筹学硕士学位。

*Moneysupermarket Group PLC 是富时 250 指数的资深成员。通过我们领先且值得信赖的品牌，我们致力于为客户提供他们所需的增长财富的服务、工具和产品。我们的商业模式是一个数据驱动的市场，为客户提供他们在别处无法获得的优惠，为我们的供应商提供价值，并为投资者提供持续的回报记录。*——摘自其官网

### 团队结构

`Moneysupermarket` 的数据职能组共有 70 人。数据组织由首席数据官领导。他们的职责范围从数据存入存储机制开始，一直延续到内部用户为分析目的访问这些数据为止。

他们有一个数据管理团队，成员来自数据工程、数据治理、商业智能和数据创新等不同领域。

有两个不同类型的分析团队，它们都集中在单一领导者之下。其中一个由 Harvinder 管理，侧重于横向，而另一个则侧重于纵向。侧重于纵向的团队负责处理某个品牌的所有产品。对于 `Moneysupermarket` 来说，这些纵向领域包括公用事业、电信、金融产品以及旅游超市。Harvinder 指出，分析部门隶属于首席数据官的情况并不常见。通常，“它们都在 `IT` 部门，尽管你可能会发现一些中央分析团队嵌入在某些业务单元中。”

Harvinder 对数据科学家的定义是“从事高级分析工作的人”。他们主要负责创建有益于客户和内部流程的模型。“他们与产品团队的协作也非常紧密。因此我们做了大量的网站优化测试和一些 A/B 测试。这些可以以批处理的形式完成；同时，我们也在越来越多地关注流式处理管道。”

公司对数据工程师的定义随着时间的推移发生了变化。过去他们有更多的 ETL 开发者。Harvinder 描述了他们的角色。“他们帮助将数据转换成数据分析师和数据科学家可以使用的格式。”他们过去还负责获取一些机器学习模型并重新进行编码。

在运营上，该团队遵循 `DevOps` 模式。Harvinder 说：“如果你构建了它，你就要拥有它并运行它。数据运营实际上是一个核心职能，隶属于数据管理部门，主要照看我们的数据库和服务器。因此，对于数据分析职能，我们减少了对运营部门的依赖。”

`Moneysupermarket` 正在转向类似 `Spotify` 的基于小组的工作模式。这将使团队拥有更高的自主性，并具备完成任何必要工作所需的所有技能。

Harvinder 说：“我们意识到，我们并不需要所有现有的数据科学家，而且实际上，他们会造成团队失衡。为了建立一个平衡良好的团队，我们正在寻找具备软件工程专长的人才。我们也想要有数据分析背景的人，这样我们就可以覆盖更广泛的技能范围，并开展交叉培训。即使你在一个团队中拥有了正确的技能组合，你仍然可能因为个体而形成孤岛。因此，我们关注的另一件事就是对人员进行交叉培训。他们永远不会完全精通彼此的领域，但只要他们知识足够，能够帮助其他团队成员并维持工作流的持续推进，这就比拥有一支全是专家的团队要好。”

### 消除障碍与摩擦

`Moneysupermarket` 最初以较为传统的方式处理数据。数据科学家和数据分析师团队主要提供决策支持。但公司意识到，组织的需求及其使用的技术会随时间变化。起初，`IT` 部门使用数据仓库，专注于治理和控制。而管理层希望创建更先进的机器学习模型。数据使用者希望在使用数据时获得更多访问权限、自由度和灵活性。平台实际上阻碍了数据团队使用数据的能力。

为了实现这些变革，`Moneysupermarket` 必须消除所有障碍和摩擦。这些变革涉及组织和技术两个层面。正如 Harvinder 所说：“我们并非打算购买某个特定工具或平台来解决所有问题，也不是仅仅需要更好地组织就能解决所有问题。有很多东西需要改变。”

从组织层面来看，公司存在“用错的人做错的事，这浪费了大家的时间”的问题。他们必须改变“团队所在的位置、向谁汇报以及其职责。”

从技术层面来看，他们必须更换所使用的工具和平台。但他们不能完全移除对数据的所有治理和控制，因为他们存储着 `PII`（个人身份信息），必须确保这些信息不被滥用。团队必须创建一个既能保证安全又不妨碍使用的平台。

作为这些组织和技术变革的一部分，数据团队自然而然地开始向 `DataOps` 模式靠拢。Harvinder 将他们的 `DataOps` 定义为“`DevOps`、精益思维和某种敏捷方法的结合。”

他们向 `DataOps` 的转型是一个持续的过程，因为总有需要改进的地方。特别是，Harvinder 专注于改进“数据管理、数据治理以及数据流的监控。”

他们在 `Moneysupermarket` 使用 `DataOps` 后发现的主要改进是速度的提升：他们能更快地创建数据产品并更快地使用它们。“从加速数据使用方式的能力来看，`DevOps` 在分析领域确实大有裨益。”速度的提升帮助了组织内多个部门，例如市场部。

在组建职能团队时，业务部门需要与多个不同部门、团队甚至 `CxO` 级高管进行优先级排序。每个团队都有自己的待办事项清单，他们的优先级可能与业务的优先级不匹配。这导致了优先级请求必须不断上报给高级管理层。每个小队或团队应具备完成任务所需的所有技能。

将所有数据团队置于一位 `C级` 高管之下也减少了摩擦。此前，`Moneysupermarket` 的一些团队隶属于 `CDO`，而另一些则隶属于 `IT`。这使得变更和更新的可见性变得困难得多。整合到一位高管之下后，沟通得以显著改善。Harvinder 说：“我们有更多机会与他们沟通，了解我们对他们的期望以及如何使用数据，这带来了巨大的好处。” 重组改善了数据团队的目标设定。“这使得优先级决策更加容易，确保我们不会在完全不同的目标上工作。”

减少摩擦的部分工作需要让数据团队与业务保持一致。“我们不希望分析或数据科学团队自行其是、进行实验，然后回过头来发现人们对他们的成果不感兴趣，因为还有其他的目标。”相反，他们首先与业务保持一致，弄清楚分析工作如何能推动业务目标。

这种规划从路线图开始。数据团队与利益相关者坐下来，了解他们的路线图以及团队如何能做出贡献。通过转向小队形式，“我们在目标上高度一致。我们发现协作性大大增强。说服业务部门我们有一个真正能提供帮助的好主意变得容易多了。他们能看到这将如何帮助他们并使其受益。”

良好的协调对于维持整个系统的运行是必要的。没有它，团队的工作很有可能无法投入生产，这会带来“工作被浪费的真实风险”。当工作被浪费时，数据科学家和数据工程师会感觉他们的努力没有产生任何影响。当人们看到自己的时间和精力因缺乏协调而被浪费时，他们就会跳槽到其他公司。这是“协调对我们来说如此重要的另一个原因。”

并非团队所做的每件事都会出现在业务的路线上图上。“仍然需要留出一些创新空间，以及回过头来清理我们积累的技术债务和引入新技术。”

### 项目管理框架

`Moneysupermarket` 使用 `Scrum`、`Kanban` 和 `Waterfall` 项目管理框架。团队主要使用 `Scrum`，但管理层将决定权留给各个团队。“我们对强制推行某些工作方式并不严格；我们发现不同方式对其他人自然会更好些。我们在强制推行某些类型的最佳实践方面则稍严格一些。例如，我们确实有软件开发的生命周期。”

有些团队可能会使用 `Waterfall`，因为存在一个特定的截止日期。例如，当一项旧技术的许可证即将到期时。团队需要规划以赶上那个最后期限。

数据科学和分析团队发现 `Kanban` 更适合他们。“由于我们工作的探索性质，我们并不总能知道何时能获得可接受的结果或令我们满意的结果。” 在数据科学或分析领域，你很可能“在迭代结束时拿不出一个可交付的产品。”

流程的多少还取决于结果是会投入生产以供反复使用，还是只为内部团队提供一次性洞察。如果某个结果要投入生产或可能涉及敏感数据，他们会为其设置软件工程流程并严格把控。

一些数据科学家对软件工程流程感到不满。他们可能觉得挑战太大，或者流程对于他们要做的事情来说过于繁重。因此，`Moneysupermarket` 对每个团队的首席数据科学家进行了软件工程方法论的培训，并向他们展示了如何以对团队有效的方式使用这些方法。首席数据科学家反过来又培训他们的团队使用这些方法。实际上，由首席数据科学家负责在团队中推行软件工程最佳实践。数据科学家们认识到，“如果做对了，它能帮你避免犯错，而犯错只会浪费你的时间。所以，流程是用来帮助你，而不是阻碍你的。”

### 团队 KPI 与目标

所有数据团队的 KPI 均与组织和技术目标保持一致。技术 KPI 用于监控数据质量、数据完整性、服务等级协议（`SLA`）以及数据的时效性等指标。

对于组织层面的 KPI，实际衡量标准并非关注产出，而是关注成果。“他们有很大的自由去决定如何实现这些成果，但达成目标的唯一途径是与利益相关者合作。”这需要与业务部门保持良好的沟通。否则，他们可能创造出绝佳的模型、洞察或数据产品，却最终无人问津。

组织目标每年设定一次。Moneysupermarket 的奖金结构更像传统金融公司，年终奖金是员工们追求的核心目标。“我们是一家上市公司，因此达成目标、让股东满意会带来相当大的压力。”Harvinder 全年都会监控团队在组织目标上的进展。“每个季度，我都会把团队召集起来，检查我们的进度是否正常。我们还会进行回顾总结，探讨团队内部如何改进以提升绩效。”

### 数据团队的变迁

机器学习带来了常规分析或软件工程无需应对的新挑战。Harvinder 将其比作计算器。如果你编写一个计算器，你总是希望它能永远给出正确的计算结果。然而，对于机器学习而言，计算结果是不断变化的。一旦模型被创建出来，就会面临诸如输入数据变化导致的模型漂移等问题，需要持续监控模型的漂移情况。如果模型确实发生了漂移，它就无法提供准确的预测或结果。

这引出了一个问题：谁负责监控模型漂移？此人需要决定最佳的行动方案。是应该重新训练模型吗？还是到了采用完全不同模型或方法的时机？Harvinder 认为这可能是机器学习工程师的职责之一。

Harvinder 认为数据工程师“对我们所做的工作至关重要，他们并非只是一个接受我们指令、在我们需要时提供数据集的独立职能部门。他们必须积极主动。”拥有合适的数据工程师能让组织的其他部分更富成效和效率。“我认为总体上我们可能不需要那么多数据科学家，但可能需要更多来自数据工程师的支持，因为我们已经拥有了远超整合能力的数据量，同时新的数据源还在不断涌现。”

组织需要确保数据团队的每位贡献者都能因其工作获得认可。通常，数据科学家获得了绝大部分赞誉，因为他们是团队中最常与客户接触的部分。“但实际上，成功也属于其他所有人。我认为，作为数据运维（DataOps）团队的一员，能让他们做出更多贡献，同时也获得更多对他们工作的认可。”确保利益相关者了解谁做出了贡献，这是管理层的责任。“不应该只让报喜的人独占所有荣耀。”

### 给他人的建议

当组织刚开始涉足数据科学时，他们会聘请“一些非常令人兴奋的人才，然后告诉他们去自由探索，找点有趣的事情做，提供一些见解。”数据科学家们会去寻找这些见解，“但他们提出的东西并不属于利益相关者的路线图或目标。”随后，数据科学家会发现，他们的模型或见解完全未被使用或投入生产，这让他们感到“极其沮丧”。Harvinder 建议不要追求“特别炫酷或尖端”的任务，而是要先获得支持，再去实现真正出色的成果。

新晋数据科学家对于入职后将要从事的工作往往抱有极不切实际的期望。他们认为自己将整天忙于创建机器学习模型和调整超参数。而实际上，数据科学家的职责是“运用数据来驱动决策”。这种对模型而非价值创造的过度关注，受到了各类会议、文章以及数据科学竞赛的推波助澜。“但我更希望拥有一个真正能应用于产品的好模型。”

对于希望数据团队取得成功的大型组织，Harvinder 建议先夯实基础。组织需要制定清晰的数据战略。这意味着必须明确回答“你将如何获取数据、如何存储数据、以及如何落实数据治理和数据管理”。组织还需要统一其战略，确保每个人都理解最终目标，并清楚个人将如何为实现该目标做出贡献。管理层需要确保所需人员或数据团队不存在缺口，并确保团队成员拥有所有必备技能。没有坚实的基础，任何数据战略或数据项目都难有大的进展。

小型组织倾向于聘用一名孤军奋战的数据科学家，期望他承担整个数据团队的所有职责。这名数据科学家往往经验不足。相反，初创公司应确保“为该职位招募到合适的人选”。

接下来是数据本身及其数量的问题。一些小型公司“根本没有足够的数据来开展任何有价值的分析”。初创公司需要现实地评估自己起步时有多少数据，以及积累到足以进行可靠分析的数据量需要多长时间。如果没有足够的数据，就很难建立基准或有效追踪数据科学家带来的改进。

在数据工程方面，Harvinder 建议重视“数据分析师、数据管家、数据血缘追踪以及元数据”。在 Moneysupermarket，他们的数据来自网站，是相对干净的 JSON 格式。即便如此，他们在数据质量或数据血缘方面仍会遇到挑战。Harvinder 原本会“更早地投入更多时间来组建软件工程团队，并确保数据科学家和数据分析师也具备软件开发技能。”
