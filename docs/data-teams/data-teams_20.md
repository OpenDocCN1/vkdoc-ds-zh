# 16. 巴斯·格尔丁克访谈

## 关于本次访谈

| 人物 | 巴斯·格尔丁克 |
| :--- | :--- |
| 时间段 | 2013–2019 年 |
| 项目管理框架 | `Scrum` |
| 涉及公司 | `ING`、荷兰合作银行 |

### 背景

巴斯·格尔丁克在创建数据驱动型公司以及在金融行业应用人工智能方面拥有丰富经验。他曾负责管理 `ING` 银行的数据团队，现在在荷兰合作银行工作。他拥有人工智能硕士学位。

`ING` 是一家拥有强大欧洲根基的全球性银行。我们的 53,000 名员工为超过 40 个国家的约 3840 万客户、企业客户和金融机构提供服务。我们的宗旨是赋能人们，让他们在生活和商业中保持领先一步。

荷兰合作银行是一家由客户创建、为客户服务的银行，是一家合作制银行，也是一家具有社会责任感的银行。我们的目标是成为荷兰所有金融市场的领导者。同时，我们致力于成为全球食品与农业领域的领先银行。——摘自其官网

### `ING` 的数据团队

2013 年，`ING` 开始认真对待大数据。这一推动力来自 `CEO` 和董事会自顶向下的战略，他们深信数据的力量。巴斯说：“当时大数据还没有现在这么重要。一些高层管理者认识到必须使他们的数据环境专业化，并指定人员对此负责。”在团队成立之前，相关人员分散在整个组织中。`ING` 借此机会将他们集中起来，组建了一个真正的数据团队。

董事会甚至更进一步，举行了战略研讨会，以触及 `ING` 业务的本质。巴斯说：“事实上，我们所做的一切都关乎数据处理。这是一个强有力的信号。公司不仅在内部沟通中，也在媒体上大声宣扬这一点。你可以在 `YouTube` 和各类会议上找到我们的 `CEO` 谈论此事的视频，他以强有力的方式传达了这个信息。我认为这种可见度确实有助于推动这些事情。”

巴斯负责管理一个大型项目，旨在提升 `ING` 的数据成熟度专业水平，并创建一个达到生产标准的数据湖。当时，他领导着一个 20 人的团队。“当我听说这个倡议后，立刻变得热情高涨，并立即申请加入团队。还有很多其他人，要么主动请缨，要么被同事招募。所以我们很快就组建起并运作起了一个团队。”

“我认为很多公司当时都是这种情况。数据在银行中一直存在，但在 `ING`，数据分散在旧的数据仓库、旧的 `Oracle` 数据库、旧的 `COBOL` 大型机应用程序中。我们的数据基础设施在银行收集数据的 20 或 30 年间有机地发展起来。所以，这是第一次严肃地尝试使该环境专业化的举措之一，其目的是，好吧，我们要为数据存储构建一个新版本的真相。”`ING` 当时正在思考架构应该是什么样的。他们想要一个治理良好、组织有序且建模完善的银行数据真相源。

每当一家大公司启动一个大型项目时，管理层都需要意识到其中涉及的政治因素。巴斯说：“在一个大型组织中，总是存在政治角力。人们想要保护旧的工作方式。”在 `ING` 的案例中，团队组建和推广进行得还算顺利。“真正有帮助的是，从项目一开始，管理者们就认识到这是一个无论如何都将进行的大项目。项目得到了业务部门、`IT` 部门以及已经在旧系统上工作的人员的大力支持。”

`ING` 是一家跨国银行。一个难点是协调不同国家，因为每个国家都有各自独立、互不往来的组织。“每个国家都有自己的数据部门和自己的 `IT` 系统。要整理好这种碎片化状态，使每个人都使用相同的工具、相同的数据模型等，需要大量的协调工作。这很困难，因为这意味着你必须协调银行内部的各个独立单位。”

为了实现这种跨国家协调，“第一步是让所有人使用相同的工具和相同的标准。”他们为数据湖创建了一个参考架构。这使得每个国家都与该参考架构保持一致，并使每个人都能使用相同的工具和数据交换协议。“我们开始使用同一种数据语言，基本上可以说是一种用于数据的通用语，即元语言。”

巴斯工作的一大部分就是要在整个企业和其他国家之间建立这种对齐。他通过“做演示、出差、沟通，有时可能还需要稍微推动一下，直接说‘这就是标准。这已经确定下来，这就是我们将要遵循的方式。’来做这件事。你只需要一些耐心和一些良好的项目管理，基本上就能把这些事情理顺。”

在创建这个国际项目时，巴斯发现“沟通是关键”。他们知道这些国际项目会很困难。“不过，我们可以相信，至少从事国际数据整合工作的人员是支持这个项目并遵循技术规划的。在鹿特丹，我们暂时让他们专注于在一个国家构建项目，然后尝试将成果推广到其他国家。”为了在国际团队之间有效沟通，他们召开了大量的协调电话会议。

### `ING` 组织架构

从顶层开始，`CEO` 向董事会汇报。在他之下是 `CIO`，负责所有基础设施和工程工作。再往下，汇报结构按国家划分，例如巴茨所在的荷兰。`CIO` 之下是各级主管经理，在他们之下是部门经理，`ING` 称之为 `IT` 主管。

`ING` 采用了在 `Spotify` 广受欢迎的敏捷团队组织形式。巴茨认为这种模式是该组织持续良好运营的较大成功因素之一。他们的架构将团队分为部落、分会和小队。巴茨说：“部落向一位类似业务经理或部门经理的主管汇报。分会是志同道合者组成团队的新名称。因此，在 `ING`，数据工程和数据科学是不同的分会。小队基本上是一个多学科团队，根据团队需求随时组建和调整。”

巴茨将数据科学家的角色定义为“在数据之上构建和训练预测模型”。数据工程师的角色是“在生产环境中运行这些模型，处理从数据输入到数据输出的全过程”。工程任务包括“准备数据，确保模型可以获取数据，最终获取模型结果，并将其放入任何需要使用结果的场景中：`API`、`Web` 应用、报告或仪表盘。”他还指出，这两个角色之间存在一些重叠。

巴茨曾隶属于 `IT` 主管之下，职位是 `CIO` 团队经理。之后，他成为了数据工程师的分会主管。`ING` 将所有国家的组织架构重组为与荷兰一致。一些国家人员较少，但职位头衔相同，有时管理层级也更少。

这种组织架构的一部分包括一个会议节奏。其中包括产品负责人与每个团队的分会主管之间的月度会议。在会议上，部落主管们“讨论团队所涉及的一切事宜，包括团队成员、团队焦点和目的是否仍然正确、团队氛围，以及成员之间是否以正确的方式相处。”

小队方式为数据工程师与数据科学家的比例提供了更大的灵活性。每个小队由不同的部落组成，通常持续一年或更长时间，“因为优秀的小队应该保持稳定。”团队构成会随着人员离职或替换而改变。其他小队的改变则是因为产品进入维护模式，他们需要再次开发新功能。“工作量和类型会随着项目进展而变化。”

巴茨领导了一个创新项目。“我们一开始只有一位数据科学家，然后团队增长到三人，后来又缩减到一人。这显然是团队当时所需要的，我们没有提前计划，只是每个月审视我们的需求。”这种持续的沟通使他们能够根据需要扩编或缩减团队。管理层通过分会间的沟通，使得在需要时能够调配人员到小队工作。

小队的日常管理由产品负责人负责。他们负责确保小队在项目上取得进展。分会主管则不参与日常互动或负责日常运营。

以下是一些运作实例。“有些团队是功能团队，例如在 `Spark` 或 `Flink` 集群之上构建某个功能。这反过来为最终用户产生了一些功能结果，比如预测算法或移动应用中的某个功能。这些团队是通过从多个分会中挑选人员组建而成的——只要是构建该功能所需的人员。就我而言，我有几个小队只配备了一两名高素质工程师。其他人员来自移动软件开发、数据科学，或者来自业务部落，如市场营销或产品开发。”

从不同数据科学家和数据科学家中临时组建小队的方式，凸显了在处理数据时多学科团队的重要性。这不仅仅涉及技术人员：它把产品负责人或业务人员与实施项目的团队紧密结合起来。巴茨说：“我们看到了数据科学家被孤立、脱离其他系统环境进行开发的后果。将数据科学家、数据工程师和业务人员聚在一起，让他们互相学习。在这些小队中，正确的事情正在发生。组建多学科小队也使得数据科学家能够专注于他们擅长的领域，例如构建预测模式的模型等。”

巴茨继续说道：“但数据科学家也可以做一些小队所需的其他工作：一点编程、文档编写，或者维护小队正在构建的所有内容。其他人员也是如此。在这种情况下，你可以将 70% 或 80% 的时间专注于你的主要角色，但你也必须处理一些可能不是你受训要做的事情，但这些事情是让你的小队成功所必需的。”

从运营角度来看，数据工程师负责 `DevOps`。小队中也可能有来自运营背景的人员。通常，数据科学家负责其模型的运营方面，例如重新训练或监控模型漂移。

### 项目管理框架

`ING` 使用 `Scrum` 作为其项目管理框架。巴茨说：“我认为当你做数据科学时，可以完美地结合像 `Scrum` 这样的框架进行敏捷工作。当然，构建模型有一些你可能想要遵循的结构。在某些情况下，你必须加入一些灵活性，因为你不知道第二天具体要做什么，但这同样适用于其他实践，如市场营销或软件工程。”他建议专注于重要且让你感到舒适的事情。

要弄清楚哪里需要严谨，哪里可以灵活。“我们刚开始采用 `Scrum` 时，一切照本宣科。一切都遵循框架；它几乎就像圣杯；每个人都必须遵循进行 `Scrum` 时应有的精确会议安排。”当他们增加了灵活性之后，“继续使用 `Scrum` 框架变得完全合理。”

为确保团队良好协作，他建议遵循 `Scrum` 会议节奏、每日站会、冲刺规划和回顾会议。他更进一步建议，“不要把团队成员安排在不同的楼层或不同的办公桌。让他们在物理上保持近距离，这很有帮助。此外，我热衷于打造强大的团队文化。因此，团队建设、一起聚餐或小酌、共享午餐，诸如此类的事情，真的很有帮助。”

### 在银行业务中使用数据科学

荷兰合作银行通过数据科学提高农场效率，从而帮助自身及其农民客户。更高效的农民能赚更多钱、花更少钱，而荷兰合作银行也从中受益，因为农民将更多资金存入银行，并降低了贷款风险。荷兰合作银行的收益还来自一种意识形态上的视角：帮助解决世界饥饿问题、减少浪费、更具可持续性，并改善全球食品链。

为实现这一目标，荷兰合作银行正转型为农业领域的数据驱动型研究公司。这项研究必须具备全球视野。为了在全球范围内进行研究，荷兰合作银行必须雇佣大量分析师，并大规模使用数据科学。数据科学家构建的模型将帮助农民确定何时种植或收割作物。

### 数据团队的关键绩效指标

Bas 为数据团队设定 KPI 的方式颇为独特。“我认为业务成果才是关键。技术性 KPI 是次要的。”

在业务方面，他建议确定“有多少人真正对这个模型充满热情。给业务用户提供评分或调查，看看有多少人在日常使用你的模型，以及有多少人因此获得了帮助。”他的理由是，如果模型未能运行或产生任何业务成果，“它就没有被实际客户使用，因此毫无用处。”

对于技术性 KPI，他建议审视模型或项目本应满足的需求。“你的模型性能高吗？维护得好吗？有管理吗？有监控吗？”

### 给其他人的建议

Bas 建议，“最大的成功来自于，在一个小组或一个团队中，大家拥有共同的目标，这个团队由数据科学家、数据工程师和业务人员组成。并且让他们在相同的架构下紧密合作，频繁沟通。他们应该讨论相同的问题和相同的 KPI，共同庆祝相同的成功。”

在组织内部设定现实的目标和期望也很重要，“因为人工智能和机器学习有时被视为灵丹妙药。它们被认为能立刻解决你的问题。你必须现实一点。你不能指望通过一件简单的事情就能解决所有问题。”相反，你需要把一个非常大的项目分解成几个较小的部分，这些部分可能会产生几个不同的模型。通过逐步创建多个模型，你才能构建一个完整的解决方案。

在大型组织中，标准化你们处理数据、数据湖以及其他技术模式的方法非常重要。“我认为我的部分职责就是实现标准化，例如，标准化两个人正在使用的基础设施，标准化模型在生产环境中的部署方式，标准化代码的版本控制流程。我们不希望看到五个团队，却以五种不同的方式使用工具。”长此以往，这五种不同的方式会扼杀创新与合作。团队可能会把所有时间都花在工具的选用和更换上。“你无法复用其他团队已构建好的成果。因此，让团队在工具使用上各自为政存在着诸多弊端。”

拥有多学科团队非常重要。“我见过当来自不同背景的人为了一个共同目标而工作时，小组能展现出最高绩效。”这个单一目标给了团队明确的优先级和关注点。

一个采用开源技术的公司更容易招到人。在我采访 Bas 之前，我就听说过 ING 正在做的事情以及那里的人才，口碑非常好。Bas 说：“我认为我们做得最正确的一件事，就是建立了内部工程的文化。我们有一个非常好的故事可以讲给软件工程师听：‘我们对开源充满热情。我们采用敏捷开发；只要你用正确的方式沟通，你基本上可以选择你想要的工具。’我认为引入这种开源敏捷文化是一个非常正确的决定。”
