# 2. 在 Fiori 应用中消费数据

欢迎来到第 2 章！本章将解释所有关于数据和数据模型的内容。您将学习如何消费数据，如何在数据不存在时模拟数据，如何从本地 JSON 模型模拟数据，以及如何暴露数据。通过`OData`（由 Microsoft 创建并被他方采用的开放数据协议）和`JSON`（JavaScript 对象表示法）模型消费数据模型是 SAP Fiori 中的关键概念。有时，需要从您的 SAP Fiori 应用程序中消费外部`REST` API（Representational State Transfer，具象状态传输）服务。本章将从 SAP Fiori 应用程序的角度，以及从一个名为`POSTMAN` REST 客户端的单元测试工具的角度，探讨所有这些要点。该工具可以在开发前端应用的同时并行使用，但您可能尚未准备好实现所有必要的 XML 视图和 JavaScript 代码以进行数据集成。准备好深入技术概念，让我们一起学习吧。

## 理解数据并在数据不可用时进行模拟

在第 1 章中，本书描述了使用不同工具设计应用程序并与关键用户协作以创建成功设计的多种方法。在设计步骤中，有时用户会提供包含数据样本的电子表格，以便设计人员和开发人员能够在需要表示数据列表、单条数据或通过用户交互从屏幕输入的数据时进行可视化。在本章中，本书将逐步从设计概念过渡到更好地理解数据。理解数据非常重要，因为它适用于后端数据库系统，也适用于创建前端应用程序，使其能够高效运行，并仅呈现所开发应用程序/产品中的相关数据。在设计和创建应用程序时，理解数据是一个关键组成部分。

开发人员有时会想知道，如果后端系统没有数据，他们应该如何开始开发应用程序。有时，开发人员会通过在应用程序中模拟硬编码的`JSON`对象来开始工作。幸运的是，对于大多数企业项目来说，数据通常来自 ERP（企业资源规划）系统，并且有大量数据可供使用。这些系统中的数据模型通常创建为`CDS`（核心数据服务视图，如果来自 SAP 或 SAP HANA），并作为`OData`服务端点公开，这些端点可以轻松地从`REST`客户端或应用程序中使用。

`CDS`是 SAP 创建的一种脚本语言，允许开发人员创建设计时对象（例如实体（表）和数据模型（视图）），目的是在更接近数据库的位置完成大部分工作。`CDS`视图可能包含由`UI5`控件利用的附加注释，以减少前端编码量，并且这些数据注释由后端控制。即使后端系统表中没有数据，但只要数据模型已创建，`OData`服务就会生成一个元数据文件，该文件提供有关端点的信息，其中公开了数据模型，并且已知不同数据实体的数据类型。此外，`OData`服务有时可能包含供应用程序使用的数据注释。

## OData 实体

`OData`服务中公开的实体是指向已公开的后端数据模型的指针，这些模型可进一步用于 CRUD（创建、读取、更新、删除）操作。后端数据模型代表`CDS`视图、表或其他入口点，客户端应用程序可以通过 HTTP(s) 协议与后端交互。您可以在`OData`服务中将不同的端点识别为实体集。如图 2-3 所示，您可以在请求`OData`服务的元数据时看到这些实体集。

在测试这些 OData 服务时，开发者可以执行多种类型的请求以验证他们正在使用的 Web 服务。这些验证 OData 服务的不同方式使用了 OData 协议提供的不同查询语法 URL。最常见的方式如表 2-2 所示：

**表 2-2** — OData 操作与运算符

| 测试描述 | URL 语法 |
| --- | --- |
| 获取服务定义 | `URL/Path` |
| 获取元数据 | `URL/Path/$metadata` |
| 获取前 N 条结果 | `URL/Path?$top=N` → N 为正整数 |
| 获取实体 | `URL/Path/Entity` → 从实体中获取所有记录。检索整个实体集时请务必小心 |
| 按属性筛选实体 | `URL/Path/Entity?$filter={Prop} eq '{SomeValue}'` • `$filter` 运算符允许按属性 `{Prop}` 进行筛选 • `{SomeValue}` 表示一个能被筛选的 `{Prop}` 理解的值 • `eq`（等于）是可应用于筛选查询的众多运算符之一；其他可用的运算符包括 `ne`（不等于）、`gt`（大于）、`lt`（小于）、`contains`（包含） |
| 获取记录数 | `URL/Path/$count` → 返回某个实体的记录数量 |
| 将数据格式化为 JSON 或 XML | `URL/Path?$format=json` → XML 是 OData v2 的默认格式，JSON 是 V4 的默认格式 |

关于 OData 协议和 OData 服务规范的更多信息，请访问其网站 [`www.odata.org/`](https://www.odata.org/)。

在将数据绑定到任何 SAPUI5 表格控件时能够使用 OData 的一个好处是，UI5 框架知道如何构建这些请求，并在后台自动完成，从而减轻了开发构建应用程序的开发者的复杂度。此外，表格控件以及其他具有列表行为的控件，可以设置为分页、滚动加载，以及其他触发类似 OData 请求的事件，以便在需要时从 OData 服务检索数据。发起较小请求的背后原因是避免拉取巨大的数据集，并在用户浏览数据和按需加载数据时提升性能。在第 3 章中，我们将展示其中一些控件如何构建较小的 OData 请求，并将在浏览器的“网络”选项卡中比较网络请求及其响应时间。

## OData 与 JSON 模型

如前所述，OData 协议支持从后端系统快速检索数据，后端系统将端点暴露为实体。OData 模型的所有交互均在客户端（浏览器或应用程序）与暴露这些端点的服务器之间进行。在某些用例中，开发者可能需要模拟一些数据、更新数据并将其反映到屏幕上，而无需将其发送到后端服务器。在这种情况下，开发者可以使用一种称为 JSON 模型的不同模型。JSON 模型是一种客户端模型，支持从应用程序操作数据，且不一定需要将数据发送回服务器。需要客户端数据模拟的场景非常适合此类用例。

从 SAPUI5 控件的角度来看，控件使用 OData 模型还是 JSON 模型并无区别。SAPUI5 应用程序同时支持 JSON 和 OData 模型。当存在多个模型时，唯一的区别在于绑定到控件或聚合时需要指定命名模型。

命名模型是指具有特定名称（而非默认的空字符串）的模型。命名模型在 SAPUI5 应用程序的清单文件中指定，然后在 SAP Fiori 应用程序的 XML 视图中进行引用。

`manifest.json` 文件（如图 2-16 所示）是应用程序配置文件，它包含了创建 SAP Fiori 应用程序、配置 OData 服务以及所有其他应用程序配置所需的信息。此文件存在于 MTA 应用程序的 HTML5 模块中。

清单文件分为三个部分：

1. `sap.app` 部分包含关于 UI5 版本、依赖项和数据源的信息。
2. `sap.ui` 部分包含关于用户界面和设置的信息，包括哪些设备类型可以显示它。
3. `sap.ui5` 部分包含关于 SAPUI5 应用程序、其视图以及其他属性的详细信息。

要设置命名模型，您必须在 `sap.app` 部分中包含数据源，并指定此 OData 服务所在的 URL。这里可以设置几种场景：

1. 在 SAP HANA XSA 应用程序中，如果 OData 服务位于同一项目的模块内，则可以通过相对路径引用该 OData 服务。
2. 在运行于前端服务器（NetWeaver 前端和 ABAP 后端）的 SAP Fiori 应用程序中，只要应用程序和 OData 服务位于同一域/主机中，我们也可以引用 OData 服务的相对路径。如果 Fiori 应用程序部署到 SAP Cloud Platform 的 `neo-app.json` 文件中，则同样适用此概念。
3. 如果所需的 OData 服务存在于我们的域/环境之外，则必须包含该 OData 服务的完整 URL，就像我们在上一节示例中使用的 Northwind OData 服务一样。

## 使用 REST API

表述性状态传递（REST）应用程序编程接口（API）是用于在请求 API 数据时处理自定义逻辑的 Web 服务。这与 `OData` 服务不同，后者仅接收 HTTP(s)请求，并在查询与后端数据匹配时返回数据，如果没有匹配的请求则返回零条记录。

在下面的示例中，本书使用了一个 `NodeJS` 微服务（REST API）来从同一实体 `DEVICE` 返回数据。`OData` 端点直接从表中返回数据与 `Node JS` 微服务 API 之间的区别在于：`Node JS` API 会接收传入的请求，对其进行分析，然后调用一个在 `SAP HANA` 中构建为计算视图的数据模型，查询同一张表，最后以 `JSON` 数组的形式返回数据。

为什么开发者想要从自定义端点（例如使用 `Node JS` API 描述的端点）开发和获取数据？原因是 `OData` 服务不允许自定义验证，并且 API 会根据 HTTP 请求返回所有匹配的记录。在某些场景下，当 API 需要验证输入、包含业务逻辑或拥有自定义响应时，这些自定义 API 是更好的选择。为 API 的调用者提供自定义响应，比仅仅得到一个空响应（不知道过滤参数是否正确或有效，或者请求是否缺少必要信息）要好得多。在由 `ABAP` 堆栈提供的 `OData` 服务中，可以通过 `ABAP` 类提供自定义验证。这超出了本书的范围，但在此提及以供参考。

当从 `SAP HANA` 或任何其他系统使用这些自定义 API 或微服务时，有多种方法可以实现这些操作：

1. 使用 `SAUI5` 框架并采用 `JSON` 模型
2. 使用 `JQuery` 异步 JavaScript（AJAX）操作，从 `Fiori` 应用程序向 `REST` API 发起异步调用

由于我们已经比较了 `SAPUI5` 框架和 `JQuery` JavaScript 框架，下面让我们在表 2-3 中比较它们的异同。

在使用 REST API 时可能会遇到一些常见问题。一些常见场景包括向我们的网络外部发起请求，从而导致跨域请求错误。为防止跨域请求并最小化攻击风险，可以在服务/API 中包含某些措施。这些措施包括：能够防御跨域请求、根据请求头拒绝请求、仅接受来自特定域的请求、以及接受包含特定令牌的请求等。从 `SAP HANA XSA` 应用程序中，我们可以将身份验证类型设置为路由、证书或基本身份验证。

路由身份验证意味着发往/来自应用程序的请求需要由 `UAA`（用户身份验证和授权）服务进行验证，正如 Cloud Foundry 规范中所述，并且 `SAP HANA XSA` 也采用了相同的实现方式。在我的书《Microservices in SAP HANA XSA》（Apress, 2020）中，我深入详细地解释了 `UAA` 服务以及它如何在 `SAP HANA XSA` 环境中使用。

# 基于 OData 驱动的设计方法

至此，我们已经讨论了在有数据可用时使用 OData 服务，以及在没有直接数据源时模拟数据的方法。但我们也可以从 OData 元数据文件中生成数据。我们还从 REST API 微服务中消费了数据。那么，让我们的 SAP Fiori 应用程序提供一种数据驱动的解决方案，从而能够几乎不费力气地创建这些企业应用程序，是不是也很有意义呢？

`智能控件` 是 SAPUI5 SDK（软件开发工具包）中的控件模板，它们提供了此类特性和行为。这些模板使用能够理解元数据的元数据 XML 文件和注解，并将这些 XML 注解和元数据转换为实际的 SAPUI5 应用程序和 Fiori 元素。

注解是附加属性，它们为 OData 端点中的属性赋予了语义含义。赋予数据额外含义的唯一目的是丰富数据本身的含义；例如，为真正代表货币金额的十进制数字添加货币符号，或者以全大写等不同格式显示标签。SAP HANA CDS 中的注解所包含的注解类型集，与 SAP ABAP CDS 中的相比是有限的。`HANA CDS`和`ABAP CDS`在源于同一种脚本语言这点上非常相似；然而，它们又非常不同，因为并非所有注解类型都适用于这两种技术。

那么，何时应该构建这类应用程序（使用元数据和注解，而非实际的 XML 和 JavaScript）？如果要遵循此路径，需要考虑一些设计指南。如果应用程序的开发非常标准化，需要设计一致性，并且不需要太多定制，那么建议按照这些预定义模板来创建应用程序。当您开始设计阶段，并注意到应用程序需要进行一些定制时，那么正在构建的应用程序可能不适合采用智能模板开发。请记住，这类开发有一个强制要求，即必须使用 OData 服务，并且要构建的应用程序必须遵循第 1 章中讨论的 Fiori 元素之一（列表报表、工作清单、概览页面）。

现在，让我们使用现有的 OData 服务来构建一个概览页面。如第 1 章所述，概览页面是对系统的快速浏览，目的是让用户快速了解数据（在本例中是设备）的概况，而无需深入每个特定的应用程序或磁贴来查找详细信息。

在由`DEVICES`表示的数据集中，我们还有一个包含设备指标的表。这里捕获的指标是温度和记录日期。这些数据仅用于练习。我将首先构建额外的数据模型，以表示我们想在概览页面中展示的数据。在概览页面中，我们显示设备的平均温度；在另一部分中，我们按降序显示设备的成本。通过查看概览页面的示例，我们需要构建名为`卡片`的部分。

`卡片`代表概览页面内的一小段数据，它们包含一个标题区域（我们可以在其中设置标题），以及一个内容区域，用于表示表格、图表、图形或其他文本。有几种不同类型的卡片：分析型（包含标题和度量）、列表、柱状图、表格和快速查看（类似于表单的信息内容）。

## 结论

在本书本章结尾处，我想强调在应用程序中使用数据的重要性，以及使用数据的不同方式，例如 OData 服务和 REST API。当没有数据时，开发人员仍然可以生成本地 JSON 模型或使用元数据文件从 SAP Web IDE 模拟一些数据。本地模拟数据功能益处巨大，并且在实际数据不可用时，应用开发人员开始开发活动的情况也时常发生。此外，本章中另一个极其重要的内容是实现与 SAP Fiori 应用程序数据集成的各个部分。理解不同类型的应用程序模板、Fiori 元素和布局，将有助于我们在下一章深入探讨更多自定义 Fiori 开发时获得启发。同时请牢记数据是如何作为数据模型呈现的，以及这些数据模型是如何绑定到应用程序的。
