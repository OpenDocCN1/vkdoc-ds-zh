# 使用 SharePoint，系统必须在用户最需要时保持可用；这是对服务质量而非数量的衡量。这在很大程度上也关乎用户感知。系统可能在周末宕机，但直到周一早上（假设员工处于同一时区）才会被人们注意到。然而，周一早上的每一分钟宕机都会严重损害用户对系统可用性的感知。

根据我的个人经验，停机的主要原因是人为失误。首要原因是日常维护任务出错，其次是 Web 服务器资源或 SQL Server 容量不足。防止日常任务出错的方法是确保资深的员工进行充分的监督并关注细节。虽然自动化并委派日常任务是标准做法，但那些拥有更高知识水平和经验的人仍需承担所有权和责任。有时，资深的员工被认为成本过高，但违反 SLA 的成本比聘用优秀人才更高。硬件故障导致停机的情况只是偶尔发生。更好的变更管理实践将有助于减少维护任务中的错误。更好的监控和资源规划将减少容量问题。

## 弹性

*“及时一针省九针。”*

——格言、箴言与谚语、智慧箴言与妙语、
古与今、外国与英国，*托马斯·富勒，1732 年*

对于不熟悉这句谚语的人，它意味着在布料上缝一个小洞缝一针，可能能防止撕裂后需要缝九针。换句话说，及时的行动可以避免后续更多的工作，谁不喜欢少干活呢？

弹性是您的 SharePoint 系统抵御灾难的能力。您可以同时在多个层面最大化弹性。最薄弱的环节最终将成为系统崩溃的点，但请记住，您的目标是尽量减少对用户的影响并为组织节省成本，而不是为了追求弹性而打造一个尽可能弹性的系统。此外，更复杂的系统拥有更多的故障点，也更难管理。

## 平台

甚至在考虑内部应用程序的冗余选项之前，SharePoint 平台本身就为我们提供了多种选项，这些选项会带来不同的弹性考量。您为云端 SharePoint 和虚拟本地场规划弹性的方式之间存在巨大差异，因为服务器的存储和维护方式不同。理解每个平台决策（特别是针对 SharePoint）的优劣势，是构建更强弹性的第一步。

## 本地部署与云端

*能力越大，责任越大！*

——斯坦·李，《神奇幻想》第 15 期，1962 年 8 月（第一部蜘蛛侠故事）

从弹性角度来看，本地部署与云端的主要区别在于，如果您的平台构建在像 SPO 这样的云解决方案上，组织中 SharePoint 平台的所有者几乎无法影响您的服务器场的物理基础设施，因为基础设施由外部提供商提供。例如，如果您自己构建基础设施，您可以决定硬盘、线缆、服务器、网卡、电源和存储。当然，这需要更多的知识和成本。即使您构建服务器并将其托管在外部，建筑物、机架空间以及部分监控、备份或其他操作也不完全在您的控制之下。这种控制伴随着责任，但如前所述，SLA 往往过于简单，只关注时间百分比。SharePoint Online Standard 提供 99.9% 的可用性（`http://download.microsoft.com/download/F/1/3/F133AF39-F878-4009-8C6A-B60144C32679/SharePointOnline%20Standard%20Service%20Description.doc`）。

这一点在*服务连续性管理*部分有进一步说明：

*SharePoint Online* *在发生灾难时设定了 RPO 和 RTO：*

*   **12 小时的 RPO：** *Microsoft 保护组织的 SharePoint Online 数据，并拥有一份不超过 12 小时的数据副本。*
*   **24 小时的 RTO：** *如果灾难导致主数据中心瘫痪，组织将在服务中断后 24 小时内恢复正常服务。*

SharePoint Online Enterprise 提供 1 小时的 RPO 和 6 小时的 RTO。我之前提到过这些信息，但在此处再次提及，是为了说明 Microsoft 如何限定了其最初的 99.9% 可用性承诺。该公司表示，无论一年中发生多少次灾难，每次您都将丢失多达 12 小时的数据。此外，如果数据中心发生故障，您需要等待 24 小时才能恢复上线。等待时间漫长，数据损失也很大。您必须根据您的 BIA 来决定这种弹性水平是否足够满足您的组织需求。如果不够，您应该确定哪些内容可以放在云端，但将不应放在云端的内容分离出来。然后，这些内容应该被放置到本地或异地托管的更具弹性的平台上。

SharePoint Online 将高可用性的许多复杂性从您手中转移到了 Microsoft 手中。这为您节省了资源，但它只能确保停机不会对您的业务造成超出其承受范围的负面影响。

## 亚马逊云

SharePoint Online 并非云端 SharePoint 的唯一选择。还有一些外部托管公司会为您管理服务器，或者以标准的多租户模式在其服务器上托管 SharePoint。然而，随着大型云提供商提供一些成熟且可靠的选项，这些选择大多变得不那么相关了。

其中一个选项是使用亚马逊名为 Amazon Web Services (AWS) 的基础设施来托管您的 SharePoint 服务器。Amazon 的 SLA 提供 99.95% 的可用性（`http://aws.amazon.com/ec2-sla/`）。它还提供的是 IaaS（基础设施即服务）而非 SaaS（软件即服务），因此您对基础设施有更多控制权——尽管发生宕机时，您仍然受制于他们。

这并非主要关乎弹性，但从灾难恢复角度来看，最大的区别在于宕机时所有者拥有的控制程度。当您的云提供商发生宕机时，您的 SharePoint 平台所有者会感到无能为力，除非基础设施所有者提供定期更新。在我看来，云提供商在这方面存在问题：他们想要掌控权，但又害怕发布信息，因为这可能显示他们对宕机的责任。

根据我的经验，云端由人为失误导致的宕机频率与本地部署场景一样高。例如，2011 年初的亚马逊宕机就是由一名网络工程师错误地将所有网络流量转移到一条仅供管理使用的低容量网络造成的。这引发了一系列问题，包括“重新镜像风暴”和存储控制平面的降级。这篇文章对具体发生了什么提供了很好的视角，同时也深刻揭示了一个错误如何导致大规模宕机，以及如何应对和解决它：`http://aws.amazon.com/message/65648/`。
