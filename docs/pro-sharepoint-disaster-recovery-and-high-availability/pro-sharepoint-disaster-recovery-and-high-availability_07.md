# 如果你担心 SharePoint 场中的数据丢失会对你所在组织造成的影响

如果你担心 SharePoint 场中的数据丢失会对你所在组织造成影响，那么这本书就是为你准备的！它部分内容偏技术性，但大部分篇幅都在阐述良好规划的原则，以及实践中成功与失败的案例。我的意图是，对于那些组织已经开始依赖 SharePoint 来运转的读者来说，本书既能提供指导，又能带来乐趣。

## 本书结构

每一章都描述了可采取的实际步骤，旨在让你的系统更具弹性，并在你的 SharePoint 场遭遇灾难时，为你提供最全面的应对方案。然而，仅仅阅读是不够的。我会提供一些要点，激励你将学到的知识应用到现实世界中。阅读完每一章后，请将你学到的内容付诸实践！至少，记下你的想法和行动计划，以便日后执行。

第一章：远离灾难

要保护你的内容，你必须了解你的技术，并认识到它对组织的重要性。必须分配角色并承担责任。此外，应该有一种方法来记录"差一点就发生的意外"，以便捕捉并解决这些问题。SharePoint 不仅仅是一个技术平台；它在一定程度上也属于用户。他们和管理层都必须参与其治理。

第二章：规划你的计划

在编写计划之前，你需要打好基础。首先需要获得利益相关者和管理层的支持。你还需要进行业务影响评估。你可能需要规划不同的 SharePoint 架构，这些架构具有不同的 RTO/RPO 以及与其内部数据重要性相关的不同成本水平。你还需要制定一份优秀的 SLA，并规划如何协调灾难应对。

第三章：激活你的计划

在将 SharePoint 灾难恢复计划付诸行动之前，必须落实许多流程和程序。这些不是纸上谈兵的抽象概念，而是需要特定角色执行的实际任务。本章详细说明了谁将在何时做什么，了解相互依赖关系，访问计划，并确保计划事先包含了应有的内容。

第四章：高可用性

高可用性不仅仅是通过满足年度正常运行时间百分比来实现的。它是一个主动的监控和变更管理过程，用以确保系统不会宕机。它也关乎拥有高质量的硬件。最后，它还关乎在从数据中心到单个服务应用程序组件的每个架构层级都实现冗余。

第五章：服务质量

改进服务质量的主要方法包括：WAN 优化、设计你的场以使内容靠近需要查看它的人，以及缓存不常更改的页面。WAN 加速只能在一定程度上缓解延迟的限制，但在 SharePoint 2013 中，有一些选项可以在用户满意度和不过于复杂的架构之间取得经济高效的平衡。

第六章：备份先行

你的场是一个独特且不断变化的复杂系统。在关注如何成功备份和恢复它时，你需要有清晰记录并经测试的步骤。你不能完全依赖自动化工具，部分原因是它们无法捕获所有内容，部分原因是它们只能捕获你告诉它们捕获的内容和时间。

第七章：监控

必须在 Windows 和应用程序级别监控 SharePoint。SharePoint 应用程序高度依赖网络基础设施，因此 SQL Server、Windows 或网络的任何问题都会影响 SharePoint。本章中的信息为你提供了监控所需事项的指导和方向。

第八章：DIY 灾难恢复

本章表明，维护有价值内容备份的任务不必是 IT 人员的专属领域。从组织的角度来看，让用户负责并拥有备份自己内容的方法是一个绝佳的主意，因为这很可能在备份空间和 IT 工时两方面节省资源。

第九章：变更管理与灾难恢复

变更管理是一个协作过程，需要从业务和技术角度评估变更的影响。变更是 SharePoint 的生命线；没有变更，系统会趋于熵增，越来越不能满足用户需求，并成为业务的负担而非福音。

第十章：灾难恢复与云

分析本地外部托管带来的额外问题与机遇。迁移到云仍然涉及大量的规划工作。本章探讨了 SharePoint 发展到当前形态的过程，云架构选项如何归结为成本和控制，以及多租户和联合规划是 SharePoint 在云中的关键方面。

第十一章：最佳实践与最差实践

谈到 SharePoint 的最佳和最差实践，不存在所谓的完美，也没有一种实现是一无是处的。但确实可以改进并避免明显的陷阱。首要的是，你必须避免追求短期结果的捷径、基于薄弱假设的泥潭、应对变革的保守方法以及对治理不负责任的态度。这四项原则将使你的 SharePoint 平台开个好头并保持正确方向。

第十二章：最终结论

本章汇总了本书包含的关键原则。我们采用的方法是创建一个可在任何情况下使用的指南，而不是只定义一种方法。原则更具普遍性，可以应用于任何版本的 SharePoint，无论底层技术如何变化。即使 SharePoint 向云端迁移，之前四个 SharePoint 版本的教训以及关于高可用性和灾难恢复的普遍原则仍然适用。
