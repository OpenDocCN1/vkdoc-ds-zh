# 10\. 管理者手册

如何从颠覆中获利

让我们回顾一下本书迄今为止所涵盖的内容。

第一章定义了颠覆性创新，并论述了当今商业分析市场中的颠覆现象。本章其余部分涵盖了基本概念，例如对数据驱动洞察的需求以及分析价值链的特征。我们区分了分析价值链内部的颠覆，以及分析技术对其他市场的颠覆。

第二章简要回顾了现代商业分析的历史。我们展示了价值链中颠覆的先前案例，例如企业数据仓库的引入。我们还提供了分析技术颠覆其他市场的例子，如信用评分和欺诈检测。最后，我们介绍了当今推动颠覆的关键趋势，包括经济数字化转型以及计算和存储成本的下降。

第三章详细介绍了开源商业模式。我们向您介绍了开源许可和分发，以及基于开源软件的商业模型。我们还详细介绍了`Python`和`R`这两个领先的分析开源软件平台。

在第四章中，我们介绍了`Hadoop`及其生态系统。我们指出了 Apache `Hadoop`与其商业发行版之间的区别，并记录了与`Hadoop`一起最广泛使用的组件。在分析方面，我们区分了`Hadoop 1.0`下可用的基础功能，以及今天在`Hadoop 2.0`下可用且日益强大和复杂的功能。

第五章记录了计算机内存成本的迅速下降，以及随之而来大规模内存计算的兴起。本章涵盖了 Apache `Spark`、Apache `Arrow`、Alluxio (`Tachyon`)和 Apache `Ignite`。

在第六章中，我们简要回顾了流式分析的历史，指出了该类别中长期存在的愿景与现实之间的差距。我们调查了流式数据源，如 Apache `Kafka`和 Amazon `Kinesis`，以及开源流式分析平台：Apache `Apex`、Apache `Flink`、Apache `Samza`、Apache `Spark` Streaming 和 Apache `Storm`。

第七章涵盖了云计算的基础知识和弹性商业模式。我们调查了三大云平台的能力：Amazon Web Services、Microsoft Azure 和 Google Cloud Platform。

在第八章中，我们回顾了机器学习的关键趋势：收敛、竞赛、集成学习、可扩展性和深度学习。我们详细介绍了神经网络和深度学习。最后，我们调查了先进的机器学习平台，包括分布式引擎、数据库内库和深度学习框架。

最后，在第九章中，关于自助式分析，我们提供了一个平衡的观点来看待普通用户和专家用户在企业分析中的作用，并提出了一个用户角色模型。我们介绍了一些体现该领域创新的产品，包括数据可视化、数据混合、`基于 Hadoop 的 BI`、“洞察即服务”、商业用户分析和自动化机器学习。

至此，如果你仍不相信当今分析领域新兴创新的力量和丰富性，请停止阅读；第十章不适合你。

在本章中，我们为管理者提供了一本行动手册，以便从创新和颠覆中获利。我们涵盖三个主要领域：

*   人员与组织
*   流程
*   平台与工具

我们提出的一些策略可能看起来激进。本手册假设您希望您的组织从分析市场的创新和颠覆中获利。要么您想，要么您不想——只有您自己才能决定。

为了从创新和颠覆中获利，您的组织很可能需要以不同的方式做事。可能会有政治或其他障碍需要克服，而变革管理始终是一个问题。我们并非轻视组织变革的难度。然而，这并非一本关于组织政治或变革管理的书；它是一本关于如何从创新和颠覆中获利的书。

## 人员与组织

在分析领域，我们往往过度关注纯技术问题。但人员和组织至关重要——尤其是在一个被颠覆的世界里。

*   围绕客户进行组织。
*   明确首席分析官的角色。
*   让成本对客户透明。
*   雇佣合适的人。

积极主动、组织良好、拥有基本工具和正确激励的人，其表现始终优于那些消极被动、组织混乱、坐拥镀金工具的人。



### 以客户为核心进行组织

为应对颠覆性世界而进行组织，需要像激光一样聚焦客户需求。（我们使用“客户”而非“顾客”一词，因为分析实践是一项专业服务。客户可以是内部或外部的——同样原则适用。）每个组织都各不相同；我们在此呈现一个典型的分析需求模型，以及满足这些需求所需的技能和工具。

企业通常围绕技术职能来组织分析工作：`数据集成`、`数据仓库`、`商业智能`等。这样做有其逻辑，包括知识共享和职业发展。但分析团队必须以内部和外部客户为核心来组织，这一点至关重要。

在第一章中，我们概述了数据驱动型洞察的五种截然不同的需求来源：

- **战略型**：为高层管理者（C-level executives）提供的洞察。
- **管理型**：为职能高管提供的洞察。
- **运营型**：为业务流程优化提供的洞察。
- **开发型**：为新产品和服务提供的洞察。
- **差异化型**：为（外部）客户提供的洞察。

这些内部和外部客户群体中的每一个，对于人员、技能和工具都有独特的需求。

**战略型**。面向高层管理者的大多数分析都是*临时性的*、不可重复且紧急的。从业者需要对业务或行业有深刻理解，具备高度专业的方法，并熟练掌握可视化演示技巧。战略分析团队需要广泛访问内部和外部数据，以及*临时性*数据集成、查询和报告的能力。

**管理型**。在此层级，主要需求是严格的绩效衡量和用于业务规划的*临时性*分析。从业者通常具有财务背景；他们必须熟悉组织的绩效指标和业务规划流程。传统的数据仓库和商业智能系统在绩效指标方面表现良好。管理型分析团队必须能够访问绩效衡量系统以生成*临时性*绩效报告，并需要工具来制定业务计划的预测。

**运营型**。业务流程利益相关者需要低延迟、实时的业务流程指标，并且需要可部署的机器学习工具来进行优化。传统的商业智能和报告系统如果部署用于实时分析，则能很好地满足运营指标需求。运营分析师应具备统计学、机器学习和内容分析方面的深厚背景，并掌握模型部署所需的编程技能。

**开发型**。产品和服务开发高管需要洞察来支持从概念到产品引入的整个开发生命周期。分析从业者需要具备消费者和市场研究背景，并结合实验设计、“测试与学习”技术以及预测方面的统计学训练。轻量级的“桌面级”工具在此领域通常就足够了，因为这些从业者很少处理大数据。

**差异化型**。面向客户的分析，例如推荐引擎，必然是生产级应用程序。开源软件比商业软件更受青睐，尤其是当组织计划向最终客户分发软件组件时。此领域的从业者应具备软件工程背景，并辅以机器学习培训。需要有编程语言知识，例如 `C`、`Java`、`Scala`、`Python` 和 `R`。

尽管各组织之间存在很大差异，但一般规则是：初级分析师倾向于向其支持的部门（如营销或信用风险部门）汇报；专家分析师倾向于集中分组；而`数据集成`、`数据管理`、`软件管理`和`资源调配`方面的专家则倾向于向 IT 组织汇报。因此，没有高级管理人员对整个分析价值链承担总体责任。

一种更好的组织模型是将分析价值链中的技术职能从 IT 部门分离出来，并将其置于首席分析官（CAO）的领导之下。在职分析师要么留在职能部门，同时虚线汇报给 CAO，要么加入 CAO 组织并被指派去支持职能部门。



### 明确首席分析官的职责

目前正兴起一种趋势，即任命一位高管担任首席分析官（`CAO`）。虽然这尚未成为普遍做法，但它标志着企业相信分析能力是一项关键战略能力。

理论上，首席分析官（`CAO`）应对从数据到洞察的整个分析价值链负责。然而在实践中，分析价值链的责任往往被分割，并且很可能继续保持这种状态。IT 部门通常管理数据仓库、数据采集流程以及“企业级”商业智能工具。IT 部门还负责管理硬件和软件采购。

职能部门则管理“影子”IT 运营，其中可能包括数据集市和分析工具。“专家”用户有时隶属于 IT 部门；但更多时候，他们隶属于职能部门。在精算分析或信用风险等专业分析领域，分析师通常向职能经理汇报；这种情况不太可能改变。

责任分工导致了一些功能失调的结果。由于 IT 部门通常拥有数据仓库，但不负责交付洞察，因而倾向于将数据收集和管理本身视为目的；而真正的洞察则被视为别人的事。尽管 IT 部门在数据仓库的构建和管理方面往往非常出色，但他们倾向于忽视或忽略职能经理未得到满足的需求。这就是为什么如此多的职能经理拥有自己的“影子”IT 运营部门。

`CAO` 应直接管理负责战略分析（如上一节所定义）的团队。该团队处理来自组织领导层的临时洞察需求，并应配备相应的人员和工具。一个战略分析团队需要高技能、专业的人员，并能广泛获取内外部数据以及快速响应所需的工具。

对于管理分析，其核心资产是绩效衡量系统：企业数据仓库和支撑它的商业智能平台。IT 部门的核心能力在于生产系统的运营，因此由`CIO`管理绩效衡量系统是合理的。然而，`CAO` 应负责推动绩效衡量的需求流程，并协调各职能利益相关方。

业务流程优化通常需要高级分析和运筹学方面的技能。一些职能部门可能已经拥有支持这些能力的专家团队；然而，集中整合这些资源，以支持那些尚未建立自己团队的部门也是合理的。`CAO` 应管理这些集中整合的资源，并推动整个组织的标准和最佳实践。

大多数组织都有专门的产品和服务开发团队，通常隶属于市场营销部门。`CAO` 在此过程中的职责应是推动最佳实践的培训和采用，与 IT 部门协调需求，并定义通用标准。

软件和硬件的配置需要仔细平衡`CAO`和`CIO`的职责。`CIO`通常管理本地部署，并且经常也管理云部署。然而，在符合安全标准的前提下，如果组织无法提供有竞争力的定价或服务水平，`CAO`应能自由地将工作负载迁移到云端。

类似地，虽然`CIO`通常管理软件许可、采购和支持，但对于高级分析软件——这类软件通常不属于 IT 部门的核心能力范围——`CAO` 应承担这一职责。

数据所有权是另一个需要仔细平衡`CIO`、`CAO`和职能部门职责的领域。数据所有权和管理是两回事。数据所有者控制数据访问（在组织整体政策框架内）并定义数据采集的业务规则；数据管理者代表所有者处理数据的管理和保管。通常，数据应“属于”为其生产提供资金的部门；`CIO`应管理生产系统和数据库；`CAO`应管理分析数据存储。

### 向客户明晰成本

在一本关于分析的书中讨论“成本分摊”问题可能显得过于琐碎，但激励机制至关重要。

作者曾会晤一家大型医疗保健机构的 IT 高管，该高管抱怨说，SAS 用户不愿意改用成本更低的替代方案。当被问及用户部门是否分担了软件成本时，这位高管回答说，没有，组织希望鼓励人们使用分析工具。

你可以看到问题所在：当成本不透明时，用户更喜欢“镀金”选项。

软件配置只有两种可行的模式。要么软件选择是一个集中管理的过程，成本作为间接费用吸收；要么允许各个部门和用户自行选择软件，并从自己的预算中支付成本。

同样的原则也适用于人员成本、资源调配和数据收集。没有什么比要求为所用资源付费更能迅速澄清需求的了。



### 招聘合适的人才

2016 年年中，合格的数据科学家处于卖方市场。因此，许多人自称数据科学家，但实际上并不合格。在没有专业认证的情况下，媒体上有许多文章¹ ² 涵盖了数据科学家的“面试问题”。这些文章大多涉及数据科学领域的琐碎知识，许多能力出众的分析师可能都无法回答。

用理论知识来测试候选人是种错误的做法。更好的方法是请候选人谈谈他们实际完成的项目：

* 你解决了什么业务问题？
* 你是如何着手解决这个问题的？
* 你是否与他人合作？如果是，请描述你与他们的互动。
* 你使用了哪些工具？你解决了哪些技术问题？
* 在项目过程中，哪些方面进展顺利？哪些方面本可以做得更好？
* 项目的最终成果如何？

顶尖的候选人可以轻松列举出他们参与过的数十个项目。许多优秀的数据科学家活跃在 Kaggle 或其他竞赛平台，也可能为开源分析项目做出过贡献；这些迹象表明该人选对该学科有很好的掌握。

在初级层面，需要评估的关键特征是内在动机：这个人是否有强烈的欲望进行分析？即使是刚毕业的学生也能举出他们做过分析的例子——研究项目，或利用公共数据集的独立工作。学习一种开源分析语言，如`R`或`Python`，是另一个体现动机的关键指标。

一个应聘分析岗位的候选人，如果无法指出实际项目，或者从未学习过分析语言，那他就不是认真的。

分析领域的高管有时会问，是否应该要求候选人掌握特定的分析工具，如果需要，应该掌握哪些。这个问题的简短答案是：这取决于你已将哪个平台确定为标准。（如果你尚未确定标准，那么你需要这样做。请参见本章后面的“构建开源技术栈”）。如果你已经将标准定为`SAS`，那么就寻找懂`SAS`的人。虽然理论上可以重新培训其他方面合格的候选人，但有些人永远无法完成这种转换。

对于任何组织中的任何候选人来说，文化契合度都是至关重要的。对数据科学家或分析师的个性一概而论是不明智的；然而，公平地说，成功的数据科学家和分析师能够与客户互动以理解业务问题、解释结果，并在团队中协同工作。评估这些品质应是你评估过程的一部分。

## 流程

敏捷开发的原则，如敏捷宣言³ 所述，既适用于一般软件开发，也适用于业务分析。为方便起见，我们重述这 12 条原则（针对业务分析稍作改写）：

1.  通过早期交付来满足客户。
2.  欢迎客户需求的变化。
3.  频繁交付工作成果。
4.  与业务相关方密切合作。
5.  建立有动力的团队，并信任他们。
6.  面对面沟通。
7.  工作成果是衡量进展的主要标准。
8.  保持可持续的工作节奏。
9.  持续关注技术卓越和良好设计。
10. 简化问题。
11. 自组织团队能设计出最佳的架构、需求和设计方案。
12. 定期反思如何提高效率，并相应调整。

在本章中，我们将这些原则分别应用于商业智能和机器学习。

此外，我们注意到，由 IT 主导的数据仓库操作往往收集了太多错误类型的数据，而没有收集足够的数据来驱动关键洞察。为了纠正这一点，我们提出了一种精益数据策略。

### 实践敏捷商业智能

尽管自助式 BI 在增长，但大多数组织仍然雇佣训练有素的专业人员来满足临时的分析请求。这些专业人员通常是集中配置的；职能团队通过书面请求和详细需求来申请分析。专业人员养成了完全按照需求说明交付的习惯。由于职能管理人员缺乏专业人员的专业知识，他们可能并不确切知道自己想要什么；这种沟通问题导致了争议。专业人员团队总是有积压的工作，因此任何请求，无论多么微不足道，都需要花费数天或数周时间。

虽然自助式 BI 通过让请求者直接参与分析的生产来缓解这个问题，但单纯通过工具所能实现的目标是有限的。自助式 BI 在数据组织良好、易于访问且范围有限时效果最佳。即使使用最好的 BI 工具，管理人员也倾向于将 BI 任务委托出去，因此自助式 BI 可能只是创造了一种新型的专业人员。

敏捷原则表明，组织可以有效地解决 BI 瓶颈，方法很简单，就是将专业人员分散到职能团队中，让他们与业务相关方同地办公，从而实现最大程度的互动。这种方法使专业人员能够预测业务对洞察的需求，帮助请求者明确需求，并与请求者互动协作以开发解决方案。

这种方法并不排除对自助式 BI 工具的投资。通常，那些将 BI 专业人员分散到职能团队的组织会发现，对数据驱动洞察的总需求会增加。BI 专业人员负责率先更广泛地使用自助式工具，并在自助式工具不足以解决问题时与业务相关方协作。



### 实践敏捷机器学习

机器学习与商业智能不同，原因有二：其交付成果是一个可运行的预测模型，而非报告、表格或图表；并且其流程本身需要更高的技能水平和专业知识。另一个关键区别在于：虽然职能团队经常使用商业智能，但对机器学习的需求往往更具选择性。在本章前文讨论的洞察需求类型中，对机器学习的最大需求源于运营业务流程优化以及产品和服务的差异化。

敏捷原则建议，与其将专业的数据科学家安置在专家团队中从事短期项目，不如将数据科学家直接安排到流程改进或产品开发团队中，这样组织能取得更好的成果。与商业智能专家的情况类似，将数据科学家纳入团队能确保在设计、开发和评估机器学习模型时采用协作方式。这也能让数据科学家深入了解领域知识以及机器学习的业务背景。

敏捷原则意味着标准数据科学实践需要做出一些改变。

首先，机器学习的产出是生产评分模型。这与标准实践不同，在标准实践中，建模者通常认为一旦在实验室环境中构建出满意的模型，工作就已完成，部署则是其他人的事。

其次，数据科学家应仅根据预测模型在生产环境中的表现来评估它们。“沙盒”测试对于初步模型选择很有用，但生产环境中的表现并非总是与沙盒表现相同。在两者存在差异时，生产环境的表现才是正确的衡量标准。

这两条原则意味着，模型投入生产的周期要比数据科学家可能习惯的周期更快。这要求数据科学家采用一种方法：快速交付一个优于朴素基准的无偏模型，然后通过检查预测误差、补充数据来源、测试新的训练算法等方式持续改进模型。

快速部署的需求引出了第三条关键原则：数据科学家应尽可能避免对无法在评分模型中复现的生产数据进行修改。数据科学家喜欢以各种方式增强原始数据，以提高机器学习模型的预测能力。但这些修改会使模型更难部署，因为建模过程中对数据的任何更改都必须能在生产环境中复现。

快速的周期时间也对工具有所影响。能够自动化常规数据科学功能并支持大规模测试的平台非常受欢迎。同样重要的是那些能将模型开发与模型评分紧密集成的能力。

### 制定精益数据策略

2015 年，技术咨询公司 Forrester 对全球组织的 1800 多名技术决策者进行了调查⁴。Forrester 让受访者估算当前用于商业智能的数据百分比。受访者分别针对结构化、半结构化和“非结构化”数据进行了报告；各类别的平均回答如下：

*   结构化数据：使用了 40%
*   半结构化数据：使用了 27%
*   “非结构化”数据：使用了 31%

Forrester 将此低利用率解释为工具问题：如果组织只是投资于自助式商业智能工具，最终用户就能利用这些数据。那些未使用的数据中隐藏着宝贵的洞察；你的组织只需再购买一套软件，一切便会揭晓。然而，除了工具可用性之外，数据利用率低还有其他几种可能的解释：

*   数据可能结构化了，但其存储模式对于大多数用户来说难以导航，或者其关系模型与管理层思考业务的方式不符。
*   数据谱系和元数据可能记录不全，导致管理层不信任这些数据。
*   数据安全策略可能过于严格，阻碍了数据在组织内的广泛使用。
*   数据可能未被编目，潜在用户压根不知道有哪些可用数据。

请注意，如果这些情况中有任何一项成立，那么该 IT 组织的数据仓库计划就已经失败了。失败可能有很好的理由，例如缺乏预算、资源或战略一致性。但失败就是失败。

还有一种可能性：数据未被使用是因为它没有有用的信息价值。

在大数据时代，这个想法可能被视为异端，但让我们花点时间探讨一下。根据定义，没人使用的数据没有价值。（对于理论上的未来用户，它可能有潜在价值，但在此之前，这些数据只是占用存储空间）。收集和管理数据的全部意义在于产生有用的洞察；没有洞察，就没有价值。唯一重要的问题是这些未使用的数据是否具有潜在价值；那堆垃圾里到底藏着金子，还是它本身就是垃圾？

有很多理由怀疑那种声称未使用的数据含有宝贵“隐藏”洞察的说法：

*   任何数据——无论是结构化的、半结构化的还是“非结构化”的——只要有合适的工具都可以访问；如果你未使用的数据有价值，为什么现在没人使用呢？
*   有动力的分析师会翻山越岭去获取有价值的数据；必要时，他们会学习新工具。你的分析师缺乏动力吗？新工具解决不了这个问题。
*   很少有（如果有的话）记录在案的案例表明，分析师是通过在“发现”的数据中寻觅才产生有用洞察的。

关于最后一点，多年来数据仓库供应商一直在夸大这种“寻觅”的价值。最好的例子就是“啤酒与尿布”的故事。

1992 年，Teradata 的一个分析团队分析了来自 25 家 Osco 药店的 120 万个购物篮，发现下午 5 点到 7 点之间，顾客会同时购买啤酒和尿布。⁵ Osco 从未利用这个洞察，因为没有明确的营销启示。尽管如此，Teradata 的市场营销团队还是引用这个例子，作为证明投资数据仓库合理性的那种洞察。啤酒与尿布的故事成了数据挖掘界的传说。

在同一项 Forrester 调查中，三分之二的受访者报告称，其组织的大部分商业智能需求是由“影子”IT 运营（即职能经理自行组建的流程）来满足的。管理者不会被动地等待 IT 部门交付他们所需的智能；他们会主动建立自己的流程，必要时会雇佣人员并投资工具。



总而言之：组织收集了大量未被使用的数据，同时，它们却未能提供功能管理者真正想用的信息。这是功能失调的表现。

造成这种失调的原因有几个。

一是缺乏用户和潜在用户的输入。用户输入对良好的数据仓库设计至关重要，这似乎显而易见；然而，任何在企业分析领域有工作经验的人都能举出一些备受推崇但并未听取用户意见就建成的项目例子。收集用户输入很困难，而且耗时；潜在用户往往不知道他们想要或需要什么，他们的信息需求也可能并不稳定。

另一个原因是某种惯性——在缺乏明确设计的情况下，简单地将数据从数据源复制到数据仓库结构中，然后就此作罢，要容易得多。作者曾与一家全球消费品营销商合作，该公司维护着两个数据仓库：一个完全由它的`SAP ERP`系统提供数据，另一个则完全由它的`Oracle CRM`系统提供数据。需要从这两个系统获取数据的用户会下载汇总数据，然后在电子表格中进行整合。

第三个原因是一种最好被描述为“数据恋物癖”的现象，即相信数据具有魔力，认为数据总是越多越好。这种思维的问题在于，数据不像原油或猪腩肉那样是一种同质化的商品，任何一单位都可以替换另一单位。恰恰相反，数据总是特定于某个事件或一系列事件：一条数据要么能回答一个问题，要么不能。如果不能回答问题，哪怕是 PB 级的数据也毫无价值。

廉价的存储也鼓励组织将价值不明的数据“囤积”起来。在过去十年中，磁盘存储每 TB 的成本急剧下降，延续了所有计算成本长期下降的趋势。但尽管存储很便宜，却并非免费；并且，在物理存储成本下降的同时，数据治理、管理和安全成本并没有下降。

“数据仓库”这个术语是一个借自物流学的隐喻，仓库的用途就是存储库存。想象一下一个零售连锁店的仓库，里面一半的商品是没人要的，而商店经理们却要通过其他渠道争相采购他们需要的商品以避免缺货。当你考虑到过去 20 多年里，企业一直不遗余力地通过精益生产和准时制物流来减少或消除库存时，这个仓库的隐喻就显得颇具讽刺意味了。

那么，与精益生产相对应的数据仓库做法是什么呢？

首先，除非有明确的业务需求需要数据所承载的信息，否则不要获取数据。实际操作中，“业务需求”意味着拥有预算的职能管理者愿意为这些数据付费。当业务需求结束时，停止获取数据。

其次，从一开始就将度量标准构建到产品、流程和项目中。不要在事后才创建绩效指标；要将它们设计到每个业务实体中。将绩效指标的成本纳入产品和项目的财务核算中。

第三，使数据呈现方式与用户角色相匹配。通常，特定数据集的最早采用者是专家型用户，他们能处理凌乱且粒度细的数据，代表业务利益相关者发掘洞见。当业务需求稳定下来后，专家开发的分析方法可以产品化，并让那些喜欢使用更简单工具的用户也能使用。

第四，不要“清洗”数据；数据清洗工具并不会让数据变得更准确；它们只是通过移除异常值来让数据显得更准确。然而，异常值具有信息价值；艾伦·图灵和他在布莱切利园的同事就是利用异常值来破译恩尼格玛密码的。如果某个数据源系统性地产生错误数据，那就修复这个数据源。

最后，不要让数据仓库本身成为目的。在任何时候，目标都应是传递洞察；开发计划应围绕具体的项目来组织，以便向特定的个人、团队、职能部门或应用程序传递洞察。识别出跨多个终端用户应用的通用数据整合需求或许是可能的；如果是这样，数据仓库可以作为一个承载这些应用的通用平台。但如果难以定义这些共性，就不要让数据仓库这个想法阻碍洞察的传递。

## 平台与工具

除非你的组织是一家初创公司，否则你会有一个遗留工具环境——即对支持分析价值链各个要素的现有工具的投资。你组织过去在软硬件上的投资已经是沉没成本；在很多情况下，保留现有工具比更换它们更具成本效益。我们并不是建议你扔掉那些仍能满足你需求的现有工具。

然而，在边际上，你可以做一些事情来从颠覆性变革中获益。首先，评估你实际正在使用的工具，并与你的许可证授权相匹配；对于增量扩展，要严格定义需求。其次，构建一个可信的开源替代方案；即使你不怎么使用开源选项，仅仅拥有它就能让你在与商业软件供应商谈判时获得筹码。最后，利用弹性配置——无论是在云端，还是通过本地虚拟化。



### 评估软件许可与使用情况

在充满变数的环境中，明确的需求定义至关重要，因为过去我们赖以决策的常规已不再适用。行业领导者举步维艰；新进入者将新能力推向市场；老牌专家难以适应。而真正了解自身需要什么、不需要什么的组织，则能在这种环境中蓬勃发展。

“明确你的需求”看似理所当然的建议，但令人惊讶的是，我们经常遇到那些对自己团队如何使用工具仅有粗浅了解的分析经理。正式的评估通常会揭示，人们只使用了商业软件工具中嵌入功能的一小部分。现在，你比以往任何时候都更需要冷静、严格地审视你已获得商业许可的软件及其使用方式。

开源软件通过基于服务型商业模式提供“足够好”的功能，对商业软件构成了颠覆。商业软件供应商指出，他们的软件产品比开源软件拥有更多功能。这种说法没错，但却具有误导性。功能只有在你的组织实际使用时才能增加价值；否则，它们只会增加成本。

如果没有明确的需求定义，软件选型就会倾向于那些功能最多、市场营销最好、分析关系最硬（或三者兼具）的产品。与其根据哪个产品功能最多来选择软件，不如选择能满足你组织所有已证实需求的最低成本产品。

此类评估的一个附带好处是：你的组织几乎肯定存在过度许可的情况。软件行业关注的是许可不足和盗版软件；但除非你的组织积极管理软件许可，否则你总软件支出中相当大的一部分很可能都花在了“架子货”（购买后未实际使用的软件）上。

我们如何得知你过度许可了？因为商业软件供应商担心，弹性“按使用付费”的定价模式会蚕食他们现有的软件许可模式。这种担忧是合理的；虽然像 Oracle、SAP、IBM 和微软这样的供应商都报告了基于云的收入实现了两位数增长，但这种增长未能抵消传统软件许可收入的下降。

如果软件供应商从弹性“按使用付费”模式中获得的收入减少，那么可以推论，标准的商业许可模式让你为你没有使用的东西付费了。当你考虑商业许可条款（要求买方预先为使用商业价值未知的软件的权利付费）时，这在一定程度上是合理的。

商业供应商保证软件按其所述工作，并在指定条件下正常运行。然而，商业供应商是基于商业价值而非功能特性来销售软件的。他们并不对这些商业价值的声明提供保证；买方承担了这一风险。

当你的组织为商业分析软件建立了一套明确的需求时，你就处于一个更有利的位置，可以在商业供应商之间、以及将它们与开源方案进行比较，来评估他们的声明。

### 构建开源技术栈

在整个软件经济领域，开源商业模式正在削弱商业软件模式。咨询公司 IDC 写道：

> 开源产品提供的功能与专有产品具有竞争力，并对这些产品施加了下行价格压力。开源技术采纳率的增长将迫使许多供应商加速转向基于服务的商业模式。

分析价值链中的每个环节都有对应的开源软件替代方案：

*   Hadoop 及其生态系统为数据采集和管理提供了全面的工具。
*   开源 SQL 引擎——如 Spark SQL、Impala、Drill 和 Presto——在交互式查询方面成功与数据仓库一体机竞争。
*   像 H2O 和 Spark MLlib 这样的机器学习引擎提供了可扩展的机器学习选项。R 和 Python 是用于分析的优秀通用平台。
*   JasperSoft、Pentaho 和 Talend 都提供了面向商业分析的端到端能力。

要构建并提供开源技术栈，请遵循以下步骤：

*   建立分析创新团队。
*   评估你组织当前的开源软件使用情况。
*   通过实时测试和试点项目评估开源组件。
*   制定支持策略。

创新团队是一个核心小组，其主要角色是评估创新技术并将其引入组织。团队成员可能是全职的，也可能临时从其他岗位委派；然而，团队的影响力和价值实现速度取决于其领导力、人员和资源。

一旦团队建立，就要盘查你组织当前对开源软件的使用情况。此类评估的结果可能会让你大吃一惊。许多业务领导者根本不知道他们组织中开源软件的使用程度，因为对于开源软件的获取和使用，往往缺乏集中管控。

你的组织已成功使用的开源软件构成了你技术栈的基础。在此基础上，你的团队可以定义额外的组件来填补技术栈中的功能缺口。没有人能为你的组织定义完美的开源技术栈；它取决于你的需求、过往经验以及持续评估的结果。

为你的开源技术栈制定支持策略至关重要。这个问题有两个方面：

*   对最终用户的支持
*   对技术支持团队的支持

减轻支持需求的一种方法是选择受支持的开源发行版。Cloudera、Hortonworks 和 MapR 提供基于 Apache Hadoop 的商业支持包；微软和 Oracle 提供受支持的 R 发行版；JasperSoft、Pentaho 和 Talend 都提供其产品的商业支持版本。

然而，没有任何单一的开源或开放核心产品能够全面支持整个分析价值链。因此，你的技术支持团队在诊断问题并将其引导到适当的支持来源方面扮演着关键角色。

你的开源技术栈充当了基线架构。这并不意味着你将永远不会使用商业许可软件；这意味着你只有在开源技术栈缺乏解决特定业务问题所需的功能特性时，才会使用商业软件。

一个可靠的开源技术栈还能创造与商业软件供应商的谈判筹码，这些供应商在与开源替代方案竞争时会大幅打折。在评估这些折扣时，要考虑软件的整个生命周期；一些供应商仅仅会降低第一年的订阅费，或者降低永久许可的费用，同时却提高维护费。



### 利用弹性配置

一旦你定义好开源软件栈，就需要提供计算基础设施，例如服务器和存储。请选择一种弹性解决方案：公共云、虚拟私有云、私有云、混合云，或本地数据中心虚拟化及集群管理工具。

`弹性配置` 意味着用户可用的计算资源会根据实际工作负载进行扩展和收缩。例如，如果用户需要运行复杂的分析来支持一次潜在并购，计算资源便会相应扩展；当该项目完成后，用户释放这些资源以供其他应用使用。`自助配置` 意味着最终用户无需 IT 支持或干预即可申请额外资源。

指导你所在组织进行弹性计算的方法应遵循三项关键原则：

-   你拥有并管理、用于业务分析的计算基础设施应保持高利用率运行。
-   最终用户的计算资源应通过自助式弹性配置交付。
-   计算成本（内部或外部）应予以计量，并计入消耗该资源的应用程序成本。

你组织的盈亏平衡容量阈值取决于你数据中心团队的效率与技能，以及你在采购方面的熟练程度。云数据中心的运行容量约为 65%；本地服务器的平均利用率⁷在 12-18%之间，因此大多数组织都有很大的改进空间。

如第七章所述，基础设施平均利用率低是因为组织按峰值需求进行配置；在需求低谷期，这些计算能力便闲置。设想一家公司在纽约和新加坡设有分析团队，每个团队都有一台专用服务器。每个团队在工作时间活跃使用其服务器，但非工作时间服务器便闲置。如果两个团队能共享计算基础设施，该公司就能将服务器利用率翻倍，并将计算成本减半。

为了优化配置，可将你的分析工作负载分为三类：

-   `基线工作负载` 是可预测的，保持在某个恒定水平。
-   `峰值工作负载` 是可预测的，在短期内高于基线水平。例如，月末报告通常会带来需求的短期激增。
-   `突发工作负载` 是高于基线水平的不可预测的需求激增。例如，当分析师训练深度学习算法时。

在这个框架下，使用你拥有和管理、并能以高容量百分比运行的基础设施来配置基线工作负载。对于峰值工作负载，使用预留实例；对于突发工作负载，使用按需或竞价型云资源。当然，你不希望将数据在云端来回迁移，因此应将使用共同数据的工作负载分组在一起。

你的分析很可能会显示分析工作的基线工作负载非常低。这很典型；分析平台的工作负载往往天生多变且难以预测，因为大部分需求都是临时的、面向项目的。尽管如此，计算和存储必须充足，以应对大规模问题的高性能需求。

如果你的工作负载大部分不可预测，或者你的组织缺乏有效管理计算基础设施的技能，那么就把所有东西都放到云端。

高管们对于使用外部云计算通常会提出三点反对意见：实际支出成本、对宕机的担忧，以及安全顾虑。

对云成本的担忧很大程度上是一种幻觉。云计算成本是可衡量、有形的，而内部计算成本常常隐藏在折旧费用、工资、场地费和电费中。即使组织非常擅长衡量成本并将其分摊给用户，它仍然在为未使用的容量付费。凭借其采购效率和熟练的数据中心管理，云数据中心实现了大多数组织梦寐以求的规模经济。

虽然对数据中心宕机的焦虑是真实的，但没有证据表明云数据中心比本地数据中心更容易宕机。任何数据中心都可能因多种原因而宕机：自然灾害、网络攻击或人为失误。与成本问题类似，人们对本地设施可能有一种虚幻的安全感：当然，我们的人不会搞砸并导致系统瘫痪。请记住，如今许多组织在云端运行关键任务应用——而业务分析应用很少是任务关键型的。

安全顾虑与对宕机的担忧类似：焦虑是真实的，但没有证据表明云数据中心比本地数据中心安全性更低。（如果有的话，情况恰恰相反：在过去两年中，前 20 大数据泄露事件中有 19 起发生在本地数据中心；唯一一起云数据泄露事件完全归因于人为失误，与数据的物理位置无关。）

无论如何，分析师可以实施一些工作实践来最大限度地降低云中的安全风险。这些措施包括：避免使用个人身份信息（PII），这些关于个人的敏感信息在分析中很少需要；从表名和列标题中移除标识符；以及在数据迁移到云端之前使用哈希对数据加密。

具有计量成本的弹性自助配置应成为提供给用户的服务标准。这是云提供商提供的服务标准；如果你的组织无法接受使用外部云平台，那么你的目标应是通过数据中心虚拟化来提供同等级别的服务。这是分析平台的基本要求。
