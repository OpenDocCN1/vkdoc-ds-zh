
# 前言

我早在 1997 年就出版了我的第一本关于需求分析和建模的书。它基于我与团队合作构建复杂、实时、模型驱动软件的经验。与许多其他关于软件建模的书籍一样，我将模型转换为代码的过程留给了学生作为练习。哈！

事实上，在实际项目中，我们能够完成这种转换，但这当然并不容易。然而，这是值得的。模型一次又一次地证明了自己的价值，值得为之付出努力。但代码转换问题从来都不是微不足道的。我们总是需要一个专门的团队，与建模工作并行地执行转换任务。请注意，这并不是一种瀑布式方法，因为建模和设计是同时完成的。

随着时间的推移，连接模型到代码路径的工具和技术得到了改进。不幸的是，它们被锁在专有解决方案和昂贵的许可产品中。这使得我在向年轻工程师宣扬建模的好处时陷入了尴尬的境地。让他们对建模的好处以及更有前景的模型执行和代码生成风格产生兴趣是很容易的。随后，我总会面临那个不可避免的问题：“听起来很棒；我该如何开始做这件事？”然后我不得不承认，虽然你可以自己玩转这些想法，但你真的需要参与一个能够为所需工具提供资金的项目。因此，我不想再写一本不給读者一条真正路径的书——任何一条能将模型带入可运行代码，且无需购买任何昂贵工具的路径。

Andrew 和我多年来在各种项目上断断续续地合作过。他早期的一个转换系统从当时名为 BridgePoint（现为 `xtUML`）的工具中提取模型，并将这些模型直接转换为汇编语言。由于使用了专门的 CPU，没有足够优化的 C 编译器可用。这是为某家特定嵌入式设备公司提供的专有解决方案，但它是一个令人信服的概念验证。抽象模型可以被压缩和重组，直接到机器指令级别，并在专门且资源有限的硬件上运行，以产生模型所指定的精确行为。

此后，Andrew 继续构建了许多开源转换系统，其中一个是 `pycca`，本书中使用了它。我最终意识到，这些开源工具是解释如何弥合从模型到代码之间鸿沟的关键，同时为任何感兴趣的人提供了一个可获得的解决方案。

于是，我们最新的这本书项目开始了。在说服 Andrew 参与，并吸引了《可执行 UML》的主要作者兼敏捷宣言签署人 Stephen Mellor 加入后，我们拥有了完美的专业组合。

当你继续阅读时，你可能会发现这不是一个简单的主题，可能需要付出一些艰苦的努力才能读完。回报是能够获取可执行模型来解决实际问题，并将其高效实现，而在此过程中不破坏模型。我想让你知道，在这段旅程中你并不孤单，如果你有问题或遇到障碍，我们非常乐意提供帮助。请随时使用本书末尾的联系页面。祝阅读愉快！

在与持有相似软件开发观点的同事交谈时，话题总会转向为什么使用模型和转换进行软件开发的实践没有更广泛地普及。人们提出了许多理由，但谈话往往以对一个行业的困惑而告终：这个行业声称想要拥有良好工程化的软件，却与其反复实践所无法交付的结果形成鲜明对比。



就我而言，我已得出结论：建模与翻译之所以困难，是因为抽象本身就很难，需要经过练习才能掌握。只需看看一个青少年初次接触初等代数中变量的概念时脸上的表情扭曲，就能明白我们人类首先是依赖于直接和具体事物的生物。明确数字带来的舒适感消失了，取而代之的是一套新的规则，用来应对这样一种观念：一个任意符号——其外观与数字完全不同——如今可以涵盖众多数值。这种表情与初学编程的学生努力想弄清变量与变量中所含值之间的区别时的表情类似，而偏偏在符号相同、仅靠上下文区分的情境下，这种区分尤为困难。尽管我多年来成功运用建模与翻译方法开发了软件系统，但有时看着满页的方框和箭头，依然很难看出页面上的符号与运行中的软件之间的鸿沟该如何填补。这看起来就像要纵身跃过科罗拉多大峡谷，只有骑着装有神奇火箭推进器的极限特技车手才敢尝试。

然而，那位初学代数的学生通过解决大量具体问题，终究会掌握背后的抽象概念。对具体事物进行推理、有时甚至是角力，最终会催生出抽象理解。在本书中，我们试图通过分析具体示例，来阐述将模型翻译成代码的一般原则。我们练习一种特定的方式：用特定编程语言对需求进行建模，并将其翻译到特定类型的目标平台。我们紧扣“无神秘鸿沟”这一口号，力求在每一步骤中明确展示翻译后的软件是如何生成并运行的。我们展示了大量的模型和大量的代码，并深信个体具有卓越的能力，能领会蕴含在具体事例中的抽象本质。

有一种风险是，某些读者会审视平台或翻译技术的细节，并因其细节与自己的兴趣或偏好不符，就认为将模型翻译成程序的想法本身并不具有普适性。若如此，我们作为作者就未能成功展现模型翻译作为一种切实可行的工程方法的愿景。但我相信，会有读者意识到，图表中的符号能够变成可运行的程序（与软件所能企及的具体程度一样具体），并且通过翻译模型来获得代码，更像是在桥上驾车行驶，而非飞跃科罗拉多河。

2017 年 3 月 15 日

莱昂·斯塔  

安德鲁·曼戈尼亚
